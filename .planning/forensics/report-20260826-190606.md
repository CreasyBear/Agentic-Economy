## Root cause model

### Root causes

1. **Completion-unit error:** a leaf interface or generated matrix could be declared complete without an actual registered production endpoint, consequence, rollback and phase integration.
2. **Pre-code semantic-design gap:** authority provenance, independent observation, runtime dominance and exact effect-path semantics were not encoded as adversarial gates before edits.
3. **Architecture timing error:** the official runtime seam and proof architecture were decided after most source work; a static analyzer then became the de facto architecture.
4. **Authority-locality/ownership error:** one integration driver owned too much late wiring while leaves and repairs created duplicate adapters and converters.
5. **Evidence-model error:** checkboxes, exact counts, coverage and diagnostic signatures lacked invariant/location/ref/freshness binding.
6. **Lifecycle-control error:** the custom planning tree was incompatible with stock GSD phase discovery and contained stale launch/state/housekeeping facts.
7. **Operability omission:** the plan treated machine/backend control planes as maturity without planning human administration and support parity.

### Symptoms

- frequent fix/test commits and repeated same-file edits;
- reviewers repeatedly finding “the next” trust defect;
- misleading “complete” commit subjects before root acceptance;
- large manifests and fixtures without migrated production consumers;
- duplicated canonical conversion logic;
- stalled review attempts and false task blockers;
- preserved but unaccepted partial source;
- stale worktree/task/goal records.

Fixing a symptom—for example one more analyzer alias case—will reproduce the churn. The rebaseline must change the root execution rules.

## Enforceable rebaseline rules

### R1 — Architecture acceptance before source edits

Every consequential phase starts with one planning-only architecture decision record. It must include:

- the exact source problem and trust boundary;
- at least two viable alternatives and the reason one is selected;
- official framework documentation, installed-version/source proof and mature first-party examples;
- a source-to-decision matrix naming actual registered endpoints, durable facts, external effects and owners;
- threat model, failure modes, rollback boundary and product-operability impact;
- independent engineering review and adversarial design acceptance at an exact ref.

**Hard gate:** until the ADR/design gate is green, commits touching production source, tests that encode a chosen architecture, package/config, generated files or migration manifests are forbidden. A material design change invalidates the gate and returns to planning-only review. The absence of a Phase 2 authority ADR is itself a finding; the late 814-line design document cannot retrospectively authorize the preceding 77 commits.

### R2 — Vertical slices through actual registered endpoints

The smallest execution unit is not an interface leaf. It is one actual framework-registered endpoint or scheduled target through its real production adapter, canonical domain module, durable/external effect boundary, denial/no-effect cases, observability and rollback.

**Hard gate:** a leaf cannot be green unless at least one named production registration consumes it and the test drives that exact registered reference. Interface-only unit tests, generated surface labels, downstream sink reachability and synthetic parallel evaluators do not qualify. Each later slice expands the same proven path; horizontal “all adapters first, integration later” fan-out is prohibited for control-plane work.

### R3 — Runtime authority seams; no bespoke load-bearing analyzer

Authority is enforced in documented runtime custom-function/middleware seams, with thin registered functions and consequence-time revalidation for delayed/external work. Explicit wrappers or another enforced membrane must prove what raw Convex capabilities remain available because Convex Helpers merges, rather than deletes, the original context.

Lint may enforce only locally decidable facts: restricted raw-builder imports, allowed registrar imports and literal categories. It may not infer aliases, dataflow, dominance, escaped values or interprocedural capabilities.

**Immediate stop trigger:** if acceptance of a security property requires extending a local lint rule into alias/dataflow/control-flow inference, the source phase stops and re-enters architecture review. No “one more syntax case” repair is allowed.

### R4 — One integration-owned canonical Convex adapter

The rebaseline names exactly one driver-owned adapter/parser seam for Convex Principal, Account, ownership, membership, Credential and workload facts. Domain leaves consume canonical typed results; they do not reconstruct rows, query the chain independently or add local converters.

**Hard gate:** the ownership manifest and dependency scan must show one canonical adapter and zero competing production converters/resolvers. A leaf needing an adapter change submits a contract delta to the integration owner; it does not edit or copy the seam.

### R5 — Semantic/adversarial gates are designed before implementation

Each gate must predeclare:

- the semantic invariant in domain language;
- attacker-controlled and trusted inputs;
- exact production registration/effect path;
- hostile counterexamples, including substitution at another registration/location;
- oracle and no-effect assertions;
- source/test-harness/hosted evidence class;
- independent owner and rerun command.

Coverage and checker counts are secondary evidence only. A test corpus must bind the exact registration identity, source location, capability/target and intended invariant. The implementer cannot mark the final semantic gate.

**Hard gate:** a mechanical pass with a semantic counterexample is red, regardless of coverage, model review or prior checkbox state.

### R6 — Exact artifact/ref/freshness attribution

Every durable evidence artifact must carry:

- exact Git ref and relevant build/deployment/package-lock digest;
- exact command and tool/runtime versions;
- generation time and explicit freshness/expiry policy;
- evidence class: `source`, `test-harness`, `hosted/external` or `operational`;
- owner and owning gate;
- exact registration/deployment/revision identity where applicable.

**Hard gate:** ignored worktree-local output, absent scratch, wrong candidate labels, stale coverage values or a command without ref/digest attribution cannot close a gate. Durable evidence is either committed/digest-bound or freshly regenerated.

### R7 — Source and external gates have separate owners

Source acceptance may return `SOURCE_ACCEPTED_EVIDENCE_OPEN` only when every open external item has an owning later gate, owner, required environment, exact deployed revision rule and freshness window. Hosted credentials unavailable locally are not a source failure. Mocks/injected identities are not hosted passes.

**Hard gate:** every claim must be assigned to exactly one evidence class. Reclassifying missing hosted access as a source blocker, or local/mock evidence as hosted success, fails review.

### R8 — Bounded repair budget and automatic rebaseline triggers

For every leaf/vertical slice:

- maximum two repair passes after the first implementation review;
- maximum two formal `CHANGES_REQUIRED` verdicts for the same phase before a new accepted architecture/design gate is required;
- same critical file in three consecutive repair commits triggers a stop and root-cause review;
- recurrence of the same trust-defect class after one repair triggers immediate semantic-contract review;
- any change to the proof property, runtime seam, trust source or effect boundary triggers immediate rebaseline regardless of count.

The repair counter is written in the gate before work resumes. A stop does not discard useful commits; it preserves them as evidence and forbids further source edits until the architecture/process decision is accepted.

### R9 — Exact ownership and blast-radius control

Before fan-out, the plan lists exact owned production/test/planning paths and the real integration consumer for each slice. Unlisted shared files remain integration-owned. Checker invocations must target one named ledger; the driver inspects the exact planning diff and reruns raw checks.

**Hard gate:** any tool or worker writing outside its declared paths stops immediately. Any new production path or runtime family requires a reviewed blast-radius amendment before editing. “Not alone in the worktree” prompts are advisory; path-diff enforcement is authoritative.

### R10 — Product-operability parity planned alongside backend control planes

Every canonical backend entity and consequential action receives an operability row during architecture work, with:

- inspect, change, recover and escalate workflows;
- HTTP, MCP, CLI, UI, staff/support and machine-only disposition;
- self-service, dual-control, staff-only or automated ownership;
- accessibility, audit, security and failure/reconciliation requirements;
- canonical terminology shared by source, product and support.

Implementation may remain in a named later workstream, as the Phase 2 assessment requires, but it cannot be absent from the maturity dependency graph. **Hard gate:** no “operated L3 platform” claim while canonical control-plane rows lack an owner and acceptance gate.

### R11 — One authoritative execution lifecycle

The rebaseline must choose one GSD-recognized ROADMAP/STATE/phase-artifact lifecycle or provide a tested compatibility adapter. Parallel custom state is not allowed to contradict launch packets, Git refs or gate state.

Required atomic lifecycle states are: design accepted, implementation active, internal handoff, independent acceptance, changes required, stopped/rebaseline and closed. Each transition records exact ref, task, owner and next allowed action.

**Hard gate:** stale `PREPARED`, `IMPLEMENTING`, active worktree or goal state after a stop-line blocks further dispatch. Missing canonical SUMMARY/VERIFICATION for a completed execution unit is partial-plan drift, not an invitation to infer completion from commits.

### R12 — Clean task/worktree/scratch closeout

Every handoff or stop-line must prove:

- current task/goal terminal state matches the source verdict;
- exact HEAD, ancestry, commit inventory and clean tracked/staged/untracked status;
- all useful commits are reachable from a named retained ref or explicit evidence commit;
