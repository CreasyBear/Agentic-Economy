## Security Considerations

**Local Clerk bypass is intentionally powerful and must stay non-production:**
- Risk: `VITE_AE_DISABLE_CLERK_FOR_LOCAL_E2E=true` bypasses Clerk for local E2E flows. The server helper throws when enabled with `NODE_ENV=production`, and tests cover that, but route-local mirrors must stay aligned.
- Files: `src/lib/server/local-e2e-bypass.ts`, `tests/unit/server/local-e2e-bypass.test.ts`, `src/routes/_operator/owner.inquiries.$threadId.tsx`, `docs/ONBOARDING.md`
- Current mitigation: `isLocalE2EAuthBypassEnabled()` fails loudly in production; tests verify production-on and test-on behavior.
- Recommendations: Keep all new bypass consumers funneled through `src/lib/server/local-e2e-bypass.ts` or a tested mirror. Never add persisted env files or deployment config enabling this flag.

**Source-write admission secrets have strict client exposure constraints:**
- Risk: Mutating routes depend on source-write admission keys. Any `VITE_` exposure of source-write secrets would leak server authority to browsers.
- Files: `src/modules/security/source-write-admission.ts`, `src/lib/server/source-write-admission.ts`, `src/lib/ui/contract-scans.ts`, `tests/imports/ts-standards.test.ts`, `tests/helpers/source-write-admission.ts`
- Current mitigation: `test:ts-standards` scans for `VITE_AE_SOURCE_WRITE_SECRET`, broad `any`, `v.any()`, hard-coded CSRF/source secrets, and broad status strings.
- Recommendations: Add new source-write scopes through `src/modules/security/source-write-admission.ts` and tests. Do not introduce client-prefixed source-write keys.

**Provider secrets and raw payloads are high-risk surfaces:**
- Risk: Billing, notification, Stripe, and answer-provider code reads server secrets and provider payloads. Leaking raw provider data would expose payment, message, or private operational material.
- Files: `src/lib/server/billing-provider.ts`, `src/lib/server/notification-provider.ts`, `src/routes/api.business-actions.stripe-webhook.ts`, `src/modules/business-action/internal/stripe-checkout.ts`, `src/modules/answer/internal/answer-tool-use-agent.ts`
- Current mitigation: Provider config readers use server env names; Phase 6 smoke asserts pages do not expose raw Stripe payloads, webhook secrets, card numbers, or payment credentials.
- Recommendations: Keep all provider calls server-only. For new webhooks, verify raw body signatures before normalization and store only redacted refs/hashes unless a private evidence retention design is accepted.

**SSRF-sensitive dynamic fetch surfaces require continued scan discipline:**
- Risk: Dynamic `fetch()` calls can become SSRF paths if owner/user-supplied URLs reach provider clients without guardrails.
- Files: `tests/unit/security/ssrf-surface-drift.test.ts`, `src/modules/storefront/internal/network-guard.ts`, `src/modules/registry/internal/catalog-search-port.ts`, `src/modules/clearance/internal/web-bot-auth.ts`, `src/modules/business-action/internal/stripe-checkout.ts`
- Current mitigation: `tests/unit/security/ssrf-surface-drift.test.ts` allowlists reviewed fixed-provider clients and requires every other dynamic fetch under `src/routes`/`src/modules` to import the shared network guard.
- Recommendations: Treat additions to `KNOWN_PROVIDER_CLIENT_FILES` as security review decisions. Owner-import, endpoint-check, or crawler-like features should use `network-guard` rather than expanding the allowlist.

**Convex auth and source authority depend on deployment env correctness:**
- Risk: Convex auth uses Clerk issuer config; source adapters depend on configured Convex deployment and generated references. Missing or wrong env can produce fail-closed behavior locally, but also blocks real production proof.
- Files: `convex/auth.config.ts`, `convex/authz.ts`, `convex/authzMigration.ts`, `src/lib/server/convex-source.ts`, `.planning/STATE.md`
- Current mitigation: Required env readers fail loudly; source/local summaries distinguish local proof from deployed proof.
- Recommendations: Do not weaken auth checks to make local gates green. Resolve env/deployment setup and run deploy smokes before claiming deployed authority.

## Performance Bottlenecks

**Large Convex functions use unbounded or post-filtered `.collect()` in multiple places:**
- Problem: Several Convex modules query full tables and filter in memory, including catalog/discovery/registry/source-state/inquiries/notification/billing/protected-action stores.
- Files: `convex/catalog.ts`, `convex/discovery.ts`, `convex/registry.ts`, `convex/inquiries.ts`, `convex/notificationOutbox.ts`, `convex/billing.ts`, `convex/source_state.ts`, `convex/businessActionStore.ts`, `convex/protectedActionStore.ts`, `convex/_generated/ai/guidelines.md`
- Cause: Early source-local implementation favors explicit reconstruction and table scans; Convex guidelines warn to prefer indexes, `take`, pagination, or async iteration for growing data.
- Improvement path: For any path expected to grow beyond seed/demo data, add named indexes in the owning schema fragment and replace `.collect()` with `withIndex(...).take(n)`, `paginate`, `first`, or a maintained counter. Preserve reconstruction semantics with tests before changing query shape.

**Very large domain/runtime files concentrate risk and review cost:**
- Problem: Multiple files exceed 1,000 lines, including `convex/inquiries.ts`, `src/modules/protected-action/internal/contact-follow-up.ts`, `src/modules/answer-thread/internal/turn-orchestrator.ts`, `convex/registry.ts`, `convex/businessActions.ts`, `src/modules/discovery/developer-discovery.ts`, `convex/discovery.ts`, and `convex/notificationOutbox.ts`.
- Files: `convex/inquiries.ts`, `src/modules/protected-action/internal/contact-follow-up.ts`, `src/modules/answer-thread/internal/turn-orchestrator.ts`, `convex/registry.ts`, `convex/businessActions.ts`, `src/modules/discovery/developer-discovery.ts`, `convex/discovery.ts`, `convex/notificationOutbox.ts`
- Cause: Source/local proof phases accumulated domain state machines, readbacks, audit writes, and reconstruction in broad modules.
- Improvement path: Split only along existing boundaries: pure domain commands, Convex adapter functions, readback projection, and provider/webhook adapters. Do not create parallel authority paths.

**Answer/chat request IDs use time plus `Math.random()`:**
- Problem: Some API/harness IDs use `Date.now()` plus `Math.random()` rather than cryptographic randomness or source-owned nonce persistence.
- Files: `src/routes/api.answer.ts`, `src/routes/api.answer.turn.ts`, `src/routes/api.chat.ts`, `src/modules/answer-thread/internal/turn-orchestrator.ts`, `src/modules/harness/action-tool.ts`, `src/modules/harness/run-loop.ts`
- Cause: Client/session-facing nonces were implemented for local flow uniqueness rather than high-consequence authorization.
- Improvement path: Keep these IDs out of authority decisions. If an ID becomes a durable public lookup, idempotency key, or authorization boundary, move generation to a stronger source-owned pattern and add collision/idempotency tests.

## Fragile Areas

**Proof-level boundaries are load-bearing across source/local, deployed, provider, and live states:**
- Files: `.planning/STATE.md`, `.planning/scopes/SCOPE-EXECUTION-READINESS.md`, `.planning/scopes/PREMORTEM-VALIDATION-GATES.md`, `.planning/scopes/scope-14day-bootstrap-gate/SCOPE-14DAY-INDEX.md`, `tests/copy/phase6-business-action-claims.test.ts`, `tests/deploy-smoke/phase6-business-action-stripe-smoke.spec.ts`

- Safe modification: Before changing public/assistant-visible text, run `npm run test:copy` and check the relevant scope index for allowed wording. Stronger claims require deployed/provider smoke artifacts, not local tests.
- Test coverage: Copy tests cover many banned claims; deployed/provider truth remains blocked until env-backed smoke inputs exist.

**Quiet agent door write admission is a multi-step fail-closed path:**
- Files: `src/routes/api.agent.tools.ts`, `src/modules/harness/tool-contract.ts`, `src/modules/actions/index.ts`, `src/modules/clearance/internal/web-bot-auth.ts`, `src/modules/clearance/internal/mandate.ts`, `src/modules/clearance/internal/signing.ts`, `src/modules/clearance/internal/convex-protocol-store.ts`
- Why fragile: The path depends on action surfaces, a pinned quiet-agent allowlist, Web Bot Auth identity, source-write admission, and clearance mandate evaluation. Collapsing identity into authorization would be a serious security regression.
- Safe modification: Add new `agentTools` actions only through `defineAction`, public module seams, `PublicQuietAgentToolIds`, typed output schemas, and write-admission scope review. Keep unsigned reads and signed writes distinct.
- Test coverage: `tests/integration/agent-tools-api.test.ts`, copy scans, import scans, and source-write tests cover core behavior; deployed signer proof remains gated by issue #5/#36.

**Convex schema composition and Node runtime boundaries are easy to break:**
- Files: `convex/schema.ts`, `convex/capabilityCheck.ts`, `src/modules/*/internal/schema.ts`, `src/modules/inquiries/internal/convex-schema.ts`, `convex/_generated/ai/guidelines.md`
- Why fragile: Convex codegen bundles function graphs. A transitive `node:*` import in a non-Node Convex function can break codegen, and inline schema changes in `convex/schema.ts` bypass module ownership.
- Safe modification: Add tables in the owning module fragment and spread them in `convex/schema.ts`. Put Node-only actions in dedicated `"use node"` files that export actions only.
- Test coverage: `npm run check:convex-codegen`, `npm run typecheck`, and `tests/unit/schema/convex-schema.test.ts` are required for Convex-adjacent changes.

**Operator/admin route surfaces carry private readback risk:**
- Files: `src/routes/_operator/admin.business-actions.tsx`, `src/routes/_operator/admin.monetization.tsx`, `src/routes/_operator/admin.inquiries.tsx`, `src/routes/_operator/owner.inquiries.$threadId.tsx`, `src/components/ae/readback/AeAdminReadbackPanel.tsx`
- Why fragile: Admin and owner pages intentionally render source-owned reconstruction and private operational states. A small projection change can leak raw contact, source hashes, provider refs, or private evidence.
- Safe modification: Route components should read through module server seams and render redacted DTOs only. Keep private raw payloads out of UI props and snapshots.
- Test coverage: Deploy smokes and unit/server seam tests check selected private-data absence, but full privacy assurance depends on continued DTO discipline.

- Safe modification: Use Astryx primitives and AE design-system instructions for UI work. Do not run shadcn CLI or add shadcn/radix/cva wrappers for new UI.

## Dependencies at Risk

**Nightly/rapid runtime dependencies require extra release caution:**
- Risk: The app depends on `vite@8.1.0`, `typescript@6.0.3`, React `19.2.7`, TanStack Start `1.168.26`, and `nitro` via a nightly alias. These can shift behavior around route generation, SSR, and build output.
- Impact: Build/dev behavior can change faster than stable LTS expectations, especially around TanStack route generation and server bundling.
- Migration plan: Pin versions deliberately, run `npm run test:all` plus browser gates after upgrades, and avoid coupling app contracts to generated implementation details.

**Handshake kernel is intentionally quarantined:**
- Risk: `handshake-protocol-kernel@0.4.0` is a dependency, but runtime import is meant to stay limited to the spike/root and `/adapter-sdk` posture. Deep imports or adjacent protocol packages would pull unsupported money/MCP/customer-edge surfaces into AE.
- Impact: Public posture can drift into unsupported protocol claims and Convex bundling can break if Node/runtime assumptions leak.
- Migration plan: Keep quarantine enforced by `src/lib/ui/contract-scans.ts` and `npm run test:imports`. Any expanded usage needs a separate ADR/plan and copy-scan updates.

**External providers are present but not production-proven:**
- Risk: Resend, Novu, Autumn, Stripe, OpenRouter, Sentry, PostHog, Meilisearch, Web Bot Auth, and Clerk integrations are represented in code/docs, but several provider smokes are fail-loud until real deployed inputs exist.
- Impact: Local tests cannot prove provider account setup, webhooks, callback headers, storage states, or deployed readbacks.
- Migration plan: Treat `tests/deploy-smoke/*` as the provider-readiness boundary. Do not replace them with screenshots, dashboard checks, env presence, or local-only source assertions.
