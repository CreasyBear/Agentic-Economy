## Scope and Coverage

The frontend guidelines lens checks whether the design-system implementation has a coherent, reusable contract for semantic HTML, token use, interaction states, responsive behavior, touch targets, focus visibility, motion, form errors, and component composition. The checked system has a strong baseline: shadcn new-york with Lucide is declared in `components.json`; the global CSS bridge defines semantic palette, font, radius, elevation, motion, focus, layout, and touch tokens; and the mapped patterns consistently favor real links/buttons, Radix behavior, `cn`/cva, and explicit idle/loading/empty/error/success states.

The review deliberately treats the design system as the surface. Repeated failures in shared primitives or a high-reach server-to-component state projection are weighted more heavily than isolated page polish. Existing map concerns are cited where they provide current-code evidence, but this lens does not claim runtime behavior that was not exercised.

## Verdict summary

The system is substantially more disciplined than a generic component collection. The semantic Operation composition, token bridge, market-row grammar, real interactive elements, explicit chat states, safe-area handling, 44px touch token, and reduced-motion base rules provide a credible foundation for implementation. `AeMarketToolbar`, `AeOperationCard`, `OperationComposer`, `AePageState`, and `AeSiteNav` demonstrate the intended contract particularly well.

The main risk is not missing visual polish; it is a handful of shared seams that can make the product communicate the wrong state or behave inconsistently. Listing-evidence failures are collapsed into a valid-looking empty track record, several shared primitives bypass the named token and motion contracts, overlay close controls are undersized and use a weaker focus selector, empty/error states are not consistently announced, form errors are not always connected to invalid fields, and the inspector can visibly swap responsive branches after first paint. These are system-level issues because the affected primitives and projections are reused across the product.

**Final verdict: Block**

The direction is approved in principle, but the system should not be treated as complete until the HIGH evidence-state finding and the reusable accessibility/state/token findings below are resolved. The current implementation can otherwise produce a polished-looking surface that is materially misleading or difficult to use in common failure and first-use paths.

## Recommendations (priority order)

1. Carry evidence availability as a typed state from `readOperationListingEvidence` through the inspector and track-record UI. Render outage/unavailable separately from a valid no-sample result, with a bounded retry/reload action and a focused test of both paths.
2. Repair shared primitive seams first: normalize `AlertDialog` overlay/content tokens, destructive foreground, close-button focus-visible treatment, close-button touch targets, and explicit motion tiers/reduced-motion behavior.
3. Make empty-state semantics state-driven rather than caller-optional. Require or derive `empty` versus `unavailable`, and make `EmptyDescription`’s DOM element match its public type.
4. Connect every visible field error to its invalid input or select trigger through stable, composed `aria-describedby` IDs. Give the secure checkout load failure an announced error state and safe retry/reload recovery.
5. Remove the inspector’s first-paint mobile-to-desktop branch swap and enlarge operator table selection targets without changing table selection semantics.
6. Add a narrow UI-contract check for shared primitives and shells that catches `transition-all`, raw overlay black, raw destructive `text-white`, and non-token motion values. Keep it focused on the existing source rules rather than adding a new design abstraction.
7. Preserve the current strengths: semantic links/buttons, Radix primitives, canonical Operation composition, market rows rather than generic card grids, safe-area handling, named tokens, and restrained motion. Do not add a second palette, dark mode, or decorative component layer to address these implementation gaps.

## Open questions for the owner

- Should `AeEmptyState` expose a required state union such as `empty | unavailable`, deriving role and recovery copy, instead of accepting a free-form optional `role`?
- Should `AlertDialog`, `Dialog`, and `Sheet` share one explicit overlay contract for scrim, radius, elevation, timing, focus-visible ring, and close-button target size?
- Should the inspector use a shared SSR-safe media-query hook, or should both breakpoint layouts be represented in one CSS-responsive DOM structure?
- Is the light-only decision permanent enough to justify removing dormant dark selectors from shared primitives, or should they remain as inert upstream shadcn residue while all new code stays light-only?
