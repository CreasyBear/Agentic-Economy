# Colors Review — Agentic Economy Design System
**Analysis Date:** 2026-09-01
**Lens/Skill:** better-colors — `.claude/skills/better-colors/SKILL.md`
**Scope:** `.planning/design-system/FOUNDATIONS.md` (token architecture, light-only mode, Color), `.planning/design-system/CONVENTIONS.md` (Token-first rule), `.planning/design-system/CONCERNS.md`, and `.planning/design-system/ACCESSIBILITY.md` (contrast and color semantics); verified `DESIGN.md`, `.planning/BRAND.md`, `src/styles/globals.css`, `src/styles/base.css`, and color-bearing component consumers. Other map lenses and runtime/browser rendering were not inspected.

## Scope and Coverage

This review treats the token manifest as the design-system surface. It checked the `:root` OKLCH values and aliases in `src/styles/globals.css`, the `@theme inline` semantic bridge, the light-only metadata in `src/routes/__root.tsx`, and the token-first rules in the map. It also spot-checked `Badge`, `Alert`, `Tabs`, `SidebarGroupLabel`, the public footer, the operation receipt, the market tabs, owner selection steps, Clerk appearance, and chat bubbles.

The review covers gamut and hue/chroma discipline, semantic role boundaries, AA contrast at the actual foreground/background pairs, non-color state meaning, light-only behavior, and raw/local palette escapes. It does not certify rendered browser behavior, assistive-technology output, or color-blind perception; those remain runtime checks.

## Verdict summary

The direction is unusually coherent: `--ae-bg`, `--ae-surface-sunken`, `--ae-surface`, and `--ae-fg` establish a restrained neutral ladder; `--ae-primary` stays ink; the single blue channel is bridged as `--ae-brand`/`--ae-info`; and green, amber, and red are used by the status badge and alert patterns for literal state. Selection and status examples carry text or semantic state in addition to hue: `AeStatusBadge` renders a label and description, and receipt stages provide a text label plus a screen-reader state.

The design system is not ready to approve on color grounds. Shared opacity text rules fail normal-text AA in four high-reach primitives, and the advertised brand blue fails normal-text AA on the public canvas. Four semantic OKLCH values also exceed the sRGB gamut. The muted token meets WCAG 2 AA but misses the better-colors APCA body-text minimum where it is used for supporting paragraphs.

## Verification

- Read `local://design-review-context.md`, the better-colors skill, and the relevant `color-usage.md`, `gamut-and-tailwind.md`, and `accessibility-contrast.md` references.
- Read the assigned map sections and verified authority in `DESIGN.md`, `.planning/BRAND.md`, `src/styles/globals.css`, and `src/styles/base.css`. The `@theme inline` block exposes `brand`, `brand-strong`, `brand-muted`, `on-brand`, `success`, `warning`, `info`, and the status foreground/ring/subtle roles; aliases resolve to the `--ae-*` source values.
- Converted every explicit root OKLCH color to sRGB and checked channel bounds. All neutral, base brand, success, warning base/ring/subtle, danger base/ring, and info ring values are in gamut; the four values named in Finding 3 are not.
- Measured WCAG 2 contrast from the authored light tokens: `--ae-fg` on `--ae-bg` **15.79:1**; `--ae-muted-fg` on `--ae-surface-sunken` **5.42:1**; `--ae-primary-fg`/`--destructive-foreground` on `--ae-danger` **5.28:1**; `--ae-on-brand` on `--ae-brand` **4.44:1**; and `--ae-brand` on `--ae-bg` **4.21:1**. The first three pass normal-text AA; the two blue pairs do not.
- Checked status badge pairs as authored/clipped for the out-of-gamut foregrounds: success foreground/subtle **10.68:1**, warning foreground/subtle approximately **10.21:1**, info foreground/subtle approximately **9.58:1**. The status pattern also carries visible labels, and receipt stages carry both labels and a screen-reader state.
- Checked APCA-style Lc for the same pairs: ink/canvas **+95.7**, muted/sunken **+68.7**, primary foreground/danger **-76.3**, and on-brand/brand **-71.3**. The muted result is sufficient for non-body labels but not the body-text minimum; the blue result is below the normal-text WCAG gate as well.
- Searched component consumers for raw color utilities, opacity text, status variants, direct brand usage, and dark selectors. Confirmed status colors are used for literal readiness/error/success/warning states or explicit information/selection affordances, not as generic peer-action decoration. Confirmed `Badge`, `AeStatusBadge`, and receipt timeline copy do not make state color-only.
- Confirmed light-only intent: `src/styles/globals.css:109` sets `color-scheme: light`, `src/routes/__root.tsx:45` sets document `color-scheme` to `light`, and no `.dark` token block exists. Dormant `dark:*` selectors remain in generated/shared components; their complete runtime behavior was not browser-tested.

**Not verified:** browser-native OKLCH gamut mapping versus the mathematical sRGB bounds above; rendered contrast through every translucent/backdrop surface; `prefers-contrast: more` behavior (no override was found); color-vision simulation; and runtime/assistive-technology state announcements. No browser, test, linter, or build command was run in this read-only review.

## Recommendations (priority order)

1. Remove opacity-based text failures from `TabsTrigger`, `SidebarGroupLabel`, destructive `AlertDescription`, and the public footer; use measured semantic roles at full contrast.
2. Make the blue token safe for its documented text use by lowering `--ae-brand` to an in-gamut L 0.53 value, or route body links through a corrected `--ae-brand-strong` role and reserve the brighter base for graphics.
3. Clamp all four out-of-gamut OKLCH declarations and update the matching Color table so the map does not advertise invalid display values.
4. Decide whether APCA body text is part of the product gate; if yes, darken `--ae-muted-fg` to approximately `oklch(0.43 0 0)` or introduce a clearly named darker supporting-copy role.
5. Normalize or explicitly document the warning-family hue spread while applying the gamut-safe warning foreground/subtle values.
6. Replace raw `bg-black/50` and `text-white` in shared primitives with `--ae-overlay-scrim` and `--destructive-foreground`; bridge Clerk's provider variables to the canonical ink/surface tokens.
7. Keep the light-only decision explicit, remove unsupported dormant chat dark branches, and generate/parity-check `SITE_THEME_COLOR_HEX` against `--ae-bg`.

## Open questions for the owner

- Is WCAG 2 AA the only release gate, or should APCA body Lc 75 also govern supporting paragraphs?
- Should the brighter current brand blue remain for graphic/selection use, with `text-brand-strong` as the only text role, or is a globally darker `--ae-brand` acceptable?
- Does Clerk require serialized literal colors in this adapter, or can it resolve `var(--ae-fg)` and `var(--ae-surface)` at runtime?
- Is the warning hue spread intentional per role, and if so, what semantic distinction should users learn from the shifted hues?
- Should the unconsumed chat `tinted` variant remain part of the supported UI API under a light-only product?
- Is a `prefers-contrast: more` token variant in scope for the accessibility contract?

**Verdict:** Block
