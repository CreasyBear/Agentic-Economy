# Accessibility Review — Agentic Economy Design System
**Analysis Date:** 2026-09-01
**Lens/Skill:** better-accessibility — `.claude/skills/better-accessibility/SKILL.md`
**Scope:** `ACCESSIBILITY.md` (all sections); `CONVENTIONS.md` (component-state and new-UI rules); `LAYOUT.md` (shell, responsive, overlay, and navigation rules); `PATTERNS.md` (Operation, command panel, chat, forms, tables, loading, and recovery patterns); and `CONCERNS.md` (accessibility and coverage gaps). Verified against `DESIGN.md`, `.planning/BRAND.md`, `src/styles/globals.css`, `src/styles/base.css`, `components.json`, and representative shared UI, shell, market, operator, chat, supply, owner, and payment components. `FOUNDATIONS.md` and `COMPONENTS.md` were not inspected as primary map lenses. I did not inspect every route or caller, Clerk/provider-rendered forms, or the Stripe payment iframe; no browser, assistive-technology, forced-colors, 320px/200% zoom, touch-geometry, or automated axe pass was run.

## Scope and Coverage

The map is explicit that it is source evidence rather than runtime certification (`.planning/design-system/ACCESSIBILITY.md:7-13`). I checked the locked accessibility contract in `.planning/BRAND.md:89-91` and `DESIGN.md:8-15,76-83`, then followed its implementation seams: `AePublicShell` and `AeOperatorShell` landmarks and skip targets; command-panel hotkeys and search; Radix Dialog, Sheet, AlertDialog, Select, Tabs, Accordion, and Toggle primitives; the operator sidebar and table; market toolbar/table/inspector; chat transcript, history, and composer; Field and inline-edit patterns; supply endpoint configuration; empty/page state; and credit top-up/payment states.

The foundation is credible. Public and operator shells expose main/navigation structure and skip links; command search has guarded Cmd/Ctrl-K, `/`, and Escape paths; native buttons, links, forms, tables, headings, and Radix primitives carry most interaction semantics; the data table has caption, column scope, sort state, and roving row actions; `ChatTranscript` supplies named articles and a polite log; inline editing connects its error by ID; page-level state and route skeletons distinguish status from alert; and `base.css` supplies a global reduced-motion fallback. The strongest callers already use 44px controls, explicit labels, `aria-invalid`, live status text, and cache-aware loading.

The remaining problems are contract-enforcement seams. Two HIGH findings are a normal-text contrast failure and a named operator control removed from the keyboard sequence. Seven MEDIUM findings are focus-token drift, modal close sizing, loading/skeleton announcement drift, field-error association, opt-in empty-state semantics, an unannounced payment-form failure, and an overly assertive default `Alert` role. These are source-grounded findings; runtime behavior and final computed hit areas still need the verification pass described below.

## Verdict summary

The system should not be treated as accessibility-complete yet. The semantic direction is right and many difficult paths are already handled well, especially Radix overlay behavior, shell focus targets, table semantics, chat live updates, and inline-edit errors. However, the receipt link uses the shared blue token below normal-text AA, and the operator's visible `SidebarRail` advertises a toggle while being removed from sequential keyboard navigation. Those are direct violations of the locked AA and keyboard contracts and meet the review's HIGH escalation triggers.

The MEDIUM findings are mostly drift from good existing patterns rather than missing primitives. A small number of shared fixes can make the system durable: one focus-visible recipe consuming `--ae-focus-ring`, one modal-close hit-area contract, one loading-region composition that hides geometry and announces state, and one field helper that appends error IDs. State roles should then be made mandatory at empty/error/loading boundaries instead of remaining caller opt-ins.

## Recommendations (priority order)

1. Fix the two HIGH findings first: change the receipt's normal-size link to an AA-tested blue text token and make `SidebarRail` a real keyboardable control (or remove its action semantics and rely on the existing keyboardable trigger).
2. Establish one shared `focus-visible` recipe consuming `--ae-focus-ring`, with a forced-colors-safe fallback, then migrate Button/Input/Dialog/Sheet and custom icon controls to it.
3. Give Dialog and Sheet default close buttons an explicit target contract, keeping compact X geometry inside a 24px minimum and 44px touch layout.
4. Add a reusable loading-region contract: stable polite status text, `aria-busy` on the region, and `aria-hidden` skeleton geometry. Apply it to history, charges, tables, owner workspaces, and every remaining async region while preserving cached rows.
5. Make field error IDs and `aria-describedby` composition automatic in the shared Field/reference helper, then repair all four supply endpoint field variants. Add the same contract to new forms rather than relying on caller memory.
6. Require semantic state at empty and failure boundaries: `status` for settled empty results, `alert` for outages/refusals, and an alerting payment-form load error. Change default informational `Alert` output to polite status and retain explicit urgent overrides.
7. Extend the a11y suite with focused browser checks for the rail, modal close target/focus restore, supply field errors, empty/unavailable transitions, loading announcements, payment-form failure, and desktop/mobile inspector parity; add automated rule checks only where they defend these observable contracts.
8. Preserve the already-correct patterns: native/Radix interaction, shell skip targets, semantic table structure, named chat turns, cache-aware states, truthful outcome-unknown copy, and the global reduced-motion fallback.

## Open questions for the owner

- Is `SidebarRail` intended to be a second full toggle, a resize affordance, or only a pointer convenience beside `SidebarTrigger`? The answer determines whether it should become keyboardable or lose button semantics.
- Does the 44px target contract apply to desktop modal close controls and table-selection checkboxes, or should those compact paths explicitly document the 24px/spacing exception?
- Should `AeEmptyState` derive `status` versus `alert` from the shared `ui-state.ts` object rather than accept a free semantic role at callsites?
- Is the default `Alert` primitive intentionally assertive for all informational messages, or should visual alert styling be decoupled from the live-region role?
- Which provider-rendered surfaces are in the supported accessibility boundary for browser and screen-reader certification: Clerk auth, Stripe Checkout, and any supplier-hosted content?

**Verdict: Needs changes**
