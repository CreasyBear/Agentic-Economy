## 1. ACTION SEAM INTEGRITY

[P1] · seam-coverage · src/modules/actions/index.ts:14-36 · Registry imports only `registry.actions` + `inquiry.actions` (8 actions total); billing/business-action/protected-action/catalog/observability/security owner+admin ops are NOT actions. · AGENTS.md ("operations are declared as actions... One action fans out to every surface"; "Add new operations as actions") + the owner-only inquiry actions (readOwnerInbox, reply, markRead, close with surfaces ['ui','http']) set the precedent that owner/admin ops ARE actions. Yet src/modules/billing/billing.functions.ts:274-318, src/modules/business-action/business-action.functions.ts:193-227, src/modules/protected-action/contact-follow-up.functions.ts:150-179, src/modules/catalog/owner-claim.functions.ts:147-157, src/modules/observability/funnel.functions.ts:50-83 all expose operations as bare `createServerFn().validator(zod).handler(...)` with NO defineAction, NO boundaries, NO summary, NO output schema, NOT registered. Same operational shape as inquiry owner ops, different (lesser) contract. · Decide explicitly: (a) promote these to actions for consistency, or (b) document in AGENTS.md/index.ts that only assistant-reachable ops + their siblings are actions and owner/admin ops are intentionally server-fn-only. Today it is an undocumented inconsistency that makes the registry incomplete and these ops invisible to any future fan-out. · Medium — 5 module .functions.ts + index.ts + AGENTS.md; ~25 server fns if promoted.

[P2] · contract-drift · src/modules/answer-thread/answer-thread.schema.ts:27 + src/modules/answer-thread/internal/tool-runner.ts:47 · `AnswerToolIdValues = ['registry.search','registry.detail']` (schema) is duplicated verbatim as `KNOWN_TOOL_IDS` (tool-runner:47), giving THREE hand-maintained tool lists: the registry's agentTools filter (3 incl inquiry.submit), the schema whitelist (2), and KNOWN_TOOL_IDS (2, pure dup). · The intentional narrowing (answer loop = read-only, no inquiry.submit) is correct per the safe contract, but the narrowing is NOT derived from the registry — it's a free-floating literal. A new read-only agentTool action would be listed by GET /api/agent/tools yet silently rejected by the answer loop (`tool_not_known`, tool-runner:60) unless the author also edits the schema. Undocumented coupling; will drift. · Derive the answer-loop set from the registry: `listAgentToolActions().filter(a => a.readOnly).map(a => a.id)` with a comment tying it to the safe contract; delete the KNOWN_TOOL_IDS duplication. · Low — 2 files.

## 2. CONTRACT DRIFT (HTTP API vs agent door vs actions)

[P1] · contract-drift · src/routes/api.businesses.search.ts:23 + src/routes/api.businesses.$slug.ts:18 vs src/modules/registry/registry.actions.ts:187,214 · The human HTTP endpoints call `readPublicRegistrySearchPage`/`readPublicRegistryBusinessDetail` DIRECTLY, bypassing `registrySearchAction.run`/`registryDetailAction.run`. Both call the same underlying read fn, so the *data* is identical, but the action wrapper (action.schema input parse, output-schema check, boundary docs) is NOT applied at the HTTP layer. Meanwhile registry.actions.ts declares `surfaces: ['http', 'agentJson', 'agentTools']` — the 'http' entry is vestigial: no HTTP route honors it. · AGENTS.md says the registry actions are "the machine counterparts to the human /api/businesses/search and /api/businesses/$slug surfaces," implying a shared contract. They share an implementation, not a contract. The agent door (api.agent.tools.ts:53,59) enforces `action.schema.parse` + `surfaces.includes('agentTools')`; the human HTTP door enforces nothing from the action, so input-shaping (the action trims/bounds; the route passes raw `q`) and output validation diverge silently. · Route the HTTP GETs through the actions (`registrySearchAction.run({data, context})`, reusing the ActionContext builder already in api.agent.tools.ts:87) so the 'http' surface is real and validation is centralized; OR drop 'http' from registry surfaces and document HTTP routes as deliberately independent. Pick one. · Medium — 2 route files + shared ActionContext plumbing.

[P2] · dead-parallel-handlers · src/routes/api.businesses.search.ts:34, api.businesses.$slug.ts:27, api.businesses.ts:26, llms[.]txt.ts:25 · `handleSearchBusinessesRequest`/`handleBusinessDetailRequest`/`handleListBusinessesRequest` (each calling `legacyPublicRegistry*`) and `handleLlmsTxtRequest` (calling `readFixtureLlmsTxt`) are exported but the live `Route` handlers use the `handleDurable*` variants; no caller of the non-durable exports found in src. · Parallel hand-written handlers implement the same surface a second way. Importable, divergence-prone, and they obscure the canonical path. (Removal is the DeadCode agent's remit; flagged here as a contract-drift surface, not pure dead code.) · Delete the non-durable `handle*` exports and their `legacyPublicRegistry*`/`readFixtureLlmsTxt` deps once DeadCode confirms dead. · Low — 4 route files + registry.functions.ts:137-179.

[GOOD] · GET /api/agent/tools is contract-faithful. api.agent.tools.ts:27 lists via `listAgentToolActions()` (filter `surfaces.includes('agentTools')`), POST:53 re-checks the surface, and the resulting tool set is exactly registry.search, registry.detail, inquiry.submit — matching AGENTS.md's three exposed actions. Owner inquiry actions correctly excluded (surfaces ['ui','http'] only). No hand-written tool list in the door.

## 3. SOURCE-OF-TRUTH (write paths)

[P2] · dual-entry-contract · src/routes/$slug.inquiry.tsx:65 vs src/modules/inquiries/inquiry.actions.ts:183-189 · The public UI submits via `useServerFn(submitInquiryServer)` (the TanStack server fn), NOT via `submitInquiryAction.run`, yet the action declares `surfaces: ['ui',...]`. Both paths call the same `submitPublicInquiryThroughSource` (inquiry.functions.ts:275) → admission-gated convex mutation, so the WRITE is unified and the source of truth (Convex inquiry tables) is singular. · The *contract* (boundary docs, output schema) is attached only to the action, which the UI bypasses. Input schema `publicInquirySubmitSchema` is parsed independently in BOTH the server fn (inquiry.functions.ts:250) and the action (inquiry.actions.ts:183) — two validation sites kept in sync by hand. The 'ui'/'http' surface claims on submit (and the owner reply/markRead/close actions) are not honored by their actual ui/http call sites. · Route the UI submit through `submitInquiryAction.run` to unify validation + boundary enforcement; OR drop 'ui'/'http' from surfaces and document server fns as the canonical ui/http entry with the action reserved for agent surfaces. Same call applies to the owner inquiry mutation UI paths. · Low-Medium — $slug.inquiry.tsx + inquiry server fns + owner inquiry routes.

[GOOD] · No client→Convex write bypass. Grep for `convex/browser`/`useMutation(api.` in src/ found the convex client ONLY in src/lib/server/convex-source.ts (server-side HTTP client). Every write (inquiry submit, owner reply/markRead/close, business-action capability/checkpoint/receipt, billing) funnels through a `*ThroughSource` fn that builds a `SourceWriteAdmission` (source-write-admission.ts) and calls an admission-signed Convex mutation. No duplicated/parallel client write paths. Convex `*Store.ts` files (e.g. businessActionStore.ts) are pure persistence/projection layers (load/persist slice + row→domain mappers) — no leaked business policy or orchestration. Source of truth for each core entity (business, inquiry, business-action, billing) is singular and lives in Convex tables.

4. [P2] Answer-loop tool whitelist is a 3rd hand-maintained list (AnswerToolIdValues + KNOWN_TOOL_IDS dup) decoupled from the registry — new read-only agentTools actions silently rejected.
5. [P2] Dead/duplicated non-durable HTTP handlers (handle*Request + legacy*) parallel the durable path.
6. [GOOD] No client→Convex write bypass; all writes admission-gated; *Store.ts are pure data layers; source-of-truth singular per entity.
