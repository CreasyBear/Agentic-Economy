# Agent-engine authority review — human-in-the-loop patterns

Date: 2026-07-31. Sources reviewed: LangGraph, OpenAI Agents SDK, Claude Code and Claude Agent SDK documentation, MCP specification, Vercel AI SDK, Browser Use source/docs, and OpenAI Computer Use documentation. The URLs below are the primary sources for each finding; claims are intentionally limited to behavior those sources document.

## Executive finding

The evidence supports a model-driven `/` loop only if “model owns planning” is kept separate from “model owns authority.” The strongest common shape is: let the model inspect, search, compare, and prepare; classify the proposed tool call at a deterministic seam; then either execute a low-risk/read action or pause **before the external effect** with a durable, reviewable request. LangGraph, OpenAI Agents SDK, Claude Agent SDK, AI SDK WorkflowAgent, and OpenAI Computer Use all put a non-model decision point between the model’s proposed action and execution. Sources: [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts), [OpenAI Agents HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/), [Claude Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions), [AI SDK WorkflowAgent](https://ai-sdk.dev/docs/agents/workflow-agent), [OpenAI Computer Use](https://developers.openai.com/api/docs/guides/tools-computer-use).

The disconfirming evidence is equally important. “Explore freely” is not permission to disclose personal data, send a message, submit a form, spend money, alter external state, or trust instructions found on a page. OpenAI’s Computer Use guidance calls typing sensitive data into a form a transmission and says to confirm at the point of risk; MCP explicitly forbids elicitation of sensitive information; Claude’s permissions are enforced by the host rather than by the model; and Browser Use’s documented human-in-the-loop pattern is merely a custom tool that the model must remember to call. Sources: [OpenAI Computer Use confirmation](https://developers.openai.com/api/docs/guides/tools-computer-use#handle-user-confirmation-and-consent), [MCP elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation), [Claude Code permissions](https://code.claude.com/docs/en/permissions), [Browser Use custom tools](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md).

## AE baseline under review

AE currently defines an ordered authority-mode vocabulary of `inspect_only`, `approve_each`, `bounded_mandate`, and `full_yolo`; a generic `customer_requests:create` scope defaults to `inspect_only`, and multiple mode scopes are rejected. Source: [AE `agent-contract.ts`](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/agent-contract.ts).

AE’s preparation boundary already carries action lineage, capability/version identity, input pointers and schema identities, data classifications, recipients, purposes, effect classes, authority requirements, reversibility, disclosure review, and limits. A preparation becomes `needs_authority` when its declarations contain non-public data or a non-`none` effect authority; authorization emits digest-bound approval evidence and an authority reservation before routing. Source: [AE `action-preparation.ts`](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/action-preparation.ts).

AE’s standing authority is also materially scoped: it binds a principal and delegated credential to a generation, route, capability contracts, effect classes, spend/data/occurrence limits, validity, revocation, and an explicit-confirmation fallback; consequential effects are refused by that policy. Source: [AE `standing-route-authority.ts`](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/standing-route-authority.ts).

The comparison below therefore asks whether OSS patterns validate those modes and whether their approval seams can safely replace AE’s deterministic authority kernel. They validate the direction, but not a model-held or prompt-only authority boundary.

## Findings

### 1. LangGraph: durable interrupts, tool-local gates, and replay hazards

Source: [LangGraph `interrupt()` documentation](https://docs.langchain.com/oss/python/langgraph/interrupts) and [LangGraph interrupt implementation](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py).

- **Enforcement seam:** `interrupt()` pauses at the exact point it is called and returns a JSON-serializable payload to the caller. It can sit in an approval node or directly inside a tool, so the tool call can be reviewed/edited before the tool’s effect code runs. The graph must have a checkpointer and a thread ID. Source: [interrupts in tools](https://docs.langchain.com/oss/python/langgraph/interrupts#interrupts-in-tools), [interrupt implementation](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py).
- **Taxonomy:** LangGraph does not impose a built-in read/write/effect taxonomy. The application chooses where to interrupt and what the payload means; the docs list API calls, database changes, and financial transactions as examples of actions to gate. Source: [approve or reject](https://docs.langchain.com/oss/python/langgraph/interrupts#approve-or-reject).
- **Approval UX:** streamed runs expose `stream.interrupted` and `stream.interrupts`; the application renders the payload and resumes with `Command(resume=...)`. The same mechanism supports approval, rejection, and edited state. Source: [streaming HITL](https://docs.langchain.com/oss/python/langgraph/interrupts#stream-with-human-in-the-loop-hitl-interrupts), [review/edit](https://docs.langchain.com/oss/python/langgraph/interrupts#review-and-edit-state).
- **Human gone / replay:** execution waits indefinitely for a resume when the checkpointer is durable. On resume, the node restarts from its beginning, so code before `interrupt()` runs again. LangGraph explicitly warns that side effects before the interrupt must be idempotent and recommends placing effects after the interrupt or in a separate node. Source: [interrupt lifecycle and replay](https://docs.langchain.com/oss/python/langgraph/interrupts#resuming-interrupts), [side-effect rules](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent).
- **Audit/observability:** checkpoints and streamed state/task events provide a persisted execution record, and the docs point to LangSmith for inspection. This is execution history, not evidence that LangGraph itself provides an immutable authority ledger or cryptographic approval binding. Source: [checkpoint payloads/source](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/types.py), [LangSmith debugging](https://docs.langchain.com/oss/python/langgraph/interrupts#debugging-with-interrupts).
- **Finding:** LangGraph validates an interruptible model loop and pre-effect review, but leaves classification, authority scope, approval identity, expiry, and audit semantics to the host application. It is a control-flow primitive, not an authority model. Source: [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts).

### 2. OpenAI Agents SDK: tool-declared approval callbacks plus serializable `RunState`

Sources: [OpenAI Agents SDK HITL guide](https://openai.github.io/openai-agents-python/human_in_the_loop/), [tool implementation](https://github.com/openai/openai-agents-python/blob/main/src/agents/tool.py), and [`RunState`](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_state.py).

- **Enforcement seam:** when the model emits a tool call, the runner evaluates `needs_approval` before executing the tool. `needs_approval` can be `True` or an async predicate over parsed parameters and call ID. The SDK exposes the same seam for function tools, nested `Agent.as_tool()` calls, shell/apply-patch tools, and MCP tools. Source: [approval flow](https://openai.github.io/openai-agents-python/human_in_the_loop/#how-the-approval-flow-works), [tool fields](https://github.com/openai/openai-agents-python/blob/main/src/agents/tool.py).
- **Taxonomy:** approval is opt-in and tool-defined rather than inferred from a standard read/write taxonomy. A predicate can implement a risk policy—for example, require approval for an email containing “refund”—but the host must author the policy. Source: [conditional `needs_approval`](https://openai.github.io/openai-agents-python/human_in_the_loop/#marking-tools-that-need-approval).
- **Approval UX:** a paused result contains `RunResult.interruptions` / streaming interruptions with agent, tool, and arguments. The host converts the result to `RunState`, calls `approve` or `reject`, and reruns the original top-level agent; rejection text is returned to the model. Source: [manual flow](https://openai.github.io/openai-agents-python/human_in_the_loop/#how-the-approval-flow-works), [custom rejection](https://openai.github.io/openai-agents-python/human_in_the_loop/#custom-rejection-messages).
- **Human gone / replay:** `RunState` is explicitly serializable to JSON/string and restores pending approvals, model items, tool input, nested-agent state, and approval decisions. Approval can be per-call or sticky for later calls during the same run (`always_approve`/`always_reject`); the SDK documents storing a version marker when a pause may last a long time. Source: [long-running approvals](https://openai.github.io/openai-agents-python/human_in_the_loop/#long-running-approvals), [RunState durable boundary](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_state.py).
- **Audit/approval binding:** serialized state preserves tool name, arguments, call identity, agent identity, interruption state, and approval records. This supports replay and attribution inside an SDK run, but is not a substitute for AE’s principal-bound, effect-bound authority reservation or external-effect reconciliation. Source: [serialization implementation](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_state.py).
- **Finding:** OpenAI validates the pre-execution seam and durable resume. It does **not** validate a single generic `approve_each` policy: the developer must set approval predicates/tool metadata, and sticky approval is scoped to one run rather than automatically becoming a cross-run mandate. Source: [approval rules](https://openai.github.io/openai-agents-python/human_in_the_loop/#marking-tools-that-need-approval), [sticky decisions](https://openai.github.io/openai-agents-python/human_in_the_loop/#how-the-approval-flow-works).

### 3. Claude Code and Claude Agent SDK: host-enforced allow/ask/deny, mutation, and deferral

Sources: [Claude Code permissions](https://code.claude.com/docs/en/permissions), [Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions), and [Agent SDK `canUseTool`](https://code.claude.com/docs/en/agent-sdk/user-input).

- **Enforcement seam:** Claude Code evaluates hooks, deny rules, ask rules, permission mode, allow rules, and finally `canUseTool`; the documentation states that permissions are enforced by Claude Code, not the model. `PreToolUse` can deny, ask, defer, or modify input before execution. Source: [permission evaluation](https://code.claude.com/docs/en/agent-sdk/permissions#how-permissions-are-evaluated), [PreToolUse control](https://code.claude.com/docs/en/hooks#pretooluse-decision-control).
- **Taxonomy:** the built-in distinction is operational: read-only tools such as file reads/Grep generally need no approval; Bash needs approval except recognized read-only commands; file modification needs approval. Rules can scope by tool, command/path, parameter, MCP server, and wildcard. Source: [permission table/rules](https://code.claude.com/docs/en/permissions#permission-system), [rule syntax](https://code.claude.com/docs/en/permissions#permission-rule-syntax).
- **Approval UX:** `canUseTool(toolName, input, context)` receives the exact tool input and returns allow or deny. Allow can replace the input (for example, sandboxing a path); deny sends a reason back to Claude. A callback is not called for auto-approved tools, so universal checks belong in `PreToolUse` hooks. Source: [canUseTool](https://code.claude.com/docs/en/agent-sdk/user-input#handle-tool-approval-requests), [response choices](https://code.claude.com/docs/en/agent-sdk/user-input#respond-to-tool-requests).
- **Human gone / replay:** `canUseTool` may remain pending indefinitely, but for headless integrations a `PreToolUse` hook can return `defer`; the process exits with a preserved `deferred_tool_use`, and a later `--resume` re-runs the hook and allows or denies that same tool call. The deferred session is retained on disk subject to cleanup retention, and a single-call constraint applies. Source: [defer lifecycle](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later).
- **Audit/permissions record:** “Yes, don’t ask again” can persist Bash rules in repository-local settings, while file-edit approval is session-scoped. This is a useful policy record but not an effect receipt, spend ledger, or immutable proof that a particular external business action occurred. Source: [saved approvals](https://code.claude.com/docs/en/permissions#permission-system), [hook lifecycle](https://code.claude.com/docs/en/hooks#hook-lifecycle).
- **Finding:** Claude strongly validates host-side enforcement, operation-specific rules, input mutation before execution, and deferred headless approval. Its path/command allowlists are not a domain authority model: they do not by themselves bind recipient, spend, disclosure purpose, external effect, or recovery. Source: [Agent SDK evaluation flow](https://code.claude.com/docs/en/agent-sdk/permissions#how-permissions-are-evaluated).

### 4. MCP elicitation: server-initiated structured input, not generic effect approval

Source: [MCP Elicitation specification, 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation).

- **Enforcement seam:** an MCP server sends `elicitation/create` nested inside another MCP server feature; the client presents a form and sends `accept`, `decline`, or `cancel`. The seam is inside a tool/server interaction, not necessarily before the tool call starts and not necessarily before an external effect. Source: [user interaction model](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#user-interaction-model), [message flow](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#message-flow).
- **Taxonomy:** the protocol defines structured fields using a deliberately restricted flat JSON Schema of primitive properties. It is designed for additional information, not a read/write/effect taxonomy. Servers **MUST NOT** use elicitation to request sensitive information. Source: [schema restrictions and warning](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#user-interaction-model), [request schema](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#request-schema).
- **Approval UX:** the protocol leaves interface design to clients but requires clear server identity, review/modification of responses, privacy, and decline/cancel options. Source: [user interaction model](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#user-interaction-model).
- **Human gone / replay:** the specification defines a request/response protocol but no durable checkpoint, timeout, notification, replay, or audit ledger. Those are client/server responsibilities, not MCP guarantees. Source: [protocol messages](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#protocol-messages).
- **Finding:** MCP validates “ask the person for bounded missing information while a tool workflow is in progress,” but it does not validate using elicitation as AE’s authority gate. Sensitive data and consequential action still need a host-side, pre-effect control. Source: [MCP elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation).

### 5. Vercel AI SDK: chat-stream approval messages, optional cryptographic binding, and durable WorkflowAgent

Sources: [AI SDK tool approvals](https://ai-sdk.dev/docs/agents/tool-approvals), [AI SDK WorkflowAgent](https://ai-sdk.dev/docs/agents/workflow-agent), and [AI SDK HITL cookbook](https://ai-sdk.dev/cookbook/next/human-in-the-loop).

- **Enforcement seam:** for `ToolLoopAgent`, `toolApproval` evaluates a model-produced tool call before the tool’s `execute` function; a rule can be global, per-tool, input-dependent, automatically approved/denied, or `user-approval`. Provider-executed tools are outside this AI SDK seam. Source: [approval statuses](https://ai-sdk.dev/docs/agents/tool-approvals#statuses), [input-dependent policy](https://ai-sdk.dev/docs/agents/tool-approvals#decide-based-on-tool-input).
- **Taxonomy:** the SDK has no fixed read/write classification; the application marks tools such as deletion, payments, code execution, messages, private-data access, or external API calls as requiring approval. Source: [tool approval rationale](https://ai-sdk.dev/docs/agents/tool-approvals).
- **Approval UX:** the model result emits `tool-approval-request`; the app appends a `tool-approval-response` and invokes the agent again. In `useChat`, parts expose `state: 'approval-requested'` and `addToolApprovalResponse`, directly fitting a chat stream. A denial is fed to the model, which can respond without a tool result. Source: [manual approvals](https://ai-sdk.dev/docs/agents/tool-approvals#handle-manual-approvals), [useChat](https://ai-sdk.dev/docs/agents/tool-approvals#use-with-usechat).
- **Human gone / replay:** standard `useChat` reconstructs history from client-controlled messages and does not persist server state. `experimental_toolApprovalSecret` HMAC-signs the exact tool name, tool call ID, and input; verification rejects forged/tampered approvals. `WorkflowAgent` instead suspends a durable workflow, persists the approval across process restarts, and resumes later. Source: [security considerations](https://ai-sdk.dev/docs/agents/tool-approvals#security-considerations), [WorkflowAgent approval](https://ai-sdk.dev/docs/agents/workflow-agent#tool-approval).
- **Audit/observability:** WorkflowAgent makes each tool execution a discrete workflow step visible in dashboards; standard ToolLoopAgent’s message history is not an authority ledger, and the SDK warns that client-controlled history can otherwise forge a valid-looking approval. Source: [durability/observability](https://ai-sdk.dev/docs/agents/workflow-agent#why-durable-agents), [approval integrity](https://ai-sdk.dev/docs/agents/tool-approvals#security-considerations).
- **Finding:** AI SDK validates the chat-stream approval UX and the need to bind approval to exact call material. It also gives the clearest warning against trusting client-replayed approval messages without a server signature. WorkflowAgent’s durability is transferable as a behavior, not as a dependency, because AE does not currently run Vercel Workflow/Temporal infrastructure. Source: [AI SDK security](https://ai-sdk.dev/docs/agents/tool-approvals#security-considerations).

### 6. Browser Use: custom human tool, not a generic hard gate

Sources: [Browser Use tool documentation in the repository](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md), [Browser Use tool registry](https://github.com/browser-use/browser-use/blob/main/browser_use/tools/registry/service.py), and [Browser Use tool basics](https://docs.browser-use.com/customize/tools/basics).

- **Enforcement seam:** Browser Use documents `@tools.action` as the extension point and shows an `ask_human` action that blocks on Python `input()`. The human action is therefore another tool the model may call; it is not a host interceptor that automatically wraps every click, form submission, or purchase. Source: [custom action example](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md), [add tools](https://docs.browser-use.com/customize/tools/add).
- **Taxonomy:** the documented tool registry supports adding and excluding named actions and domain restrictions, but the human-in-the-loop example supplies no generic read/write/effect classification or mandatory approval metadata. Source: [registry source](https://github.com/browser-use/browser-use/blob/main/browser_use/tools/registry/service.py), [available tools](https://docs.browser-use.com/customize/tools/available).
- **Approval UX and async:** the example is terminal input and returns an `ActionResult`; the source/docs do not establish a durable pending approval object, chat-stream approval part, or resume-after-process-exit mechanism for this custom action. Source: [human action example](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md).
- **Audit/replay:** `ActionResult` gives the agent extracted content or an error, but the cited pattern does not establish cryptographically bound approval evidence, immutable audit entries, or an external-effect receipt. Source: [tool basics](https://docs.browser-use.com/customize/tools/basics).
- **Finding:** Browser Use is disconfirming evidence against treating a model-visible `confirm` tool as an authority kernel. The model can omit or misuse it, and a blocking terminal prompt does not solve a person who is offline. A strict AE implementation must gate at the registry/dispatch boundary instead. Source: [Browser Use custom actions](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md).

### 7. OpenAI Computer Use: point-of-risk confirmation in the harness

Source: [OpenAI Computer Use guide](https://developers.openai.com/api/docs/guides/tools-computer-use).

- **Enforcement seam:** the model returns a `computer_call` with low-level actions; the application/harness executes the actions and sends a screenshot back. The API does not itself decide whether a click, type, or submit is high impact; the harness must apply confirmation policy before executing the risky action. Source: [computer-use loop](https://developers.openai.com/api/docs/guides/tools-computer-use#option-1-run-the-built-in-computer-use-loop).
- **Taxonomy:** the guidance classifies by risk rather than by tool name: deletion, access changes, CAPTCHA, downloaded code, third-party submission, financial transaction, security settings, medical care, and sensitive-data transmission require confirmation or hand-off. It treats page content and on-screen instructions as untrusted. Source: [confirmation/consent](https://developers.openai.com/api/docs/guides/tools-computer-use#handle-user-confirmation-and-consent).
- **Approval UX:** the product should let the agent make safe progress, then explain the action, risk, and data/change immediately before the next risky action. The guidance allows grouping multiple imminent, well-defined risky actions but not unclear future steps. Source: [point-of-risk confirmation](https://developers.openai.com/api/docs/guides/tools-computer-use#confirm-at-the-point-of-risk).
- **Human gone / replay:** the guide describes an action/screenshot loop and isolation/allowlists, but does not provide a durable approval object or offline resume protocol. Any such behavior must be implemented by the harness. Source: [computer-use loop](https://developers.openai.com/api/docs/guides/tools-computer-use#option-1-run-the-built-in-computer-use-loop), [safe environment](https://developers.openai.com/api/docs/guides/tools-computer-use#prepare-a-safe-environment).
- **Critical caveat:** later calls can batch actions in `actions[]`, and the guide says to run every action in order. A harness that wants a pre-effect gate must validate or split a batch before a risky action, rather than execute the whole batch first. Source: [batched actions](https://developers.openai.com/api/docs/guides/tools-computer-use#run-every-returned-action).
- **Finding:** Computer Use strongly supports AE’s point-of-risk principle and its treatment of disclosure as an effect, but it leaves the hard gate to the harness. It is evidence for a deterministic kernel around UI actions, not evidence that model-generated coordinates are authority. Source: [confirmation guidance](https://developers.openai.com/api/docs/guides/tools-computer-use#handle-user-confirmation-and-consent).

## Cross-source synthesis: where the seam actually sits

1. **Before provider/tool effect (strong pattern):** OpenAI Agents SDK evaluates approval after the model emits a tool call and before execution; AI SDK does the same; Claude `PreToolUse`/`canUseTool` does the same; LangGraph can place an interrupt inside the tool immediately before its effect. Sources: [OpenAI](https://openai.github.io/openai-agents-python/human_in_the_loop/#how-the-approval-flow-works), [AI SDK](https://ai-sdk.dev/docs/agents/tool-approvals), [Claude](https://code.claude.com/docs/en/agent-sdk/permissions#how-permissions-are-evaluated), [LangGraph](https://docs.langchain.com/oss/python/langgraph/interrupts#interrupts-in-tools).
2. **Inside a running tool/server workflow (weaker for authority):** MCP elicitation is nested inside another server feature and asks for information; Browser Use’s human action is itself selected by the model; neither guarantees that no consequential work occurred before the prompt. Sources: [MCP](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#user-interaction-model), [Browser Use](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md).
3. **Outside the framework in the harness (must be explicit):** Computer Use returns low-level UI actions and expects the harness to execute them, so effect classification and confirmation sit in the harness. Source: [Computer Use loop](https://developers.openai.com/api/docs/guides/tools-computer-use#option-1-run-the-built-in-computer-use-loop).
4. **After model proposal but before approval replay:** AI SDK explicitly warns that a client can forge a valid-looking approval when history is client-controlled and recommends HMAC binding to exact tool/call/input material. Source: [AI SDK approval integrity](https://ai-sdk.dev/docs/agents/tool-approvals#security-considerations). This is the closest OSS analogue to AE’s digest-bound approval evidence.
5. **Replay is not execution:** LangGraph reruns the interrupted node from its start; OpenAI restores `RunState`; Claude deferred calls are re-run on resume; AI SDK WorkflowAgent resumes a durable workflow. All require the application to ensure pre-gate work is idempotent or persisted and to avoid treating approval as proof that an external effect already happened. Sources: [LangGraph replay](https://docs.langchain.com/oss/python/langgraph/interrupts#resuming-interrupts), [OpenAI long-running approval](https://openai.github.io/openai-agents-python/human_in_the_loop/#long-running-approvals), [Claude defer](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later), [WorkflowAgent](https://ai-sdk.dev/docs/agents/workflow-agent#tool-approval).

## Implications for AE decisions D1–D6

| Decision | Result | Evidence-backed implication |
|---|---|---|
| **D1 — `/` becomes a model-driven agent engine** | **SUPPORTS, but REFINES** | Tool-call loops, streamed interruptions, and durable resume are first-class in LangGraph, OpenAI Agents SDK, Claude Agent SDK, and AI SDK; however, every serious implementation keeps a deterministic runner/checkpoint/permission seam, so replacing classification/routes cannot mean replacing deterministic admission and recovery. Sources: [LangGraph](https://docs.langchain.com/oss/python/langgraph/interrupts), [OpenAI](https://openai.github.io/openai-agents-python/human_in_the_loop/), [Claude](https://code.claude.com/docs/en/agent-sdk/permissions), [AI SDK](https://ai-sdk.dev/docs/agents/tool-approvals). |
| **D2 — deterministic router demoted to safety kernel** | **SUPPORTS** | Claude states permissions are enforced by the host, AI SDK re-evaluates approval policy and can HMAC-bind the exact call, OpenAI evaluates `needs_approval` in the runner, and Computer Use places action policy in the harness. The deterministic kernel should own identity, capability/effect classification, authority, spend/data limits, idempotency, evidence, and recovery while the model proposes actions. Sources: [Claude host enforcement](https://code.claude.com/docs/en/permissions#manage-permissions), [AI SDK security](https://ai-sdk.dev/docs/agents/tool-approvals#security-considerations), [OpenAI approval flow](https://openai.github.io/openai-agents-python/human_in_the_loop/#how-the-approval-flow-works), [Computer Use](https://developers.openai.com/api/docs/guides/tools-computer-use#handle-user-confirmation-and-consent). |
| **D3 — explore freely, approve effects** | **SUPPORTS with a hard boundary** | Read/search/compare can be auto-approved when the host classifies them as safe, while writes, payments, submissions, sensitive disclosure, and external state changes are gated. OpenAI’s computer guidance says direct user instructions—not page text—count as permission, and MCP forbids sensitive elicitation; Browser Use contradicts a prompt-only confirm tool because the model may omit it. Sources: [Claude read/write tiers](https://code.claude.com/docs/en/permissions#permission-system), [OpenAI point-of-risk](https://developers.openai.com/api/docs/guides/tools-computer-use#confirm-at-the-point-of-risk), [MCP warning](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#user-interaction-model), [Browser Use](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md). |
| **D4 — machine endpoints plus async human/business inquiries; chase/notify is product** | **REFINES** | LangGraph waits indefinitely on durable checkpoints, OpenAI serializes `RunState`, Claude supports deferred headless calls, and AI SDK WorkflowAgent survives workflow suspension. MCP and Browser Use do not guarantee persistence. AE can implement the behavior with a Convex pending-approval record plus answer-thread SSE and a resume command, without adopting a new queue runtime. Sources: [LangGraph](https://docs.langchain.com/oss/python/langgraph/interrupts#pause-using-interrupt), [OpenAI](https://openai.github.io/openai-agents-python/human_in_the_loop/#long-running-approvals), [Claude defer](https://code.claude.com/docs/en/hooks#defer-a-tool-call-for-later), [AI SDK durability](https://ai-sdk.dev/docs/agents/workflow-agent#why-durable-agents), [MCP](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#protocol-messages). |
| **D5 — capture contact at first async effect, not up front** | **REFINES / sometimes CONTRADICTS** | Lazy capture is compatible with safe exploration only when contact is treated as data release and the first async effect is prepared/gated before sending it. OpenAI explicitly classifies contact information as sensitive and typing it into a form as transmission; MCP forbids sensitive elicitation. Therefore “capture at first effect” must not mean silently collect or disclose contact under `inspect_only`; it should be part of the exact prepared disclosure scope approved at the seam. Sources: [OpenAI sensitive data](https://developers.openai.com/api/docs/guides/tools-computer-use#protect-sensitive-data), [OpenAI confirmation](https://developers.openai.com/api/docs/guides/tools-computer-use#confirm-at-the-point-of-risk), [MCP](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#user-interaction-model), [AE preparation](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/action-preparation.ts). |
| **D6 — act first, ask when blocked** | **SUPPORTS, with risk-triggered exceptions** | Point-of-risk guidance says do safe work first and ask immediately before the risky action; LangGraph supports an interrupt at the effect boundary. But “blocked” must include a required sensitive disclosure, ambiguous recipient/terms, prompt injection, or authority mismatch—not merely missing information the model can guess. Sources: [Computer Use point-of-risk](https://developers.openai.com/api/docs/guides/tools-computer-use#confirm-at-the-point-of-risk), [LangGraph tool interrupt](https://docs.langchain.com/oss/python/langgraph/interrupts#interrupts-in-tools), [Computer Use untrusted pages](https://developers.openai.com/api/docs/guides/tools-computer-use#treat-only-direct-user-instructions-as-permission). |

**Overall D3 verdict:** OSS patterns validate AE’s `inspect_only` → `approve_each` → `bounded_mandate` direction, provided modes are enforced by the kernel against effect/data scope and not merely expressed as prompt instructions. They do not validate “free exploration” that includes contact disclosure, third-party submission, or spending. Sources: [AE modes](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/agent-contract.ts), [Claude enforcement](https://code.claude.com/docs/en/agent-sdk/permissions#how-permissions-are-evaluated), [OpenAI confirmation](https://developers.openai.com/api/docs/guides/tools-computer-use#handle-user-confirmation-and-consent).

## Recommended single approval-seam design for AE

**Seam:** `model tool proposal → canonical action preparation → deterministic authority decision → (execute or pending approval) → provider dispatch → receipt/reconcile`.

1. **Make every registered action declare effect metadata.** Extend the existing registered action descriptor/contract so each action declares whether it is observation, comparison/quote, data release, financial exposure, or external state change; reversibility; recipient kind; data classifications; spend/currency; and whether explicit approval or bounded mandate is required. The model may choose only registered actions and values that pass the existing contract. This follows Claude’s host-side classification and OpenAI Computer Use’s risk taxonomy while preserving AE’s existing capability/effect vocabulary. Sources: [Claude permission rules](https://code.claude.com/docs/en/permissions#permission-system), [Computer Use risk classes](https://developers.openai.com/api/docs/guides/tools-computer-use#handle-user-confirmation-and-consent), [AE preparation types](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/action-preparation.ts).
2. **Compile the model call into a digest-bound preparation before any provider call.** Bind request principal, request/revision, agent identity, action/version, exact input digest, selected recipient/business, purpose, data scope, effect scope, spend, expiry, and recovery rule. Reuse AE’s existing `projectActionPreparation`: it already returns `needs_authority` for non-public/non-`none` declarations and creates disclosure review material. Sources: [AE action preparation](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/action-preparation.ts), [AI SDK exact approval binding](https://ai-sdk.dev/docs/agents/tool-approvals#signing-approvals-with-experimental_toolapprovalsecret).
3. **Use one kernel admission rule for all modes.** `inspect_only` executes only safe observation/comparison actions; it refuses data release, payment, commitment, and external state change. `approve_each` persists a pending approval for the exact preparation. `bounded_mandate` executes only when the prepared action matches the principal-bound mandate’s route/capability/data/effect/spend/count/time limits; otherwise it steps up to explicit approval. Keep `full_yolo` explicit if retained in the current contract, but never let it bypass authentication, capability checks, idempotency, evidence, or reconciliation. Sources: [AE authority modes](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/agent-contract.ts), [AE standing authority refusal rules](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/standing-route-authority.ts), [Claude permission ordering](https://code.claude.com/docs/en/agent-sdk/permissions#how-permissions-are-evaluated).
4. **Pause before provider dispatch, not in a model-visible `confirm` tool.** On `approve_each`, create a Convex pending-approval record containing the preparation/authority-scope digest, review payload, current request revision, owner/principal, expiration, and next action. Emit an approval-required event on the existing answer-thread SSE stream; show action, recipient, data to be disclosed, spend, reversibility, and recovery. This matches OpenAI/AI SDK interruption UX and avoids Browser Use’s model-optional confirmation. Sources: [OpenAI interruption UX](https://openai.github.io/openai-agents-python/human_in_the_loop/#how-the-approval-flow-works), [AI SDK chat UX](https://ai-sdk.dev/docs/agents/tool-approvals#use-with-usechat), [Browser Use limitation](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md).
5. **Approve by exact digest, then execute once.** The Customer Request approval command must authenticate the owner/agent authority, verify principal and request revision, recompute the preparation and authority-scope digest, enforce expiry/revocation, and issue AE’s existing approval evidence/reservation. Dispatch only after this succeeds, with idempotency bound to the exact operation payload. If approval changes input, recipient, purpose, data, effect, spend, or route, invalidate the old approval and create a new preparation rather than mutating the old one. This is the stricter AE equivalent of AI SDK’s HMAC binding and Claude’s `updatedInput` option. Sources: [AI SDK binding](https://ai-sdk.dev/docs/agents/tool-approvals#signing-approvals-with-experimental_toolapprovalsecret), [Claude input mutation](https://code.claude.com/docs/en/agent-sdk/user-input#approve-with-changes), [AE approval evidence](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/action-preparation.ts).
6. **Resume the loop without replaying an external effect.** Approval resumes the pending action invocation or a fresh model turn with an authoritative tool result; it does not blindly replay the entire model plan. A provider timeout or ambiguous response becomes `outcome_unknown` and triggers reconciliation before retry. This preserves LangGraph’s idempotency warning and AE’s existing preparation/route recovery model. Sources: [LangGraph replay warning](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent), [AE customer request states](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/agent-contract.ts), [AE route execution](https://github.com/CreasyBear/Agentic-Economy/tree/main/src/modules/customer-request/route-execution).
7. **Treat lazy contact capture as part of the first prepared disclosure.** Search/compare can proceed without contact. When an async business inquiry first requires contact, include the exact contact fields, recipient/business, purpose, retention/use, and any spend/commitment in the preparation; `inspect_only` pauses/refuses, `approve_each` asks once at that point, and `bounded_mandate` proceeds only when the mandate explicitly covers that disclosure. Do not use MCP-style elicitation or a generic chat question as a substitute for the authority grant. Sources: [OpenAI contact-data rule](https://developers.openai.com/api/docs/guides/tools-computer-use#protect-sensitive-data), [MCP sensitive-data prohibition](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation#user-interaction-model), [AE disclosure review](https://github.com/CreasyBear/Agentic-Economy/blob/main/src/modules/customer-request/action-preparation.ts).

This seam preserves act-first behavior for genuinely safe work, while making the exact transition from exploration to commitment/data release durable, observable, and non-bypassable. It also fits the supplied AE stack: the Convex record is the durable pause, answer-thread SSE is the notification/approval UX, and the existing preparation/authority modules remain the enforcement point rather than introducing a second queue or workflow control plane. Sources for the analogous durability/streaming behavior: [OpenAI RunState](https://github.com/openai/openai-agents-python/blob/main/src/agents/run_state.py), [LangGraph streaming interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#stream-with-human-in-the-loop-hitl-interrupts), [AI SDK WorkflowAgent](https://ai-sdk.dev/docs/agents/workflow-agent#tool-approval).

## Skip list — patterns that should not be copied as AE authority

- **LangGraph static breakpoints:** documented as debugging breakpoints, not the recommended HITL mechanism; they do not encode effect scope or authority. Use dynamic pre-effect preparation instead. Source: [LangGraph static interrupt note](https://docs.langchain.com/oss/python/langgraph/interrupts#debugging-with-interrupts).
- **LangGraph side effects before `interrupt()`:** replay can rerun them; copying this shape would risk duplicate business contact, payment, or commitment. Keep provider effects after admission and make uncertain outcomes reconcile-only. Source: [LangGraph side-effect warning](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent).
- **OpenAI SDK `always_approve`:** sticky approval is scoped to the remainder of one SDK run and is not a principal-bound, expiring, spend/data/route mandate. Use AE `bounded_mandate`, not an SDK callback flag, for repeat authority. Source: [OpenAI sticky decisions](https://openai.github.io/openai-agents-python/human_in_the_loop/#how-the-approval-flow-works).
- **Claude Code path/command allowlists:** useful for local files and shell commands, but they do not express business recipient, purpose, currency, external commitment, or provider reconciliation. Do not model AE authority as `Bash(*)`-style strings. Source: [Claude rule syntax](https://code.claude.com/docs/en/permissions#permission-rule-syntax).
- **Claude `bypassPermissions` / AI SDK client-controlled approval history:** both can be unsafe defaults for a marketplace authority boundary; AI SDK explicitly warns that client-controlled messages can forge approvals without a shared signing secret. Source: [Claude bypass warning](https://code.claude.com/docs/en/agent-sdk/permissions#permission-modes), [AI SDK security warning](https://ai-sdk.dev/docs/agents/tool-approvals#security-considerations).
- **MCP elicitation as approval:** elicitation is for structured missing information and forbids sensitive requests; it has no built-in authority grant, durability, or effect receipt. Source: [MCP elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation).
- **AI SDK WorkflowAgent runtime:** durable suspension is evidence for the behavior, not a reason to add Vercel Workflow/Temporal infrastructure to AE. Reproduce the state transition with existing Convex + SSE and preserve AE’s source of truth. Source: [WorkflowAgent durability](https://ai-sdk.dev/docs/agents/workflow-agent#why-durable-agents).
- **Browser Use `ask_human` custom action:** the model must call it, the example blocks on terminal input, and no cited source provides a mandatory dispatcher gate or offline approval resume. Do not ship a model-optional confirmation tool as the authority boundary. Source: [Browser Use example](https://raw.githubusercontent.com/browser-use/browser-use/main/AGENTS.md).
- **Computer Use coordinate-level batching:** low-level UI actions can be batched and the harness is told to run them in order; copying this without splitting before risky actions can execute a submission before confirmation. Source: [Computer Use batched actions](https://developers.openai.com/api/docs/guides/tools-computer-use#run-every-returned-action).
- **Generic yes/no approval prompts:** none of the strong patterns treats a bare boolean as sufficient evidence for a material external effect; the useful payload includes tool/action, arguments, scope, recipient, risk, and an exact resumable operation. Source: [OpenAI approval item](https://openai.github.io/openai-agents-python/human_in_the_loop/#how-the-approval-flow-works), [Claude `canUseTool` inputs](https://code.claude.com/docs/en/agent-sdk/user-input#handle-tool-approval-requests), [AI SDK approval request](https://ai-sdk.dev/docs/agents/tool-approvals#handle-manual-approvals).
