# Durable execution for agent plans that wait on people and businesses

Date: 2026-07-31. Sources reviewed: Convex (official documentation and the `get-convex/agent`, `get-convex/workflow`, and `get-convex/workpool` source repositories), Temporal (official documentation), Restate (official documentation), Inngest (official documentation), Trigger.dev (official documentation), Resend (official documentation), Postmark (official documentation), and Twilio (official documentation).

## Executive verdict

**Build on Convex components now; do not adopt Temporal, Restate, Inngest, or Trigger.dev as new execution infrastructure for the first `/` agent engine.** The smallest credible plan runner is `@convex-dev/agent` plus `@convex-dev/workflow`, with a small application-owned plan/event/outbox model. Convex Workflow already provides durable steps, retries, arbitrary sleeps, indefinite external-event waits, cancellation/restart, and reactive status, while the Agent component persists threads/messages and streams updates to clients ([Convex Agent docs](https://docs.convex.dev/agents/overview), [Agent source README](https://github.com/get-convex/agent/blob/main/README.md), [Workflow source README](https://github.com/get-convex/workflow/blob/main/README.md)).

This is a **conditional** feasibility result, not evidence that Convex provides exactly-once delivery of email/SMS or general workflow-code versioning. Convex's own source warns that a workflow can fail if a step function's name changes while the run is asleep for a later event, and its workflow handler must be deterministic ([Workflow source README, custom names](https://github.com/get-convex/workflow/blob/main/README.md#specifying-a-custom-name-for-a-step), [Workflow source README, usage restrictions](https://github.com/get-convex/workflow/blob/main/README.md#usage)). The action retry boundary is therefore an external-effect boundary: stable effect IDs, provider-specific deduplication where available, inbound-event deduplication, and explicit terminal/reconciliation states remain AE code ([Convex Workpool source README, idempotency](https://github.com/get-convex/workpool/blob/main/README.md#idempotency), [Convex Workflow source README, retry behavior](https://github.com/get-convex/workflow/blob/main/README.md#specifying-retry-behavior)).

**D4 is feasible without a new queue/worker product at small volume:** instant registered actions and asynchronous business inquiries can share one Convex Workflow, with email/SMS provider webhooks waking typed workflow events. **D5 is feasible only as an explicit async-boundary interaction:** capture and validate the person's notification contact immediately before the first external notification/inquiry, not at request creation; the plan must be able to pause if the person declines. **D1/D2/D3/D6 need refinement:** the model may choose the next bounded step, but durable execution and safety still own step identity, authorization, idempotency, deadlines, and effect recording (inference from the execution guarantees and limits in the sources above).

## Findings: Convex components first

### 1. Agent component: durable conversation context, not the plan scheduler

- Convex's Agent component persists threads and messages, permits sharing a thread across users and agents (including human agents), and streams text/objects as deltas so clients stay synchronized. It is designed to separate long-running agentic workflows from the UI without losing reactivity ([Agent source README](https://github.com/get-convex/agent/blob/main/README.md), [Convex Agent overview](https://docs.convex.dev/agents/overview)).
- Convex explicitly places multi-step, long-lived, pause/resume work in the Workflow component. Agent calls can be used inside workflow steps; the workflow docs show `step.runAction` around model generation and passing a stable `promptMessageId` so a retry can reuse the same prompt/response record ([Convex Agent workflows](https://docs.convex.dev/agents/workflows), [agent workflow example](https://github.com/get-convex/agent/blob/main/example/convex/workflows/chaining.ts)).
- Convex documents a human-agent pattern: save a human reply into the same thread, or represent an `askHuman` tool call and later save a tool result before continuing generation. The support inbox/assignment is application code, not an automatic human-task queue ([Convex human agents](https://docs.convex.dev/agents/human-agents)).

**What this gives AE:** the answer thread remains the conversation spine, with model turns, business replies, and human decisions represented as durable messages. **What it does not give:** a durable wait, external callback correlation, notification transport, approval authorization, or outbound-effect exactly-once guarantee; those belong in Workflow plus AE-owned tables and routes (inference from the Agent API and the separate Workflow API).

### 2. Workflow component: the smallest useful durable plan primitive

- The Workflow source says a workflow can pause indefinitely on an asynchronous event or sleep for arbitrary time with no resources consumed during the wait; steps are ordinary Convex queries, mutations, or actions and can be sequential or parallel ([Workflow source README](https://github.com/get-convex/workflow/blob/main/README.md)).
- Workflow handlers re-execute deterministically until the next incomplete step, replaying recorded history. The handler must avoid unrestricted nondeterminism such as `fetch`, environment reads, and crypto; those belong in called Convex actions ([Workflow source README, how it works](https://github.com/get-convex/workflow/blob/main/README.md#how-it-works), [Workflow source README, usage restrictions](https://github.com/get-convex/workflow/blob/main/README.md#usage)). This is the principal constraint on a model-driven loop: model calls and business effects must be explicit durable steps, not arbitrary work in the orchestration body.
- `step.awaitEvent` is a direct human/business wait primitive. A workflow can wait by name or by a dynamically created event ID; another mutation/action sends the event to the matching workflow ID; values and errors can be validated and delivered. The event is consumed once, so an AE callback must persist its own deduplication/audit record before waking the plan ([Workflow source README, waiting for external events](https://github.com/get-convex/workflow/blob/main/README.md#waiting-for-external-events)).
- `step.sleep`, `runAfter`, and `runAt` cover reminders, deadlines, and “try again tomorrow” without a polling loop ([Workflow source README, sleeping and delayed steps](https://github.com/get-convex/workflow/blob/main/README.md#sleeping-and-running-steps-after-a-delay)).
- Action retry is opt-in by default in the Workflow component; retry policies can be configured per action, while Convex query/mutation system failures are retried under Convex's transaction guarantees. The source explicitly says mutations execute exactly once except rollback/retry behavior caused by database conflicts, but action side effects are not made exactly once by this statement ([Workflow source README, retry behavior](https://github.com/get-convex/workflow/blob/main/README.md#specifying-retry-behavior), [Convex scheduled-function error handling](https://docs.convex.dev/scheduling/scheduled-functions#errors)).
- Workflow status and step history are queryable and reactive; the source documents cancellation, restart from a step, paginated listing, and explicit cleanup. Completed workflow storage is not automatically cleaned up ([Workflow source README, status](https://github.com/get-convex/workflow/blob/main/README.md#checking-a-workflows-status), [Workflow source README, cancellation/restart/cleanup](https://github.com/get-convex/workflow/blob/main/README.md#canceling-a-workflow)).
- Workflow outputs and arguments count toward Convex database bandwidth; the docs recommend passing IDs and storing large data separately. This matters for an agent that may produce long transcripts, search results, or many provider options ([Convex Agent workflows](https://docs.convex.dev/agents/workflows), [Workflow source README, usage restrictions](https://github.com/get-convex/workflow/blob/main/README.md#usage)).
- The source imposes a concrete journal budget: steps can take in/return only 1 MB total within one workflow execution and the journal has an 8 MiB limit; it also says adding, removing, or reordering steps causes a determinism violation and the implementation should stay stable for active workflows ([Workflow source README, limitations](https://github.com/get-convex/workflow/blob/main/README.md#limitations)). This is disconfirming evidence against unconstrained model-generated plans: store transcripts/results by ID, bound the loop, and treat deployed workflow shape as an API.
- A material operational hazard is code evolution: the source warns that renaming/moving a step function can fail a workflow when it resumes after a long sleep/event wait; it suggests retaining the old name. The reviewed Convex Workflow docs do not describe a Temporal-style patch/worker-versioning mechanism. **[INFERENCE]** AE must treat workflow step names and control-flow shape as a compatibility surface and carry an explicit plan/engine version in its own state; this is not equivalent to built-in version pinning ([Workflow source README, custom step names](https://github.com/get-convex/workflow/blob/main/README.md#specifying-a-custom-name-for-a-step), [Temporal versioning docs for contrast](https://docs.temporal.io/develop/go/versioning)).

### 3. Workpool: bounded action throughput and retries, not human waiting

- Workpool pools actions/mutations, limits parallelism, supports configurable exponential backoff/jitter for retryable **idempotent** actions, and invokes an `onComplete` callback for success/failure/cancellation ([Workpool source README](https://github.com/get-convex/workpool/blob/main/README.md)). Workflow uses Workpool under the hood, so adding a separate Workpool instance is optional rather than required for a first plan runner ([Workflow source README](https://github.com/get-convex/workflow/blob/main/README.md#how-it-works)).
- Workpool's own idempotency example uses a payment processor transaction ID to avoid double charging. It says retries are safe only when the external operation can recognize a stable key or otherwise no-op duplicates ([Workpool source README, idempotency](https://github.com/get-convex/workpool/blob/main/README.md#idempotency)). This is directly applicable to AE's credit ledger, payments, and business-inquiry sends.
- Workpool persists job status for reactive reads, but status is kept one day by default unless `statusTtl` is changed; an async plan's source of truth must therefore live in AE tables or Workflow state, not a default Workpool status record ([Workpool source README, reactive status](https://github.com/get-convex/workpool/blob/main/README.md#reactive-status-of-asynchronous-work)).

### 4. Scheduled functions and crons: durable clocks, not the plan state machine

- Convex stores scheduled functions in its database, so functions can be scheduled minutes, days, or months ahead and survive downtime/restarts. Scheduling from a mutation is atomic with the mutation; scheduling from an action is not atomic because actions can have side effects and later fail ([Convex scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions)).
- Scheduled mutations are guaranteed exactly once under Convex's semantics, but scheduled actions are at-most-once and not automatically retried; the docs recommend an explicit check-and-reschedule pattern for action retries. Scheduled functions do not inherit the caller's auth, so identity/authority must be passed and rechecked ([Convex scheduled functions, error handling/auth](https://docs.convex.dev/scheduling/scheduled-functions#errors), [Convex scheduled functions, auth](https://docs.convex.dev/scheduling/scheduled-functions#auth)).
- Cron jobs permit recurring cleanup/reminders, but at most one run of a cron job executes at a time and later runs may be skipped when the prior run is still executing ([Convex cron jobs](https://docs.convex.dev/scheduling/cron-jobs#error-handling)).

**Decision:** use Workflow `sleep`/`runAt` for a plan's own deadline/reminder path; use crons only for bounded retention cleanup, stale-plan reconciliation, and metrics sweeps. A cron-driven poller for every waiting business inquiry would add delay and duplicate state without improving durability (inference from the documented event/sleep and cron semantics).

## Findings: canonical durable-execution patterns

### Temporal: event history + signals/timers + idempotent activities + explicit versioning

- Temporal defines a Workflow Execution as durable, reliable, and scalable, with no imposed time limit; state is persisted in an Event History and replay resumes after failure. A workflow can block on SDK awaitables including Signals, Activities, and durable timers ([Temporal Workflow Execution](https://docs.temporal.io/workflow-execution)).
- Signals are asynchronous messages sent by a client/CLI/workflow to a running workflow; Updates provide a synchronous handler/result option, and Queries read state without changing it ([Temporal message passing](https://docs.temporal.io/sending-messages)). A human approval is therefore usually a Signal/Update into a workflow, not a worker sitting in a “human queue.”
- Temporal's official approval guide models a human wait with `wait_condition`, a durable timer, reminders, escalation, resubmission, and an audit record; the Worker is idle while waiting and the state is replayed when a Signal or timer arrives ([Temporal reliable document approvals](https://docs.temporal.io/guides/reliable-document-approvals)). This is the canonical D4/D6 shape: wait on an event, race it against a deadline, then escalate or resume.
- Activities contain nondeterministic I/O such as API calls, LLM calls, database writes, or email. Temporal retries Activities, but an Activity may execute more than once before completion is recorded; official guidance requires idempotency keys/check-before-act/upsert semantics, and suggests Workflow Run ID + Activity ID as a stable key ([Temporal Activities](https://docs.temporal.io/activities), [Temporal Activity idempotency](https://docs.temporal.io/activity-definition#idempotency)). “Exactly once” is therefore an observed completion/history property, not a promise that an external email/payment cannot be duplicated.
- Temporal supports Worker Versioning and patch markers so new executions use new logic while existing executions continue old logic; its docs explain that long-lived workflows require this because incompatible replay changes otherwise cause nondeterminism ([Temporal Go versioning](https://docs.temporal.io/develop/go/versioning)). Long model-driven loops also need history management: the approval guide cites event-history size limits and recommends Continue-As-New for long/resubmission-heavy runs ([Temporal approval event-history guidance](https://docs.temporal.io/guides/reliable-document-approvals)).
- Temporal Task Queues route Workflow/Activity work to polling Workers; the human decision itself is still an application/UI Signal or Update ([Temporal task queues](https://docs.temporal.io/task-queue), [Temporal message passing](https://docs.temporal.io/sending-messages)). Do not mistake a worker task queue for a business-operator inbox.

**Transfer to AE:** use `awaitEvent` + `sleep` + typed audit rows like a Signal/timer workflow; isolate OpenRouter/provider calls in actions; use stable effect IDs; cap model-loop steps and periodically roll state into a new plan/run record if history grows (inference from Temporal's documented constraints). Temporal's versioning and Continue-As-New are valuable warning signs for Convex, but importing Temporal solely to get them would add a new service/worker fleet that AE does not currently operate ([Temporal workers](https://docs.temporal.io/workers)).

### Restate: journaled steps + awakeables + immutable deployments

- Restate records each durable step and its result in a journal, replays the journal after failure while skipping completed steps, and can suspend FaaS handlers while waiting for external events ([Restate key concepts](https://docs.restate.dev/foundations/key-concepts), [Restate actions/durable steps](https://docs.restate.dev/foundations/actions)).
- Restate has three relevant wait primitives: repeatable named Signals, one-shot Awakeables with generated IDs for external callbacks, and workflow-scoped promises. All survive retries/process restarts and can suspend execution without consuming resources ([Restate TypeScript external events](https://docs.restate.dev/develop/ts/external-events)). Awakeables are nearly a direct analogue for a business reply webhook or human approval token.
- Restate deduplicates duplicate invocation requests when callers provide an idempotency key; its journal is not a substitute for making a third-party side effect safe ([Restate key concepts](https://docs.restate.dev/foundations/key-concepts)).
- Restate uses immutable deployment endpoints: in-flight requests stay on their original deployment, new requests use the latest deployment, and old deployments must remain until invocations drain. It explicitly recommends avoiding handlers that run for days/months and instead breaking work into delayed calls; state schemas must remain backward compatible ([Restate versioning](https://docs.restate.dev/services/versioning)).
- Restate requires a Restate Server (or Restate Cloud) in front of services; the server owns invocation/journal delivery and flow control ([Restate key concepts](https://docs.restate.dev/foundations/key-concepts)).

**Transfer to AE:** model provider callbacks as opaque, one-shot event IDs and use a durable timer for expiry; keep business state in Convex rather than introducing a second state authority. The deployment-pinning warning reinforces that multi-day model plans need stable step contracts even on Convex (inference from the Restate versioning model and Convex's step-name warning).

### Inngest: checkpointed steps + waitForEvent + step-ID evolution

- Inngest persists state outside a function invocation; each `step.run` is an independently retryable unit whose successful result is memoized and skipped on subsequent executions. The execution model uses ordinary language primitives rather than Temporal-style deterministic replay ([Inngest function execution](https://www.inngest.com/docs/learn/how-functions-are-executed), [Inngest steps](https://www.inngest.com/docs/learn/inngest-steps)).
- `step.waitForEvent` pauses until a matching event or timeout, supports match/CEL predicates, and is explicitly documented for human-in-the-loop approvals and webhooks; `step.sleep` covers seconds-to-months delays ([Inngest waitForEvent](https://www.inngest.com/docs/reference/typescript/v4/functions/step-wait-for-event), [Inngest sleep](https://www.inngest.com/docs/reference/functions/step-sleep)).
- Inngest includes concurrency, throttling, rate limiting, prioritization, debouncing, and idempotency controls in its execution service ([Inngest function execution, flow control](https://www.inngest.com/docs/learn/how-functions-are-executed)).
- Its versioning model uses stable step IDs: adding steps is generally safe, changing a step ID intentionally forces re-execution, removed steps are ignored, and major incompatible rewrites should use a new function/timestamp cutover. This is a more forgiving evolution model than Convex Workflow's documented step-function-name hazard, but it is a property of Inngest's own memoization runtime and does not transfer automatically ([Inngest versioning](https://www.inngest.com/docs/learn/versioning)).

**Transfer to AE:** stable semantic step IDs and explicit “v2” cutovers are good application conventions. Do not assume Convex can safely reorder/insert arbitrary model-generated steps; use fixed named step adapters and versioned plan data (inference from comparing Inngest's memoization contract with Convex Workflow's deterministic replay contract). Inngest has no separate queue cluster to operate in its documented model, but it is still an additional managed execution/state dependency for AE ([Inngest function execution](https://www.inngest.com/docs/learn/how-functions-are-executed)).

### Trigger.dev: checkpoint/resume + waitpoint tokens + task handles

- Trigger.dev tasks run in the background and return a handle for status; the platform describes a Checkpoint-Resume system that snapshots task state at waits/subtask boundaries, releases resources, and restores execution when a subtask/event/timer completes ([Trigger.dev how it works](https://trigger.dev/docs/how-it-works)).
- Trigger.dev's wait API supports fixed waits, absolute deadlines, and waitpoint tokens. A token can have a timeout, be completed by SDK or HTTP callback, and expose a scoped public access token for browser approval; this is a polished human-task/callback primitive ([Trigger.dev wait overview](https://trigger.dev/docs/wait), [Trigger.dev wait-for-token](https://trigger.dev/docs/wait-for-token)).
- Trigger.dev assigns idempotency keys to subtasks, caches results, and retries failed subtasks/subsequent tasks; the wait token itself also supports an idempotency key and TTL ([Trigger.dev how it works](https://trigger.dev/docs/how-it-works), [Trigger.dev waitpoint token options](https://trigger.dev/docs/wait-for-token#waitcreateToken)).
- The documented architecture includes a task queue, scheduler, worker pool, isolated task environments, and a cloud/self-hosted deployment; the checkpoint mechanism is not a Convex primitive ([Trigger.dev how it works](https://trigger.dev/docs/how-it-works)).

**Transfer to AE:** copy the *interface* idea—opaque approval token, expiry, scoped completion, resumable status—not the CRIU/process-snapshot implementation. On Convex, use a generated workflow event ID, a Clerk-authenticated or signed callback, and a Convex mutation that validates ownership before calling `sendEvent` (inference from Trigger.dev's token contract and Convex's event API).

## Findings: outbound business-inquiry channels

### Resend inbound email/reply loop

- Resend receives any mail sent to a receiving domain, parses it, and POSTs an `email.received` webhook to AE. The webhook contains metadata only; the body/headers/attachments must be fetched from the Received Emails API, which favors a fast webhook acknowledgement followed by a durable fetch/parse step ([Resend receiving email](https://resend.com/docs/dashboard/receiving/introduction)).
- Resend stores inbound mail when the webhook endpoint is down, retries webhook delivery, and supports replay; its webhooks include verification headers/secrets ([Resend receiving email, storage/retry/verification](https://resend.com/docs/dashboard/receiving/introduction#faq)). This makes Resend a reasonable first business-inquiry transport, but AE must still deduplicate `email_id`/`message_id` before waking a workflow (inference).
- Resend documents same-thread replies with `In-Reply-To` and `References` headers, using the received `message_id`; this enables a business to reply from an ordinary email client while AE keeps the inquiry in the plan/thread ([Resend reply-to emails](https://resend.com/docs/dashboard/receiving/reply-to-emails)).

### Postmark inbound email/reply loop

- Postmark accepts and parses emails sent to a server's unique inbound address or inbound forwarding domain, then POSTs a JSON document to the configured URL. The payload includes sender/recipient, `MailboxHash` (plus-addressing), `MessageID`, text/HTML bodies, stripped reply text, and attachments ([Postmark inbound webhook](https://postmarkapp.com/developer/webhooks/inbound-webhook#what-is-an-inbound-webhook), [Postmark inbound webhook data](https://postmarkapp.com/developer/webhooks/inbound-webhook#inbound-webhook-data)).
- Postmark retries an inbound webhook ten times with increasing intervals when it does not receive HTTP 200, stops retrying on 403, and allows failed inbound messages to be retried manually ([Postmark inbound webhook errors/retries](https://postmarkapp.com/developer/webhooks/inbound-webhook#errors-and-retries)). AE must treat retries as at-least-once delivery and use `MessageID`/a plan mailbox hash as a deduplication key (inference).
- The plus-address `MailboxHash` is a useful low-friction correlation mechanism: encode an opaque plan/inquiry token in the receiving address, never a user email or authority-bearing secret (inference from Postmark's documented plus-addressing fields).

### Twilio inbound SMS loop

- When an SMS arrives, Twilio sends a synchronous `application/x-www-form-urlencoded` HTTP request with a unique `MessageSid`, `From`, `To`, `Body`, and media fields; the endpoint responds with TwiML. Twilio warns that webhook parameters evolve and recommends the SDK signature-validation library rather than custom validation ([Twilio incoming message webhook](https://www.twilio.com/docs/messaging/guides/webhook-request)).
- Twilio is therefore suitable for user notification/reply or a business's SMS-capable number, but it is not a generic email replacement. The webhook must ACK quickly, validate the signature, persist/deduplicate by `MessageSid`, and then wake the plan asynchronously (inference from the synchronous request contract and parameter list).

### Channel conclusion

The transport pattern is the same across providers: **send a provider message containing an opaque correlation token; persist provider IDs and the outgoing effect before/around the send; receive a signed webhook; ACK immediately; deduplicate the inbound event; store the message; wake a typed workflow event; render the update in the plan/thread.** The provider's retry/storage behavior is useful delivery resilience, but none of the reviewed provider docs establishes exactly-once external sending, so AE must expose “sent/received/unknown/reconciled” states rather than claiming certainty (inference from [Resend](https://resend.com/docs/dashboard/receiving/introduction), [Postmark](https://postmarkapp.com/developer/webhooks/inbound-webhook), and [Twilio](https://www.twilio.com/docs/messaging/guides/webhook-request)).

## Resumable notification UX

- Convex React queries automatically subscribe to backend data and rerender when the underlying database changes; Convex promises a consistent view when multiple query results depend on the same database state ([Convex React reactivity/consistency](https://docs.convex.dev/client/react#reactivity)).
- Workflow status is itself queryable/reactive, and the Workflow component documents observation by many users simultaneously, including after page refresh; Agent threads/messages are persisted and live-updating ([Workflow component page](https://www.convex.dev/components/workflow), [Agent overview](https://docs.convex.dev/agents/overview)).
- **Recommended UX (inference):** treat the Convex plan/event timeline as the source of truth and push notifications as accelerators. Store append-only `planEvents` with a monotone sequence, `planStatus`/`waitingOn`/`deadlineAt`, and `notificationDeliveries` keyed by `(planId, effectId, channel)`. The route loads the latest snapshot plus events after a client cursor; reconnecting or opening the plan later reconstructs the same timeline even if an SSE connection, email, or SMS notification was missed. Use Agent messages for the conversational narrative, and store machine/audit metadata separately so model context does not become the only audit trail ([Convex React reactivity](https://docs.convex.dev/client/react#reactivity), [Convex Agent messages/human agents](https://docs.convex.dev/agents/human-agents)).
- **Notification state (inference):** distinguish `planned`, `waiting`, `contact_required`, `queued`, `sent`, `delivery_unknown`, `reply_received`, `approved`, `rejected`, `timed_out`, `failed`, and `completed`; make every transition an authorized Convex mutation. A provider webhook or UI callback may be retried, so the mutation first inserts/claims the provider event ID and only then calls `sendEvent` for the matching workflow ([Convex Workflow events](https://github.com/get-convex/workflow/blob/main/README.md#waiting-for-external-events), [Postmark retry behavior](https://postmarkapp.com/developer/webhooks/inbound-webhook#errors-and-retries)).
- An approval link or SMS command must not itself confer authority. The callback should authenticate the person with Clerk or a scoped one-time token, check plan ownership and current expected event, and only then write the decision/send the event (inference from AE's stated Clerk authority model and Convex's requirement that scheduled functions do not inherit caller auth ([Convex scheduled functions auth](https://docs.convex.dev/scheduling/scheduled-functions#auth))).

## Smallest durable-plan design Convex supports

This is the minimum design that covers an instant action, a human/business wait, a reminder/deadline, and a resumable UI without adding a queue service (inference from the Convex component APIs and AE's current stack):

1. **Install/register two components:** add `@convex-dev/agent` and `@convex-dev/workflow`; register them in `convex/convex.config.ts`. Do not add a direct Workpool instance until independent outbound/LLM concurrency needs it; Workflow already uses Workpool internally ([Convex Agent source README](https://github.com/get-convex/agent/blob/main/README.md), [Convex Workflow installation](https://github.com/get-convex/workflow/blob/main/README.md#installation), [Workflow source README](https://github.com/get-convex/workflow/blob/main/README.md#how-it-works)).
2. **Persist a thin `plans` row:** `planId`, owner/agent identity, `workflowId`, `engineVersion`, status, current `waitingOn` event ID (opaque), deadline, contact state, and terminal result/error. Add `planEvents` with unique `(planId, eventKey)` and `notificationDeliveries` with unique `(planId, effectId, channel)`. This application state is needed for ownership, callback correlation, contact capture, and a durable audit; the component's internal status is not a substitute (inference from component APIs and Workpool's one-day default status TTL ([Workpool status](https://github.com/get-convex/workpool/blob/main/README.md#reactive-status-of-asynchronous-work))).
3. **Start atomically:** a mutation authenticates the caller, creates the plan/event/outbox rows, and calls Workflow `start`. Keep the plan's user/authority identifiers as explicit workflow arguments because scheduled functions do not propagate auth ([Convex scheduled functions auth](https://docs.convex.dev/scheduling/scheduled-functions#auth)).
4. **Use a bounded deterministic loop:** each model turn is a named `step.runAction` that calls OpenRouter through the existing harness and returns a compact decision (`nextTool`, `askContact`, `awaitBusinessReply`, `proposeEffect`, `complete`). Each registered action is a separate step adapter. Persist large tool output/transcripts in Convex and pass IDs, not whole payloads ([Convex Agent workflows](https://docs.convex.dev/agents/workflows), [Workflow source README, usage](https://github.com/get-convex/workflow/blob/main/README.md#usage)). The model proposes; an authorized mutation/effect adapter validates identity, mandate, spend, idempotency key, evidence, and ledger state immediately before any commitment/payment/sensitive disclosure (inference from AE's stated safety kernel and the component's action/mutation boundaries).
5. **At the first async boundary, capture contact:** if the next step requires notifying the person, write a `contact_required` event and wait for a typed `contactProvided` event. Only after validation/consent does an action create the provider send request. If the inquiry can proceed through AE's business mailbox without contacting the person, do not collect a person contact merely to start the plan (inference implementing D5 while preserving instant-only paths).
6. **Send inquiry idempotently:** in a mutation, claim `effectId = planId + inquiryAttempt`; in an action, send via Resend/Postmark/Twilio with an opaque correlation address/token and record the provider message ID. Configure action retry only when the adapter has a dedupe/check-before-act strategy; otherwise mark `delivery_unknown` and reconcile by provider API/webhook rather than blindly retrying ([Workpool idempotency](https://github.com/get-convex/workpool/blob/main/README.md#idempotency), [Temporal activity idempotency](https://docs.temporal.io/activity-definition#idempotency)).
7. **Wait durably:** call `step.awaitEvent` with a typed dynamic event ID. Race/sequence it with a durable `step.sleep` or `runAt` deadline; on timeout write a reminder/escalation event or terminal `timed_out` result. The provider webhook route validates its signature, ACKs, inserts a dedupe row and inbound message, and invokes `sendEvent` only for the still-waiting plan ([Convex Workflow external events](https://github.com/get-convex/workflow/blob/main/README.md#waiting-for-external-events), [Resend webhook verification/storage](https://resend.com/docs/dashboard/receiving/introduction#faq), [Twilio webhook security warning](https://www.twilio.com/docs/messaging/guides/webhook-request)).
8. **Resume/notify:** write every received reply/decision to `planEvents` and Agent thread messages, then let a reactive status query drive the plan page. Send email/SMS notifications as outbox effects; on browser reconnect the query reconstructs state and does not depend on an unresumable SSE stream ([Convex React reactivity](https://docs.convex.dev/client/react#reactivity), [Convex Agent source README](https://github.com/get-convex/agent/blob/main/README.md)).
9. **Operate cleanup/recovery:** add a bounded cron for completed-workflow cleanup and stale `delivery_unknown` reconciliation. Use Workflow cancellation/restart for operator recovery; never silently restart an external effect without its stable key ([Workflow cleanup/restart](https://github.com/get-convex/workflow/blob/main/README.md#restart-a-failed-workflow), [Convex cron error handling](https://docs.convex.dev/scheduling/cron-jobs#error-handling)).

This design does **not** claim that arbitrary plans can run forever without maintenance. Step names/control flow must remain compatible, event and transcript payloads must stay bounded, provider credentials/webhooks must remain available, and model-loop iteration needs a hard budget/terminal policy (inference from Convex Workflow deterministic replay/name constraints and the payload guidance above).

## Implications for AE: D1–D6

| Decision under test | Verdict | Evidence and one-line implication |
| **D1. `/` becomes a model-driven agent engine and replaces predefined-route orchestration.** | **CONTRADICTS (unconstrained shape)** | Convex Agent + Workflow support dynamic routing, loops, ReAct, multi-agent flows, and pause/resume ([Convex Agent workflows](https://docs.convex.dev/agents/workflows)), but the Workflow contract contradicts an arbitrary model-produced graph: replay must be deterministic, step shape must stay stable, and one run has 1 MB step data / 8 MiB journal limits ([Workflow limitations](https://github.com/get-convex/workflow/blob/main/README.md#limitations), [custom step names](https://github.com/get-convex/workflow/blob/main/README.md#specifying-a-custom-name-for-a-step)). Keep model choice inside bounded registered step adapters rather than replacing orchestration wholesale. |
| **D2. Deterministic router demoted to safety kernel; model owns planning/action selection.** | **SUPPORTS** | Durable systems consistently separate deterministic orchestration from nondeterministic/external activities: Convex puts network/LLM work in actions ([Convex Agent workflows](https://docs.convex.dev/agents/workflows)); Temporal puts nondeterminism in Activities ([Temporal workflow definition](https://docs.temporal.io/workflow-definition)); Restate wraps it in durable `run` steps ([Restate actions](https://docs.restate.dev/foundations/actions)). Keep identity, mandate, spend, idempotency, effect commit, evidence, and recovery outside model choice. |
| **D3. Agent explores freely; person approves only effects.** | **REFINES** | Typed events/signals/awakeables are a strong fit for approval waits ([Convex Workflow external events](https://github.com/get-convex/workflow/blob/main/README.md#waiting-for-external-events), [Temporal approval guide](https://docs.temporal.io/guides/reliable-document-approvals), [Restate external events](https://docs.restate.dev/develop/ts/external-events)). Exploration still needs bounded reads, privacy filters, and per-effect authority checks; a reply/approval callback must be authenticated and tied to the current plan (inference). |
| **D4. Instant endpoints + async human-business inquiries in one plan; chase/notify is product.** | **SUPPORTS (conditional)** | Convex can sleep for days/months, pause indefinitely for an external event, and expose reactive status ([Workflow source README](https://github.com/get-convex/workflow/blob/main/README.md), [Convex component page](https://www.convex.dev/components/workflow)); Resend/Postmark/Twilio provide inbound webhook loops ([Resend receiving](https://resend.com/docs/dashboard/receiving/introduction), [Postmark inbound](https://postmarkapp.com/developer/webhooks/inbound-webhook), [Twilio incoming message webhook](https://www.twilio.com/docs/messaging/guides/webhook-request)). The product still needs provider adapters, webhook verification, dedupe, reminders, and an AE-owned inbox/outbox (inference). |
| **D5. Capture contact at first async effect, not up front.** | **REFINES** | Convex can make contact a typed event immediately before the first notification; provider replies can correlate to an opaque address/token ([Convex Workflow external events](https://github.com/get-convex/workflow/blob/main/README.md#waiting-for-external-events), [Postmark MailboxHash](https://postmarkapp.com/developer/webhooks/inbound-webhook#inbound-webhook-data)). Do not collect contact for instant-only paths; at the async boundary ask for validated consent, then make the plan wait if no channel is supplied (inference). |
| **D6. Act first, ask when blocked; strong defaults/minimal questions.** | **REFINES** | Durable event waits plus timers support asking only at a typed blocker and escalating after an SLA ([Convex Workflow external events](https://github.com/get-convex/workflow/blob/main/README.md#waiting-for-external-events), [Temporal approval guide](https://docs.temporal.io/guides/reliable-document-approvals), [Inngest waitForEvent](https://www.inngest.com/docs/reference/typescript/v4/functions/step-wait-for-event)). The blocker must have a deadline, expected response schema, and safe default/terminal state; free-form “grilling” cannot be the recovery mechanism (inference). |

## Build on Convex components vs adopt new infrastructure

| Option | What it buys | Cost/fit for current AE |
|---|---|---|
| **Convex Agent + Workflow (recommended now)** | Persisted thread context, model/tool calls, durable sleeps/events, reactive status, cancellation/restart, and existing Convex auth/data/ledger boundaries ([Agent docs](https://docs.convex.dev/agents/overview), [Workflow source](https://github.com/get-convex/workflow/blob/main/README.md)). | Requires adding/configuring components and writing the plan/outbox/webhook tables. Lacks a documented built-in Workflow code-versioning strategy and does not make third-party sends exactly once ([Workflow custom names](https://github.com/get-convex/workflow/blob/main/README.md#specifying-a-custom-name-for-a-step), [Workpool idempotency](https://github.com/get-convex/workpool/blob/main/README.md#idempotency)). This is the smallest change that preserves AE's source of truth. |
| **Temporal** | Mature Event History, Signals/Updates, durable timers, task queues, Activity retry/idempotency guidance, Worker Versioning/Patching, Continue-As-New ([Temporal Workflow Execution](https://docs.temporal.io/workflow-execution), [Temporal versioning](https://docs.temporal.io/develop/go/versioning)). | Requires Temporal Server/Cloud and Worker processes, plus a second durable execution/state model; overkill before AE has demonstrated plan volume or multi-service orchestration need ([Temporal workers](https://docs.temporal.io/workers), [Temporal approval prerequisites](https://docs.temporal.io/guides/reliable-document-approvals#prerequisites)). |
| **Restate** | Journaled steps, durable signals/awakeables, idempotency keys, immutable deployment pinning, FaaS suspension ([Restate external events](https://docs.restate.dev/develop/ts/external-events), [Restate versioning](https://docs.restate.dev/services/versioning)). | Requires Restate Server/Cloud and another journal/state authority; its own docs warn to avoid multi-day handlers or retain old deployments until they drain ([Restate key concepts](https://docs.restate.dev/foundations/key-concepts), [Restate versioning](https://docs.restate.dev/services/versioning)). |
| **Inngest** | Managed step memoization, waitForEvent/sleep, flow control, stable step-ID evolution, serverless-friendly execution ([Inngest execution](https://www.inngest.com/docs/learn/how-functions-are-executed), [Inngest versioning](https://www.inngest.com/docs/learn/versioning)). | Adds a separate managed execution/state dependency and its event model; useful if Convex Workflow's replay/name compatibility or throughput becomes limiting, not necessary for first implementation. |
| **Trigger.dev** | Task handles, checkpoint/resume, waits, scoped human waitpoint tokens, retries/idempotency ([Trigger.dev how it works](https://trigger.dev/docs/how-it-works), [Trigger.dev wait tokens](https://trigger.dev/docs/wait-for-token)). | Adds task queue/scheduler/worker infrastructure or hosted dependency; process snapshots are not needed when Convex can persist plan state and wait on events. |

**Adoption trigger:** reconsider a new engine only after evidence of a concrete Convex boundary—e.g. sustained workflow throughput/parallelism pressure, plans whose event/transcript history exceeds practical Convex limits, a requirement for first-class workflow-code version pinning/patching, or a need to orchestrate many non-Convex services with independent worker fleets (inference from the documented trade-offs and limits above). Do not adopt one merely because it has a nicer human-approval token; Convex's `createEvent`/`awaitEvent` plus a signed AE route supplies the same minimal primitive ([Convex Workflow external events](https://github.com/get-convex/workflow/blob/main/README.md#waiting-for-external-events)).

## Skip list: patterns that do not transfer directly

- **Temporal Task Queues/Workers as AE's human inbox — skip.** Temporal Task Queues route work to polling Workers; human approval still arrives as a Signal/Update. AE needs an application-owned business/person inbox backed by Convex, not a worker fleet ([Temporal task queues](https://docs.temporal.io/task-queue), [Temporal message passing](https://docs.temporal.io/sending-messages)).
- **Temporal Event History/Continue-As-New assumptions — skip as an implementation recipe.** They are Temporal's persistence/replay model; Convex Workflow has its own step history, bandwidth constraints, and function-name compatibility warning. Borrow the bounded-history principle, not the storage/API shape ([Temporal approval event history](https://docs.temporal.io/guides/reliable-document-approvals), [Convex Workflow usage](https://github.com/get-convex/workflow/blob/main/README.md#usage)).
- **Restate journal and server — skip for now.** Restate's durable `run`/awakeable semantics require the Restate Server/Cloud path; implement the smaller equivalent with Convex Workflow steps/events and keep Convex as the sole state authority ([Restate key concepts](https://docs.restate.dev/foundations/key-concepts), [Restate external events](https://docs.restate.dev/develop/ts/external-events)).
- **Inngest's “reorder is a warning” evolution contract — skip as a Convex guarantee.** Inngest memoizes stable step IDs; Convex Workflow replays deterministic history and warns that a renamed step function can fail after a long wait. Preserve names/control flow and version AE plan rows explicitly ([Inngest versioning](https://www.inngest.com/docs/learn/versioning), [Convex Workflow custom names](https://github.com/get-convex/workflow/blob/main/README.md#specifying-a-custom-name-for-a-step)).
- **Trigger.dev CRIU snapshots/public waitpoint implementation — skip.** Convex does not snapshot arbitrary process memory; use serializable plan state, dynamic workflow event IDs, and an authenticated AE callback. Borrow the scoped-token UX, not its runtime internals ([Trigger.dev how it works](https://trigger.dev/docs/how-it-works), [Trigger.dev waitpoint tokens](https://trigger.dev/docs/wait-for-token)).
- **Cron-per-plan polling loops — skip.** Convex already has indefinite event waits and durable sleeps; crons are recurring jobs that can skip an overlapping run. Use crons for bounded cleanup/reconciliation only ([Convex Workflow external events](https://github.com/get-convex/workflow/blob/main/README.md#waiting-for-external-events), [Convex cron error handling](https://docs.convex.dev/scheduling/cron-jobs#error-handling)).
- **“Exactly-once email/SMS/payment” claims — skip.** Convex guarantees do not extend through an external provider; Workpool and Temporal both document the need for idempotency because actions/Activities can run more than once ([Workpool idempotency](https://github.com/get-convex/workpool/blob/main/README.md#idempotency), [Temporal Activity idempotency](https://docs.temporal.io/activity-definition#idempotency)).
- **LLM calls directly in the durable handler — skip.** Convex Workflow handlers must be deterministic; put OpenRouter/LLM and network calls in named action steps, pass IDs/compact outputs, and let the safety kernel validate the resulting proposed effect ([Convex Workflow usage](https://github.com/get-convex/workflow/blob/main/README.md#usage), [Convex Agent workflows](https://docs.convex.dev/agents/workflows)).
- **Provider webhook as the source of truth — skip.** Resend, Postmark, and Twilio deliver different payloads/retry semantics; provider events are inputs to a signed, deduplicated Convex mutation. The plan timeline and authority decision remain in Convex ([Resend inbound](https://resend.com/docs/dashboard/receiving/introduction), [Postmark inbound](https://postmarkapp.com/developer/webhooks/inbound-webhook), [Twilio incoming message webhook](https://www.twilio.com/docs/messaging/guides/webhook-request)).
