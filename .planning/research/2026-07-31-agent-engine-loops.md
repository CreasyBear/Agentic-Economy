# Production agent loops: evidence against a single settled shape

Date: 2026-07-31  
Scope: first-party production guidance, official documentation, and source repositories for Anthropic, OpenAI, LangGraph/LangChain, Hugging Face `smolagents`, Microsoft AutoGen, and CrewAI. The question is not whether model-driven loops are possible. It is where their builders deliberately retain deterministic orchestration, and what that means for AE's proposed `/` agent engine.

Current AE context used for the mapping (from the project brief): TanStack Start + Convex are the source of truth; the registered action registry is the tool surface; answer threads/SSE are the conversation spine; OpenRouter supplies LLMs; Clerk keys/OAuth device flow provide agent authority; T12 is the credit ledger; there is no Temporal or queue infrastructure today.

## Executive findings

1. **The strongest disconfirming evidence is explicit.** Anthropic says to find the simplest solution, and that workflows are preferable for well-defined tasks because they provide predictability and consistency; Hugging Face says deterministic workflows should be used when they fit and advises “regularize towards not using any agentic behaviour”; OpenAI says code orchestration is more deterministic and predictable for speed, cost, and performance. A blanket replacement of classification→route with a model loop is therefore not supported. Sources: [Anthropic, “Building effective agents”](https://www.anthropic.com/engineering/building-effective-agents), [smolagents, “What are agents?”](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents), [OpenAI Agents SDK, “Agent orchestration”](https://openai.github.io/openai-agents-python/multi_agent/).

2. **Where a loop is justified, the common shape is a bounded feedback cycle, not unconstrained autonomy.** The model observes the current state, chooses a tool or handoff from a registered surface, receives an environment result, and repeats until a typed/final result or explicit stop condition. Max turns, budgets, recursion/message limits, timeouts, termination words, retries, permissions, hooks, and guardrails are intentional control points. Sources: [Claude Agent SDK loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [OpenAI Runner loop](https://openai.github.io/openai-agents-python/running_agents/), [LangGraph workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents), [smolagents introduction](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents), [AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html), [CrewAI agents](https://docs.crewai.com/v1.15.9/en/concepts/agents).

3. **Planner/executor separation is a useful optimization, not a universal replacement for ReAct.** LangGraph's official plan-and-execute example explicitly contrasts a planner plus executor/replanner against ReAct: stronger models can plan while smaller models execute, but the example is sequential and says a DAG is needed for embarrassingly parallel work. LangGraph's current workflow guide presents both explicit orchestrator/worker graphs and a continuous tool loop. Sources: [LangGraph plan-and-execute notebook (pinned first-party source)](https://raw.githubusercontent.com/langchain-ai/langgraph/23961cff61a42b52525f3b20b4094d8d2fba1744/docs/docs/tutorials/plan-and-execute/plan-and-execute.ipynb), [LangGraph workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents).

4. **The deterministic “kernel” is larger than identity and spend.** Production SDKs retain permission evaluation, hooks, typed schemas, approval pauses, tool execution ordering/concurrency, handoff destination registration, output validation, max-turn/budget enforcement, persistence, and termination logic outside the model. OpenAI explicitly says high-impact or approval-sensitive tools are usually better kept as direct calls so a person can review each action. Sources: [Claude Agent SDK loop and permissions](https://code.claude.com/docs/en/agent-sdk/agent-loop), [Claude Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions), [OpenAI guardrails](https://openai.github.io/openai-agents-python/guardrails/), [OpenAI tools](https://openai.github.io/openai-agents-python/tools/), [OpenAI handoffs](https://openai.github.io/openai-agents-python/handoffs/).

5. **Large tool surfaces require retrieval/namespace selection, not dumping every action into context.** Claude's Tool Search documentation reports that 50 tool definitions can consume 10–20K tokens and that selection accuracy degrades beyond roughly 30–50 tools; it defers definitions, searches by names/descriptions, and loads a small relevant set. OpenAI's hosted Tool Search defers tools/namespaces and recommends small namespaces (ideally fewer than 10 functions). Sources: [Claude Agent SDK Tool Search](https://code.claude.com/docs/en/agent-sdk/tool-search), [OpenAI Tools — hosted tool search](https://openai.github.io/openai-agents-python/tools/).

6. **Long loops need explicit memory/context policy.** Claude accumulates history and tool I/O, automatically compacts near the context limit, and supports session resume/fork plus persisted session storage. OpenAI Sessions persist items and expose pruning/limits and compaction. LangGraph splits thread-scoped checkpoints from cross-thread stores. AutoGen retains team context; CrewAI can summarize to respect context windows. These are not free: old context increases latency/cost, compaction can lose early instructions, and retained state requires storage/retention policy. Sources: [Claude loop context and sessions](https://code.claude.com/docs/en/agent-sdk/agent-loop), [OpenAI Sessions](https://openai.github.io/openai-agents-python/sessions/), [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html), [CrewAI agents](https://docs.crewai.com/v1.15.9/en/concepts/agents).

7. **Cost/latency controls are first-class loop design.** Anthropic recommends routing easy/common cases to a smaller model and hard cases to a stronger model, plus parallelization when independent work permits it. Claude exposes budgets, effort levels, prompt caching, compaction, tool search, and fresh-context subagents. OpenAI exposes cheap blocking guardrails, tool search, programmatic tool calling (batch loops/branches/parallel work without a model round trip after every call), usage telemetry, and model choice. CrewAI exposes a separate function-calling LLM, cache, max RPM, retries, and execution limits. Sources: [Anthropic essay](https://www.anthropic.com/engineering/building-effective-agents), [Claude Agent SDK loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [OpenAI guardrails](https://openai.github.io/openai-agents-python/guardrails/), [OpenAI tools](https://openai.github.io/openai-agents-python/tools/), [OpenAI usage](https://openai.github.io/openai-agents-python/usage/), [CrewAI agents](https://docs.crewai.com/v1.15.9/en/concepts/agents).

8. **Evaluation is trace-and-outcome based, not merely “the model produced text.”** Anthropic recommends extensive sandbox testing for autonomous agents, workbench testing of tool use, and systematic evaluation before adding complexity. OpenAI provides per-run/per-turn tracing, guardrail/tool/handoff spans, and eval integration. LangGraph points builders to LangSmith traces for debugging, testing, and monitoring. AutoGen and CrewAI expose practical termination, verbose/callback, and usage-metric instrumentation, but the reviewed pages do not establish a universal eval methodology. Sources: [Anthropic essay](https://www.anthropic.com/engineering/building-effective-agents), [Claude loop hooks/results](https://code.claude.com/docs/en/agent-sdk/agent-loop), [OpenAI tracing](https://openai.github.io/openai-agents-python/tracing/), [OpenAI evals](https://developers.openai.com/api/docs/guides/evals), [LangGraph workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents), [AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html), [CrewAI agents](https://docs.crewai.com/v1.15.9/en/concepts/agents).

## Findings by primary source

### 1. Anthropic — “Building effective agents” (published 2024-12-19)

**Workflow/agent boundary and the anti-loop case.** Anthropic distinguishes workflows (LLMs/tools orchestrated through predefined code paths) from agents (LLMs dynamically directing process/tool usage). It recommends the simplest solution and says agentic systems trade latency and cost for task performance. Workflows provide predictability and consistency for well-defined tasks; agents fit flexibility and model-driven decisions at scale. This is direct evidence against making every `/` request a model loop. Source: [Anthropic, “Building effective agents”](https://www.anthropic.com/engineering/building-effective-agents).

**Patterns, from fixed to dynamic.** The essay describes prompt chaining with programmatic gates, routing, parallelization (sectioning or voting), orchestrator-workers (dynamic decomposition), evaluator-optimizer loops, and autonomous agents. The choice is made by task structure and measurable need, not by a preference for autonomy. Source: [Anthropic, “Building effective agents”](https://www.anthropic.com/engineering/building-effective-agents).

**Agent loop anatomy.** An agent starts from a command/discussion, plans and operates independently, obtains “ground truth” from tool/environment results at each step, may pause for human feedback at checkpoints/blockers, and stops on completion or a maximum iteration condition. Anthropic calls out higher costs and compounding errors, requiring sandbox testing and guardrails. Source: [Anthropic, “Building effective agents”](https://www.anthropic.com/engineering/building-effective-agents).

**Tools are part of the control plane.** Anthropic recommends clear, well-documented tools with examples, edge cases, boundaries, and error-resistant arguments. It reports spending more time optimizing tools than the overall prompt, and says requiring absolute file paths removed a recurring model error. Source: [Anthropic, “Building effective agents,” Appendix 2](https://www.anthropic.com/engineering/building-effective-agents).

**Cost/model tiering/evals.** Routing can send easy/common queries to a smaller model and hard/unusual queries to a stronger model. Parallel calls can improve speed or confidence. The essay recommends comprehensive evaluation, sandboxed testing, and testing tool use in Workbench before production. Sources: [Anthropic, “Building effective agents”](https://www.anthropic.com/engineering/building-effective-agents), [Anthropic Workbench/tool-use guidance in Appendix 2](https://www.anthropic.com/engineering/building-effective-agents).

### 2. Anthropic — Claude Agent SDK documentation and source

**Single ReAct-style cycle.** The official loop is: prompt + system/tools/history → Claude evaluates and emits text and/or tool calls → SDK executes calls → results return to Claude → repeat until no tool calls → final result with text, cost, usage, and session ID. Read-only tools can run concurrently; state-changing tools run sequentially; hooks can block or modify calls. Sources: [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop).

**Deterministic boundaries.** `max_turns` and `max_budget_usd` stop runaway loops; production guidance recommends a budget by default for open-ended work. Permission modes, allow/deny rules, hooks, `plan` mode, and approval callbacks decide what executes. A `PreToolUse` hook can validate or block a call; `PostToolUse` can audit or inject context. Sources: [Claude Agent SDK loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [Claude permissions](https://code.claude.com/docs/en/agent-sdk/permissions), [Claude hooks](https://code.claude.com/docs/en/agent-sdk/hooks).

**Human interaction and durable interruption.** The SDK can pause at `canUseTool` approval or `AskUserQuestion` clarification. A callback may remain pending; defer/resume hooks are documented for work that outlives the process. This supports asynchronous human boundaries, but it does not prove an asynchronous business-inquiry queue/product. Source: [Claude user input](https://code.claude.com/docs/en/agent-sdk/user-input).

**Context/memory.** History, tool definitions, inputs, and outputs accumulate. Tool Search defers large MCP surfaces; automatic compaction summarizes older history and can lose early instructions; persistent rules should live in project memory such as `CLAUDE.md`. Sessions can resume or fork with full context, and a session-store adapter is needed to resume across stateless hosts. Sources: [Claude Agent SDK loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [Claude Tool Search](https://code.claude.com/docs/en/agent-sdk/tool-search), [Claude sessions/overview](https://code.claude.com/docs/en/agent-sdk/sessions), [Claude session storage](https://code.claude.com/docs/en/agent-sdk/session-storage).

**Cost/eval observability.** Effort controls reasoning tokens and latency; lower effort is recommended for routine work. Prompt caching reduces repeated-prefix cost. Results include turn count, usage, and estimated cost; hooks and result subtypes expose failure/limit paths. Source: [Claude Agent SDK loop](https://code.claude.com/docs/en/agent-sdk/agent-loop).

**SDK/source-level shape selection.** The Python SDK source distinguishes `query()` (one-shot/batch/CI, stateless) from `ClaudeSDKClient` (bidirectional, stateful, streaming, interruption, long-running sessions). That is an explicit “choose the simpler path for known inputs” decision, not a requirement that all calls enter a durable loop. Sources: [Claude Agent SDK Python `query.py`](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/query.py), [Claude Agent SDK Python `client.py`](https://github.com/anthropics/claude-agent-sdk-python/blob/main/src/claude_agent_sdk/client.py).

### 3. OpenAI Agents SDK

**Runner loop.** The runner calls the current agent; a typed final output with no tool calls terminates; a handoff swaps current agent/input; otherwise tools run, results append, and the loop repeats; `max_turns` raises on exhaustion. Source: [OpenAI “Running agents”](https://openai.github.io/openai-agents-python/running_agents/).

**Model orchestration and code orchestration are deliberately co-equal.** OpenAI documents two options: let an LLM plan/reason/select steps, or orchestrate via code. It says code is more deterministic and predictable in speed, cost, and performance, and gives structured-output classification→code routing, fixed chains, evaluator loops, and parallel calls as standard patterns. This directly contradicts a blanket “router demotion” rule. Source: [OpenAI “Agent orchestration”](https://openai.github.io/openai-agents-python/multi_agent/).

**Handoffs versus agents-as-tools.** Handoffs appear to the LLM as `transfer_to_*` tools; register one per destination and let the model choose among those registered destinations. Agents-as-tools let a manager retain control of the user-facing conversation. Handoff `input_type` is model-generated metadata, not application state and not a dynamic destination selector. Input filters can change what history the receiving agent sees. Source: [OpenAI “Handoffs”](https://openai.github.io/openai-agents-python/handoffs/).

**Guardrails and effect boundaries.** Input guardrails can run in parallel for latency or block before the expensive agent starts to avoid tokens and side effects. Output guardrails check final output; tool guardrails run around each custom function call. Tripwires halt execution. OpenAI specifically says approval-sensitive/high-impact tools are usually better as direct calls so a person can review each action, rather than burying them in a generated program. Sources: [OpenAI “Guardrails”](https://openai.github.io/openai-agents-python/guardrails/), [OpenAI “Tools”](https://openai.github.io/openai-agents-python/tools/), [OpenAI human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/).

**Large tool sets and model round trips.** Hosted Tool Search defers large function/namespace/MCP surfaces and loads only the subset needed. OpenAI recommends namespaces over many individually deferred functions and says namespaces should ideally contain fewer than 10 functions. Programmatic Tool Calling lets the model write a bounded JavaScript program to call eligible tools, loop/branch/parallelize, and aggregate without a model round trip after every call. Sources: [OpenAI “Tools — hosted tool search and programmatic tool calling”](https://openai.github.io/openai-agents-python/tools/).

**Memory, interruption, and evals.** Sessions persist conversation items across runs and allow limits/custom pruning; compaction sessions reduce long-history pressure. RunState serializes an interruption and resumes after approval. Tracing emits runner/turn/agent/generation/tool/guardrail/handoff spans, which feed debugging, monitoring, and evaluation. Sources: [OpenAI Sessions](https://openai.github.io/openai-agents-python/sessions/), [OpenAI running agents](https://openai.github.io/openai-agents-python/running_agents/), [OpenAI tracing](https://openai.github.io/openai-agents-python/tracing/), [OpenAI evals](https://developers.openai.com/api/docs/guides/evals).

### 4. LangGraph/LangChain

**The workflow/agent distinction is explicit.** LangGraph defines workflows as predetermined code paths and agents as dynamic systems that define their own process/tool use. Its current guide provides prompt chains, routers, parallelization, orchestrator-workers, evaluator-optimizers, and a continuous agent loop, rather than endorsing one universal topology. Source: [LangGraph “Workflows and agents”](https://docs.langchain.com/oss/python/langgraph/workflows-agents).

**Plan-and-execute versus ReAct.** LangGraph's first-party plan-and-execute notebook stores `input`, `plan`, `past_steps`, and `response`; a planner creates a multi-step plan, a ReAct executor executes one step, and a replanner updates or ends. It states two advantages over thinking one step at a time (ReAct): explicit long-term planning and using a stronger model only for planning while a smaller model executes. It also states a limitation: sequential tasks add latency; a DAG is needed for embarrassingly parallel operations. Source: [LangGraph plan-and-execute notebook, pinned commit](https://raw.githubusercontent.com/langchain-ai/langgraph/23961cff61a42b52525f3b20b4094d8d2fba1744/docs/docs/tutorials/plan-and-execute/plan-and-execute.ipynb).

**State machines retain determinism.** The documented Graph API uses `StateGraph`, named nodes, explicit edges, conditional edges, and `END`; the ReAct loop is just `llm_call → tool_node → llm_call`, with a deterministic `should_continue` that ends if no tool calls exist. `ToolNode` handles parallel tool execution, error handling, and state injection. Source: [LangGraph agents implementation](https://docs.langchain.com/oss/python/langgraph/workflows-agents).

**Persistence and recovery.** Checkpointers persist thread-scoped graph state for conversation continuity, human-in-the-loop, time travel, and fault tolerance; stores persist cross-thread preferences/facts/shared knowledge. Production persistence needs a durable backend and retention policy; in-memory saver state is lost at restart and checkpoints can grow unbounded. Source: [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence).

**Tracing/evaluation.** The workflow guide recommends tracing and comparing patterns with LangSmith for debugging and monitoring; the plan-and-execute notebook says LangSmith traces help debug, test, and monitor LangGraph applications. Sources: [LangGraph workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents), [LangGraph plan-and-execute notebook](https://raw.githubusercontent.com/langchain-ai/langgraph/23961cff61a42b52525f3b20b4094d8d2fba1744/docs/docs/tutorials/plan-and-execute/plan-and-execute.ipynb).

### 5. Hugging Face `smolagents`

**Explicit anti-agent guidance.** Hugging Face defines agency as how much LLM output controls program flow, from a router, to tool selection, to iteration and multi-agent spawning. Its guidance says if a predetermined workflow fits, code it for reliability and no LLM error risk; it advises “regularize towards not using any agentic behaviour.” This is direct contradiction of automatic model-loop replacement. Sources: [smolagents “What are agents?”](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents), [smolagents “Building good agents”](https://huggingface.co/docs/smolagents/tutorials/building_good_agents).

**Loop anatomy and single-loop variants.** The conceptual guide gives the minimal loop: `memory = [task]`; while the model says continue, get the next action, execute it, and append action/observation. The library supports both `CodeAgent` (LLM writes code containing calls, loops, conditionals) and `ToolCallingAgent` (JSON/text tool calls). Code agents improve composability but require sandboxed execution. Sources: [smolagents introduction](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents), [smolagents overview](https://huggingface.co/docs/smolagents/).

**Deterministic simplification and cost.** The “Building good agents” guide says reduce LLM calls, group tools where possible, and make logic deterministic rather than agentic; doing so reduces cost, latency, and error risk. It recommends clearer tool schemas, explicit error details, logging, retry mechanisms, and using a stronger model before changing prompt templates when debugging. Source: [smolagents “Building good agents”](https://huggingface.co/docs/smolagents/tutorials/building_good_agents).

**Context/debugging.** Memory is the explicit bridge from one iteration's observation to the next. Tool logs and execution traces expose step timing and token counts, supporting debugging, but the reviewed pages do not establish a general benchmark/eval protocol. Sources: [smolagents introduction](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents), [smolagents “Building good agents”](https://huggingface.co/docs/smolagents/tutorials/building_good_agents).

### 6. Microsoft AutoGen (brief)

**Model-selected loop.** `SelectorGroupChat` uses a model and shared context to choose the next speaker, broadcasts the response, checks termination, and repeats. A custom selection function can override model selection, and a candidate function can narrow the candidate set. This is a model router bounded by registered participants and deterministic configuration. Source: [AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html).

**Planner/worker shape and termination.** The official example uses a planning agent, web-search agent, and data-analyst agent. It ends on a planner-emitted `TERMINATE` or a 25-message maximum. The docs warn that selector prompts should not be overloaded; if many per-agent conditions are needed, use a custom selection function or split into sequential tasks. Source: [AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html).

**Single-agent tool loop.** AutoGen's quickstart shows an assistant emitting a function call, receiving the function result, and responding; `reflect_on_tool_use` adds a reflection step when tool output needs conversion to natural language. Source: [AutoGen quickstart](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/quickstart.html).

### 7. CrewAI (brief)

**Two orchestration modes.** CrewAI documents sequential processes (predefined task order; prior output becomes context) and hierarchical processes (a manager LLM/agent plans, delegates, reviews, and assesses completion). Its Flow abstraction is event-driven with explicit `@start`, `@listen`, state, branching, loops, and conditional control. Sources: [CrewAI processes](https://docs.crewai.com/v1.15.9/en/concepts/processes.md), [CrewAI flows](https://docs.crewai.com/v1.15.9/en/concepts/flows.md).

**Loop controls and model tiering.** CrewAI agents expose `max_iter` (default 20), max RPM, max execution time, retry limit, tool cache, context-window summarization, and optional reasoning attempts. A separate `function_calling_llm` can be cheaper than the main LLM for tool calls. Source: [CrewAI agents](https://docs.crewai.com/v1.15.9/en/concepts/agents.md).

**Usage/evaluation instrumentation.** CrewAI exposes verbose/step callbacks and Flow-wide usage metrics aggregating tokens across all nested crews, tools, and direct calls. The reviewed docs establish instrumentation and limits, not a universal task-quality evaluator. Source: [CrewAI agents](https://docs.crewai.com/v1.15.9/en/concepts/agents.md), [CrewAI flows](https://docs.crewai.com/v1.15.9/en/concepts/flows.md).

## Cost, context, and eval checklist for AE

### Cost/latency controls to borrow

- Route by task difficulty rather than using one expensive model for every turn; Anthropic explicitly recommends smaller models for easy/common routes. [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- Keep `max_turns`, a credit/spend budget, and a per-effect timeout at the engine boundary; Claude and AutoGen show why loop caps are normal production controls. [Claude](https://code.claude.com/docs/en/agent-sdk/agent-loop), [AutoGen](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html)
- Defer large registered-action schemas via an AE-native catalog/search surface; do not preload every action into every model turn. [Claude Tool Search](https://code.claude.com/docs/en/agent-sdk/tool-search), [OpenAI Tool Search](https://openai.github.io/openai-agents-python/tools/)
- Batch or parallelize independent reads/searches; serialize conflicting writes/effects. [Claude](https://code.claude.com/docs/en/agent-sdk/agent-loop), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- Use prompt caching for stable prefixes and compact/summarize old context; retain a durable task summary with IDs, approvals, and pending effects, not only raw transcript. [Claude](https://code.claude.com/docs/en/agent-sdk/agent-loop), [OpenAI Sessions](https://openai.github.io/openai-agents-python/sessions/)
- Prefer deterministic multi-action/programmatic execution for bounded read-only batches; keep approval-sensitive tools as direct calls. [OpenAI Tools](https://openai.github.io/openai-agents-python/tools/)

### Evaluation/testing pattern to borrow

1. **Trace every loop transition:** request, model decision, candidate action(s), tool args, authority decision, effect result, retries, waits, human approval, resume, and termination. OpenAI tracing and LangSmith tracing establish the production precedent. Sources: [OpenAI tracing](https://openai.github.io/openai-agents-python/tracing/), [LangGraph workflows](https://docs.langchain.com/oss/python/langgraph/workflows-agents).
2. **Build task fixtures with ground truth and effect assertions:** not only final prose; check correct route/action, no unauthorized effect, idempotency, spend ledger, and recovery after interruption. OpenAI's evals guidance explicitly uses test inputs plus labeled ground truth and graders; Anthropic emphasizes measurable outcomes and tool testing. Sources: [OpenAI evals](https://developers.openai.com/api/docs/guides/evals), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents).
3. **Exercise adversarial boundaries in a sandbox:** malformed tool args, denied tools, repeated calls, low budget, max-turn exhaustion, stale async response, sensitive disclosure, and user approval/rejection. Anthropic recommends sandbox testing; Claude/OpenAI expose hooks/guardrails/tripwires and typed error subtypes. Sources: [Anthropic](https://www.anthropic.com/engineering/building-effective-agents), [Claude hooks/results](https://code.claude.com/docs/en/agent-sdk/agent-loop), [OpenAI guardrails](https://openai.github.io/openai-agents-python/guardrails/).
4. **Measure cost and latency as first-class outcomes:** tokens/turns, tool-search overhead, cache hits, time-to-first-answer, time-to-effect, and abandoned/waiting runs. Sources: [Claude loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [OpenAI usage](https://openai.github.io/openai-agents-python/usage/), [CrewAI flows](https://docs.crewai.com/v1.15.9/en/concepts/flows.md).
5. **Compare loop topologies, not just prompts:** fixed route, single ReAct, planner/executor, and hybrid should run against the same fixtures. LangGraph's docs explicitly encourage tracing/comparing workflow patterns. Source: [LangGraph workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents).

## Implications for AE

The labels below are deliberately skeptical. “Supports” means the source directly supplies a pattern; “contradicts” means the source recommends a competing pattern or boundary; “refines” means the source narrows the proposed decision rather than deciding it.

| Decision | Evidence-backed implication | Verdict |
|---|---|---|
| **D1. `/` becomes a model-driven engine loop replacing classification→predefined-route orchestration.** | Anthropic, OpenAI, LangGraph, and smolagents all document model loops for open-ended/unpredictable work. **But** Anthropic says workflows are better for well-defined tasks, smolagents says code deterministic workflows when they fit, and OpenAI calls code orchestration more deterministic/predictable while giving classification→code routing as a normal pattern. Keep a task-shape gate: fixed route/structured call first; enter the loop only when uncertainty or step count warrants it. | **SUPPORTS** loops for open-ended work; **CONTRADICTS** blanket replacement; **REFINES** to a hybrid engine. |
| **D2. Deterministic router demoted to safety kernel; model owns planning/action selection.** | Model selection of registered tools/handoffs is real, but deterministic code still owns the action catalog, tool-search boundary, schema validation, permissions, guardrails/hooks, approvals, destination enablement, concurrency ordering, max turns/budget, state persistence, and stop conditions. OpenAI explicitly retains code orchestration as a co-equal option. AE's router should become a **policy-and-candidate kernel**, not disappear or become “safety only.” | **SUPPORTS** model planning within a bounded surface; **CONTRADICTS** demoting all routing; **REFINES** router into policy + candidate selection + deterministic workflow fallback. |
| **D3. Agent explores freely; person approves only effects (commitments, payments, sensitive disclosure).** | Claude permissions/hooks and OpenAI tool guardrails/HITL support free exploration with pre-effect gates. OpenAI says approval-sensitive/high-impact tools should remain direct, reviewable calls; guardrails can block before tokens/tools execute. Not every “read” is harmless (sensitive retrieval/disclosure can itself be an effect), and input/output guardrail scope is not automatically every handoff. | **SUPPORTS** exploration/effect-gate split; **REFINES** effect taxonomy to include sensitive reads/disclosures and per-tool checks. |
| **D4. Hybrid supply: instant endpoints + async human-business inquiries in one plan; async chase/notify is the product.** | SDKs prove sessions, interruption, approval pauses, durable state, and resume are useful. They do **not** prove a human-business inquiry protocol, outbound chasing, notification guarantees, or queue semantics. Most reviewed examples are synchronous runner/graph executions; AE has no Temporal/queue infrastructure. Start with a persisted pending-effect/answer-thread state machine and explicit resume/notification contract rather than claiming the loop itself creates async product behavior. | **REFINES** durable pause/resume requirements; **UNRESOLVED** for async human-business supply; **CONTRADICTS** any assumption that a synchronous agent SDK supplies D4. |
| **D5. Contact captured at first async effect, not up front.** | The sources discuss approval and session context, not contact-capture timing. They support collecting only what is needed at a boundary and deferring irreversible/sensitive actions until approval, but there is no evidence that “first async effect” is the right contact moment. Contact timing remains an AE product experiment; make the contact requirement an explicit typed blocker/effect and test conversion/abandonment rather than hiding it in model reasoning. | **REFINES** via explicit boundary/state modeling; **UNRESOLVED** on timing; do not claim literature support. |
| **D6. Act-first, ask-when-blocked grilling (strong defaults, minimal questions).** | Anthropic says agents can operate independently and return for information/judgment at checkpoints/blockers; Claude supports `AskUserQuestion` and permission callbacks; OpenAI supports approval interruptions and durable resume. This supports minimal questions after exploration, but deterministic permissions can require approval before an effect and loops need caps/termination. “Ask only when blocked” must not bypass authority or sensitive-disclosure gates. | **SUPPORTS** act-first/blocker questions; **REFINES** with mandatory policy gates, max turns/budget, and explicit approval/resume states. |

### Proposed AE boundary (evidence-constrained)

Use `/` as a **hybrid dispatcher**:

1. Classify only enough to choose the cheapest safe mode: direct answer, deterministic registered workflow, or bounded agent loop. This preserves OpenAI's code-orchestration option and Anthropic/smolagents' simplicity rule. Sources: [OpenAI orchestration](https://openai.github.io/openai-agents-python/multi_agent/), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents), [smolagents](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents).
2. In loop mode, let the model plan/search/compare and choose among a small, searchable projection of registered actions. Keep identity, authority, spend, idempotency, effect typing, approvals, evidence, retries/timeouts, concurrency, persistence, and stop conditions in deterministic Convex/kernel code. Sources: [Claude loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [Claude Tool Search](https://code.claude.com/docs/en/agent-sdk/tool-search), [OpenAI Tools](https://openai.github.io/openai-agents-python/tools/), [LangGraph](https://docs.langchain.com/oss/python/langgraph/workflows-agents).
3. Treat async business contact as a persisted pending effect with a resumable answer-thread state, not as an incidental tool call. Capture contact at the minimum point where the next effect requires it, but test D5 rather than treating it as settled. **[INFERENCE]** This is an AE design recommendation derived from the reviewed pause/resume primitives, not a source claim. Sources informing the inference: [Claude user input](https://code.claude.com/docs/en/agent-sdk/user-input), [OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/), [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence).
4. Record an append-only loop/effect trace in the answer thread and ledger: planned action, candidate set, authorization decision, approval, tool result, evidence, cost, and termination. Evaluate both success and non-occurrence of forbidden effects. Sources: [OpenAI tracing](https://openai.github.io/openai-agents-python/tracing/), [OpenAI evals](https://developers.openai.com/api/docs/guides/evals), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents).

## Skip list: patterns that do not transfer directly

- **Do not copy “always agent” architecture.** Anthropic and smolagents explicitly recommend simple workflows when the path is known; OpenAI says code orchestration is more predictable. AE should not pay loop cost for a deterministic registered action. Sources: [Anthropic](https://www.anthropic.com/engineering/building-effective-agents), [smolagents](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents), [OpenAI](https://openai.github.io/openai-agents-python/multi_agent/).
- **Do not copy coding-agent assumptions.** Claude's built-in tools and examples assume filesystem/shell access, sandboxing, CLAUDE.md, and developer workflows. AE's action registry operates businesses and money; effect typing, mandate checks, idempotency, and ledger reconciliation are different boundaries. Sources: [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [Anthropic](https://www.anthropic.com/engineering/building-effective-agents).
- **Do not expose all actions as one flat tool list.** Claude/OpenAI both document schema/context costs and deferred tool search; AE should use registry projections/namespaces and only load candidates relevant to the current task. Sources: [Claude Tool Search](https://code.claude.com/docs/en/agent-sdk/tool-search), [OpenAI Tool Search](https://openai.github.io/openai-agents-python/tools/).
- **Do not treat a plan list as durable async orchestration.** LangGraph's plan-and-execute notebook is a useful topology but is sequential and in-process; it explicitly identifies parallel latency as a limitation. AE needs Convex state, answer-thread events, idempotency, and resumable effects. Source: [LangGraph plan-and-execute](https://raw.githubusercontent.com/langchain-ai/langgraph/23961cff61a42b52525f3b20b4094d8d2fba1744/docs/docs/tutorials/plan-and-execute/plan-and-execute.ipynb).
- **Do not copy AutoGen broadcast group chat for business effects.** SelectorGroupChat broadcasts every selected agent's response to all participants and uses shared conversation context; this is useful for collaboration but risks unnecessary disclosure and token growth for customer/business actions. Use narrow action results and explicit disclosure policy. Source: [AutoGen SelectorGroupChat](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html).
- **Do not copy CrewAI role-play as authority.** Roles, goals, backstories, hierarchical managers, and delegation are coordination conveniences, not proof of customer mandate, spend authority, payment permission, or provider consent. CrewAI's sequential/hierarchical process still relies on explicit application configuration. Sources: [CrewAI agents](https://docs.crewai.com/v1.15.9/en/concepts/agents.md), [CrewAI processes](https://docs.crewai.com/v1.15.9/en/concepts/processes.md).
- **Do not copy unrestricted smolagents code execution.** Code agents gain composability but require sandboxing. AE should not let a model-generated program bypass the registered action boundary, authority checks, ledger, or effect approval. Sources: [smolagents overview](https://huggingface.co/docs/smolagents/), [smolagents introduction](https://huggingface.co/docs/smolagents/conceptual_guides/intro_agents), [OpenAI Tools](https://openai.github.io/openai-agents-python/tools/).
- **Do not assume framework tracing equals product truth.** OpenAI/LangSmith/CrewAI instrumentation measures runs and tokens; it does not by itself establish business commitment, provider response, settlement, or successful async completion. AE must preserve source evidence and ledger/effect state separately. Sources: [OpenAI usage](https://openai.github.io/openai-agents-python/usage/), [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence), [CrewAI flows](https://docs.crewai.com/v1.15.9/en/concepts/flows.md).
- **Do not assume SDK pause/resume supplies queue infrastructure.** Claude/OpenAI/LangGraph provide primitives for interruption, persistence, and resume; none of the reviewed sources establishes AE's required human-business outreach, notification delivery, retry policy, or provider SLA. AE must build these in Convex/answer-thread state or add infrastructure deliberately. Sources: [Claude user input](https://code.claude.com/docs/en/agent-sdk/user-input), [OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/), [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence).
