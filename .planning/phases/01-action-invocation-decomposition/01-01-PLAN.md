## Plain-language glossary (every new name, one jargon-free sentence)

| Name | What it means to a non-engineer |
|---|---|
| **action invocation** | One record of a single request to do one specific, already-listed thing (like "send this inquiry"), that can pause and be picked up again later. |
| **invocation origin** | A label on that record saying where the request came from: `request_owned` (part of a bigger planned job) or `standalone` (started on its own). |
| **invocation reference** (`invocationRef`) | The stable name/handle for one action invocation, so a person or another program can look it up later. |
| **invocation version** | A counter that goes up whenever the important details of the invocation change, so an old approval cannot apply to changed details. |
| **prepared-input digest** | A short fingerprint of the exact inputs that were approved, so any later change to those inputs is detectable. |
| **authority reference** | An opaque token that says "this exact invocation, with these exact inputs, is approved" — it is not a password and possessing it is not permission. |
| **paused authority gate** (`awaiting_authority`) | The state where an invocation has stopped and is waiting for a person or principal to approve it before anything happens. |
| **desired state** | What the approved caller currently wants done. |
| **observed resolution** | What we actually have evidence happened (which may be "unknown"). |
| **freshness** | Whether that evidence is current and the source is reachable. |
| **control state** | Where the work is in its lifecycle: prepared, waiting for approval, claimable, in progress, reconciling, or finished. |
| **reconcile-before-retry** | A rule that says: when we are unsure whether an outside effect already happened, check first — never blindly try again. |
| **attempt reference** (`attemptRef`) | The stable name for one single outside-effect try, so repeated tries stay distinguishable. |
| **provider simulator** | A stand-in "provider" used only in tests to produce the "we're not sure it worked" outcome, without touching any real business or expanding any public claim. |

*(No coined abstract nouns are introduced. ADR-009 itself rejects an `EconomicOperation` schema; this design does not reintroduce it under any other name.)*

## The six locked decisions

### Axis (i) — Seam-attachment shape → **Adapter over existing handlers, discriminated `invocationOrigin`, in-memory first**
**One sentence:** A standalone call attaches through the existing action registry via a thin adapter that tags each call `request_owned | standalone`, delivered first as an in-memory adapter — no new module, no shared-core refactor.

**Rationale.** RESEARCH §B scores this lowest on files×callsites and it is the only two-way-door option: it reuses `src/modules/actions/index.ts:38-58` and the `*ThroughSource` fan-out, and the first standalone action already carries no `requestRef` (`src/modules/inquiries/inquiry.actions.ts:214`), so `standalone` origin needs zero coupling removed. It matches spec §12's "in-memory adapter for evals" ordering exactly (`.planning/specs/ACTION-INVOCATION-ENGINEERING-SPEC.md:289-294`) and reuses the shipped in-memory store pattern (`src/modules/customer-request/preparation-authority.ts:238-334`).

**Rejected:** (ii) a new `action-invocation` module — higher blast radius and trips the ROADMAP bloat detector "one-implementation adapter for later" (`.planning/ROADMAP.md:242`); (iii) an extracted shared step-core — a one-way-door refactor of the 14 `src/lib/server/customer-request-*-api.ts` route files before any eval, contrary to ADR-009's "narrow rather than loosen" instruction (`.planning/adr/ADR-009-...md:190-191`).

**Makes falsifiable:** SPEC R1; ADR-009 gates 4, 5, 7; ADR-010 gate 2 (same source-owned transition on both surfaces).

### Axis (ii) — First standalone action → **Qualified inquiry (`inquiry.submit`) + provider simulator for the uncertain-effect fault path only**
**One sentence:** Slice one wraps the already-standalone `submitInquiryAction` in the invocation adapter's `awaiting_authority` gate, and uses a test-only provider simulator solely to exercise reconcile-before-retry — because the inquiry's own delivery states cannot represent an uncertain effect.

**Deciding evidence.** `submitInquiryAction` is already standalone (no `requestRef`; schema `src/modules/inquiries/inquiry.actions.ts:210`, surfaces `:214`), has attributable delivery (`src/modules/inquiries/internal/governed-send.ts:24,138-149`), and refuses booking/payment/dispatch (`inquiry.actions.ts:203-209`). Its delivery status set is `queued|sent|failed|held` with **no `unknown`** (`src/modules/inquiries/internal/schema.ts:51`), so per spec §12 (`.../ACTION-INVOCATION-ENGINEERING-SPEC.md:280-284`) a provider simulator supplies the uncertain-effect path, reusing the Request path's `unknown_external_state` (`src/modules/customer-request/internal/convex-v2-schema.ts:1048`) and reconciliation unknown reasons (`:414-418`). The paused gate is added by the adapter (spec §7 `:211-213`); it does not make the inquiry book or fulfil.

**Rejected:** a purely provider-simulated action for slice one — unnecessary; the inquiry already meets three of four §12 conditions with real attributable delivery, and simulating everything would weaken the parity evidence.

**Makes falsifiable:** SPEC R2 (incl. the boundary edge); ADR-009 gates 1, 2, 3, 8; ADR-010 gate 1.

### Axis (iii) — Persistence → **In-memory first; then ONE new module-owned Convex table `actionInvocations` (not reuse of the Request-scoped V2 records)**
**One sentence:** Slice one persists nothing (in-memory adapter); when persistence is needed, add one new additive, module-owned Convex table for the invocation control record, because every reuse candidate would force Request lineage optional.

**Rationale.** ADR-009 permits a new table only when an existing record would mix meanings or force optional Request lineage (`.planning/adr/ADR-009-...md:56-58,73-74`). RESEARCH §A.3 shows every candidate — `customerRequestV2ActionAttempts` (`convex-v2-schema.ts:928-931`), `customerRequestV2ApprovalGrants` (`:912-916`), `customerRequestV2ActionAttemptResolutions` (`:1045-1049`) — carries **non-optional** `requestId`/`requestRevision`; reuse would force them optional, which spec §4 forbids (`.../ACTION-INVOCATION-ENGINEERING-SPEC.md:173-174`). The new table stores only continuity/control (invocation reference, `invocationOrigin`, action id + version, prepared-input digest, the four state dimensions, and references to the existing attempt/authority/resolution records) — never business facts (spec §9, Further Notes `:368-370`). It is owned by a `src/modules/action-invocation/internal/convex-schema.ts` fragment spread into `convex/schema.ts` exactly as `customerRequestTables` is (`convex/schema.ts:7,26`; fragment pattern `src/modules/customer-request/internal/convex-schema.ts:239-241`); all new fields use `v.optional()`; no `node:` import enters the fragment (`skill://ae-convex-guardrails`).

**Rejected:** reuse of `customerRequestV2ActionAttempts` / `ApprovalGrants` — would require making Request lineage optional (forbidden). Historical Request-owned rows are read through the existing adapter union pattern (`convex-v2-schema.ts:715-720`), never migrated flag-day.

**Makes falsifiable:** SPEC R3 (incl. the migration edge); ADR-009 gates 5, 6; spec §4, §9.

### Axis (iv) — Per-action authority binding → **Bind one invocation by exact fields; invalidate on any material change; no cross-action inheritance**
**One sentence:** An `authority reference` binds exactly one invocation's inputs, target, effect and limits, and grants authority to no other invocation.

**Bound fields (an implementer can turn each into an assertion):** invocation reference; invocation version; prepared-input digest; principal; target; allowed effect (read-only / communication / external-effect); spend limit; data-use limit; expiry. (Spec §7 `.../ACTION-INVOCATION-ENGINEERING-SPEC.md:215-216`; ADR-010 `.planning/adr/ADR-010-...md:76-83`; shape analog `src/modules/customer-request/action-preparation.ts:137-154`.)

**Material-change invalidation triggers (any one invalidates the reference and forces re-preparation):** material input change; target change; action-version change; provider-suitability change; freshness-window expiry. (Spec §7 `:218-219`; refusal-taxonomy analog `src/modules/customer-request/preparation-authority.ts:17-34`.)

**Negative rule (acceptance):** approval of one action grants authority to no other action, no material revision, and no fallback branch (ADR-009 gate 10 `.planning/adr/ADR-009-...md:187`; ADR-010 gate 7 + interaction boundary `.planning/adr/ADR-010-...md:118-120,186`). Possession of an invocation or authority reference is never permission (spec Further Notes `:364-366`).

**Rejected:** reusing whole-route authority granularity (`customerRoutePlanDecisionSchema` confirm-creates-authority `src/modules/customer-request/agent-contract.ts:540-543`; cumulative repeat-permission `:793-812`) — that is exactly the too-broad binding ADR-010 forbids per action.

**Makes falsifiable:** SPEC R4 (incl. cross-task-leakage edge); ADR-009 gate 10; ADR-010 gates 5, 7.

### Axis (v) — Four-dimension state model → **desired / observed / freshness / control kept separate; no collapsing enum**
**One sentence:** State is four independent readings, and no single status enum may combine them.

| Dimension | Allowed values (initial) | Source analog |
|---|---|---|
| Desired state | `prepare`, `sent`, `cancel` | ADR-010 `:93` |
| Observed resolution | `none`, `succeeded`, `failed`, **`unknown`** | resolution union `convex-v2-schema.ts:1048` |
| Freshness | `current`, `stale`, `unreachable` | reconciliation unknown reasons `:414-418`; availability `agent-contract.ts:368` |
| Control state | `prepared`, `awaiting_authority`, `claimable`, `in_progress`, `reconciling`, `terminal` | egress-state analog `:455-458`; retry class `reconcile_before_retry` `.planning/adr/ADR-009-...md:218` |

**Worked example (required):** an inquiry sent but not yet acknowledged → `desired=sent`, `observed=unknown`, `freshness=stale`, `control=reconciling`.

**Negative acceptance criterion:** no single status field may encode two or more of the four dimensions; a design or implementation that collapses them fails R5 (spec §5 `.../ACTION-INVOCATION-ENGINEERING-SPEC.md:188`; ADR-010 `:90-96`).

**Makes falsifiable:** SPEC R5 (incl. uncertain-external-effect edge); ADR-010 gates 5, 8.

### Axis (vi) — Barrier experiment → **Two arms; predeclared metric + threshold; designed-only**
**One sentence:** Compare per-action authorization against whole-route approval on first-task authorization completion, accept the barrier claim only on a predeclared lift, and build none of it here.

- **Arm A (control):** whole-route approval — the caller must approve the full route before any task proceeds (today's `customerRoutePlanDecisionSchema` confirm boundary, `src/modules/customer-request/agent-contract.ts:540-565`).
- **Arm B (treatment):** per-action authorization — the caller authorizes one useful task at a time via the paused authority gate.
- **Primary metric:** proportion of entering callers who authorize and complete at least one useful task.
- **Secondary metric:** authority-abandonment rate at the approval step.
- **Predeclared threshold:** accept the ADR-009 barrier hypothesis only if Arm B shows **≥ 10 percentage-point absolute lift** in the primary metric at **p < 0.05**; otherwise the hypothesis is not supported and ADR-009 is narrowed per its own rule (`.planning/adr/ADR-009-...md:190-191`).
- **Designed-only statement:** this experiment is designed here and is **not built or run** in this phase; running it requires live-funnel changes and separate explicit authorization (ADR-009 `:23`; SPEC R6; `.planning/records/README.md` hypothesis rules).

**Makes falsifiable:** SPEC R6.
