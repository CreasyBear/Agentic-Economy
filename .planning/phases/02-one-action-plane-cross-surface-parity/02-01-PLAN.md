## Plain-language glossary (every new Phase 2 name, one jargon-free sentence)

| Name | What it means to a non-engineer |
|---|---|
| **surface parity check** (`compareActionInvocationSurfaces`) | One function that checks the AE-agent screen and an outside-agent's view of the same action call carry the same meaning, and lists exactly what disagrees. |
| **seven parity dimensions** | The seven things that must mean the same on both surfaces: what the business is and how fresh it is; what you can do and what info is needed; how options are compared; what you are allowed to do with data; what a retry means; what the evidence/refusal/unknown state is; and what can happen next. |
| **host adapter** | A per-place translator (the human screen, the AE chat, an outside agent's connection) that may render and talk, but may not decide who's eligible, what's approved, how to retry, or what the evidence means. |
| **host-adapter boundary test** | An automatic check that fails if a host adapter reaches past the shared action into the private business rules it is not allowed to touch. |
| **structured non-visual equivalent** / **structured invocation view** | A plain-data version of a rich screen, carrying the same options, consequences, evidence, and next steps, tagged to the exact action call, so a screen and an outside agent act on one and the same paused call. |
| **projection family** | A reusable screen shape (for example "approve this" or "compare these options") that the system fills only from real, already-known information. |
| **invent-nothing boundary** | The rule that a screen may reorder and explain, but may never make up a business fact, an action, a control, a consequence, or a permission that the records do not already contain. |
| **reconstruct-from-records rule** | The rule that the current screen can always be rebuilt from the durable records alone, so the chat log and on-screen state are throwaway. |
| **parity eval** | The set of automatic tests that prove the two surfaces stay equal by running one real action through both and checking every dimension. |

**Reused Phase 1 names (unchanged):** action invocation, `invocationRef` (invocation reference), invocation version, `invocationOrigin`, prepared-input digest, authority reference, `awaiting_authority` (paused authority gate), desired state, observed resolution, freshness, control state, attempt reference, reconcile-before-retry, provider simulator. Definitions: `01-01-PLAN.md:57-76`.

## The six locked decisions

### Axis (i) — Semantic-parity contract → **A net-new action/invocation-scoped seven-dimension check (`compareActionInvocationSurfaces`), a SIBLING of the Request check, proven against `inquiry.submit`**

**One sentence:** Build `compareActionInvocationSurfaces`, keyed to `invocationRef` + invocation version, that returns pass/fail over ADR-010's seven dimensions expressed as *semantic equalities* (not pixel/DOM), and prove it first against qualified inquiry `inquiry.submit`.

**Extend vs replace (Requirement 1 decision): SIBLING — keep `compareCustomerRequestSurfaces` untouched.** RESEARCH §B: extending in place would force the Request-keyed `SurfaceObservation` (`cross-surface-parity.ts:4-13`) to make `requestRef` optional and mix Request-terminal parity with action parity in one signature; replacing it would lose the whole-Request terminal parity it already proves. A sibling reuses the pattern (typed observations → verdict + typed failure list, `cross-surface-parity.ts:24-49`), costs one new file, edits zero callers, and is a two-way door. This mirrors Phase 1's "don't force optional Request lineage" reasoning (`01-RESEARCH.md:65`).

**The seven dimensions as checkable equalities** (each must be equal across the embedded observation and the external-agent observation for the same `invocationRef` + version; encodings and analogs in RESEARCH §C):
1. `businessInfoDigest` + `sourceRef` + `freshness`
2. `availableActionIds` + `requiredFields`
3. `suitabilityRuleDigest` (ordering + coverage)
4. `authorityScope` (bound fields + data-use limit — Phase 1 authority reference)
5. `retryClass` + `attemptRef` (Phase 1)
6. `observedResolution` (`none|succeeded|failed|unknown`) + `refusalReason` (Phase 1)
7. `allowedContinuations` (next-action set) + `finalOutcome`

**First action proven against:** `inquiry.submit` (Phase 1 axis ii; `01-01-PLAN.md:89-96`) — do not introduce a different first action (SPEC D-02).

**Rejected:** (a) extend `compareCustomerRequestSurfaces` in place — forces optional `requestRef`, mixes two scopes; (b) replace it — loses Request-terminal parity, one-way door.

**Makes falsifiable:** SPEC R1; ADR-010 gates 1, 2.

### Axis (ii) — Host-adapter boundary enforcement → **A typed host-adapter interface + a net-new import-boundary test**

**One sentence:** A host adapter may import only the shared action contract and read-only authoritative-projection readers and may only *call* the registered action; a net-new `tests/imports/host-adapter-boundaries.test.ts` (same shape as `tests/imports/customer-request-boundaries.test.ts`) fails if a host module imports any business-rule internal (eligibility / preparation / authority / execution / retry / evidence / recovery).

**Why this works with the grain of the code.** The harness already derives a host's whole view of an action *from the action definition, not the host*: `actionToHarnessToolContract` runs `action.run` directly (`tool-contract.ts:148`), `exposureForAction` computes surfaces (`:288-301`), `policyForAction` computes approval/tier (`:303-332`), and the host receives only a filtered contract (`filterAnswerModelToolContracts`, `:279-286`). The boundary ADR-010 requires is therefore already honored by construction; the only gap is an enforcement test (RESEARCH §A.3).

**The boundary the test draws.**
- **A host adapter MAY import:** `src/modules/common/action.ts` (the action contract), the harness tool-contract projection, and read-only structured-view / projection modules (axes iii-iv).
- **A host adapter MAY NOT import:** `src/modules/customer-request/action-preparation.ts`, `preparation-authority.ts`, any `internal/*`, any `*.functions.ts` business internal, or the Phase 1 `action-invocation/internal/*` adapter — i.e. nothing that lets it re-implement eligibility/authority/retry/evidence.
- **Violation detection:** `npm run test:imports` (the suite the new file joins, `package.json:46`).

**Rejected:** (a) convention + code review only — not enforceable; ADR-010 gate 2 needs a test; (b) a runtime capability object handed to each host — heavier, and does not catch a compile-time import reach into internals.

**Makes falsifiable:** SPEC R2; ADR-010 gate 2.

### Axis (iii) — Structured non-visual equivalent → **Every rich projection has a `structured invocation view` addressed to the same `invocationRef` + invocation version**

**One sentence:** For each rich projection there is a structured (non-visual) representation carrying the same options, consequences, evidence, and continuations, addressed to the same `invocationRef` + invocation version, so a UI decision and an external-agent decision resume the *same* paused invocation and neither host recomputes business inputs.

**Equivalence as a testable equality:** the structured form's `{options, consequences, evidence, allowedContinuations}` field-set equals the rich view's, and both carry the identical `invocationRef` + invocation version + `authorityReference`. It extends the existing structured-descriptor shape (`describeActionForAgent`, `action.ts:128-143`) and is a projection of the same frozen data every human view is built from (`requestView`, `customer-projection.ts:757-830`).

**Worked pair (required):** a rich **bounded-approval** view (the `disclosureReview` screen, `customer-projection.ts:275-288`) ↔ its structured form:

```
{
  invocationRef, invocationVersion,
  kind: 'bounded_approval',
  purpose, maximumRecipients, dataCategories: [{ label, classification }],
  authorityReference,
  consequenceSummary,
  allowedDecisions: ['approve', 'reject'],
  invalidatesOn: ['material_input_change', 'action_version_change', 'freshness_expiry']
}
```

Both are addressed to the same `invocationRef` + version; approving through the rich view or the structured form resumes one `awaiting_authority` invocation (Phase 1 identity, `01-01-PLAN.md:67`). "Equivalent" = the two carry the same decision-relevant field-set and the same invocation identity.

**Rejected:** (a) a per-host bespoke serialization — risks divergence and breaks single-resume; (b) deriving the structured form from the transcript — violates axis (v).

**Makes falsifiable:** SPEC R3; ADR-010 gates 3, 4.

### Axis (iv) — Generative-UI projection families first modelled → **Bounded approval + candidate/option comparison, bounded by an invent-nothing negative acceptance criterion**

**One sentence:** Model exactly two of ADR-010's six families first — bounded approval and candidate/option comparison — because they are the pair the inquiry slice needs, each mapped to its existing `customer-projection.ts` analog, with a hard invent-nothing boundary.

**Chosen families → existing analogs:**
- **Bounded approval** → `needs_authorization` branch, `customer-projection.ts:275-288` (`disclosureReview`).
- **Candidate/option comparison** → `projectOptionsReady`, `customer-projection.ts:364-395` + `projectCustomerOptionSet`, `customer-option-set.ts:6-36` (ordering, coverage, per-option provenance).

**Invent-nothing boundary (negative acceptance criterion):** a projection's emitted field-set MUST be a subset of `{registered-action descriptor fields, authoritative-state fields}`. The model may reorder, explain, and format; it may NOT introduce a business fact, an available action, a control, a consequence, or an authority that is not present in a registered action + an authoritative record. **A projection that emits any field with no authoritative source fails the criterion.**

**Rejected:** (a) modelling all six families first — out of scope; ADR-010 keeps the families as hypotheses to evaluate first (`:138-140`), and the other four (objective/constraints/known-unknowns; material clarification; progress/ownership/waiting; contradiction/incident/recovery) are not required to prove inquiry parity; (b) modelling only bounded approval — the inquiry slice presents candidate businesses, so option-comparison parity cannot be proven without it.

**Makes falsifiable:** SPEC R4; ADR-010 gates 1, 4.

### Axis (v) — Reconstruct-from-records rule → **The current view is a pure function of the durable records; conversation + component state are disposable caches**

**One sentence:** The current view is rebuildable from Phase 1's Action Invocation control record, authority reference, attempts, evidence, and result alone; conversation and component state are disposable caches that may hold only transport cursors, presentation preferences, and a pending-interaction reference, and may never be the source of truth for any of the seven dimensions.

**Checkable assertions:**
- (a) **Restart:** reopen after a process restart with the transcript + component state cleared → the structured invocation view is byte-equal to the pre-restart view (spec suite 12, `.../ACTION-INVOCATION-ENGINEERING-SPEC.md:324`).
- (b) **Transcript deletion:** delete the transcript → no dimension value changes and no work is lost.
- (c) **Cache boundary:** a host cache type carries only `{ transportCursor, presentationPrefs, pendingInteractionRef }` — a compile-time/test assertion fails if it carries anything a dimension depends on.

**Rejected:** (a) chat-as-record — ADR-010 rejects it (`:159-161`); (b) allowing component state to hold authority — a persuasive interface standing in for scoped authority, the named security risk (`ADR-010:207-209`).

**Makes falsifiable:** SPEC R5; ADR-010 gates 3, 9.

### Axis (vi) — Parity eval design → **An in-memory-adapter-first behavior suite crossing the Action Invocation interface, reusing the fifteen spec suites and both host harnesses**

**One sentence:** The parity eval runs `inquiry.submit` through an embedded host adapter and the external-agent host adapter over Phase 1's in-memory Action Invocation adapter first, asserting `compareActionInvocationSurfaces` verdict `pass` and mapping ADR-010's ten gates onto the spec's fifteen behavior suites — reusing existing fixtures rather than cloning them.

**Design specifics:**
- **Assertion primitive:** `compareActionInvocationSurfaces` (axis i).
- **Adapter order:** in-memory adapter first, production adapter later; both exercise the same interface, so it is a real seam (spec Testing `:304-306`).
- **Reused fixtures (not cloned, spec `:331-334`):** external surface `runHostedCustomerRequestJourney` (`hosted-agent-journey.ts:305`); negative control `runFrozenDirectAgentBaseline` (`direct-agent-baseline.ts:51-176`); plus the existing cancellation, idempotency, provider-denial, and unknown-effect suites.
- **Boundary:** the eval asserts observable interface contracts, never internal table layout (spec `:302`); passing proves contract behavior only, not real supply or fulfilment (spec `:336-337`).

**Rejected:** (a) a bespoke parity harness cloning the journey lifecycle — spec `:333-334` mandates reuse; (b) asserting DOM/visual parity — ADR-010 rejects pixel parity (`:163-164`).

**Makes falsifiable:** SPEC R6; ADR-010 gates 1-10 (the eval is where they are proven).

## ADR-010 ten-gate → falsifiable-test table (mandatory; R6)

Each row names an observable pass/fail and the spec behavior suite it reuses (`.../ACTION-INVOCATION-ENGINEERING-SPEC.md:308-329`). "First slice" = built when the inquiry slice is executed; "Deferred" = designed here, built in a later slice.

| Gate (ADR-010 `:176-192`) | Falsifiable test (observable pass/fail) | Reuses spec suite(s) | Slice |
|---|---|---|---|
| 1. One action, semantically equivalent through embedded + ≥1 external surface | `compareActionInvocationSurfaces` returns verdict `pass` (zero dimension mismatches) for `inquiry.submit` run through the embedded host and the external-agent host | 1 | **First slice** |
| 2. Same source-owned transition on both surfaces, no duplicated business rules | `npm run test:imports` (host-adapter-boundaries) is green AND both host paths resolve to one `action.run` for one action id | 1 | **First slice** |
| 3. Task-shaped view reconstructable from records without the transcript | After restart with transcript + component state cleared, the structured invocation view is byte-equal to the pre-restart view | 12 | **First slice** |
| 4. Non-visual fallback communicates same options/consequences/evidence/continuations | The structured invocation view's `{options, consequences, evidence, allowedContinuations}` field-set equals the rich view's, same `invocationRef` + version | 14, 1 | **First slice** |
| 5. Corrections update authoritative work and invalidate stale projections | A material-input change bumps invocation version, invalidates the authority reference, and marks the prior projection stale; a late observation from gen N after N+1 cannot become current | 4, 8 | Suite 4 **first slice**; suite 8 **Deferred** |
| 6. Missing information gathered without unnecessary interrogation | Only material-field changes trigger a clarification/re-preparation; a non-material presentation change leaves authority valid (count of clarification prompts = count of material-field gaps) | 5 | **First slice** |
| 7. Approval binds the exact action and cannot be reused after a material change | The authority reference bound to `invocationRef` + version + prepared-input digest is refused when replayed after a version bump | 4 | **First slice** |
| 8. Interruption/refusal/timeout/uncertain-effect/recovery retain semantic parity | Each fault path produces the same structured resolution + continuation on both surfaces; uncertain effect enters reconcile-before-retry and is not auto-retried (provider simulator, Phase 1 axis ii) | 9, 10, 11 | Uncertain-effect + reconcile **first slice**; timeout/refusal variants **Deferred** |
| 9. Cold agent continues without hidden first-party context | A cold external agent resumes the paused invocation using only `invocationRef` + authoritative records (no first-party session state); reverse (external handoff → reopen human) also passes | 2, 3 | Human→cold agent (2) **first slice**; reverse handoff (3) **Deferred** |
| 10. Human effort reduced without worsening correctness / control / privacy / accessibility / operator burden | **Measured, not asserted** — see the six sub-metrics below | 15 + composite | **Deferred** (composite live measurement); correctness + control sub-metrics **first slice** |

**Gate 10 — how each sub-metric is measured (not asserted):**
- **Correctness:** `compareActionInvocationSurfaces` verdict `pass` across every first-slice suite (zero dimension mismatch). *(First slice.)*
- **Control:** count of consequential effects executed without a bound authority reference for the exact `invocationRef` + version = **0** (axis iv/gate 7 assertion). *(First slice.)*
- **Privacy:** count of data-use categories disclosed beyond the authority reference's data-use limit = **0** (compare the structured view's `dataCategories` against the authority scope). *(Deferred — needs the persisted authority scope, Phase 1 Task 4.)*
- **Accessibility:** the structured non-visual equivalent exists and is field-complete for every first-slice rich projection (suite 14 pass) — the non-visual form IS the machine/screen-reader-consumable proof, measured by field-set equality, not a visual audit. A separate rich-UI accessibility audit is **Deferred** to a UI execute-phase and named here, not asserted. *(Structured-completeness first slice; UI a11y audit deferred.)*
- **Operator burden:** count of net-new backstage business-rule paths a host adapter must own = **0** (host-adapter-boundaries test / gate 2). *(First slice.)*
- **Human effort:** the embedded path's burden tuple (origins provided, invocation calls, schema mappings — `direct-agent-baseline.ts:219-230`) is **≤** the frozen direct-agent baseline on the same tuple. This is the effort side; it is distinct from Phase 1's barrier A/B (`01-01-PLAN.md:136-146`), which is designed-only and separately authorized. *(Deferred — needs the direct-vs-embedded comparison run.)*
