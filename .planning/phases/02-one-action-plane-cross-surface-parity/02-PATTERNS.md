# Phase 2 — Codebase pattern / analog map

**Created:** 2026-07-17
**Persona:** Codebase Onboarding Engineer (+ Code Reviewer) — `msitarzewski/agency-agents/engineering/engineering-codebase-onboarding-engineer.md`, `.../engineering-code-reviewer.md` (both re-fetched 2026-07-17, 200 OK; no substitution).
**Scope:** Read-only. Maps each NEW design element for the one-action-plane cross-surface parity (Phase 2) to its closest existing analog in the working tree, with `path:line`. Facts only — every row points at code actually inspected.
**Boundary:** No source edits. This is an onboarding map, not a change. It consumes Phase 1's Action Invocation identity (`invocationRef`, invocation version, `invocationOrigin`, the four state dimensions, the authority reference) and does not re-decide the seam, persistence, or authority binding.

## 1-line summary

AE already ships a cross-surface parity check, a family of customer-semantic projections, a harness that derives each action's exposure/approval/tier **from the action definition** (so a host never sets its own business rules), an external-agent journey harness, a direct-agent negative control, and an import-boundary test suite — but every one of these is **keyed to a Customer Request**, proves parity only at terminal outcome, and has no rule tying a rich projection to one invocation + version. Phase 2 re-homes those same shapes onto Phase 1's Action Invocation identity.

## Null-presence confirmation (the genuinely new names)

A repository-wide search for the proposed Phase 2 identifiers returns nothing today, so they are net-new and cannot collide:

- `grep -n "compareActionInvocationSurfaces|structured invocation view|structuredInvocationView|host-adapter-boundaries|hostAdapterBoundary|parity dimension|projectionFamily|reconstructFromRecords"` over `src` + `convex` + `tests` → **no matches** (verified 2026-07-17).
- Phase 1's `ActionInvocation | invocationRef | invocationOrigin | awaiting_authority` remain absent in `src` + `convex` (re-confirmed; consistent with `01-PATTERNS.md` null-presence check).

Everything below is therefore a *shape* analog (an existing record/function the new element resembles), not a name clash.

## Element → closest existing analog

| New design element (Phase 2) | Plain-language meaning | Closest existing analog (`path:line`) | Why it is the analog | Gap the new element closes |
|---|---|---|---|---|
| Action/invocation-scoped **seven-dimension parity check** (`compareActionInvocationSurfaces`) | One function that checks the embedded-agent view and an external-agent view carry the same *meaning* for one action call | `compareCustomerRequestSurfaces` `src/modules/customer-request/cross-surface-parity.ts:24-49` | Already compares a human observation and an agent observation and returns a pass/fail verdict with a typed failure list | Existing check is keyed to `requestRef` and covers only 6 terminal dims (`:1-22`) + a reload flag (`:36`); the new check is keyed to `invocationRef` + invocation version and covers ADR-010's 7 richer dimensions |
| **Host adapter** limited to transport/conversation/rendering | A per-host translator that may render and talk, but may not decide eligibility/authority/retry/evidence | Harness `actionToHarnessToolContract` `src/modules/harness/tool-contract.ts:130-154` — its `execute` just calls `action.run` (`:148`); `exposureForAction` `:288-301` and `policyForAction` `:303-332` derive surfaces/approval/tier **from the action definition**, not from the caller | The harness is already an adapter that owns no business rule: exposure, approval mode and tier are computed from the `ActionDefinition`, and the host only receives a filtered contract (`filterAnswerModelToolContracts` `:279-286`) | Nothing today *tests* that a host module cannot import business-rule internals; the new boundary test makes the existing convention enforceable |
| **Host-adapter boundary test** (`tests/imports/host-adapter-boundaries.test.ts`) | A test that fails if a host module reaches past the action contract into business internals | `tests/imports/customer-request-boundaries.test.ts` + `tests/imports/private-imports.test.ts` (both wired into `npm run test:imports`, `package.json:46`) | The import-boundary test pattern already guards module internals; adding a host-adapter rule is one more file of the same shape | No existing import rule names "a host adapter may import the action contract + authoritative projections only" |
| **Structured non-visual equivalent** addressed to `invocationRef` + version (`structured invocation view`) | A plain data form of a rich screen, carrying the same options/consequences/evidence/next steps, tagged to the exact invocation | `describeActionForAgent` `src/modules/common/action.ts:128-143` (structured, machine-readable description of one action); `requestView` assembler `src/modules/customer-request/customer-projection.ts:757-830` (the frozen structured shape every rich view is built from) | AE already emits a structured, non-visual description of an action and already assembles every human view from one frozen data object — the non-visual form is a projection of the same data | Neither is addressed to `invocationRef` + invocation version, so a UI decision and an external-agent decision cannot be proven to resume the *same* paused invocation |
| Chosen **generative-UI projection families** (bounded approval; candidate/option comparison) | The first two task-shaped screens the model may fill from authoritative state | bounded approval: `projectRequestEvaluation` `needs_authorization` branch `src/modules/customer-request/customer-projection.ts:275-288` (`disclosureReview`); option comparison: `projectOptionsReady` `:364-395` + `projectCustomerOptionSet` `src/modules/customer-request/customer-option-set.ts:6-36` | Both families already exist as Request-scoped projections that only select/populate from evaluated authoritative state (options, coverage, disclosure categories) | They are not organized as the ADR-010 family set, not bounded by an explicit invent-nothing rule, and not addressed to an invocation |
| **Invent-nothing boundary** (a projection may only select/populate from registered actions + authoritative state) | The model may reorder/explain but may never make up a fact, control, consequence, or permission | `requestView` `src/modules/customer-request/customer-projection.ts:757-830` freezes every field from typed inputs; `projectCustomerOptionSet` provenance `kind: 'provider_assertion'` `src/modules/customer-request/customer-option-set.ts:27-32` | The existing projections already carry provenance and are built only from evaluated inputs — the boundary is present in spirit but not stated as a negative acceptance criterion | No test asserts that a projection field set is a subset of registered-action + authoritative-state fields |
| **Reconstruct-from-records rule** (view rebuildable from invocation/authority/attempt/evidence/result; transcript disposable) | The screen can always be rebuilt from durable records; the chat log is a throwaway cache | reload-resume flag `src/modules/customer-request/cross-surface-parity.ts:36`; hosted-journey restart/replay assertions `src/modules/customer-request/hosted-agent-journey.ts:1999-2037`; spec §10 host architecture `.planning/specs/ACTION-INVOCATION-ENGINEERING-SPEC.md:243-255` | The Request path already proves a human can reload and resume, and the journey harness already asserts execution-start replay | Reconstruction is proven narrowly for the Request reload; no general rule ties it to the Action Invocation record set independent of the transcript |
| **Parity eval** (falsifiable suite, in-memory adapter first, reuse fixtures) | The test set that proves the ten ADR-010 gates by running one action through two hosts | external-agent surface: `runHostedCustomerRequestJourney` `src/modules/customer-request/hosted-agent-journey.ts:305`; negative control: `runFrozenDirectAgentBaseline` `src/modules/customer-request/direct-agent-baseline.ts:51-176`; spec Testing Decisions 1-15 `.planning/specs/ACTION-INVOCATION-ENGINEERING-SPEC.md:308-329` | The two host harnesses and the 15 behavior suites already exist; the eval crosses the Action Invocation interface and reuses these fixtures rather than cloning them | No suite is keyed to a registered action + invocation, and no suite asserts the seven-dimension parity across both hosts |
| **Human-effort / operator-burden measurement** (gate 10) | A number for "did the human do less without losing correctness/control/privacy" | `burden()` in the direct-agent negative control `src/modules/customer-request/direct-agent-baseline.ts:219-230` (counts origins provided, invocation calls, schema mappings) | The negative control already computes a burden tuple for the direct path — the same shape measures embedded-vs-baseline effort | It is not compared against the embedded-agent path per invocation, and privacy/accessibility sub-metrics are not yet expressed |
