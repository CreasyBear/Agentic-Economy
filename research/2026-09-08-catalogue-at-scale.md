# A million Tools, a short path to a useful Call

Date: 2026-09-08. Research and source review; no installation, deployment, paid Call or scale benchmark performed. This assignment owns this document only. Runtime checked: Node 22.22.0, npm 11.5.1.

## Judgment

“Airbnb for agentic services” should mean that a complicated choice becomes easy to make: describe the contribution, see credible alternatives, narrow on the facts that matter, inspect the consequential details, and buy with a clear way back if the result is uncertain. It should feel rich, useful and welcoming. A search input above endpoint URLs does not achieve that, however correct its transport is.

The largest near-term opportunity is to use capabilities already present in the official Coinbase SDK and make the result useful to a buyer. The million-Tool target needs a maintained search engine with contextual facets, not more application-level text matching or a thousand upstream requests per agent. Benchmark **Algolia + React InstantSearch** against **Typesense Cloud + its maintained InstantSearch adapter** before choosing. Keep Convex as the commercial authority and indexed discovery as a rebuildable observation. This is a shortlist, not authorization to purchase or install either.

Joel's latest Airbnb direction governs proposed catalogue exploration. DESIGN.md's current Twenty-inspired rows and market-terminal structure are existing constraints to deliberately revise during consolidation; they are not grounds to reject this direction. Preserve fonts, colours, accessibility and evidence distinctions while exploring the catalogue's composition. The rest of the operator product need not become a leisure marketplace.

PRODUCT.md's 2026-09-08 clarification also controls this work: an x402 endpoint is a Tool and can be discovered without AE publication or a stored readiness result. Older maturity references to admission determining discoverability are historical. Their useful objective survives: help a caller choose, execute and recover without founder intervention.

## What the excellent version feels like

A customer enters “Extract the invoice line items from these PDFs.” They see concise Tools with a clear contribution, a representative output preview where the Provider supplied a safe example, supported inputs, the price basis and evidence freshness. They refine by PDF input, structured JSON output and their data constraints. Their selected filters stay visible and removable. The page shows which facts are declared, observed or unknown. A capable service with unknown retention is visible when browsing but cannot silently satisfy a hard “no retention” requirement.

The customer compares three alternatives in a tray that survives navigation. The comparison highlights meaningful differences: what comes back, what information leaves, the supported request shape, how the price scales and what AE actually knows about delivery. It does not repeat twelve identical rows or invent a five-star reputation. “Use from your agent” gives a working interface-specific instruction with the exact reference. Quote collects the actual inputs and supplies the binding buyer total. The selected Tool, filters and comparison remain reachable after setup, funding, a failed Quote or a pending Call.

The agent has the same choice through a compact contract: bounded intent, explicit hard constraints, a small candidate page, source coverage, facts and unknowns, and an unambiguous next action. It can request details for selected candidates, Quote the winner, Call, and later recover the same purchase. It does not read a megabyte of schemas or enumerate a million Tools to discover which take PDFs. The surrounding job remains in its existing harness.

For a different category the visible facets change. Web-data Tools need extraction output, rendering support and published data-use facts; image Tools need accepted input and output formats and dimensions; on-chain reads need supported chain and read contribution. These are proposed category examples, not claims that AE currently has this metadata. Only show a facet backed by useful, attributable supply data. A generic “advanced filters” drawer full of mostly empty fields is not depth.

The prior [bounded stress review](../docs/reviews/catalogue-infrastructure-stress.md) measured native machine pages at 3.49 s and 2.91 s and repeated first-page reads at 2.71–6.07 s; four repeated reads produced stable references. It also found an unexplained omission on page two. Those are development observations, not results measured by this assignment or capacity claims.

The parent assignment's concurrent live UI audit reports a concrete relevance failure: “weather forecast for Perth” returned nine results, mixing services claiming global coverage with NOAA US-only and fixed Seattle/Portland/Chicago endpoints. It observed no region, output, freshness or price filters; default browsing reported 14,456 Tools and its first page was dominated by OneSource crypto endpoints. This is parent-reported runtime evidence from browser inspection, not independently retested here. Use the Perth query as an acceptance case: eligible Australian coverage must be explicit or unresolved; a US-only result is not a fit merely because it says “weather.” Declared coverage and observed successful coverage remain distinct.

The official [Convex text-search documentation](https://docs.convex.dev/search/text-search) documents equality filters, relevance-only ordering, prefix matching and no fuzzy matching after January 2025. It limits a query to 16 terms, eight filter expressions and a 1,024-result search scan. Post-filtering consumes candidate work. It does not document contextual multi-select facets or arbitrary price sorting for this path. The [Aggregate component](https://stack.convex.dev/efficient-count-sum-max-with-the-aggregate-component), already installed, provides efficient maintained aggregate structures; it is not evidence that arbitrary text-query facet intersections come for free. Building an aggregate for every facet combination would recreate a search engine badly.

## Filter semantics that survive a million options

1. **AND across dimensions; explicit OR within ordinary multi-select dimensions.** `(category = extraction OR conversion) AND (output = JSON)`. “Requires every feature” uses a distinct ALL operator. Do not let widget defaults silently define product meaning.
2. **Negative permission constraints are not positive tags.** “No external writes” requires complete, attributable effect information and no prohibited effect; “contains a read effect” is insufficient. Missing declarations remain unknown. Discovery can include unknowns, while a hard constraint either excludes them or marks them unresolved according to a visible mode.
3. **Counts describe the candidate universe, not the current page.** For an OR facet, show option counts under other active dimensions while preserving selected values so users can expand the group. Preserve selected zero-count options and explain the conflict. Include `exact`, `estimated` or `unavailable` precision and source/snapshot coverage in the machine projection. Never compute “12 Providers” from the current 20 cards and call it a catalogue count.
4. **Search high-cardinality facets.** Provider/domain and category values need searchable refinements and a bounded visible list. A thousand checkboxes is not advanced filtering. Category hierarchy should be shallow and evidence-backed.
5. **Separate money bases.** A maximum total for this request, an indicative AUD per-call amount, an upstream USD price, and an unbounded “from” price cannot share one slider. Group by comparable unit and request shape. Unknown price is a visible bucket, not zero. If the request size is unknown, say what must be supplied to Quote. Search-side numeric representations must never authorize spending; exact money remains authoritative at Quote.
6. **Separate source freshness, compatibility and caller viability.** “Seen in Bazaar 5 minutes ago,” “request format supported,” “used successfully by AE” and “permitted for this Agent” are distinct. A wallet, domain, payment count or verified identity is not proof of output quality. Keep evidence origin, sample size and time window. Do not translate upstream call counts into review stars.
7. **Keep task meaning visible.** Free text remains an intent hint. Structured hard constraints survive any semantic retrieval, typo correction or suggested category. The engine can retrieve on meaning; the system must not silently remove a constraint to make the results look good.
8. **Treat zero results as a decision.** Show which selected filters conflict, one or two concrete soft-filter changes with counts, and direct browsing of the wider source. An unavailable index or upstream timeout is a different state. Agents receive the same distinctions and bounded next action. Relaxation suggestions do not authorize purchases.

Primary technical support: [InstantSearch](https://www.algolia.com/products/features/ui-component-libraries), [Typesense UI](https://typesense.org/docs/guide/search-ui-components.html), [Meilisearch React integration](https://www.meilisearch.com/integrations/react), [Meilisearch facets and query matching](https://www.meilisearch.com/docs/reference/api/search/search-with-post), [Meilisearch pagination](https://www.meilisearch.com/docs/capabilities/full_text_search/how_to/paginate_search_results), [OpenSearch PIT pagination](https://docs.opensearch.org/latest/search-plugins/searching-data/paginate/). Meilisearch's [performance guidance](https://www.meilisearch.com/docs/capabilities/full_text_search/advanced/performance_tuning) warns against raising ranking depth to 100k or 1m merely to expose every page. A million indexed records does not mean a human should scroll a million ranked results.

Cost illustration, not an AE quote: the checked [Algolia pricing page](https://www.algolia.com/pricing) lists Grow with 100k included records and 10k monthly search requests, then $0.40/1k records and $0.50/1k requests. At one million counted records and one million monthly requests, arithmetic gives **$855/month in the page's displayed dollar currency** before extras, tax, replicas, contract variation and currency conversion. Grow Plus's listed search overage is $1.75/1k, making the same simple arithmetic $2,092.50. Semantic feature eligibility and Australian serving requirements must be checked separately. This is why agent traffic and search-per-successful-Call belong in the benchmark, not just catalogue size.

[Typesense Cloud](https://cloud.typesense.org/) advertises hourly capacity pricing without per-search/per-record fees; its [billing explanation](https://cloud-help.typesense.org/article/billing-process) confirms the fixed capacity charge while idle. Its [sizing guide](https://typesense.org/docs/guide/system-requirements.html) suggests roughly 2–3 times indexed searchable data size in RAM for keyword search and recommends production HA. No fixed AE monthly estimate is defensible without the actual compact records, query distribution, chosen regions and HA configuration. [Meilisearch pricing](https://www.meilisearch.com/pricing) and [AWS OpenSearch pricing](https://aws.amazon.com/opensearch-service/pricing/) likewise require workload/configuration assumptions; headline minimums are not million-Tool operating costs.

## Smallest viable architecture to benchmark

Use one compact, attributable discovery projection across sources. Keep source membership, source endpoint identity and observation/version facts; multiple directories observing the same endpoint must not create multiple counted Tools. Preserve source-specific conflicting claims rather than blending them. Endpoint equality alone may be insufficient if request methods/contracts differ; use the existing canonical identity rules and document unresolved identity cases. Imported snapshots support discovery and actual use without turning publication into a visibility gate.

Index only searchable/filterable summary facts and references. Do not index full JSON Schemas, secrets, request bodies or every Account's current balance. Serve summary pages with page-bounded payloads; describe loads the selected contract. Use maintained engine ranking and facets. AE's thin adaptation owns exact vocabulary, permissions, money/evidence interpretation and machine parity—not tokenisation, stemming, synonym guessing or a homemade relevance formula.

Refresh sources through existing scheduled/workpool mechanisms with checkpoints, explicit deletion/tombstone handling and bounded retries. Make the index rebuildable, track an index generation and per-source freshness/coverage, and reconcile missing updates. Search failure cannot erase saved Tools or prevent lookup/recovery of an existing Call. Search popularity must not starve purchase recovery work. Shared public result caching and per-Account private overlays need separate keys; changing Agent authority cannot leak another Account's facts or retain stale permission as executable truth.

The index can answer declared compatibility at scale. The authoritative commercial boundary answers whether this request can be Quoted and Called now. Do not live-probe every endpoint in a result set, multiply one Account's balance into a million search records, or claim that a public catalogue count is an exact count of currently purchasable Tools for a changing Agent. Support a bounded personalized shortlist overlay and state what has been checked. Revalidate on Quote.

One machine search contract should carry normalised filters, sort/matching mode, result references, per-source coverage and freshness, count precision, safe continuation and typed unavailable/zero-result states. Pagination tokens must be bound to the query/filter/index context or have explicitly documented live-pagination semantics. Do not wrap an offset in base64 and claim snapshot stability. OpenSearch PIT is an available maintained option if exhaustive stable traversal is required. Interactive faceted search and bulk directory export are different workloads; do not force agents to misuse interactive search as an export API.

Keep normal filter state in the URL using the installed router. A durable comparison list requires exact Tool references and version facts. Account-saved searches are a later explicit storage choice; a URL already solves the first share/revisit case. Reuse installed accessible Sheet, Dialog, checkbox and command components for shell controls. If InstantSearch is selected, style its maintained connectors/widgets with AE tokens instead of rebuilding its faceting state machine.

## Proposed acceptance: usefulness and scale, not a green test suite

All targets below are proposed benchmark gates, not measured results or production SLO promises. Use realistic compact records and real public-schema distributions; add duplicates across sources, sparse facts, broad and highly selective queries, malicious metadata and request-dependent pricing. Preserve a reproducible corpus and judged task set. Benchmark the two finalists with the same data before purchasing a production service.

| Stage | Workload proposal | Passing evidence |
| --- | --- | --- |
| 1k Tools | 30 independently judged tasks, 10 concurrent callers, keyboard/mobile and CLI/MCP journeys, known-answer facet counts | A suitable candidate in the top five for at least 90% of tasks with known supply; 100% of hard constraints honoured or explicitly unresolved; users can explain the price and next action; facet arithmetic matches the corpus. Record failures, not just an average score. |
| 100k Tools | Broad text plus rare filters, 100 concurrent callers, multiple directories, updates/deletions during paging; compare long-tail providers with a dominant provider | No O(catalogue-size) app hydration per query. Proposed warm search p95 ≤500 ms at the AE gateway with bounded summaries; partial/stale source failure remains intelligible; no duplicate identities or unauthorized private facts. Measure engine requests and cost per completed selection. |
| 1m Tools | Staircase offered load at 100/300/1,000 search requests/s to locate sustainable throughput; burst/failure/rebuild tests on isolated benchmark capacity | Report the saturation knee, latency distribution, error rate, freshness lag and full capacity cost. Do not assert 1,000 requests/s must pass without a capacity decision. Confirm count precision, selective-filter performance, provider diversity and agreed continuation semantics under index change. |

Across stages: trace `intent → search → comparison → Quote → Call → result/recovery → agent continues` through the existing HTTP, CLI and official MCP clients. Measure time and interactions to a useful result, unnecessary upstream requests, false zero-results, known-fact Quote refusals, successful interruption recovery and whether a new user can proceed without a chat explanation. Use authority and delivery checks as hard gates, not relevance-score tradeoffs. A beautiful catalogue that ends in commercial-policy failure is unfinished; a perfect payment kernel that cannot surface the right Tool is unfinished too.

## The roast, and what not to copy

- A million options behind a single text box is a warehouse with a doorbell. Rich discovery is a system for reducing uncertainty, not just exposing inventory.
- A `GET` badge is excellent debugging information and weak merchandising. Lead with the bounded job and useful output. Raw JSON is an escape hatch, not the product explanation.
- “Best filtering” cannot be achieved by filtering the first 20 upstream matches. That creates confident false negatives with a polished UI.
- Geography inferred from a Business name is not a location filter. A positive data-use tag is not a prohibition. A payment recipient is not the Provider. These shortcuts become more harmful when the UI becomes more persuasive.
- Do not copy Airbnb's travel imagery, decorative maps, scarcity language, host status badges or review stars. Real safe output examples can earn visual space. Unknown evidence should remain visible without making every result look broken.
- Do not copy revenue-oriented personalisation as the default market objective. A service should not outrank a better fit because it generates more AE margin or because a self-funded agent inflated its Call count.
- Do not ship a drawer containing every conceivable filter. Show a few useful constraints first and category-specific depth when it matters. Simplicity is the work of making the next decision obvious while retaining the facts behind it.

Consolidation decision: agree the catalogue's first three intent/category journeys and the shared filter/price/evidence semantics; make the current SDK path useful; then benchmark the maintained search finalists with explicit operating economics. Defer a new service, schema expansion, saved-view storage and broad visual-system changes until that evidence is reviewable.
