# Batteries included around the x402 Call

**Research date:** 2026-09-08, Australia/Perth.  
**Status:** consolidation input, not an implementation or release claim.  
**Source baseline:** worktree at `bf46215a5`, including concurrent uncommitted work.  
**North star:** hide complexity in simplicity; retain the capability.

## Product judgment

Batteries included means a customer can connect several agents to one Account, give them bounded spending permission, find a service, receive useful delivery, understand the bill, and recover when anything interrupts the purchase. The Agent stays in its existing harness. AE carries the commercial and operational work surrounding its short `search → Quote → Call → result` interface.

The Airbnb analogy reaches beyond cards and filters: the user should return to one recognisable purchase record for what was selected, what was promised, what happened, and what can happen next. The same record must serve an Agent recovering after a restart, a finance person reviewing spend, and a support operator resolving uncertainty. Different roles receive different detail and permissions; the commercial facts remain the same.

The strongest next improvement is continuity. A beautiful catalogue feeding a fragile first Call is not mature. Nor is a flawless payment kernel that requires its customer to diagnose missing commercial policy or retain a command's transient retry key.

## Five high-impact surprises worth building toward

1. **Make every interruption a saved place to return.** Quote expiry, lost response, funding handoff, credential rotation, Provider verification, and refund delay should all bring the user back to their current authoritative record. Most of the required states already exist. The missing product is their continuity across surfaces.
2. **Give the owner one live answer to “How much can my agents still spend?”** Include pending exposure and the limiting policy, not merely balance or captured spend. Show the top cause when an Agent is blocked. This is immediately useful to a business operating a fleet and directly uses existing economic machinery.
3. **Let support explain a Call without asking what application bought it.** A safe reference opens Tool/version, acting Agent, Quote, delivery, buyer charge, Provider obligation, and recovery history according to the operator's permissions. The customer should not coordinate AE's internal departments.
4. **Make “millions of Tools” a metadata problem, not millions of integrations.** Browse the source catalogue openly; fetch bounded detail and assess supported execution at the point of use. Credential-specific viability is a presentation overlay and never silently deletes external supply. Providers need to onboard only for the managed activities they choose.
5. **Design recovery capacity before maximising purchase throughput.** A platform that can accept new work while status, ledger reconciliation, or refunds are starved gets worse as it grows. Reserve operational capacity with the installed queue/rate-limit machinery, then measure it under a noisy neighbour and dependency outage.

## Source-confirmed rotation defect: a retained Call becomes invisible to its Agent

This is a traced source defect for **credential replacement that changes the underlying credential ID**. It is not a claim that every OAuth access-token refresh changes that identity, and it was not reproduced with a live purchase.

| Step | Current source | Consequence |
|---|---|---|
| Promote a replacement | [`transitionCredentialReplacementCore`](../convex/agentAccessPrincipals.ts), around lines 977–993, revokes the predecessor and patches the same Agent principal with the successor credential ID. | Durable Agent identity survives; the current credential changes. The replacement implementation does not rewrite `capabilityCalls`. |
| Authenticate status | [`agent-access-auth`](../src/lib/server/agent-access-auth.ts), around lines 201–223, projects the authenticated current key ID and resolves its canonical principal. `canonicalResolvedPrincipal` requires the returned credential to match that projection. | The caller cannot pretend it still uses the predecessor. |
| Send recovery request | HTTP [`handleCallStatusGet`](../src/lib/server/call-api.ts), around lines 683–716, and MCP [`callStatusAction`](../src/modules/capability-execution/call-recovery.actions.ts), around lines 246–254, pass the current authenticated principal into the same service. | The successor credential reaches the backend recovery path. |
| Authorize prior Call | [`readCallStatusHandler` and `authorizeRecovery`](../convex/lib/callLifecycle/callActions.ts), around lines 648–673 and 214–228, pass the current principal ID and credential ID to `readRecovery`. | The lookup is bound to the new credential. |
| Read original evidence | `readRecoveryHandler`, around lines 813–820, returns null unless the stored Call has both the same principal ID and exact credential ID. `readReplayHandler` does the same. | The original Call still records the predecessor, so valid successor recovery returns `invocation_not_found`. Cancel/reconcile share this guard; worker recovery loading repeats it. |
| Find earlier Calls | `listAgentCallSummariesHandler`, around lines 65–80, queries and filters on credential ID. | The successor's Agent history excludes predecessor Calls. |

The owner recovery path remains present: `authorizeOwnerRecovery` checks the signed-in owner, and `readOwnerCallStatusHandler` passes the original row identity to the worker. Records are not lost; automated continuity is broken and human intervention can become necessary precisely when a credential must be replaced.

Existing tests do not establish the missing behavior. The [recovery test](../tests/unit/convex/capability-call-recovery.test.ts) named “recovers by stable principal identity after the original grant is absent or rotated” changes grant state, keeps the same credential, and mocks `readRecovery`. The [two-Agent lifecycle test](../convex/agentAccessPrincipals.test.ts) retains credential/audit history, not purchased-Call history.

The correction should authorise the current successor against durable Agent/Account ownership and supported recovery permission, then use the stored original identity for effect evidence. Do not rewrite the original Call's credential, weaken cross-Account isolation, or re-enable a revoked credential. Complete Agent revocation requires an explicit owner recovery/handoff policy. A regression must create a Call with the old credential, promote the real replacement lifecycle, and recover/list it through the real lookup path with the successor; a sibling Agent and another Account must remain refused.

## The fleet surface should answer three questions

The customer-facing Agents view should answer **who can spend, what is in progress, and what needs me**. Group by durable Agent within the active Account, with a compact rollup of spent, pending, remaining permission, last use, and connection health. Expand an Agent for permissions, its Calls, credential lifecycle, and audit history. Keep key IDs and internal grants inside diagnostics.

An attention view should contain only unresolved actionable work. Every row names the current state, affected money/delivery, responsible actor, age, and one supported action: resolve it, inspect current status, or hand it to the owner. Bulk actions need identical safe semantics; “retry all failed” is not a valid operation across uncertain purchases. Normal completed work belongs in Calls, and global infrastructure health belongs with the operator. This is a fleet product, not a kitchen-sink admin console.

## What to reject

- A mandatory “complete your account” checklist that asks every buyer to learn Provider, ledger, treasury, readiness, or publication concepts before discovering a Tool.
- A new universal workflow engine, webhook scheduler, OAuth client, KYC form, wallet, or budget ledger. The project already owns too much good machinery to justify parallel replacements.
- Treating the addition of a named group as proof of enterprise governance. The proof is concurrent, durable, non-bypassable policy across the real routes.
- Automatic purchase retry after an uncertain upstream effect. Commodity retry middleware does not know the commercial consequence.
- Copying Nevermined's mutable workspace fallback into paid Calls. AE's authenticated Account binding is a valuable simpler boundary.
- Copying Whop's 24-hour idempotency expiry as permission to repurchase an unresolved Call. Reference ergonomics never override AE's known effect identity.
- Creating Provider registration work for every x402 endpoint, or labelling all unverified supply “unavailable” to make a dashboard greener.
- A premature proprietary ranking/reputation system, star ratings without observed provenance, fake scale numbers, or a new “market learning” abstraction before ordinary discovery and purchase quality work.
- A generic event stream containing private full inputs/results. Most continuation needs identity, version, state, and permission to retrieve detail.

## Proposed proof session

Use the existing deterministic Provider, money fixture, CLI, official MCP client, browser, and telemetry. Extend existing tests only where they fail to exercise the observable boundary. No new paid call or service is authorised by this research.

Start with a clean customer and two Agents. Browse public x402 supply, connect, set limited authority, add sandbox credit, obtain an exact Quote, Call a deterministic Tool, and use its literal output in a subsequent ordinary task step. Confirm the customer sees the same purchase and money facts. Then repeat with response loss, process death, credential rotation, policy reduction, funding failure, Provider timeout before release, uncertainty after release, duplicate submission, refund delay, and Provider withdrawal. After each case, a second person should recover through product surfaces without implementation knowledge.

Only after that loop works, expand the same fixture to many Accounts/Agents and a large catalogue. Keep the scenarios; vary offered traffic, cardinality, skew, and dependency health. Capture completed useful work, truthful refusals, duplicate-effect count, queue age, spend invariant, fairness, memory/context footprint, support resolution time, and unresolved state age. Choose customer-facing latency targets before publishing a claim; measure the supported operating envelope instead of selecting an impressive round number.
