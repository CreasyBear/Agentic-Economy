# Mercator documentation reference and AEcon capability map

**Captured:** 27 September 2026. **Purpose:** define the Mercator capability floor Joel wants AEcon to meet, using Mercator's own public contracts and this checkout's source. This is a documentation study, not a claim that paid Mercator behavior works or that AEcon's hosted release matches this checkout.

The OpenAPI file is 158,130 bytes and lists 43 paths, including discovery documents, account flows and 19 `/v1/` operations. ## Mercator's public contract, in task order

1. **Discover and choose.** `GET /v1/services/search` and MCP `search_services` accept a natural-language query, return ranked endpoints and a next tool, and can apply provider `prefer` or `require`. Default `resolution=static`; `resolution=live` attempts bounded Provider probes. Results expose rank, relevance/price score, estimated price, input requirements and health information. Search is free. The OpenAPI permits a 500-character query and up to 25 results. [Docs](https://mercator.sh/docs#search-services), [OpenAPI](https://mercator.sh/openapi.json). `Documented`; the prior benchmark observed only static search.
2. **Inspect.** `GET /v1/services/{serviceId}` and MCP `describe_service` expose endpoint method/path, input schema, examples, payment offers and source metadata. The Agent should select one endpoint within a large service. Inspection is free. [Docs](https://mercator.sh/docs#describe-a-service). `Documented`; one description was observed.
3. **Compose and price.** A plan contains one to ten nodes with service, endpoint, exact input and `dependsOn` references. `POST /v1/quote` / `quote_plan` checks current Provider terms without payment and returns per-node prices, stages, total, multiplier, plan hash, validity and whether pricing is dynamic. It is advisory: submission revalidates against the approved total and node limits. [Docs](https://mercator.sh/docs#quote-a-plan), [OpenAPI](https://mercator.sh/openapi.json). `Documented`; one- and two-node Quotes were observed. The public docs show dependency ordering but do not give a complete worked example of passing one node's output into another node's input; confirm that behavior before treating arbitrary dataflow as proven.
4. **Authorize and execute.** `POST /v1/jobs` / `create_job` accepts the unchanged plan plus a persisted idempotency key and approved total. A paid job charges before downstream execution and returns a durable job ID. Hosted OAuth limits and any explicit Agent budget cap spend; native MPP or local-wallet clients need quote approval or a sufficient budget. Retry with the same payer, key and plan after an uncertain submission; a new key can buy a second job. [Docs](https://mercator.sh/docs#create-a-job). `Documented`, paid execution untested.
5. **Observe, resume and recover.** `GET /v1/jobs/{jobId}` / `get_job` returns `pending`, `running`, `succeeded`, `partially_succeeded` or `failed`. Active jobs return HTTP 202; terminal reads return cached results and per-node failures. `GET /v1/jobs` lists payer-scoped retained jobs; cached reads do not rerun Providers. Paid Provider requests are attempted at most once after durable purchase claim. Job records, outputs and charged idempotency records expire after seven days. [Docs](https://mercator.sh/docs#get-a-job), [job list](https://mercator.sh/docs#list-and-recover-jobs). `Documented`, interruption behavior untested.
6. **Limit Agent context.** A summary result lists successful node IDs; `GET /v1/jobs/{jobId}/results/{nodeId}` can return just one cached node or a JSON Pointer field, and oversized results can use artifact links. A public share card carries accounting information without Provider outputs. [Docs](https://mercator.sh/docs#get-node-results), [OpenAPI](https://mercator.sh/openapi.json). `Documented`, output-size behavior untested.
7. **Record feedback.** `POST /v1/jobs/{jobId}/feedback` accepts overall and per-node ratings, comments and tags. It requires a route-bound proof from the original payer; an identical review replays, a changed review conflicts. Reviews are retained 90 days. The optional MACH reward is a Mercator incentive, not a necessary AEcon feature. [Docs](https://mercator.sh/docs#review-a-job). `Documented`, ranking effect untested.
8. **Distribute supply.** A service owner emails a URL, docs/OpenAPI URL, payment protocol and capability description. Mercator says it reviews and ingests catalogues and endpoint metadata; the public docs give no self-service publish-to-earn funnel or measured conversion. [Docs](https://mercator.sh/docs#mercator-for-service-owners). `Documented`, Provider outcome untested.

**Payments and roles.** Mercator's buyer payment is through Tempo/MACH or supported pathUSD/Stripe mechanisms; it pays downstream Providers through MPP on Tempo or x402 on Base. Its quoted buyer cost includes a multiplier. Failed Tempo jobs may refund unused capacity as MACH; configured Stripe payments have no automatic refund, and completed Provider purchases remain billable after a partial failure. AEcon's AUD prepaid buyer relationship and separate Provider obligation are different commercial choices. Parity means the buyer can acquire the same useful contribution within clear authority and cost, not that AEcon must reproduce MACH, Tempo wallets or Mercator's exact refund policy. [Payments](https://mercator.sh/docs#costs-and-payment), [privacy](https://mercator.sh/privacy.md).

## The minimum parity test

Use the same Agent, model, harness, task wording and scoring rubric on each service. Give each a funded safe account and comparable eligible supply where possible; also report when one marketplace lacks the relevant Provider. Include at least: (1) a single precise data contribution, (2) two independent contributions composed in the harness, (3) an offered quoted bundle, (4) a genuinely missing service, (5) a Provider refusal and an uncertain paid response, (6) a large result needing one field, and (7) a repeat task with buyer feedback. The [travel-search task](https://mercator.sh/use-cases/travel-search) is a strong multi-source case, but its example price is illustrative and neither product has delivered that itinerary in this study.

For each task record top-one/top-three fit, actual callable supply, Agent turns, Quotes and their validity, approved versus charged amount, useful output quality, elapsed time, payload/tokens, interruptions, refunds/remedies and repeat choice. For the Provider journey record admission-to-discovery time, qualified appearances, selection and earnings. Run hosted latency probes from the same region with enough repetitions for p95; the existing loopback versus hosted times are descriptive only.

## What remains unverified

- No paid Mercator job, partial-node execution, refund, Provider settlement, payer review or actual feedback-driven ranking was exercised. Those are documented contracts, not verified performance.
- No fresh AEcon paid Call, multi-Call harness recovery, quoted bundle, MPP Provider Call or hosted performance test was run in this documentation study. Source paths and existing tests establish narrower guarantees.
- Mercator's public docs specify the plan and dependency graph, but do not fully demonstrate cross-node output binding. The quoted two-node probe used independent nodes. Confirm real dependent execution before making a more specific parity claim.
- Mercator's seven-day job retention, MACH-only unused-capacity refund and manual Stripe refund route are limitations to assess, not standards AEcon must copy.

**Product decision recorded 27 September:** Joel's target is base-level Mercator capability parity. The Customer's harness composes independent AE Calls; AE owns any quoted bundle it offers. This maps parity to buyer and Provider outcomes while preserving the Tool as AE's callable supply unit and each Call's individual purchase evidence.
