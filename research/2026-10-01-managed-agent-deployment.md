## 1. What business we would actually be in

The offer should name the work, its owner and the service we provide. A client
should be able to say: these requests are handled, these exceptions come to my
staff, and this person is accountable when the operation fails. An agent's name,
model or computer is an implementation choice underneath that offer.

Three possible businesses have different burdens:

| Offer | What we would charge for | Main burden to prove |
| --- | --- | --- |
| Managed deployment and operation | Initial setup plus an ongoing service | Useful delivery without excessive operator time. |
| Software for agent operators | Running several client deployments reliably | Operators repeatedly need the same management capabilities. |
| A self-service agent product | A repeatable business function customers activate | Setup, exceptions and support can work without bespoke delivery. |

Our proposed sequence is managed delivery, followed by software for repeated
operator needs. Productisation would depend on recurrence across real customers.
This is a business hypothesis, not an adopted implementation roadmap.

The first contract needs a defined operating scope: supported inputs, permitted
actions, working hours or triggers, approval points, expected outputs, escalation
and support. Pricing an unspecified promise to run a business would leave both
the customer and operator unable to judge completion.

## 2. Where the value and difficult work would sit

Use E01, E02, E05, E09 and E19 to frame a customer investigation. The practical
questions are: where do requests enter, which records are authoritative, whose
permission is needed, which decisions require judgement, and what currently
breaks or delays completion?

Our proposed delivery work would include:

- Mapping the current process with the employee who actually performs it.
- Connecting the required systems and resolving missing or conflicting data.
- Turning business judgement into examples, instructions and approval rules.
- Establishing whether an output is usable and whether a downstream action ran.
- Training the responsible staff and making escalation fit their existing work.
- Keeping the deployment useful as applications, business rules and models change.

These activities create a possible source of recurring revenue and also a major
cost. We need to measure which work repeats and which remains customer-specific.
Existing procurement and payment infrastructure can contribute, but does not
demonstrate that we can operate a client's business process.

## 3. Which workflows would be worth investigating

E06, E07, E16 and E19 suggest different questions about the opportunity. We should
evaluate candidate work against observable characteristics rather than select a
sector from an interview.

| Characteristic | Question for a prospective customer |
| --- | --- |
| Recurrence | How often does the same kind of request arrive? |
| Access | Can we obtain the necessary records and permission to act? |
| Completion | Can a responsible person recognise an acceptable result? |
| Delay | How much time is spent doing work versus waiting on someone else? |
| Recovery | What happens when the answer or action is wrong? |
| Budget | Who pays today, and what would they pay to improve the result? |
| Additional value | Is useful work going undone because no one has capacity? |

For illustration, a customer-request operation could receive a message, gather
account information, prepare a response, route sensitive cases for review,
send an approved reply and update the customer record. Its useful outcome is a
resolved request with correct records. We would separately measure elapsed time,
staff handling time, correction rate and unresolved cases.

For a process waiting on an external decision, automation might reduce internal
handling without accelerating the whole transaction. Our sales claim must match
the portion we can affect. Work newly made possible also needs its own value
case; there may be no existing staff-cost baseline to subtract.

## 4. What a managed-agent product would need to make observable

These are proposed acceptance conditions derived from our brief, using E02,
E08–E15 and E18 as research prompts. They are not statements of current capability.

| Requirement | Observable acceptance condition |
| --- | --- |
| Authorised data access | A client can see connected systems and granted scope; withdrawn access prevents subsequent retrieval. |
| Isolation | An agent serving one client cannot retrieve another client's private records or memory. |
| Work state | Each request shows whether it is running, waiting for approval, blocked, completed or failed. |
| Durable operation | A restart preserves pending work and approval state; resumption does not silently repeat completed actions. |
| Human control | The appropriate employee can approve, correct, stop or take over the relevant step. |
| Business-specific quality | A deployment passes an agreed set of real examples, including exceptions and unacceptable outputs. |
| Model changes | A replacement is compared on the same work before rollout, with a usable return path if performance worsens. |
| Action evidence | A generated response and a successfully delivered message are recorded as different events. |
| Integration choice | We can compare a supported API with computer interaction on reliability, permissions, cost and maintainability. |
| Customer experience | Staff can handle their work and exceptions without learning model parameters or agent internals. |

A demonstration should include a blocked request, missing information, denied
access, a rejected approval and a retry. Happy-path output alone cannot establish
that the operator has a manageable service.

For the memory decision, our starting proposal is permission-scoped retrieval
and explicit client records. Training private business information into model
weights would need a separate case for access changes, removal and economic
benefit. The interview does not settle that design for us.

## 5. Model choice, quality and economics

E03, E04 and E10–E14 motivate a measurable selection process. Our proposed rule
is to choose the least costly supported configuration that meets the customer's
quality, latency and data-handling requirements. That includes the full run,
not merely the advertised price of one model call.

Compare the proposed agent with the existing process on the same examples.
Record accepted results, corrections, operator intervention, elapsed time and
cost. Include difficult cases and a held-back set that was not used while tuning
the configuration. Agree who judges acceptability. Keep each result tied to the
model, instructions, connected systems and configuration actually tested.

Possible routing to cheaper models is an optimisation to earn through evidence.
It is not a reason to install several models at launch. Nor does independence
itself establish superior economics: we would have to show that our choices
improve the client's result and our own cost of delivery.

Our proposed service contribution calculation is:

```text
customer fees
  - computer and hosting costs
  - model and connector costs
  - onboarding and maintenance labour
  - monitoring, intervention and support labour
  - rework and remedies
```

Track setup effort separately from recurring operation. A service can look
profitable while unpaid founder time covers its exceptions. Growth should make
the relationship between customer count and operator hours visible. E17 and E20
are prompts to measure useful work and commercial value, not to make token use,
computer count or generated output our success metric.

## 6. Customer adoption and defensibility

E08 and E18–E21 prompt us to investigate the customer's working experience and
our route to that customer. A queue of work requiring attention, clear evidence
and a named escalation owner may be more useful than adding another interface
employees must remember to visit. We should test the existing channel they use
before choosing a new one.

Our possible advantage would be demonstrated delivery in recurring workflows,
relationships with customers, reusable integration and operating knowledge, and
evidence of which configurations work. None of those advantages is established
by possessing an agent framework or a cloud computer.

Customer-facing evidence to collect would include:

1. A baseline and an agreed definition of useful completion.
2. Paid operation with actual exceptions and staff participation.
3. Renewal or increased use because the customer values the result.
4. Delivery cost after accounting for intervention and support.
5. A second deployment showing which work can genuinely be reused.

Our ability to reach suitable customers, learn their operations and deliver
reliably remains a founder-fit question. Faster software development helps us
build; it does not supply those relationships or operating experience.

## Attribution and unresolved decisions

The supplied recommendation to hire independent forward-deployed engineers
(FDEs) is commentary, not a direct Levie quotation. E03 supports investigating
model-neutral optimisation; it does not prove a blanket claim about every
vendor or independent operator.

[Levie's subsequent deployment post](https://x.com/levie/status/2105354449795621179)
and [Nick Vasilescu's managed Hermes/Orgo proposal](https://x.com/nickvasiles/status/2105445413620978138)
are separate sources. Neither establishes our customer demand, margins or a
decision to adopt their suggested stack. Company performance reports and market
forecasts require verification before we use them as investment evidence.

The main open decisions are the business function we can deliver, customer access,
our operating responsibilities, quality requirements, access model and support
economics. The latest managed-agent brief entails responsibility for a broader
workflow than the current procurement charter. This research records the proposed
direction; it does not represent that broader capability as implemented.
