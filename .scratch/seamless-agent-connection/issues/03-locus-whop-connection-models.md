# Contrast Locus and Whop connection models

Type: research
Status: resolved
Blocked by:

## Question

How do current Locus and Whop model developer or agent connection, transport verification, authentication/authorization, funding or entitlement readiness, credential lifecycle, and recovery; what shared familiar sequence emerges, and where do their approaches materially differ?

Use the existing Locus and Whop scavenger/maturity corpus first. Record exact first-party sources, maintained dependencies or standards they rely on, and the user-facing states worth copying. Do not propose AE-specific design yet.

## Answer

### Decision-grade finding

The two references converge on a familiar staged journey, but only Locus presents it as one coherent agent-connection product.

1. Publicly discover how to connect.
2. Add a standard transport or maintained client.
3. Prove that the client can reach the service.
4. Authenticate a technical caller without handing it root authority.
5. Grant read access before paid or consequential execution.
6. Establish the separate facts needed to act: scope, resource access, capability readiness, enablement, and funds or entitlement.
7. Show one truthful current state and its next action.
8. Preserve identity through expiry, interruption, rotation, revocation, and recovery.

The important shared rule is that **transport connected**, **authenticated**, **authorized**, and **ready to spend/use** are not synonyms. Locus makes this separation explicit through MCP `mcp:read` versus `mcp:execute`, catalog enablement, Agent Connection limits, and usable balance. Whop reaches the same separation through distinct credential kinds, exact-resource permission checks, account capability states, installation consent, and payment/entitlement state. The Locus evidence is the cleaner reference for an agent connection journey; the Whop evidence is the stronger reference for using familiar maintained standards, SDKs, CLI conventions, and hosted human steps.

Evidence labels below mean:

- **OBSERVED** — directly exercised or mechanically inspected in the retained corpus.
- **PUBLISHED** — stated by a first-party reference and not independently exercised here.
- **INFERRED** — a synthesis across published mechanisms; not a vendor claim.

Neither source supports collapsing the journey to a binary connected/not-connected flag.

### Shared familiar sequence

**INFERRED from both corpora:** the least-surprising reference sequence is:

```text
public guide / docs
  → choose a supported client or maintained SDK
  → add endpoint / install connector
  → verify a harmless read
  → authenticate
  → consent to bounded scopes
  → show read-ready
  → satisfy capability + funding/entitlement prerequisites
  → show execute-ready
  → operate
  → inspect / rotate / revoke / recover
```

Three familiar interaction patterns recur:

1. **Start free and harmless.** Public docs/discovery are usable before private data or spend authority.
2. **Escalate at the boundary.** Browser consent, owner step-up, or hosted payment/KYC appears only when the next requested action needs it.
3. **Return to the same durable thing.** Pending authorization, funding, payment, or work keeps a stable resource identity and a status read rather than demanding a blind restart.

The two-stage readiness concept is therefore reference-backed, but the exact labels are not universal vendor terminology. Locus directly supports a semantic split between read-ready and execute-ready. Whop supports it indirectly through public Docs MCP versus credentialed API MCP, permission checks, and resource capability state.

### Meaningful differences

| Dimension | Locus | Whop |
|---|---|---|
| **Primary user story** | Connect an agent to discover and consume metered capabilities from one balance. | Connect a developer, app, user, or embedded surface to a broad commerce platform. |
| **Connection object** | First-class Agent Connection with readable status, scope, budgets, and expiry. | No single equivalent in this corpus; API keys, app installation, OAuth grants, Elements tokens, and resource permissions compose the connection. |
| **Initial authority** | Explicitly separable `mcp:read` and `mcp:execute`; Agent Connection has no management authority. | Depends on credential type and granted action/resource permissions. Public Docs MCP is separate from authenticated API MCP. |
| **Headless bootstrap** | AgentID path can establish/recover a restricted technical account without an existing tenant identity. | Root/API-key/app installation starts from human/session-mediated developer or account setup; non-interactive use follows credential creation. |
| **Economic readiness** | Central: zero-balance account, exact payer-safe funding handoff, usable balance, endpoint enablement, and budgets. | Contextual: permission, account capability, payment method, verification, membership, product, or other resource state. |
| **MCP authentication** | Standards-discoverable OAuth public client with PKCE, dynamic registration, read/execute scopes, rotating refresh families. | Existing Account/App API keys on API MCP; the corpus does not describe an equivalent MCP-specific OAuth journey. |
| **Transport state** | Deliberately stateless MCP; durable application call IDs own recovery. | Streamable HTTP preferred, SSE retained; exact API MCP session/recovery semantics are less fully documented in the retained evidence. |
| **Tooling breadth** | Ready client configs and compact MCP meta-tools; API is the core. | Public Docs MCP, API MCP, CLI, OpenAPI, five official SDK languages, hosted Elements, and numerous framework-facing surfaces. |
| **Credential operations** | Explicit create/list/read/rotate/revoke for connections; OAuth family rotation/revocation; some independent keys support overlap. | Mature but distributed across Account/App keys, OAuth tokens, access tokens, webhook secrets, app grants, and sessions. |
| **Version/environment model** | Product generations and sandbox capabilities must be kept distinct; Locus sandbox omits MCP and important live behavior. | Dated REST and webhook contracts, SDK generation pins, and strict production/sandbox separation; more powerful but more ways to mismatch. |

| Whop | Hosted OAuth, verification, payment next actions, account links | Human consent/compliance steps with machine-readable continuation | **PUBLISHED:** [OAuth](https://docs.whop.com/developer/guides/oauth) · [Verification](https://docs.whop.com/developer/verification/overview) · [Payment status](https://docs.whop.com/api-reference/beta/payments/retrieve-payment-status) · [Account links](https://docs.whop.com/api-reference/account-links/create-account-link) |

No retained source names a first-party SDK that clients must use for Locus MCP; its strongest non-handrolled story is protocol conformance and ready client configurations. Whop’s strongest non-handrolled story is its maintained OpenAPI/SDK/CLI/Elements ecosystem. The corpus also warns that published helper examples can lead package releases: Whop’s TypeScript webhook/user-token helpers were documented as unavailable at capture time, so installed exports still require verification. [Webhooks](https://docs.whop.com/developer/guides/webhooks) · [Versioning](https://docs.whop.com/developer/api/versioning)

### Reference patterns worth copying

These are patterns demonstrated by the references, not an AE design proposal.

1. **One visible staged journey, not a credentials page.** Locus’s guide, machine-readable configurations, browser authorization, and connection object form a legible sequence.
2. **Public discovery before authentication.** Whop Docs MCP/`llms.txt` and Locus’s public connection/onboarding contracts let a runtime understand the next step without a secret.
3. **Use client-native installation shapes.** Both publish concrete client configurations; Whop goes further with CLI commands to add MCP and skills.
4. **Verify with a harmless read.** Locus scopes initialize/discovery/resources separately; Whop exposes exact permission and requesting-account reads.
5. **Separate technical connection from executable readiness.** Locus distinguishes read scope, execute scope, endpoint enablement, budgets, and balance. Whop distinguishes credential, permission, resource access, capability state, and payment/entitlement state.
6. **Escalate consent only when authority expands.** Locus uses owner step-up and OAuth consent; Whop requires installer reapproval for added permissions and human/session governance for roots.
7. **Use hosted boundaries for sensitive steps.** Locus delegates payer card handling to Stripe Checkout. Whop uses hosted OAuth, Elements, verification, account links, and next-action URLs.
8. **Show credential posture without ever showing the credential again.** Locus list/read returns metadata, status, budgets, and expiry while secret material is one-time-only. Whop similarly keeps long-lived keys server-side and mints short-lived embedded tokens.
9. **Give every pending step a stable resource and authoritative read.** Both expose status endpoints and preserve the difference between pending, action-required, terminal, and unknown states.
10. **Use maintained protocols and generated clients.** Locus leans on MCP/OAuth RFCs; Whop adds OpenAPI-generated SDKs, CLI, Standard Webhooks, and hosted Elements.
11. **Keep owner authority separate from runtime authority.** Both prevent ordinary agent/app credentials from governing their own root authority.
12. **Treat recovery as part of connection.** Rotation, revocation, expiry, reauthorization, environment mismatch, and interrupted hosted steps are normal states, not exceptional documentation.

### Papercuts to avoid

#### Locus

- **PUBLISHED:** managed Agent Connection rotation invalidates the old credential immediately, while a different scoped-key surface supports bounded overlap. Immediate replacement is simple but can create runtime downtime. [Rotate Agent Connection](https://docs.paywithlocus.com/api-reference/authentication/rotate-a-scoped-agent-connection-credential) · [Rotate one scoped key](https://docs.paywithlocus.com/api-reference/tenants/rotate-one-key;-sibling-keys-of-the-same-kind-keep-working)
- **PUBLISHED:** an Agent Connection may live up to 365 days and an agent-owned credential rotation extends expiry 365 days. Long duration increases leaked-secret blast radius despite scopes. [Connect an agent](https://docs.paywithlocus.com/locus-pro/connect-agents) · [Rotate agent-owned credential](https://docs.paywithlocus.com/api-reference/agent-native-onboarding/rotate-the-agent-owned-credential)
- **PUBLISHED:** AgentID adds a second authorization/PKCE/callback/replay sequence. It enables true headless recovery but introduces identity-provider and redirect-continuity complexity. [Agent-native onboarding](https://docs.paywithlocus.com/locus-pro/agent-native-onboarding)
- **PUBLISHED:** stateless MCP offers no GET resumption or DELETE session lifecycle; application resources must carry recovery. A client that expects transport resumption will fail. [Unsupported GET](https://docs.paywithlocus.com/api-reference/mcp/unsupported-in-stateless-mode) · [Unsupported DELETE](https://docs.paywithlocus.com/api-reference/mcp/unsupported-in-stateless-mode-1)
- **PUBLISHED:** HTTP/JSON-RPC success can still contain `result.isError`; a generic transport-success indicator would lie. [Hosted MCP](https://docs.paywithlocus.com/api-reference/mcp/hosted-mcp-server-stateless-streamable-http)
- **PUBLISHED:** the Locus sandbox omits management APIs, MCP, routing, live balance/reservations, and live idempotency conflicts. Passing sandbox cannot verify connection or execution readiness. [Sandbox](https://docs.paywithlocus.com/locus-pro/sandbox)
- **PUBLISHED:** live-priced MPP/x402 supply can return no numeric estimate. A budget cap is not the same as an exact ready-to-buy quote. [Catalog](https://docs.paywithlocus.com/locus-pro/catalog) · [Explain price](https://docs.paywithlocus.com/api-reference/catalog/explain-one-endpoints-price)
- **INFERRED:** Locus’s strong product specificity makes its journey coherent, but the account-owned and agent-owned lanes, static credentials, MCP OAuth, AgentID login, and distinct key-rotation rules still create branch complexity that a single “connected” badge would conceal.

#### Whop

- **PUBLISHED:** Account keys, App keys, OAuth tokens, embedded access tokens, iframe tokens, and sessions are intentionally non-interchangeable. This is secure but easy to misconfigure if the UI does not state actor and resource context. [Authentication](https://docs.whop.com/developer/guides/authentication) · [OAuth](https://docs.whop.com/developer/guides/oauth)
- **PUBLISHED:** app permission additions require renewed installer approval. Retrying the same `403` without presenting the approval action is hostile. [Permissions](https://docs.whop.com/developer/guides/permissions)
- **PUBLISHED:** sandbox and production have separate URLs, keys, IDs, data, webhooks, and connected-account records. Credential/base-URL mismatch is a documented common `401`; API MCP does not publish a sandbox switch in the retained corpus. [Sandbox](https://docs.whop.com/developer/guides/sandbox) · [Troubleshooting](https://docs.whop.com/developer/troubleshooting) · [AI and MCP](https://docs.whop.com/developer/guides/ai_and_mcp)
- **PUBLISHED:** CLI coverage is narrower than REST and API MCP operation parity is not fully specified. A successful CLI/MCP smoke cannot be treated as broad API parity. [CLI](https://docs.whop.com/developer/cli) · [AI and MCP](https://docs.whop.com/developer/guides/ai_and_mcp)
- **PUBLISHED:** REST versions, SDK generation dates, and webhook payload versions evolve separately. New optional fields/endpoints and additive status details can appear; a one-time connection test is not continuing compatibility proof. [Versioning](https://docs.whop.com/developer/api/versioning)
- **PUBLISHED:** documented TypeScript webhook and iframe verification helper examples were ahead of current package exports at capture time. Copying snippets without testing the installed SDK can produce a broken “official” setup. [Webhooks](https://docs.whop.com/developer/guides/webhooks) · [Authentication](https://docs.whop.com/developer/guides/authentication)
- **PUBLISHED:** resource status and error envelopes vary by API generation and resource. A universal `connected|failed` or `pending|success|failed` mapping loses actionable truth. [Versioning](https://docs.whop.com/developer/api/versioning) · [Troubleshooting](https://docs.whop.com/developer/troubleshooting)
- **INFERRED:** Whop supplies all the necessary primitives but no single connection workbench or first-class “ready to use/buy” state is established by this corpus. Integrators must join credential, permission, capability, environment, and economic-resource state themselves.
