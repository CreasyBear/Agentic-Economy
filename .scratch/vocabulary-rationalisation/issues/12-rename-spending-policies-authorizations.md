`revokeCompromisedPredecessor()` calls `revokeReplacementMaterial()`, which revokes the predecessor credential, binding, grant, delegation, and provider-revocation outbox entry—but does not invalidate OAuth refresh families.

`claimRefreshFamily()` checks only the refresh family/token lifecycle. It does not re-check the canonical credential or binding. The HTTP refresh flow can therefore:

1. Claim an old refresh token from an active family.
2. Create a successor provider key.
3. Fail later at `commitRefreshFamilyRotation()` because the predecessor binding is already revoked.

The best-effort cleanup at lines 918–920 cannot guarantee recovery if the process fails after provider issuance.

Alternate paths were checked:

- Owner credential revoke invalidates families at `agentAccessPrincipals.ts:1473`.

None covers compromise replacement. The comparison checkout has the same gap; this is preexisting relative to the final normalization edits, but it remains a cumulative complete-module blocker.
