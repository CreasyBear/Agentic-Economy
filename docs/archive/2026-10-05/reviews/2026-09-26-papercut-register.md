# Agentic Economy papercut register — 26 September 2026

## Scope and evidence

This is a task-centred pass over the current Agentic Economy application and checkout. The product standard is the six core market journeys in `PRODUCT.md`: find a relevant capability, compare, buy and continue, publish and reach demand, retain missing demand, and improve repeat selection. The entry release and future vision are distinct. Findings concern buyer, Provider, agent, CLI, MCP, HTTP, operator, adversarial, accessibility, alpha-user, code, documentation and repository experience. Eight requested three-reviewer waves were completed, followed by a ninth three-reviewer wave for gaps in the retained-demand and repeat journeys. The three-reviewer slots were reused after the collaboration system reached its unique-agent limit; all assignments used Luna Max.

**Runtime boundary:** the existing local server at `http://127.0.0.1:3024` reports source revision `851e1454558db59e80e321d7b0d3cb2d5551558a`; checkout HEAD at audit start was `bb6c50ba5ea8dd7a51767dd87d2388f4748d9b91`. Vite runs from this checkout, but the revision is injected at launcher start. A live observation therefore proves the running local snapshot; a source citation shows current checkout behavior or a plausible trace, not necessarily the exact served revision. Existing modified `PRODUCT.md` and `docs/README.md` and two untracked design docs were preserved.

**Evidence classes:** `Live` = observed AEcon request/browser behavior; `External live` = observed competitor request/browser behavior; `Test` = existing executable test; `Source` = current code inference; `Docs` = published product contract or instruction. No traffic or funnel analytics were available. “Likely abandonment” ranks task blockage and friction, not a measured abandonment rate. Read-only passes avoided paid Calls and external charges; end-to-end purchase, payout and production behavior need a controlled test environment. **Overall coverage is partial:** the `3/3` ledger counts completed reviewer assignments, not complete feature proof.

**Priority:** P0 data loss, security or financial integrity; P1 core task blocked or materially misleading choice; P2 significant extra work, uncertainty or wasted context; P3 local polish. `Open` means this audit did not verify a fix. ### Mercator benchmark addendum — 27 September 2026

The [Mercator documentation capability map](../../../../research/MERCATOR-DOCS-CAPABILITY-MAP-2026-09-27.md) inventories the published search, quote, job, recovery, payment, feedback and Provider contracts against current AE source. It is a reference for parity decisions; documented Mercator behavior remains distinct from the live observations below.

The [focused competitive benchmark](../../../../research/MERCATOR-AECON-BENCHMARK-2026-09-27.md) sent four identical needs twice to Mercator's hosted REST search and this checkout's local AEcon HTTP search, then inspected a service and requested Mercator's free one- and two-node quotes. This addendum strengthens existing search and context findings and adds two distinct Agent task gaps below; it is not another reviewer wave. For SEC filings, tomorrow's weather and scanned-invoice line items, Mercator exposed a directly suitable endpoint within its first two choices; AEcon's sampled first choices resolved company identity, gave current conditions and extracted raw text respectively. Both interfaces returned unrelated candidates for a licensed French-speaking mediator request. Candidate fit was assessed from descriptions, not purchased Provider output. The two catalogues differ, so these observations evaluate the buyer's returned choices, not isolated ranking-model accuracy.

Mercator's hosted search took 5.15–12.58 seconds across eight calls; AEcon's local search took 0.11–0.84 seconds across eight calls. Different network paths, inventory and AEcon's degraded ranking state prevent a speed winner or p95 claim. The one-node Mercator Quote was USD 0.003 and the two-node Quote USD 0.006; both were advisory, with no execution. Mercator's published job, feedback and model-score claims remain documentation or vendor evidence here. A comparable paid outcome, Provider distribution and task-level performance remain unmeasured on both services. Keep the product comparison centred on completed tasks and Provider reach, not the number of rows or protocol names.

The linked [travel-search use case](https://mercator.sh/use-cases/travel-search) adds a concrete multi-source task: two business-class SFO–Tokyo seats, cash versus points, each leg's cabin, taxes, rules and current flight conditions. Its $0.021 example subtotal is explicitly illustrative, not a live trip Quote. In a [follow-up free search probe](../../../../research/MERCATOR-AECON-BENCHMARK-2026-09-27.md#travel-search-use-case-probe), Mercator surfaced plausible award, cash-fare and condition endpoints across the full need and three focused subtasks. AEcon's combined-need top five were unrelated; focused cash-fare and award-seat queries returned `noMatch`, while the condition query returned current weather and unrelated Tools as `degraded`. This establishes a visible acquisition gap for the sampled travel task, not that AEcon has no travel supply anywhere or that Mercator completed an itinerary. Neither service was asked to buy a seat, validate availability or produce the advertised comparison.

### How to use the groups

First align the served revision with the checkout and prepare controlled buyer, Provider and Admin fixtures. This is an **evidence prerequisite**, not another product feature: the current live/source mismatch and missing paid-role fixtures prevent confident closure of several groups. Reproduce the high-impact observations on that build before assigning root causes.

Then work through a complete buyer acquisition task across **G1 → G2 → G3 → G4**. Fix the specific failed handoffs found by that task using the existing Tool, Quote and Call contracts. The acceptance result is a relevant choice or honest no-match, one authorised Call with useful output and exact AUD record, and a support route that preserves its CallRef. For a task needing two independent Tools, prove the harness can see the expected total from separate Quotes before its first Call and recover cleanly if it stops between Calls. If AE presents a quoted bundle, prove AE binds and fulfils that bundle as one commercial choice. G5 is the corresponding Provider journey; G6 tests whether the market retains unmet and repeat demand. G7 can supply small independent fixes as the buyer and Provider tasks expose documentation gaps. G8 needs a controlled queue fixture before treating its source risks as live incidents.

Do not create a new unified marketplace layer or rank these 43 rows by count alone. Search relevance, source truth, authority, money records and Provider publication are distinct concerns that change for different reasons. A shared interface is justified only after the completed task reveals a real duplicated contract; the existing registry and Tool/Quote/Call seams are the starting alternatives.
