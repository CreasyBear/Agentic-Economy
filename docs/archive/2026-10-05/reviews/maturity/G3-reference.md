# G3 reference — Connect and govern Agents

Scope: PC-15, PC-16, PC-17, PC-18, PC-19 and PC-21. AE observations below are from the [papercut register](../2026-09-26-papercut-register.md), not a source or live-state audit. Product rows describe documented behaviour, not an assertion that the same control exists in AE. Sources checked 27 September 2026.

## Behaviour: Show effective spend authority, distinguishing hard limits, alerts and unset limits (PC-15)

| Product | How it behaves | Official source URL |
|---|---|---|
| Ramp | A fund has a stated amount and renewal frequency; a separate maximum expense amount declines over-limit transactions. Merchant/category restrictions and active/lock dates further constrain use. The card/fund limit is not the entire business limit. | [Ramp card and fund controls](https://support.ramp.com/setting-up-controls-on-ramp-cards-and-funds/), [monitoring card and business limits](https://support.ramp.com/monitoring-card-and-business-limits) |
| Brex | A spend limit details who can spend, amount, currency, period, policy and reset. For eligible plans, the owner can allow users to see the amount and request an increase; optional flexibility can allow over-limit expenses subject to review. An optional budget amount is a planning field, not a spend-limit amount. | [Manage budgets and spend limits](https://www.brex.com/support/manage-budgets-and-spend-limits), [spend limits overview](https://www.brex.com/support/spend-limits-overview) |
| OpenAI API Platform | Project monthly spend can be an alert only (traffic continues) or a hard limit (requests fail with a named 429 code, subject to propagation lag). An organization hard limit can also apply, separately from a project limit and an OpenAI-assigned usage-tier limit. | [Spend limits](https://developers.openai.com/api/docs/guides/spend-limits), [managing projects](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform) |

Familiar pattern: show each actual governing constraint with its scope, currency, reset and enforcement effect; distinguish **no cap configured**, **no value available**, **soft alert**, **hard cap**, and **no spend authority**. “Active” describes policy state, not an amount. An absent per-Call/daily/monthly field cannot responsibly be translated to “unlimited” without the governing contract. AE reason to differ: **AUD money and authority** require the effective Agent-, principal- and account-level relationship to be truthful for a proposed Quote/Call. This is a question about what is actually enforced, not a recommendation to adopt card-limit mechanics.

## Behaviour: Identify each Agent and key without exposing a secret (PC-18)

| Product | How it behaves | Official source URL |
|---|---|---|
| GitHub | A fine-grained PAT is given a token name, optional purpose description, owner, selected resources, permissions and expiry. Organization token inventory includes `token_id`, `token_name`, `token_last_used_at` (nullable) and expiry. GitHub recommends an App rather than a person's PAT for long-lived organizational integration. | [Managing personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), [organization PAT REST API](https://docs.github.com/en/rest/orgs/personal-access-tokens) |
| Stripe | Restricted keys have editable names/notes, environment-specific `rk_test_`/`rk_live_` prefixes and per-resource permissions; Stripe recommends a separate named key per service/use case. A live key created by the customer cannot be revealed again; its per-key request logs can establish activity, but the cited guide does not promise a last-used timestamp in the key list. | [Restricted API keys](https://docs.stripe.com/keys/restricted-api-keys), [API keys](https://docs.stripe.com/keys) |
| OpenAI API Platform | The project-key inventory contract includes stable `id`, name, redacted value, nullable `last_used_at`, owner, owner-project-access state, creation and expiry; the secret itself is not reproduced by that list. Project keys belong to a project, and service accounts have an identifiable name/ID. | [List project API keys](https://developers.openai.com/api/reference/java/resources/admin/subresources/organization/subresources/projects/subresources/api_keys/methods/list), [managing projects](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform) |

Familiar pattern: human purpose/name plus stable **non-secret** identifier or redacted credential fingerprint, environment, owner/scope and activity time where actually collected; distinguish “never used”, “not recorded” and a real date. Names alone are not unique (Stripe's duplicated key inherits the source name), and a key prefix such as `rk_live_` identifies type/environment, **not** one credential. AE reason to differ: **authority** distinguishes the Agent identity, connection and key generation; its display identifier must disambiguate them without rendering recoverable secret material. Which stable reference/fingerprint AE may safely show remains a design question.

## Behaviour: Revoke the intended credential, not merely the similarly named Agent (PC-19)

| Product | How it behaves | Official source URL |
|---|---|---|
| GitHub | Delete is an action beside the particular PAT in its token list; deletion may also delete a deploy key created with it. Organization owners can separately revoke a token's **organization access**, which is narrower than deleting the owner's token. The guide does **not** specify a confirmation dialog naming token ID. | [Deleting a PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#deleting-a-personal-access-token), [reviewing and revoking organization access](https://docs.github.com/en/organizations/managing-programmatic-access-to-your-organization/reviewing-and-revoking-personal-access-tokens-in-your-organization) |
| Stripe | A selected key's overflow menu offers Expire key, followed by an Expire key/Cancel dialog; expiry stops callers using **that key**. Rotation creates a replacement and can delay old-key expiry to permit migration. A duplicate can carry the same name, so a name-only confirmation is insufficient for AE's reported duplicate case; the docs do not attest to Stripe's dialog showing a fingerprint. | [Expire and rotate API keys](https://docs.stripe.com/keys#expire-an-api-key), [restricted key duplication](https://docs.stripe.com/keys/restricted-api-keys#create-a-restricted-api-key) |
| OpenAI API Platform | The project-key inventory gives each key an ID and redacted value; project-key deletion targets a **project ID and key ID** and returns that key ID with `deleted: true`. The documented endpoint returns an error for a service-account-owned key; this establishes object-specific targeting, not any undocumented dashboard confirmation wording. | [List project API keys](https://developers.openai.com/api/reference/java/resources/admin/subresources/organization/subresources/projects/subresources/api_keys/methods/list), [delete project API key](https://developers.openai.com/api/reference/ruby/resources/admin/subresources/organization/subresources/projects/subresources/api_keys/methods/delete) |

Familiar pattern: select one stable credential record; before a destructive action disclose the **same unique record**, its safe identifier, scope/environment and affected callers. Distinguish revoking a key, withdrawing a grant, and disabling an Agent. A confirmation step alone is not protection if every confirmation names only “Agentic Economy CLI.” AE reason to differ: **authority** may have multiple key generations and caller refs under one Agent; impact and target must follow the actual revocation primitive, not the display name. No cited product proves its modal includes a fingerprint; exact-dialog wording here is a safety inference from the duplicate-name risk, not a borrowed UI claim.

## Behaviour: A connect/create-key CTA opens the promised next step (PC-17)

| Product | How it behaves | Official source URL |
|---|---|---|
| GitHub | The documented fine-grained PAT creation path ends with Generate new token. GitHub also supplies a `/settings/personal-access-tokens/new` URL that **pre-fills** name, owner, expiry and permissions, validating combinations in the form; this is a direct entry to the creation form, not automatic issuance. | [Fine-grained PAT creation and pre-filled URLs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#pre-filling-fine-grained-personal-access-token-details-using-url-parameters) |
| Stripe | From API keys the specific **Create restricted key** command leads to a permission/name form, then verification and one-time secret reveal. A duplicate-key action carries existing permissions into the creation flow; it does not silently produce an unrestricted secret. | [Create a restricted API key](https://docs.stripe.com/keys/restricted-api-keys#create-a-restricted-api-key) |
| OpenAI API Platform | In the selected project's API Keys settings, **+ Create new secret key** opens key creation; users choose key permissions on creation and see the service-account secret once. | [Manage project API keys](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform#how-do-i-manage-api-keys-within-my-organizations-projects), [save a service-account key](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform#save-the-service-account-api-key) |

Familiar pattern: if the action says “Create/Issue key,” land on the creation step (after any required auth), not another page with the same CTA; if it says “Connect an Agent,” either start a genuine connect flow or use wording that accurately describes the first step. Issuance remains explicit with permissions, identity and one-time-secret handling. AE reason to differ: **authority** might make “connect” more than issuing a key (approval/funding/harness installation); that warrants an honest staged flow, not a fake one-click promise. The register observes Connect an Agent → key-list page → Issue Agent key.

## Behaviour: Explain team invitation permission and blocked states (PC-16)

| Product | How it behaves | Official source URL |
|---|---|---|
| Vercel | The member invitation form accepts email and a role, can assign project roles, and lists pending/expired invitations separately. Its guide explicitly marks “Inviting new team members” as permission-required; owners manage membership. An invitee is not a member until acceptance. | [Managing team members](https://vercel.com/docs/rbac/managing-team-members), [access roles](https://vercel.com/docs/rbac/access-roles) |
| Linear | Settings → Administration → Members → Invite takes email, role on paid plans and optional teams. On paid plans only admins invite by default; an admin may enable “Allow users to send invites.” On Free all members are admins. SAML/SCIM workspaces can use IdP/JIT and SCIM provisioning; manual guest invitations remain possible. | [Invite members](https://linear.app/docs/invite-members), [members and roles](https://linear.app/docs/members-roles) |
| OpenAI API Platform | Organization owners can manage users, while project owners add users to their projects. An external invitee must join the organization before being added to a project; a missing or archived target project is a documented invitation error condition. | [Managing projects and member roles](https://help.openai.com/en/articles/9186755-managing-projects-in-the-api-platform) |

Familiar pattern: a visible invite entry matches actor permission and actual scope; when unavailable, explain **which role, plan, parent membership or provisioning mode** is required, with the appropriate next action. Do not present instructional “Invite someone” copy to an owner with no usable affordance without explaining why. AE reason to differ: **authority** means member invitation, Agent authorization and ownership delegation are different grants; never suggest inviting a teammate confers spend authority unless that is the real contract. Whether the observed `canInvite` is false because of entitlement or broken mapping is not established by references.

## Behaviour: Tell a newcomer what setup is available in this release (PC-21)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe | The keys guide explicitly separates sandbox keys/objects (`rk_test_` etc.) from live keys/objects (`rk_live_` etc.), says sandbox operations are simulated rather than live charges, and supplies a separate go-live checklist. Operational API availability therefore does not imply a customer is live for payments. | [API keys: sandbox versus live mode](https://docs.stripe.com/keys#sandbox-versus-live-mode), [go-live checklist](https://docs.stripe.com/get-started/checklist/go-live) |
| Linear | Its Agents guide is headed **Developer Preview**, says APIs may change before general availability, then gives app setup/install steps. It explicitly states installation requires workspace admin permissions and describes where the agent can be used. Documentation can contain working installation steps without claiming GA. | [Linear Agents getting started](https://linear.app/developers/agents) |
| GitHub | Fine-grained PAT docs disclose unsupported use cases and that organization approval may leave a generated token **pending**, able to read public resources only. The setup guide does not equate creation of a credential with approved access to all resources. | [Fine-grained PAT limitations and approval](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token) |

Familiar pattern: state **environment, rollout/eligibility, prerequisite, currently supported step and blocked step** beside setup instructions; distinguish service uptime from admission, account funding and live purchase eligibility. “Operational” on status cannot promise access for a new account. AE reason to differ: **x402 settlement and AUD authority** distinguish installing an MCP connector, authenticating, funding, obtaining an AUD Quote and making a paid Call; release language must identify which transitions are open without promising a live paid flow. The register reports `/for-agents` install instructions, FAQ saying public access/funding/purchases are not open, and `/status` saying API/new Calls operational; references cannot determine AE's actual release scope.

## Anti-patterns mature products avoid

- A generic **Active** badge or dash in lieu of explicit policy scope and enforcement: OpenAI separates spend alerts from hard limits and their error consequences; Brex and Ramp expose amount/period/controls ([OpenAI](https://developers.openai.com/api/docs/guides/spend-limits), [Brex](https://www.brex.com/support/manage-budgets-and-spend-limits), [Ramp](https://support.ramp.com/setting-up-controls-on-ramp-cards-and-funds/)).
- Name as sole credential identity, secret re-exposure, or confusing a non-unique type prefix with a fingerprint: GitHub's inventory has a token ID and last-used timestamp; OpenAI's project inventory has ID plus redacted value; Stripe treats customer-created live secrets as one-time reveals ([GitHub](https://docs.github.com/en/rest/orgs/personal-access-tokens), [OpenAI](https://developers.openai.com/api/reference/java/resources/admin/subresources/organization/subresources/projects/subresources/api_keys/methods/list), [Stripe](https://docs.stripe.com/keys)).
- Treating a disabled/missing invitation control or a status-page health check as an explanation of the user's permissions/release eligibility: Linear documents invite restrictions and identity-provider mode; Stripe documents sandbox/live separation ([Linear](https://linear.app/docs/invite-members), [Stripe](https://docs.stripe.com/keys#sandbox-versus-live-mode)).

## Questions the references raise for AE

1. **Effective authority (PC-15):** Are absent Per Call/Daily/Monthly figures intentionally uncapped, unknown to this projection, or inherited from another principal/account control? Which of those actually rejects a Quote or Call, and what label shows the *effective* restriction? OpenAI demonstrates why “alert” and “hard cap” cannot share a label ([source](https://developers.openai.com/api/docs/guides/spend-limits)).
2. **Agent versus credential identity (PC-18/19):** Which non-secret stable Agent ID, key generation/ref, redacted fingerprint and last-use signal may be shown to owners, and what scope does revocation actually remove? Separate key and Agent names rather than inventing uniqueness. GitHub and OpenAI inventory contracts give the analogue, but cannot define AE's key material ([GitHub](https://docs.github.com/en/rest/orgs/personal-access-tokens), [OpenAI](https://developers.openai.com/api/reference/java/resources/admin/subresources/organization/subresources/projects/subresources/api_keys/methods/list)).
3. **Connect meaning (PC-17):** Does the homepage CTA promise key issuance, connector installation, or an end-to-end funded Agent capable of buying? Direct-to-form and honest staged setup are both documented patterns; the AE release contract chooses between them ([GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#pre-filling-fine-grained-personal-access-token-details-using-url-parameters), [Linear](https://linear.app/developers/agents)).
4. **Team invitations (PC-16):** Which AE roles may invite, and must unavailable invitations be explained as role restriction, unavailable feature, or external provisioning? Linear's answer depends on plan/security mode; that fact cannot settle AE's role contract ([source](https://linear.app/docs/invite-members)).
5. **Release scope (PC-21):** Which of MCP install, sign-in, Agent/key issuance, funding, Quote and real purchase is supported **for a new outside account now**? Is `/status` scoped to service uptime while docs describe public eligibility? Stripe's sandbox/live boundary and Linear's Developer Preview label show different honest answers, not AE's actual state ([Stripe](https://docs.stripe.com/keys#sandbox-versus-live-mode), [Linear](https://linear.app/developers/agents)).

Cross-group boundaries: effective Agent budget presentation touches **G4** Quote/Call spend and exact money records; Agent key/connection permissions touch **G7** CLI/MCP onboarding; release and availability claims touch **G8** operational status and **G1/G2** callable supply claims. Those groups must agree on one truth for each scope; this study makes no product decision for them.
