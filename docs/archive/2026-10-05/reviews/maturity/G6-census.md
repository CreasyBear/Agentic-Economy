The existing CLI test explicitly expects no `request create` continuation (`tests/unit/market-terminal/cold-loop.test.ts:142-156`). Across surfaces, **no automatic alert** is established: request status recomputes canonical search on an explicit status read; its action states checking does not notify or call (`src/modules/market-demand/market-demand.actions.ts:310-415,531-540`).
- Source owner and adapters: `marketDemand.record` is a bounded 1–200-character phrase plus idempotency key (`src/modules/market-demand/market-demand.actions.ts:14-18,55-77`); the service checks exact-credential replay before search, refuses matched, degraded, incomplete or paginated results, then signs a Convex mutation (`:218-265`). Tests: `tests/unit/convex/market-demand-signals.test.ts` (ownership, replay, concurrency), `tests/unit/market-demand/market-demand-actions.test.ts` (matching, expiry, incomplete pages), `tests/unit/server/market-demand-api.test.ts`, `tests/unit/server/mcp-api-market-demand.test.ts`, `tests/unit/market-terminal/request-memory.test.ts`.

- Status-quo challenge: a mature product should not imply Notify when no notification mechanism exists. A hidden authenticated command can store a need but does not make the public browser buyer's missing need recoverable; retaining raw phrases beyond match eligibility raises a separate lifecycle choice.
- Candidate disposition: **redesign**, contingent on Joel's authority, consent and expiry choices. Value: intuitive next action, safer honest scope and maintainable one canonical no-match boundary; do not silently wire a public read to a write.

## Hard questions for Joel
1. **What may a no-match user actually save?** Options: (a) keep authenticated Agent-only exact-credential requests and show a clear connect/request-create handoff, (b) add buyer-account web retention with explicit consent and account-owned storage, (c) keep public no-match read-only and accept that this release cannot retain a public buyer's unmet need. Source cannot determine the intended buyer identity, consent and authority boundary (`market-demand.actions.ts:419-459`; `AeX402Directory.tsx:423`).
2. **What does “later matched” promise?** Options: (a) explicit `request status` polling only (rename any Notify language), (b) opted-in notifications with delivery/withdrawal ownership, (c) merely record aggregate demand without buyer follow-up. No notifier is in this path; current status re-searches on demand and returns up to three current choices (`market-demand.actions.ts:343-354,397-415`).
3. **What happens to expired phrases?** Options: (a) remove/erase raw phrase automatically at 30 days while preserving minimal dedupe receipt, (b) keep private expired history with explicit stated retention period, (c) change matching window and retention together. Current 30-day check affects match eligibility, while list permits expired rows and storage has no TTL (`market-demand.actions.ts:339-342,495-503`; `internal/convex-schema.ts:16-32`).
4. **What is the repeat-selection contract?** Options: (a) browser-only Saved Tools with clear scope, (b) buyer-account synced favourites and freshly resolved Tool facts, (c) agent-portable explicit shortlist/export independent of browser. Source proves only local snapshots; no identity or multi-harness persistence policy is specified (`DirectorySavedTools.tsx:86-99,124-180`; `AeX402Directory.tsx:344-355`).
5. **How should exhausted search guide people without claiming absent supply?** Options: (a) read-only broaden/query suggestions only, (b) show an authenticated opt-in retained-demand handoff after an exhaustive credible no-match, (c) omit retention from search and explain the separate command elsewhere. Current `next` is intentionally public/read-only, and incomplete/degraded searches refuse storage (`next-action.ts:8-17`; `market-demand.actions.ts:251-258`).
