# G5 reference — Publish and earn

Scope: PC-03 (first Tool), PC-26 (earnings/payouts), PC-29 (Agent Plugin source feedback). AE's current-behaviour statements below come only from the [papercut register](../2026-09-26-papercut-register.md), not a fresh source or live Provider audit. References describe documented behaviour, not a verified AE payout or publication. Rapid's current creation flow is **Studio / My APIs**, despite older documentation referring to the Provider Dashboard.

## Behaviour: A first-run seller reaches the actual creation flow, with a recoverable prerequisite (PC-03)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe Connect onboarding | A platform sends its connected account directly into hosted onboarding via a single-use Account Link, or embeds account onboarding. An expired/used link has a refresh route; returning from onboarding does **not** prove completion, so the platform checks outstanding requirements and offers a continue path. | [Stripe — Onboard your connected account](https://docs.stripe.com/connect/marketplace/tasks/onboard) |
| App Store Connect | The Apps page is blank until the first app exists, but its **+ → New App** creates the record; Apple names the latest-agreement prerequisite, required role and missing-information feedback. The resulting record is **Prepare for Submission**, not published. | [Apple — Add a new app](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app/) |
| RapidAPI Studio | **My APIs → Add API Project** opens the creation dialog directly, with name, description, category, owner and optional spec import. Creation leads to the project's **Hub Listing**; it does not imply public visibility. | [Rapid — Adding APIs: Getting Started](https://docs.rapidapi.com/docs/add-api-getting-started), [Rapid — OpenAPI document visibility](https://docs.rapidapi.com/docs/adding-and-updating-openapi-documents) |
| Shopify Dev Dashboard | **Apps → Create app** starts creation; the documented dashboard-created app then gets a version, dev-store installation and authentication. Shopify explicitly says App Store-targeted apps should instead start with its CLI. Partner payouts live in a separate Partner Dashboard with an explicit task map. | [Shopify — Create apps using the Dev Dashboard](https://shopify.dev/docs/apps/build/dev-dashboard/create-apps-using-dev-dashboard), [Shopify — Dashboard task map](https://help.shopify.com/en/partners/manage-account/dashboard) |

**Familiar pattern:** A creation CTA enters the next actionable step; when prerequisite or permissions block it, name the requirement, its owner and the resumable action. A return or record creation is a stage, not proof of a published offer. AE's register says public **Add Tool** currently lands on an unavailable `/owner/operations/new` waypoint and requires inferring a return to identity setup. That differs from the documented direct-entry/resume pattern.

**AE reason to differ:** Provider identity/authority and Tool admission may require stages before publication; the Tool/Quote/Call contract means an imported source is not automatically callable. Neither justifies an unexplained dead end. Whether **Add Tool** should begin identity setup, source entry or a staged checklist is a product decision, not settled by these references.

## Behaviour: A Provider reconciles earnings, balance, transfers and payout state (PC-26)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe Connect Express Dashboard | Connected accounts see net-volume earnings, balance transactions **including charges, transfers and payouts**, available versus in-transit money, next payout date and optional payout actions; reports include payout reconciliation for automatic payouts. Feature availability is configurable, including manual payout access. | [Stripe — Express Dashboard](https://docs.stripe.com/connect/express-dashboard) |
| App Store Connect | **Payments and Financial Reports** distinguishes **Total Estimated Proceeds** from money **paid**; paid entries show bank suffix, issue date and bank-reference Transaction ID. Country/region breakdown includes tax, adjustment and exchange-rate facts. Returned payments show reason, required adjustment and reference. | [Apple — View payments and proceeds](https://developer.apple.com/help/app-store-connect/getting-paid/view-payments-and-proceeds/), [Apple — Payment information fields](https://developer.apple.com/help/app-store-connect/reference/reporting/payment-information/) |
| RapidAPI Studio | Provider **Analytics → Revenue Analytics** breaks down monetized income by fixed price and overages. **Monetize → Transactions** exposes payout status; actual provider payouts depend on collected buyer payment and later settlement, with fees/refunds/disputes described separately. | [Rapid — Provider Analytics](https://docs.rapidapi.com/docs/provider-analytics), [Rapid — Monetize tab](https://docs.rapidapi.com/docs/hub-listing-monetize-tab), [Rapid — Payouts and Finance](https://docs.rapidapi.com/docs/payouts-and-finance) |
| Shopify Partner Dashboard | Partner **Payouts** lists regular payments and lets a partner open a date range for net line items, fees and taxes, filter activity, export CSV and retry a **failed** payout after checking payment details. The dashboard separates payout view from app-building metrics. | [Shopify — Manage your payouts](https://help.shopify.com/en/partners/manage-account/manage-payouts-invoices/payouts), [Shopify — Dashboard task map](https://help.shopify.com/en/partners/manage-account/dashboard) |

**Familiar pattern:** Make economic facts visible in the Provider's normal work area or in a clearly linked finance view: earned/estimated, available, transferred, paid/failed, dates, currency, fees and durable payout references are distinct. Show only actions the Provider is entitled to perform; a connection-status badge is not an earnings statement. AE's register reports the workspace currently passes only a boolean into its ready earnings sheet while a richer earnings card has no consumer; this is a source finding, not an observed payout.

**AE reason to differ:** AE's AUD buyer charge, Provider obligation, transfer evidence and Stripe payout may be different records and timelines. Present their relationship faithfully rather than relabeling an upstream x402 payment or a Stripe connection as Provider cash available for withdrawal. The references do not prescribe AE's payout schedule, transfer policy, or whether a manual payout action is appropriate.

## Behaviour: Validation feedback says what was checked, not what is approved (PC-29)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe Connect | Embedded onboarding reads account-specific requirements and provides localized field validation/error states; even after a return redirect, the platform must inspect account requirements/capability status. Verification may introduce further requirements or take time. | [Stripe — Onboard your connected account](https://docs.stripe.com/connect/marketplace/tasks/onboard) |
| App Store Connect | Creating an app record yields **Prepare for Submission**; adding a version for review yields **Ready for Review**, while **Submit for Review**, review and distribution are separate steps. Rejected submissions expose **Unresolved Issues** and an edit/remove/resubmit path. | [Apple — Add a new app](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app/), [Apple — Submit an app](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/submit-an-app), [Apple — Resolve review issues](https://developer.apple.com/help/app-store-connect/manage-submissions-to-app-review/manage-a-submission-with-unresolved-issues) |
| RapidAPI Studio | Its endpoint editor labels a syntactically parsable JSON example **Valid example** in the context of that example; separate guidance recommends validating an OpenAPI document before upload and notes unsupported remote `$ref` imports. Importing a spec populates endpoint definitions, not proof that the underlying API works. | [Rapid — Hub Listing Definitions](https://docs.rapidapi.com/docs/hub-listing-definitions-tab), [Rapid — Adding and Updating OpenAPI Documents](https://docs.rapidapi.com/docs/adding-and-updating-openapi-documents) |
| Shopify app review | A newly created public app is **Draft**. The seller must resolve issues identified on the review page before submitting; after submission Shopify may **Pause** review for core failures, then require **Submit fixes**. Only approval yields **Published**. | [Shopify — App review process](https://shopify.dev/docs/apps/launch/app-store-review/review-process) |

**Familiar pattern:** Scope feedback to the evidence: “JSON parses” or “basic fields present” is not “source preview passed”, “eligible for publication” or “published”. Expose authoritative preview/review errors with a correction route and distinguish pending/blocked/approved. AE's register says an empty `mcpServers` object can receive **Valid JSON payload** after a shallow shape check but fail server preview as `agent_plugin_remote_missing`. The later server correction exists; the earlier claim is broader than its check.

**AE reason to differ:** The server must decide source admissibility and callable Tool status under AE's authority and Tool/Quote/Call contract; local feedback may accelerate correction but cannot certify a remote MCP server, execution, x402 settlement or publication. No reason to use a stronger validity badge than the performed check.

## Anti-patterns mature products avoid

- A success-like return or account-created state masquerading as completed onboarding: Stripe explicitly says the return URL conveys no completion state; Apple calls an initial app record **Prepare for Submission**. [Stripe](https://docs.stripe.com/connect/marketplace/tasks/onboard), [Apple](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app/).
- Conflating sales/estimated earnings with cash sent, or hiding failed payout remediation behind a generic connection badge: Apple distinguishes estimated versus paid and shows returned-payment reasons/references; Shopify shows failed status and retry; Stripe differentiates available, in transit and upcoming. [Apple](https://developer.apple.com/help/app-store-connect/getting-paid/view-payments-and-proceeds/), [Shopify](https://help.shopify.com/en/partners/manage-account/manage-payouts-invoices/payouts), [Stripe](https://docs.stripe.com/connect/express-dashboard).
- Calling format checks publication approval: Rapid's “Valid example” concerns an example body; Shopify's Draft/Submitted/Paused/Published and Apple's Ready/In Review/Rejected are separate stages. [Rapid](https://docs.rapidapi.com/docs/hub-listing-definitions-tab), [Shopify](https://shopify.dev/docs/apps/launch/app-store-review/review-process), [Apple](https://developer.apple.com/help/app-store-connect/reference/app-information/app-and-submission-statuses).

## Questions the references raise for AE

1. What should **Add Tool** do for an unestablished Provider: open identity setup, open a source draft with identity deferred, or a guided multi-stage entry? Which states can be saved/resumed, and where does authority block progress? Stripe supports incremental/up-front requirements; Apple gates app creation on agreement; neither selects AE's ordering. [Stripe](https://docs.stripe.com/connect/marketplace/tasks/onboard), [Apple](https://developer.apple.com/help/app-store-connect/create-an-app-record/add-a-new-app/).
2. What exact Provider money states and entitlements should the workspace expose: obligation earned, transfer initiated/settled, Stripe balance, payout issued/returned; is manual payout ever Provider-controlled? Stripe makes manual payouts configurable, while Apple's payout is scheduled and its amount can change. [Stripe](https://docs.stripe.com/connect/express-dashboard), [Apple](https://developer.apple.com/help/app-store-connect/getting-paid/overview-of-receiving-payments).
3. Which level of source feedback is worthwhile before authoritative preview: parse-only label, local structural hints, or immediate server preview on request? How should server refusal/error become the editable field or next action without promising a callable Tool? Rapid separates example syntax and spec import, Shopify separates review blockers from publication. [Rapid](https://docs.rapidapi.com/docs/hub-listing-definitions-tab), [Shopify](https://shopify.dev/docs/apps/launch/app-store-review/review-process).
4. Should earnings live directly in the Provider workspace, in a dedicated finance view reached by a clear link, or both? Stripe places finance in Express; Shopify separates Dev and Partner dashboards but publishes a task map. Access and financial authority may differ in AE. [Stripe](https://docs.stripe.com/connect/express-dashboard), [Shopify](https://help.shopify.com/en/partners/manage-account/dashboard).

**Cross-group boundaries to retain:** G2 truthful choice needs admitted/callable Provider supply, not merely source import; G4 owns buyer charge/receipt and remedy while G5 owns Provider obligation/transfer/payout explanation; G3 authority determines which owner or Provider can enter onboarding or see/act on money; G8 review/exception operations may determine a source's admission status. These are boundary questions, not claims of shared AE source ownership.
