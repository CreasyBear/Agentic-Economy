# G8 reference — Operate and maintain

Reference scope: PC-27 (exception queue), PC-28 (approval expiry and ordering), PC-37 (dependency-gate comment). AE observations below are **register claims**, not a fresh source or live-admin census: [papercut register](../2026-09-26-papercut-register.md#highest-priority-register). These references describe external contracts, not evidence that AE already implements them.

## Behaviour: Reach every actionable exception without mistaking a displayed cap for the entire queue (PC-27)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe Radar | The open-reviews API returns only `open: true` records, newest-created first; `limit` is 1–100 and `starting_after`/`ending_before` allow continuation beyond that page. Dashboard list and detail views let reviewers inspect payment context, navigate between reviews and filter owned or unassigned work. | [Review list API](https://docs.stripe.com/api/radar/reviews/list), [review queue](https://docs.stripe.com/radar/transaction-reviews) |
| Zendesk Support | Ticket views are condition-based worklists. The tickets-in-view API recommends cursor pagination; the separate view-count API estimates backlog without fetching all rows, but large counts may be cached for 60–90 minutes and expose `fresh`/`value` metadata. | [Views: list tickets and count](https://developer.zendesk.com/api-reference/ticketing/business-rules/views/#list-tickets-from-a-view), [view count](https://developer.zendesk.com/api-reference/ticketing/business-rules/views/#count-tickets-in-view) |
| GitHub pull requests | Review-status filters distinguish unreviewed, review-required and requested-reviewer PRs; search can order oldest or newest. Its REST PR list exposes `per_page` (maximum 100) **and** `page`, rather than ending access at the first 100. | [Filtering/searching PRs](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests), [list PRs API](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests) |
| Convex | The documented backend-native mechanism is a cursor-paginated query using `paginationOptsValidator` and `.paginate()`; React's `usePaginatedQuery` supplies `loadMore` and explicit `CanLoadMore`/`Exhausted` states. The paginated query remains reactive, so page sizes can change as work is added or removed. | [Paginated queries](https://docs.convex.dev/database/pagination) |

**Familiar pattern:** Keep pages bounded, expose a reachable next page (or explicit exhausted state), distinguish page size from overall backlog, and scope counts to the same actionable population as the list. Stripe does not promise an overall count in its open-review list; Zendesk calls its view count an estimate, not an exact immediate invariant. [Stripe API](https://docs.stripe.com/api/radar/reviews/list), [Zendesk count contract](https://developer.zendesk.com/api-reference/ticketing/business-rules/views/#count-tickets-in-view), [Convex pagination](https://docs.convex.dev/database/pagination).

**AE reason to differ:** Operator authorization and case visibility must remain bound to AE's authority boundary; no AUD, Tool/Quote/Call or x402 reason supports an unreachable 101st exception. The register reports “oldest 100 of N” with no continuation and a 107-case test returning 100; neither the reference nor that test establishes real backlog volume. [Register PC-27](../2026-09-26-papercut-register.md#highest-priority-register).

## Behaviour: Represent expiry honestly and keep live approvals reachable (PC-28)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe Radar | Its open review is a distinct object with `open` and a closing reason; a disputed payment automatically closes its Radar review. Radar does **not** document a general 24-hour automatic review expiry. For uncaptured payments, approval and capture are separate and the underlying authorization's capture window varies by payment method and card conditions. | [Review queue/actions](https://docs.stripe.com/radar/transaction-reviews), [review object](https://docs.stripe.com/api/radar/reviews/object), [auth and capture](https://docs.stripe.com/radar/reviews/auth-and-capture) |
| Zendesk Support | SLA views can show time until the next target breaches and order by SLA ascending; breached targets remain visible with negative values, since a missed service target is not the same thing as a ticket ceasing to exist or being resolved. | [Using SLA policies](https://support.zendesk.com/hc/en-us/articles/5604663490458-Using-SLA-policies), [ticket views](https://support.zendesk.com/hc/en-us/articles/4408888828570-Creating-views-to-build-customized-lists-of-tickets) |
| GitHub pull requests | Review worklists filter on open PR/review-request state; separately, protected-branch settings may dismiss a previously valid approval if the reviewed diff changes, requiring fresh approval rather than treating the old approval as current. This is *staleness of authority*, not a timed expiry rule. | [PR review-status filters](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests), [stale-approval rule](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging) |
| Convex | `ctx.scheduler.runAt` schedules a durable function at a deadline; scheduling inside a mutation is atomic with that mutation, while scheduling from an action is not. Internal scheduled mutations are executed exactly once under the documented scheduler error model; periodic cleanup can instead use `convex/crons.ts`, but an overlong cron run can cause the next run to be skipped. | [Scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions), [cron jobs](https://docs.convex.dev/scheduling/cron-jobs) |

**Familiar pattern:** Separate **deadline**, **actionability now**, and **recorded terminal status**. A time-sensitive approval must not remain apparently actionable simply because no reviewer has clicked it. An overdue SLA may instead remain open and escalated; the correct meaning of “expired” depends on the proposal's authority contract. A scheduled transition can materialize status, but a reader or action still needs deadline-aware eligibility if the scheduled job has not yet run. The last sentence is an engineering inference from Convex's scheduled/cron execution semantics, **not** a product decision or a documented guarantee of clock-exact execution. [Stripe review/capture](https://docs.stripe.com/radar/reviews/auth-and-capture), [Zendesk SLA](https://support.zendesk.com/hc/en-us/articles/5604663490458-Using-SLA-policies), [Convex scheduling](https://docs.convex.dev/scheduling/scheduled-functions), [Convex cron behavior](https://docs.convex.dev/scheduling/cron-jobs).

**AE reason to differ:** A 24-hour *approval authorization* may need a stricter fail-closed cutoff than a Zendesk SLA target or a Radar manual review. Whether expiry should leave a visible expired history, hide it from the actionable queue, or create an escalation queue is for Joel to decide. The register says pending-only reads sort by expiry, stop at 50, and mark expiry on attempted approval; it does not show a live Admin backlog. [Register PC-28](../2026-09-26-papercut-register.md#highest-priority-register).

## Behaviour: Put the next meaningful task first without starving later work (PC-27/28)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe Radar | The Dashboard calls its queue prioritized and offers assignment/ownership filters; **the separate API** documents newest-created-first ordering, not Dashboard risk ranking. Do not infer one order from the other. | [Dashboard review queue](https://docs.stripe.com/radar/transaction-reviews), [API list order](https://docs.stripe.com/api/radar/reviews/list) |
| Zendesk Support | A view specifies group/order columns and ascending/descending direction; an SLA view can prioritize the closest breach via SLA ascending. | [Views API execution](https://developer.zendesk.com/api-reference/ticketing/business-rules/views/#execution), [SLA policies](https://support.zendesk.com/hc/en-us/articles/5604663490458-Using-SLA-policies) |
| GitHub pull requests | Review filters can be combined with oldest-created or newest-created sorts; shared filtered URLs preserve the triage lens rather than imposing one universal queue order. | [PR filtering/sorting/sharing](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests) |
| Convex | `.withIndex(...).order(...).paginate(...)` is the documented shape for a filtered, ordered, cursor-based query; the framework handles continuation and reactivity, not the product's prioritization policy. | [Paginated queries and extra arguments](https://docs.convex.dev/database/pagination) |

**Familiar pattern:** Make the sort criterion legible and match it to the task: oldest unresolved for fairness, nearest *valid* deadline for expiring authority, or risk/ownership when those fields exist. Paginate over the same filtered order; avoid presenting 50 already-inactionable rows as the 50 urgent approvals. Those are design implications of the cited products, not a claim that AE currently has risk scores or assignments. [GitHub sorting](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests), [Zendesk SLA](https://support.zendesk.com/hc/en-us/articles/5604663490458-Using-SLA-policies), [Convex pagination](https://docs.convex.dev/database/pagination).

**AE reason to differ:** A case tied to real AUD movement, x402 delivery uncertainty, or authority loss could demand a different operational priority; no referenced product determines that AE policy. [Register G8](../2026-09-26-papercut-register.md#grouped-register-customer-promise-and-failure-pattern).

## Behaviour: Keep dependency-gate explanations consistent with what the gate enforces (PC-37)

| Product | How it behaves | Official source URL |
|---|---|---|
| dependency-cruiser | Its `comment` field explains a rule but is **not used in rule logic**. The `severity` and conditions such as `circular` govern findings; `error` can make the `err` reporter exit nonzero. A comment about grandfathered cycles cannot override an active zero ceiling. | [Maintained rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md) |
| ESLint | Rule severity `warn` reports without affecting exit code, while `error` exits nonzero. Configuration comments may carry explanations, but config determines enforcement; unused inline configurations can be reported. | [Rule configuration/severities](https://eslint.org/docs/latest/use/configure/rules) |
| GitHub protected branches | Required status checks must pass before merge; the effective branch protection configuration and check results, rather than a source-code comment describing them, determine the merge gate. | [Required status checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-status-checks-before-merging) |

**Familiar pattern:** Treat the executable rule and observed check result as authority; align or delete obsolete commentary instead of creating a new enforcement layer merely to make an old statement true. This is a documentation-maintainability issue, not evidence of live dependency cycles. [dependency-cruiser rules](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md), [register PC-37](../2026-09-26-papercut-register.md#highest-priority-register).

**AE reason to differ:** None for the comment. The register reports the ratchet passed with zero cycles and a zero ceiling; it does not justify reintroducing a 48-cycle exception. [Register PC-37](../2026-09-26-papercut-register.md#highest-priority-register).

## Anti-patterns mature products avoid

- A hard list cap with no reachable continuation, while calling a larger count the backlog: Stripe, Zendesk, GitHub and Convex all distinguish bounded pages from the complete filtered result set. [Stripe](https://docs.stripe.com/api/radar/reviews/list), [Zendesk](https://developer.zendesk.com/api-reference/ticketing/business-rules/views/#list-tickets-from-a-view), [GitHub](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests), [Convex](https://docs.convex.dev/database/pagination).
- Treating a breached service target as a closed case, or a closed/expired authorization as still approvable: Zendesk displays SLA breaches for action; Stripe distinguishes open from closed reviews and authorization from capture. [Zendesk](https://support.zendesk.com/hc/en-us/articles/5604663490458-Using-SLA-policies), [Stripe](https://docs.stripe.com/radar/reviews/auth-and-capture).
- Calling a possibly cached backlog count exact or equating it to the rows already loaded. [Zendesk](https://developer.zendesk.com/api-reference/ticketing/business-rules/views/#count-tickets-in-view), [Convex](https://docs.convex.dev/database/pagination).
- Relying on a scheduler alone to define immediate authorization eligibility, or claiming a recurring sweep is guaranteed to execute on every tick: Convex documents the durable one-time scheduler, distinct mutation/action atomicity and skippable overlapping cron runs. [Scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions), [cron jobs](https://docs.convex.dev/scheduling/cron-jobs).
- Treating a dependency-cruiser `comment` as a policy control when executable rule severity/conditions and the gate result disagree. [Rules reference](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md).

## Questions the references raise for AE

1. **Expired proposal semantics:** After 24 hours, is the request permanently unapprovable and retained as an expired audit/history record, eligible for an explicitly renewed proposal, or merely SLA-overdue but still valid? Stripe's reviews and Zendesk's breached SLAs deliberately differ; only AE's authority policy can choose. [Stripe](https://docs.stripe.com/api/radar/reviews/object), [Zendesk](https://support.zendesk.com/hc/en-us/articles/5604663490458-Using-SLA-policies), [register PC-28](../2026-09-26-papercut-register.md#highest-priority-register).
2. **Queue membership and count:** Should Admin see only currently actionable items with a separate expired/history lens; all pending including expired but disabled; or a combined list with clear status? Should its badge mean exact eligible total, estimated total with freshness, or only displayed rows? Zendesk distinguishes approximate count; Stripe's API only lists open reviews. [Zendesk](https://developer.zendesk.com/api-reference/ticketing/business-rules/views/#count-tickets-in-view), [Stripe](https://docs.stripe.com/api/radar/reviews/list).
3. **Priority and escalation:** For AE exceptions and approvals, should default order be oldest-first, earliest *still-valid* deadline, authority/financial risk, or distinct saved views? Should overdue-but-unresolved exceptions escalate rather than disappear? References offer different lenses, not AE's policy. [Stripe](https://docs.stripe.com/radar/transaction-reviews), [Zendesk](https://support.zendesk.com/hc/en-us/articles/5604663490458-Using-SLA-policies), [GitHub](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/filtering-and-searching-issues-and-pull-requests).
4. **Expiry materialization:** Does AE need a materialized transition at the proposal deadline (with scheduled mutation and retry-aware idempotent status check), a periodic sweep for audit/history cleanup, or deadline-aware reads/actions plus background reconciliation? Convex supports one-time and recurring scheduling, but does not choose the product's freshness/observability requirement. [Scheduled functions](https://docs.convex.dev/scheduling/scheduled-functions), [cron jobs](https://docs.convex.dev/scheduling/cron-jobs).

**Cross-group boundary to check at design:** G3 owns spending/approval authority and actor identity; G4 owns money exception/Call remedy facts; G5 owns Provider consequence/recovery. G8 queue pagination and expiry must not rewrite those owners' authorization or monetary state transitions. This is a boundary hypothesis from the register's group taxonomy, not a traced source-owner assertion. [Grouped register](../2026-09-26-papercut-register.md#grouped-register-customer-promise-and-failure-pattern).
