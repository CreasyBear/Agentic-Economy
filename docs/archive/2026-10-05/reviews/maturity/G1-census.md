## Search topology on main
- **Canonical admitted Tool search:** HTTP `POST /api/v1/market-tools/search` validates a 1–256-character query and passes to `registryToolsSearchAction` (`src/routes/api.v1.market-tools.search.ts:20-42`, `src/modules/registry/tool-choice-contracts.ts:48-55`, `src/modules/registry/tools.actions.ts:122-152`). Its source adapter calls `capabilityToolCatalog.search` (`src/modules/capability-supply/tool-source.ts:24-26`, `convex/capabilityToolCatalog.ts:91-118`); **the actual current-source query** uses Convex full-text search over `capabilityPublications.searchText` for nonempty queries and a `by_disposition` index for browse, filtering hydrated Tools and paginating at Convex (`convex/lib/capabilitySupply/tool/reads.ts:28-89`). The separate `searchCapabilityTools` helper in `src/modules/capability-supply/internal/tool-search.ts:203-294` is tested but not called by this runtime path. Coinbase/payai source options are separate (`convex/capabilityToolCatalog.ts:97-115`). Decision Gateway assesses only the fetched page (up to 20) and can return an unassessed original on outage (`src/modules/registry/tool-reranker.ts:105-130,255-321`). `projectToolSearchChoices` gates default health to operational (inspection-required exception) and emits `matched`, `degraded`, `noMatch`, or `unavailable` (`src/modules/registry/tool-choice-contracts.ts:323-337,357-429`). Tests: `tests/unit/capability-supply/tool-projection-search.test.ts` (helper, not live Convex query), `tests/unit/registry/registry-tools-search-rerank.test.ts`, `tests/unit/registry/tool-reranker.test.ts`.
- **Adapters are not identical:** HTTP emits the whole validated envelope (`src/routes/api.v1.market-tools.search.ts:25-31`); MCP invokes the registered action, puts a short sentence in `content` and the full result plus next actions in `structuredContent` (`src/lib/server/mcp-api.ts:256-270,552-555`; `tests/unit/server/mcp-api-registry.test.ts`); CLI calls that HTTP route, preserves envelope in `--json`, prints fewer fields in plain mode (`tools/ae/commands/search.ts:9-42,79-99`; `tests/unit/market-terminal/cold-loop.test.ts`). Header/command-panel search consumes the same HTTP response but prioritises its `groups` projection over `kind` (`src/components/ae/command-panel/tools-search-page/useMarketToolSearch.ts:129-175`). Durable chat does **not** invoke the HTTP action: it calls `capabilityToolCatalog.searchInternal`, then `presentSearch`, constructs an assessment and projects the choice without the HTTP freshness/groups (`convex/lib/chat/tools/search.ts:58-115`; `convex/lib/capabilitySupply/toolCatalog/presentation.test.ts`). The public `/market` directory uses a separate Coinbase x402 directory index and reranker (`src/modules/market/market-route-data.ts:127-148`, `src/modules/market/x402-directory-index.server.ts:99-140`); its results are not proof of an admitted, callable Tool.

## PC-01 — Chat ends without a durable answer
- **Register claim on current main: holds for the recorded failure; preview fix is not on main.** Main can take a second `agent.streamText` pass after tool results, await its text, and return without checking that a substantive final assistant message was saved (`convex/lib/chat/generate/stream.ts:49-75`). On failure `run.ts` saves the generic stopped message; the UI's Retry resubmits the same prompt (`convex/lib/chat/generate/run.ts:84-113`, `src/components/ae/chat/chat-session/useChatSession.ts:497-503`). PR [#243](https://github.com/CreasyBear/Agentic-Economy/pull/243) was verified on **well-15 preview**, not release, with an admitted x402 web-search Tool, final answer/card and reload persistence (`docs/reviews/2026-09-26-papercut-register.md:72-78`). Do not treat a sandbox diagnostic, CI or this preview as production closure.
- **Surfaces:** Chat has the failing final-answer/retry path; web `/t/new` renders it. HTTP/MCP/CLI search produce their own result envelopes rather than this chat final answer (`src/routes/api.v1.market-tools.search.ts:20-42`, `src/lib/server/mcp-api.ts:552-555`, `tools/ae/commands/search.ts:37-55`). Tests: `tests/integration/chat-durable-messaging-share.test.ts:143-276`, `tests/integration/chat-scheduled-authority.test.ts`, `src/components/ae/chat/chat-session/useChatSession.test.ts:130-133`.
- **Root class: contract gap** (final answer durability and recovery, not search ranking). **Status-quo challenge:** a tool-result stream plus no usable answer is not a completed conversation; automatic resend after a possibly charged Call is not safe. **Candidate disposition: fix** for intuitive, safe recovery. **Draft:** `bb1ed8c` changes chat generation/recovery, retains CallRefs when effects exist, verifies final saved output and replaces retry with edit-question affordance; related chat tests change. This addresses PC-01 in source, but the PR #243 preview and the separate worktree commit are not a release verification; the 13-file dirty search diff does not replace the committed answer fix.

## PC-02 — Irrelevant degraded matches and phrasing-sensitive false no-match
- **Register claim on current main: holds.** The register observed nonsensical/task-specific needs returning irrelevant degraded choices and an admitted x402 web-search Tool falsely missed under one natural phrasing but found under another (`docs/reviews/2026-09-26-papercut-register.md:28,78`). Source explains possible mechanisms without proving which caused those specific live misses: the **current runtime** first searches the publication full-text index for supplied non-stop words (`convex/lib/capabilitySupply/tool/reads.ts:37-67`), so synonymous need phrasing can prevent a relevant Tool entering the fetched page; only that page is decision-assessed (`src/modules/registry/tools.actions.ts:129-143`); assessment outages return a `degraded` envelope with unassessed original candidates (`src/modules/registry/tool-reranker.ts:115-130`, `src/modules/registry/tool-choice-contracts.ts:400-416`). The unused in-memory `searchCapabilityTools` helper has a different lexical ranking policy (`src/modules/capability-supply/internal/tool-search.ts:80-128`); its unit results must not be mistaken for runtime proof. A no-match may mean this **page** only (`src/modules/registry/tool-choice-contracts.ts:402-409`). Separate Market directory ranking can also leave original results if ranking is unavailable (`src/modules/market/x402-directory-reranker.ts:24-55`).
- **Surfaces:** HTTP's envelope and MCP structured result expose `degraded` candidates; CLI prints “Unverified matches”; command-panel web can show unrelated `groups` even on `noMatch`; Market x402 directory remains a different search; chat independently scores a lexical page and suppresses scores below 0.5, so a false no-match can survive there (`src/lib/server/mcp-api.ts:256-269`, `tools/ae/commands/search.ts:84-97`, `src/components/ae/command-panel/tools-search-page/useMarketToolSearch.ts:138-167`, `convex/lib/chat/tools/search.ts:81-115`). Tests: `tests/unit/registry/registry-tools-search-rerank.test.ts:54-71,128-170`, `tests/unit/capability-supply/tool-projection-search.test.ts:150-180`, `tests/unit/registry/tool-reranker.test.ts`, `tests/unit/market/x402-directory-page.test.tsx`.
- **Root class: ranking.** **Status-quo challenge:** “degraded” cannot mean an unrelated choice is safe to recommend; nor does a lexical-page miss establish absent supply. **Candidate disposition: redesign** relevance/no-match semantics for safety and intuitiveness without pretending the two source inventories are the same. **Draft: partially addresses.** Its action fetches a bounded empty-query admitted pool and assesses all if at most 20 with no more pages; otherwise it falls back to lexical retrieval and marks no-match incomplete. Its prompt distinguishes task capability from asking for price/input/purchasability; unassessed candidates become typed unavailable; command-panel no longer turns a no-match with `groups` into success. But chat's independent path and Market x402 ranking are unchanged; a pool above 20 remains a lexical-page limitation, and no live task proof is in this census (`git diff` in the separate worktree: `src/modules/registry/tools.actions.ts`, `tool-reranker.ts`, `tool-choice-contracts.ts`, `useMarketToolSearch.ts`).

## PC-05 — Search payload consumes excessive agent context
- **Register claim on current main: holds for recorded MCP/HTTP byte observations, not an inferred token count.** The dated MCP weather sample was 39,416 bytes, of which 37,777 was `groups`; an impossible-filter no-match was still 11,574 bytes; HTTP limit-5 samples were 15,319–25,620 bytes (`docs/reviews/2026-09-26-papercut-register.md:31`). `registryToolsSearchAction` always reads and appends group listings, including directory and business catalogue projections, even after no-match (`src/modules/registry/tools.actions.ts:143-151`, `src/modules/registry/internal/listing-search.ts:73-106`). `groups` is in the strict public schema (`src/modules/registry/tool-choice-contracts.ts:184-212`). The small MCP text line does not remove the full `structuredContent`; HTTP emits that envelope, and CLI `--json` keeps it (`src/lib/server/mcp-api.ts:256-270,552-555`, `src/routes/api.v1.market-tools.search.ts:25-31`, `tools/ae/commands/search.ts:79-81`). Chat calls a different internal path and does not request these groups; the command-panel web **does** consume them (`convex/lib/chat/tools/search.ts:70-115`, `src/components/ae/command-panel/tools-search-page/useMarketToolSearch.ts:138-148`). Tests: `tests/unit/server/mcp-api-registry.test.ts`, `tests/unit/market-terminal/cold-loop.test.ts`, `src/components/ae/command-panel/tools-search-page/useMarketToolSearch.test.ts`.
- **Root class: presentation.** **Status-quo challenge:** an Agent asking for a bounded Tool choice should not pay context cost for a second, page-scoped listing universe; a compact MCP `content` sentence is not a compact MCP response. **Candidate disposition: redesign** response shape for performance and ergonomics, subject to the consumer contract. **Draft: partially addresses:** canonical `noMatch` and assessment-unavailable paths return before fetching groups; command-panel reads `kind` first. Matched/degraded responses still append `groups` and HTTP/MCP still carry them, so ordinary response weight is not solved.

## Hard questions for Joel
1. **What must “no match” mean?** (a) exhaustively assessed admitted inventory only; (b) no suitable candidate in this page with explicit continuation; (c) separate “cannot assess” when the decision service is down. Source proves these are different states but cannot choose the buyer-facing promise. How should a directory-only listing be labelled alongside them?
2. **Should canonical Tool search return non-admitted `groups` at all?** (a) split as a distinct browse operation; (b) only opt-in for web; (c) retain inside search but compact with explicit listing/callability labels. The recorded MCP/HTTP payload cost and web command-panel dependency do not decide the product contract.
3. **Should `GET /api/v1/registry` remain a public raw-metadata search?** (a) retain full metadata only in explicit detail/expand; (b) keep a compact external-directory listing; (c) delete/redirect the redundant entry point after checking real consumers. Route existence is not evidence of use frequency.
4. **Which freshness clock is authoritative for each choice?** (a) x402 index generation for Market/external registry and publication readiness for canonical admitted Tools; (b) current separate clocks with clearly labelled scope; (c) fail closed whenever the relevant clock is stale/absent. Main's completion timestamp belongs to a different projection than the traced current-Tool read, and the observed absence cannot settle this policy.
5. **What Market query bound and recovery should users see?** (a) align Market and Tool search at 256; (b) retain the source's 200 limit with an inline, nonfatal counter/error; (c) use separate limits but explain source scope. Different backends impose different bounds; no source code can decide the user-facing policy.
6. **After selecting a facet category, should its search text persist?** (a) preserve until the sheet closes; (b) preserve while on Market; (c) intentionally clear on selection, but make that behavior explicit. The preserved main URL query and cleared local facet query are distinct behaviours.
7. **When a chat answer fails after a Tool/Call, what retry affordance is safe?** (a) edit-question only with CallRef inspection; (b) regenerate answer from saved results without rerunning tools; (c) resend only after explicit confirmation and fresh authority. Call side effects and the inability to infer an exact completion from the failed text make an automatic retry decision unsafe.
