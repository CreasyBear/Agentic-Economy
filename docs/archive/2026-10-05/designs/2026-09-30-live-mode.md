# Live mode: switching an account into real x402 (30 September 2026)

Goal: an admin can switch their own workspace into real money, then buy real Bazaar listings from chat, before any customer does. The same seam later takes aecon beyond Base.

Reference model: **Stripe test mode vs live mode.** There are two worlds with separate money. The UI marks test mode clearly. Going live is deliberate and guarded. This model is familiar, and it maps onto what aecon already has.

## What the code already does (facts)
- **Environment is threaded through the buyer path.**
  - Principal and grant carry `sandbox | production` (`principal-convex-schema.ts:4-15`, `agent-access.ts:264-273`).
  - A Tool's runtime environment comes from its network: Base mainnet → production, Base Sepolia → sandbox, anything else skipped (`facilitatorDiscovery/identity.ts:43-50`).
  - Quote refuses when the buyer's and the Tool's environments differ (`issueQuote.ts:86-97`).
  - The payment profile per environment selects the network and USDC contract (`x402-payment-profile.ts:3-64`).
  - The worker carries the environment into CDP authorisation and settlement (`x402Authorization.ts:90-95,594-650`).
- **Treasury:** one CDP wallet, observed on `base-sepolia` and `base` (`moneyTreasuryObservation.ts:31-40,108-154`).
  - Quote refuses `treasury_capacity_unavailable` when there is no observation or the capacity is short (`issueQuote.ts:199-203`).
  - Custody is opt-in (`AE_X402_CUSTODY_ENABLED` plus the CDP bundle, `x402-custody-configuration.ts:11-83`).
- **Settlement** is verified locally from EVM receipts through `AE_X402_RPC_URLS_JSON`. Production needs 2 RPC endpoints (`x402Settlement.ts:38-103`). No facilitator verify/settle URL is used.
- **Service mode:** `standard` allows both environments. `hosted_alpha` allows sandbox only (`service-mode.ts:3-15`).
- **Production agent policy exists** but defaults to zero caps (`production-policy.ts:70-96`). The owner-chat credential is hard-coded to sandbox (`agent-access.functions.ts:470-485`).
- **Money ledger:** there is ONE Formance ledger per deployment (`AE_FORMANCE_ENVIRONMENT`, `AE_FORMANCE_LEDGER`). The owner AUD balance read takes no environment argument (`formanceBalance.ts:31-43`). Stripe mode is chosen per deployment by the key prefix (`stripe-money-provider-config.ts:54-96`).
- **Admin:**
  - `adminMemberships.role` is `owner_admin`, `support` or `reviewer`. Admin commands need a Clerk second factor no older than 10 minutes (`submitAdminCommand.functions.ts:49-69`).
  - Proposal kinds: suppression, commercial policy, and grant/revoke admin (`admin-console/contracts.ts:66-70`).
  - There is no settings or mode toggle today. `ConfigurationBanner` shows Formance, custody, FVA and Convex presence, read only.
- **Accounts** have no mode field (`account/convex-schema.ts:40-53`).

## The flaw a naive toggle would hit
Balances are not separated by environment. A top-up with a test card and a real mainnet purchase would draw on the same AUD balance, so aecon would pay real USDC against fake credit. Any design must keep the two money worlds apart.

## Design (production-first; revised 30 September 2026)
aecon is a production app. Users only ever see real money. The sandbox world (Base Sepolia, Stripe test, Formance sandbox) exists only in development deployments, as tooling, never as a user-facing mode. Stripe works the same way: separate accounts and keys per environment.

1. **One payment environment per deployment.**
   - `deploymentPaymentEnvironment()` is derived from the deployment's existing money configuration (`AE_FORMANCE_ENVIRONMENT`).
   - Production deployments are `production` everywhere: Stripe live, Formance production, Base mainnet, production agent policy. Dev deployments are `sandbox` everywhere.
   - No account ever mixes the two, so the shared AUD balance is always consistent with its money world.
2. **The owner-chat credential follows the deployment.**
   - Environment is `deploymentPaymentEnvironment()`, and the idempotency key is `owner-chat-spend-${env}-${userId}`.
   - Production policy is `buildProductionAgentAccessPolicy` with A$1 per Call, A$5 a day and A$20 a month.
   - `resolveOwnerChatActor` accepts only the grant for the deployment's environment. The issuance guard admits `ae-owner-chat` in either environment.
3. **Launch gate, not a test mode.**
   - `platformLaunch.paymentsOpenTo: 'admins' | 'everyone'`. Default `admins`.
   - Before launch, admins buy with real money and everyone else can search and read.
   - Flipping to `everyone` is an admin proposal (`open_payments`) with fresh MFA, audited.
   - It is enforced at owner-chat enable and at Quote.
4. **Go-live readiness panel.** `ConfigurationBanner` becomes pass/fail checks. `open_payments` stays disabled until every check passes:
   - Stripe keys are live, the webhook is live, and the GST rate is set.
   - Formance is in production.
   - Custody is complete.
   - The Base treasury has been observed recently, with enough capacity.
   - There are 2 Base RPC endpoints.
   - Service mode is `standard`.
5. **Run only where aecon can pay.** In production, Run is offered on Base mainnet listings. Other networks show no Run until their payment profile ships.
6. **Config drift:** standardise Stripe on restricted `rk_live_` keys, both at runtime and in the manifest.

## Moving beyond Base
The payment profile is keyed by environment (one network each). It becomes a list per environment: `production: [base, …]`, `sandbox: [base-sepolia, …]`. Touchpoints (E4 scout):
- Payment profile.
- Discovery acceptance and runtime mapping.
- CDP asset policy.
- Treasury observation per network.
- Settlement RPC per network.
- The call-contract and schema network unions.

Order of work:
1. **Base mainnet live.**
2. **Other EVM networks with EIP-3009 USDC** (Polygon, Arbitrum, OP). The scheme and signer are the same; this means config, a treasury balance per network, and RPC endpoints.
3. **Solana.** This is a separate project: `@x402/svm`, CDP Solana accounts, and a different settlement verifier.
