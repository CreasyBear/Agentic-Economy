## Exact SDK primitive shapes (local authority)

[Declarations, lines 35–119, 127–154, 159–190, 203–228 and 381–402](../../../node_modules/@typesafe-ai/sdk/dist/index.d.mts):

```ts
// EntryType = string | JSON object | JSON array | null.
client.systemOne({ state: EntryType, questions: { [name]: Question }, model?: string },
  { signal?: AbortSignal, timeout?: number, retry?: Partial<RetryPolicy> });
noul(instructions?, criteria?: { true?: EntryType; false?: EntryType } | null);
choice(instructions, criteria: { [label: string]: EntryType });
score(instructions, criteria: readonly [EntryType, EntryType, ...EntryType[]]);
```

These are compact transcriptions of the *signatures*, not runnable TypeScript declarations. All three question objects have `type: "noul" | "choice" | "score"` and optional `instructions`; `choice` requires labelled criteria, `score` requires **at least two ordered entries** indexed from zero, and `noul` may omit criteria or describe its true/false outcomes. The [factories](../../../node_modules/@typesafe-ai/sdk/dist/index.d.mts) construct these same wire objects; literal question objects also work ([independent source](https://github.com/Arize-ai/openinference/blob/main/js/packages/openinference-instrumentation-typesafe/examples/all-question-types.ts)). `state` is text, JSON object/array, or null. `SystemOneResult` has `{ model, answers, usage }`, with answers keyed by question name:

| Question | Exact answer fields from installed declarations | How to interpret |
| --- | --- | --- |
| `noul` | `{ readonly type: "noul"; readonly noul: number }` | `noul` is **P(yes)**, not a boolean. |
| `choice` | `{ readonly type: "choice"; readonly choice: keyof T & string; readonly confidence: number; readonly probabilities: { [label in keyof T]: number } }` | Selection and distribution over criterion labels. |
| `score` | `{ readonly type: "score"; readonly score: number; readonly confidence: number; readonly legend: { [score]: criterion }; readonly probabilities: { [score]: number } }` | `score` is an **expected value**, potentially between rubric indices; not an integer category. |

The SDK config defaults to `jev-latest`, a **10,000 ms per-attempt timeout** and **two retries after the initial attempt**; per-call `timeout`/`retry` can override these. There is **no total retry deadline** in the [request options](../../../node_modules/@typesafe-ai/sdk/dist/index.d.mts). Those are SDK defaults, not claims about the examples' measured latency. The SDK [README quickstart](../../../node_modules/@typesafe-ai/sdk/README.md) uses `state: { document: ... }`, `category: choice(..., { billing: null, technical: null, other: null })`, then `response.answers.category.choice`.

## Transfer to aecon's Jev-backed tool ranking

1. **Single-request ranking + absolute fit/no-match.** [BuilderIO](https://github.com/BuilderIO/agent-native/blob/main/packages/core/src/agent/jev-tool-prefetch.ts) explicitly scores a sentinel `__no_match__` and keeps only candidates above its probability; [FastMCP](https://github.com/PrefectHQ/fastmcp/blob/main/fastmcp_slim/fastmcp/experimental/transforms/jev_search.py) instead pairs `choice` with one independent `noul` suitability judgment per shortlisted tool. These address *different* failure modes: an attractive wrong winner and globally irrelevant candidates. FastMCP's wide/close pass also avoids asking Jev to compare a huge catalog at once. Its own caveat: probabilities from **separate chunks are not comparable**.
2. **Bound Jev without making discovery depend on it.** [BuilderIO](https://github.com/BuilderIO/agent-native/blob/main/packages/core/src/agent/jev-tool-prefetch.ts) caps its shortlist at 128, budgets 750 ms against the caller deadline, disables SDK retries on the direct path, and preserves the original tool set on failure. This is closer to aecon's latency-sensitive selection than treating the SDK's 10 s *per-attempt* default as a request deadline. Aecon's current 1,500 ms (5,000 ms discovery) budgets are supplied by the task context, not inferred from third-party sources.
3. **One structured state, several named judgments, explicit failure behavior.** [OpenViking](https://github.com/volcengine/OpenViking/blob/main/openviking/models/rerank/jev_rerank.py) sends candidate documents once and attaches one `noul` per document, then its [retrieval caller](https://github.com/volcengine/OpenViking/blob/main/openviking/retrieve/hierarchical_retriever.py) keeps preexisting vector scores when reranking fails. [TradingAgents](https://github.com/TauricResearch/TradingAgents/blob/main/tradingagents/agents/post_screen.py) batches topicality and stance for *one post* in each request, retaining posts when screening fails. Which layout wins depends on whether decisions share a large immutable candidate state, not an assumed universal Jev batching trick.

Do not transplant the vendor n8n route's failure-output policy into procurement: its [source](https://github.com/typesafe-ai/n8n-nodes-typesafe-ai/blob/main/nodes/TypeSafeAi/TypeSafeAi.node.ts) routes errors according to workflow output topology, not a market safety or purchase guarantee. These are source-derived design patterns, **not measured accuracy, latency or correctness claims**.
