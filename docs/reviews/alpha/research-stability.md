# Stability without fallback sprawl — source dossier

**Decision context (28 September 2026).** AEcon is a TanStack Start/React app on Vercel with Convex as its authoritative store, Clerk for signed-in identity, Stripe/Formance and x402 custody/Providers for money and Calls, and Jev/OpenRouter, Coinbase FX/Bazaar and telemetry around those journeys. The rules below are **recommendations for AEcon**, not claims that these designs have already been implemented or fault-injected. Local examples are from the read-only [backend](fragility-backend.md), [external](fragility-external.md), and [UI](fragility-ui.md) takedown maps; their risks are not necessarily observed outages.

## Principles and AEcon rules

1. **Define a useful core outcome before building an exception path.** AWS distinguishes *fallback* (a different mechanism for the same result) from retry, proactive retry and failover, and says it almost always prefers improving the primary path; its cache-bypass-to-database fallback took down both a retail site and fulfillment ([Gabrielson, *Avoiding fallback in distributed systems*, pp. 2, 5–7](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf#page=2)). AWS Well-Architected REL05-BP01 separately says an optional dependency failure must not erase core business functionality, and failure paths should be simpler than the main path ([REL05-BP01, “Implementation guidance”](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html)). **AEcon:** admitted/indexed Tool rows remain useful without Jev's prose/ranking; a permission check, executable Quote or paid Call does *not* become optional because its authority is down ([external J3–J5, J10, J14–J15](fragility-external.md)).
2. **Prefer a continuously exercised serving path over an emergency second path.** AWS says an essential alternative should be exercised regularly as an equally valid source—then it is failover, not dormant fallback; proactively push required data instead of fetching it during trouble ([Gabrielson, pp. 6–7](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf#page=6)). **AEcon:** serve ordinary Bazaar/source-filtered browse from reconciled Convex publications and update them in scheduled scans, rather than bypassing a failed index into a new live Coinbase request during buyer search ([external J6–J7](fragility-external.md)); retain Bazaar supply, not remove it.
3. **Make the serving plane statically stable; allow the update plane to stall.** AWS defines static stability as continuing previously working operations during a dependency impairment even when new updates are unavailable; recovery should not require new provisioning or a functioning control plane ([Weiss & Furr, *Static stability using Availability Zones*, “Static stability”](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/)). Well-Architected REL11-BP05 rejects a bimodal failure mode that refreshes all configuration on timeout or bypasses a cache ([REL11-BP05](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_withstand_component_failures_static_stability.html)). **AEcon:** the last **completed** directory generation can serve while a new scan fails; previously validated FX can price Quotes only within an explicit bounded age and with its exact observation attached, never after expiry or from an invented default ([backend J1–J2](fragility-backend.md)). This is advance placement of authoritative state, not emergency cache bypass.
4. **Do not confuse AWS's AZ capacity example with a solo-founder deployment requirement.** The Builders' Library preprovisions active-active capacity or a standby *before* an AZ failure, but expressly says simpler regional-to-regional service calls suit many application services; zonal siloing has cost and complexity appropriate to foundational data planes ([Weiss & Furr, “Static stability patterns”; “Under the hood”](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/)). **AEcon:** first remove synchronous enrichment dependencies and global startup gates; do not add a second home-grown database, region, or Vercel control-plane workflow merely to mimic EC2.
5. **Bound every remote wait, including completion of the response body.** AWS calls for connection *and* request timeouts and notes that some socket timers exclude DNS/TLS; choose budgets against observed downstream latency, not an arbitrary tiny threshold ([Brooker, *Timeouts, retries, and backoff with jitter*, pp. 2–3](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf#page=2)). Nygard's second-edition Chapter 4 excerpt says a stalled socket read can block indefinitely, consuming caller capacity ([*Release It!*, 2nd ed., Ch. 4, “Integration Points,” excerpt pp. 10–12](https://media.pragprog.com/titles/mnee2/antipatterns.pdf#page=10)). **AEcon:** CLI HTTP find/Quote/Call needs a whole-request/body deadline; the Vercel Provider-consequence bridge needs deadlines, while an ambiguous paid Call must remain outcome-unknown until reconciled ([external J13, J16](fragility-external.md)).
6. **Put retries at one point, within a deadline, only when the effect is repeatable.** AWS calculates 243 downstream attempts from three tries at each of five layers, advises one retry point, bounded attempts, backoff/jitter, and idempotency for side effects; circuit breakers can introduce hard-to-test modes and delay recovery ([Brooker, pp. 3–5](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf#page=3)). Google likewise limits retries per request and per client and avoids retrying a broadly overloaded backend ([Google SRE, Ch. 21, “Deciding to Retry”](https://sre.google/sre-book/handling-overload/#deciding-to-retry)). **AEcon:** don't layer SDK + route + UI retries for Jev or directory scans; never reissue an ambiguous signed x402 purchase with a fresh identity—look up its same CallRef/effect journal first ([external J3, J14, D4–D5](fragility-external.md)).
7. **Keep work no larger under stress than under normal conditions.** AWS constant-work examples push fixed-size health status and repeatedly load complete configuration instead of creating a burst of changes in response to faults; it warns that ordinary caches have dangerous empty-cache modes ([MacCárthaigh, *Reliability, constant work, and a good cup of coffee*, pp. 3–7](https://d1.awsstatic.com/builderslibrary/pdfs/Reliability-constant-work-and-a-good-cup-of-coffee-Colm-MacCarthaigh.pdf#page=3)). **AEcon:** refresh directory projections on a bounded cadence and retain the last complete generation; never launch a live upstream directory crawl because one buyer's indexed search missed. Full-size padded AWS tables are *not* prescribed for this app—the essay notes cost trade-offs ([ibid., p. 8](https://d1.awsstatic.com/builderslibrary/pdfs/Reliability-constant-work-and-a-good-cup-of-coffee-Colm-MacCarthaigh.pdf#page=8)).
8. **Observe backlog age and protect urgent work; a queue defers, not deletes, failure.** AWS shows that one hour of halted processing at normal arrival rate needs an additional hour at double capacity to catch up; it recommends first-attempt age, work isolation, backpressure, expiry where safe, and stopping/renewing work when a visibility lease expires ([Yanacek, *Avoiding insurmountable queue backlogs*, pp. 3–4, 6–10](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-insurmountable-queue-backlogs.pdf#page=3)). **AEcon:** ensure paid Call reconciliation/expiry work is not disabled by an optional analytics/index cron switch or starved by scan/metrics refresh; old decorative scans may be superseded, but settlement/refund work may not be dropped ([backend J8–J9, D6](fragility-backend.md)).
9. **Separate synchronous hard dependencies from asynchronous enrichment, without assuming a queue is magical.** Well-Architected REL04-BP01 says multiple synchronous dependencies make every element necessary to one result; set deadlines and avoid indefinite waits. REL04-BP02 favors asynchronous decoupling *where an acknowledgement suffices*, but also specifies backpressure and stale-message policy ([REL04-BP01](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_prevent_interaction_failure_identify.html); [REL04-BP02](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_prevent_interaction_failure_loosely_coupled_system.html)). **AEcon:** Tool descriptor loads must not wait for live FX or secondary listing evidence; Provider publish can commit canonical publication independently of repairable search projection, but withdraw must synchronously revoke callability ([UI J2–J3](fragility-ui.md); [backend J4](fragility-backend.md)).
10. **Contain overload; reject unserviceable work rather than simulate success.** Google SRE Ch. 22 describes positive-feedback cascades from slow work, retries and resource exhaustion; shedding cheap requests and reducing per-request work are options, while Ch. 21 says even reduced-quality answers eventually become too expensive and then errors are appropriate ([Ch. 22, “Preventing Server Overload,” “Load Shedding and Graceful Degradation”](https://sre.google/sre-book/addressing-cascading-failures/#preventing-server-overload); [Ch. 21, opening](https://sre.google/sre-book/handling-overload/)). **AEcon:** under Jev outage use already-retrieved deterministic candidates with truthful coverage; under Convex outage do not claim a catalogue result exists, and under insufficient funds do not assert a Quote/Call succeeded ([external J3, J10](fragility-external.md)).
11. **Scope failure to the smallest truthful surface.** REL05-BP01's example keeps an ecommerce page visible when recommendations fail, not by manufacturing recommendations but by showing the other working sections ([REL05-BP01, “Implementation guidance”](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html)). Google warns unexercised degraded modes are risky and recommends testing noncritical backends that *never respond*, not just immediate errors ([Google SRE, Ch. 22, “Load Shedding and Graceful Degradation,” “Test Noncritical Backends”](https://sre.google/sre-book/addressing-cascading-failures/#xref_cascading-failure_load-shed-graceful-degredation)). **AEcon:** admin metrics failure should not blank admin configuration; a share-status or history widget should not remove the chat transcript/composer; telemetry initialization should not stop public pages ([UI A2, J6, J8](fragility-ui.md)).
12. **Exercise the error branch that can erase state; resist the fiction that more handlers guarantee safety.** Yuan et al. studied 198 sampled issue-reported failures across five distributed data systems, of which 48 were catastrophic: 92% of those catastrophic failures involved mishandled explicitly signaled nonfatal errors, 58% had faults detectable by simple error-handler testing, and 77% of all sampled failures could be reproduced by unit tests. The sample and issue-ticket selection limit generalization beyond those systems ([Yuan et al., OSDI '14, pp. 249–251, 255–256](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf#page=2)). **AEcon:** exercise failure of optional FX/Clerk-name/Jev/enrichment reads and assert canonical records remain visible; separately assert authority, receipt and payment effects are not fabricated—not a giant matrix of speculative fallback states ([UI J9–J10, D4](fragility-ui.md)).
13. **Recover using the same startup path; keep durable state outside disposable workers.** Candea and Fox describe crash-only systems as `stop=crash`, `start=recover`, with important nonvolatile state in dedicated stores, timeouts and self-describing/idempotent requests; recovery code gets exercised at ordinary startup. Their scope is a *single-datacenter* Internet service, not a direct claim that an external SaaS can be made crash-only ([Candea & Fox, *Crash-Only Software*, Abstract, §§1–3](https://www.usenix.org/legacy/events/hotos03/tech/full_papers/candea/candea_html/)). **AEcon:** Vercel workers restart from Convex-authoritative Call/effect state, not in-process guesswork; a lost HTTP response does not prove the paid effect never occurred ([external J8, J14](fragility-external.md)).
14. **Treat stability as a system property, not a collection of “just in case” branches.** Cook observes that catastrophe commonly requires multiple latent failures, that complex systems often operate with defects, and that after-accident single-cause remedies can increase coupling and hidden failure paths. This is a descriptive systems-safety analysis, **not** authorization to silently substitute incorrect data ([Cook, *How Complex Systems Fail*, Rev. D, §§3–5, 7, 14–16](https://www.adaptivecapacitylabs.com/HowComplexSystemsFail.pdf#page=1)). **AEcon:** audit dependency chains from public route → global boot config → telemetry/Clerk/Convex rather than blaming the last exception; remove a global optional-service veto rather than layering another catch over it ([external A1, D1–D2](fragility-external.md)).
15. **Model a dependency against the user action it supports, not an abstract “app uptime.”** Google SRE Workbook says a critical component's reliability guarantee should meet that of the dependent high-value action; when it cannot, choose a different component or engineer caching, store-and-forward or graceful degradation. It cautions that nominally redundant instances share dependencies, failure domains and control planes, making naive availability arithmetic deceptive ([*Implementing SLOs*, “Modeling Dependencies”](https://sre.google/workbook/implementing-slos/#modeling-dependencies)). **AEcon:** measure public find/compare separately from funded Quote, Call and receipt completion; no amount of Vercel redundancy makes Coinbase FX/Convex/Clerk outage probabilities independent, and a model outage should not count as a failed deterministic search.
16. **Choose containment patterns by mechanism, not by name.** Nygard's second-edition contents explicitly groups Timeouts, Circuit Breaker, Bulkheads, Steady State, Fail Fast and Decoupling Middleware in Chapter 5 ([*Release It!*, 2nd ed., publisher contents](https://pragprog.com/titles/mnee2/release-it-second-edition/#extracts)). Independent official guidance gives their actionable boundaries: a timeout bounds remote wait ([AWS Brooker, pp. 2–3](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf#page=2)); a breaker stops repeated calls to a timed-out dependency but can delay recovery ([REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html); [Brooker, p. 4](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf#page=4)); a bulkhead limits concurrency per workload, while steady-state capacity needs spare headroom, and asynchronous decoupling still needs backpressure ([AWS Yanacek, pp. 8–10](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-insurmountable-queue-backlogs.pdf#page=8); [REL04-BP02](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_prevent_interaction_failure_loosely_coupled_system.html)). **AEcon:** use the Provider-specific timeout and bounded work already present, protect paid reconciliation from optional scan load, fail fast at missing money/identity authority, and avoid adding a new breaker/queue until a measured shared-resource failure warrants it.

## Stability antipatterns to delete or constrain

- **Rare failure-only fallback to a more expensive/live source:** cache bypass overloaded Amazon's supply database ([Gabrielson, pp. 5–6](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf#page=5)); delete AEcon's synchronous upstream Bazaar-on-index-miss serving branch once persisted source-filtered publications serve buyers ([external J6–J7](fragility-external.md)).
- **Global “everything configured/healthy” boot or readiness gates:** REL04-BP01 warns that synchronous chains require every dependency to be available ([REL04-BP01](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_prevent_interaction_failure_identify.html)); remove model, custody, funding, directory scan, analytics and telemetry as prerequisites for public serving, while preserving their operation-local hard checks ([external A1, A4, D1](fragility-external.md)).
- **Retry and circuit-breaker towers:** AWS's 243× example and warning about circuit breakers' modal behavior ([Brooker, p. 4](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf#page=4)); remove duplicate retry/refusal states around Jev and never wrap a possibly settled Call in a generic automatic retry ([external J3–J4, J14](fragility-external.md)).
- **Unbounded query/result/queue/thread work:** Nygard's publisher lists “Blocked Threads” and “Unbounded Result Sets” as Chapter 4 antipatterns; the available Chapter 4 excerpt directly establishes hanging remote calls and resource loss ([*Release It!*, 2nd ed., publisher contents](https://pragprog.com/titles/mnee2/release-it-second-edition/#extracts); [excerpt pp. 9–12](https://media.pragprog.com/titles/mnee2/antipatterns.pdf#page=9)); page an owner's funding history `.collect()` and bound CLI body waits ([backend J10](fragility-backend.md); [external J16](fragility-external.md)).
- **A single optional failure blanking an entire route or treating unknown as zero:** REL05-BP01 rejects serving no data when partial useful data remains and warns against invalidating local state after a failed refresh ([REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html)); split optional analytics/chat/name panels from canonical Tool/account/transcript reads, but retain explicit *unknown* for money and permissions ([UI J1–J10, D4](fragility-ui.md)).
- **Fragile error “recovery” that aborts a healthy whole:** Yuan et al. identify an overly broad error handler that aborts the cluster as a trivial catastrophic-failure pattern **in their sample**, not a universal rate ([Yuan et al., p. 250](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf#page=3)); remove broad all-or-nothing catch/`Promise.all` coupling for independent market enrichment; preserve hard-failure signaling for canonical state ([UI J1–J3](fragility-ui.md)).
- **Speculative microservice/queue duplication as “decoupling”:** Nygard's Chapter 4 excerpt describes more connections as more integration risks ([*Release It!*, 2nd ed., Ch. 4, “Integration Points,” excerpt pp. 7–9](https://media.pragprog.com/titles/mnee2/antipatterns.pdf#page=7)), and AWS warns asynchronous backlog can make recovery much slower ([Yanacek, pp. 2–4](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-insurmountable-queue-backlogs.pdf#page=2)); keep existing Convex scheduled jobs, limit and inspect their ages rather than adding an independent queue solely for search decoration.

## Where the sources genuinely disagree—and the pre-alpha choice

- **Circuit breakers.** Nygard's *Release It!* 2nd-edition **Chapter 5 contents** names “Circuit Breaker,” “Bulkheads,” “Steady State,” “Fail Fast,” and “Decoupling Middleware” as patterns ([publisher contents](https://pragprog.com/titles/mnee2/release-it-second-edition/#extracts)); AWS REL05-BP01 explicitly suggests a breaker during time-critical dependency timeout ([REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html)). Brooker cautions that breakers add modal behavior and delayed recovery and favors bounded local retry tokens ([Brooker, p. 4](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf#page=4)). **Choose:** existing client deadlines, admission/concurrency limits, and one retry budget first; add a breaker only for measured saturation where it demonstrably protects shared capacity. Publisher contents establish Nygard's pattern *names*, not a claim about his unpublished Chapter 5 implementation details.
- **Graceful degradation versus avoiding fallback.** Google SRE advocates cheaper, incomplete responses and even deliberate degraded mode under overload but warns dormant paths can fail and recommends exercising them ([Google SRE, Chs. 21–22](https://sre.google/sre-book/addressing-cascading-failures/#xref_cascading-failure_load-shed-graceful-degredation)); AWS says avoid a **different, rarely exercised mechanism for the same result** and prefer one constantly exercised path ([Gabrielson, pp. 6–7](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf#page=6)). **Choose:** one deterministic Convex retrieval path that always works without model ranking, and independently attach optional ranking/analytics; show truthful partial coverage when incomplete. Do not implement a second emergency live search stack, nor silently call unranked results model-assessed.
- **Fail fast versus remain useful.** Nygard names “Fail Fast” among the stability patterns ([publisher contents](https://pragprog.com/titles/mnee2/release-it-second-edition/#extracts)); AWS REL05-BP01 says preserve the core outcome when optional dependencies fail *but* payment transactions prioritize consistency ([REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_graceful_degradation.html)). **Choose:** fail fast at the actual missing authority (Clerk identity, Convex source, Formance funds, fresh x402 challenge, settlement/custody) while allowing independent public find/compare and already-existing read-only receipts.
- **Crash-only retries versus consequential effects.** Candea and Fox propose transparent component retries for short restarts but require idempotent/self-describing requests and bounded retry behavior ([*Crash-Only Software*, §§3–4](https://www.usenix.org/legacy/events/hotos03/tech/full_papers/candea/candea_html/#restart-retry)); Brooker cautions that timeout says nothing about whether a side effect executed ([Brooker, p. 2](https://d1.awsstatic.com/builderslibrary/pdfs/timeouts-retries-and-backoff-with-jitter.pdf#page=2)). **Choose:** restart Vercel/Convex work from durable state and reconcile the **same** CallRef after ambiguity; no transparent new paid purchase.
- **Costly constant work versus solo-founder simplicity.** AWS describes deliberately padded constant-size processing, yet concedes elastic web-serving can be a better fit where always-on capacity is wasteful ([MacCárthaigh, pp. 5–8](https://d1.awsstatic.com/builderslibrary/pdfs/Reliability-constant-work-and-a-good-cup-of-coffee-Colm-MacCarthaigh.pdf#page=5)). **Choose:** existing periodic bounded refresh + last completed snapshot, not fixed-size dummy traffic, extra Regions or a bespoke breaker framework.
- **Cook's “degraded mode” is descriptive, not a product directive.** Cook reports practitioners already maintain operation amid latent flaws and says they need early detection for graceful cutbacks ([Cook, §§5, 12, 15](https://www.adaptivecapacitylabs.com/HowComplexSystemsFail.pdf#page=1)); Google provides engineering rules for cheaper but meaningful responses ([SRE Ch. 22](https://sre.google/sre-book/addressing-cascading-failures/#xref_cascading-failure_load-shed-graceful-degredation)). **Choose:** measure and isolate actual failed surfaces; never relabel a guessed payment, permission or result as a successful degraded answer.

**Evidence boundary:** Nygard 2nd-edition Chapter 4 is publicly excerpted only through early “Integration Points”; other Chapter 4 antipatterns and Chapter 5 pattern names above are verified by the publisher's contents, not presented as quotations from unseen prose. Yuan's percentages describe its sampled five data systems, not AEcon or all SaaS applications. No source above establishes that removing *all* defensive handling would improve reliability; the supported cut is unnecessary failure-mode coupling, not safety-critical authority or payment validation.
