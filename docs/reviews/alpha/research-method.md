# A small-team method for removing fragility — 28 September 2026

**Objective:** reduce the number of independent conditions able to stop a *specific user journey*, not maximize the number of error branches. This is a proposed operating protocol, not a claim that the proposed injections have been run. AEcon examples refer to the read-only [external](fragility-external.md), [backend](fragility-backend.md), and [UI](fragility-ui.md) takedown maps; those maps distinguish observed behavior from source-derived risks.

## Source-grounded rules

1. **Define success from the user's action, then draw its dependency graph.** Google recommends starting with common critical user tasks, request/data flow and dependencies, then choosing a small set of user-relevant indicators; AWS REL04-BP01 distinguishes synchronous, asynchronous and batch interactions and warns that chained synchronous calls make every link necessary. [Google SRE Workbook, *Implementing SLOs*, “Getting Started”](https://sre.google/workbook/implementing-slos/); [AWS REL04-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_identify.html). **AEcon:** trace public browse, sign-in, Provider publish, Quote, paid Call and receipt separately across Vercel, Convex, Clerk, Stripe, Formance, Coinbase, CDP and the called Provider; one vendor need not have the same role in every journey.
2. **Classify hard/soft *per journey*, not by vendor label.** AWS defines a *hard* dependency as one whose interruption directly interrupts the invoking system, and a *soft* one whose failure the application compensates for. Independent hard dependencies multiply theoretical failure exposure; correlated failures make naive multiplication unreliable. REL05-BP01 says decide which function is core and preserve it where feasible. [AWS Reliability Pillar, *Availability*, “Calculating availability with hard dependencies”](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html); [REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_graceful_degradation.html). **AEcon:** Convex catalogue is hard for catalogue reads; Clerk authority is hard for protected writes but not public pages; Jev ranking, directory refresh, analytics and telemetry are soft for browse; the *called* Provider is hard only for its Call. Price authority remains hard when no validated, bounded-age FX exists.

   **Current versus target:** the [UI A3](fragility-ui.md) map identifies a current global Clerk wrapper risk on public routes; “not hard for public pages” above is the *intended* boundary, so classify that edge **C** until an injected outage proves the decoupling. AWS's definition is descriptive of actual behavior, not a declaration that an optional service has already been isolated ([Availability](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html)).

3. **Treat an avoidable synchronous edge as a defect, not an invitation to add another mode.** REL04-BP01 recommends minimizing calls for a request, deadlines for synchronous dependencies, and asynchronous work where the result is not needed immediately; REL04-BP02 recommends loose coupling to contain failure, not gratuitous decomposition. [AWS REL04-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_identify.html); [REL04-BP02](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_loosely_coupled_system.html). **AEcon:** do not require a live Bazaar scan or analytics build during Vite boot or per-request Convex catalogue browse; retain the last *completed* indexed generation while refresh runs, without adding a new queue/service just to satisfy an architecture diagram.
4. **Use a short, effect-first software FMEA.** NIST's FMEA description starts with selected high-risk functions, their failure modes/effects/causes and prevention/detection controls; severity is the *worst effect*, occurrence estimates the cause's likelihood, detection rates how likely controls are to notice it, and conventional RPN is `S × O × D`. It explicitly says FMEA need not cover every process step. AWS REL12-BP04 proposes coarse high/medium/low fault priority from impact and frequency, using incident evidence where available. [NIST AMS 300-7, §2, pp. 2–3](https://doi.org/10.6028/NIST.AMS.300-7); [AWS REL12-BP04, “Assign a priority to each fault”](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_failure_injection_resiliency.html). **AEcon:** prioritize optional model config crashing all routes (app-down) above a single analytics tile; never let a low guessed occurrence or easy detection bury a high-severity payment-integrity or auth failure. Use ordinal S/O/D notes, not spurious numeric precision before traffic data exists.

   **Scoring caution:** in conventional FMEA, detection rating **10 means unlikely to detect before user impact**, not “good monitoring”; an alert raised after incorrect settlement does not prevent its effect ([AHRQ FMEA, steps 9–12](https://digital.ahrq.gov/health-it-tools-and-resources/evaluation-resources/workflow-assessment-health-it-toolkit/all-workflow-tools/fmea-analysis)). SAE's software-specific recommended practice says occurrence estimates depend on relevant records, detailed software FMEA is labor-intensive, and single-mode analysis misses multiple failures and timing/sequencing interactions; reserve combined-fault injections for plausible shared-cause risks ([SAE ARP5580, §§3.2.2, 3.3, 6.4](https://s3vi.ndc.nasa.gov/ssri-kb/static/resources/SAE20ARP5580.pdf)).

5. **Prefer the continuously exercised path.** Amazon says distributed fallbacks are difficult to test, can themselves fail, can amplify an outage and accumulate latent bugs; it favors making the primary path robust or proactively placing necessary data on the serving path. If an alternate is essential, exercise it continually as a genuine peer (failover), not an emergency-only branch. Google similarly warns that a rarely exercised degraded path may not work and complex degradation can cause feedback failures. [AWS Builders' Library, Gabrielson, *Avoiding fallback in distributed systems*, pp. 4–7](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf); [Google SRE Book, ch. 22, “Load Shedding and Graceful Degradation”](https://sre.google/sre-book/addressing-cascading-failures/#load-shedding-and-graceful-degradation). **AEcon:** ordinary search should always produce deterministic indexed results; Jev may improve their order but may not be the only route to results. Persist validated FX before Quote needs it, then apply *the same age/validity rule* normally and during refresh failure; no invented price after expiry.
6. **Bound work, not just latency.** AWS REL04-BP03 illustrates a fixed-size health snapshot rather than failure-proportional updates; the Builders' Library warns that a cache→database fallback once overloaded a shared database and brought down Amazon retail and fulfillment. Google warns retries amplify an overloaded backend. [AWS REL04-BP03](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_constant_work.html); [AWS Builders' Library, Gabrielson, pp. 5–7](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf); [Google SRE Book, ch. 22, “Retries”](https://sre.google/sre-book/addressing-cascading-failures/#retries). **AEcon:** preserve bounded directory pages and last-complete-generation reads; do not send every buyer browse to Coinbase when indexing fails, or retry every failing model request synchronously. Timeout the CLI request *and response body*; distinguish a timed-out paid Call from a definitely unexecuted Call.
7. **Fault injection must measure the user's output and containment.** The Principles of Chaos Engineering define measurable steady state, hypothesis, realistic fault and attempted disproof; prefer realistic conditions and minimize blast radius. AWS REL12-BP04 explicitly lists third-party blocking, latency, DNS and dropped messages, says restore known-good state and turn passing experiments into regression tests. [*Principles of Chaos Engineering*, “Chaos in Practice” and “Advanced Principles”](https://principlesofchaos.org/); [AWS REL12-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_failure_injection_resiliency.html). **AEcon:** inject Jev 500/timeout and check browse still presents actual Tool rows and Bazaar; inject Stripe refusal and check funding stays pending without contaminating search; inject Provider timeout and check only that Call cannot claim success.
8. **Practice recovery, not only error responses.** AWS REL12-BP05 says game days simulate workload events, exercise *actual* response procedures, observe outcomes, review gaps and complete corrective actions; Google says tests that pass do not prove reliability, while regression tests capture previously observed bugs. [AWS REL12-BP05](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_game_days_resiliency.html); [Google SRE Book, ch. 17, “Relationships Between Testing and Mean Time to Repair” and “Regression tests”](https://sre.google/sre-book/testing-reliability/). **AEcon:** one short solo game day exercises a specific saved Call reference after an ambiguous transport timeout; check status/reconciliation and ensure no second charge, then retain a deterministic regression for that contract.
9. **An SLO is a choice of user outcome, not a dashboard project.** Google suggests a few good-events/total-events indicators, including a distinct *quality* indicator for undegraded results; error budget equals `1 − SLO`. Its four-week release freeze is explicitly an example policy. [Google SRE Workbook, ch. 2, “What to Measure” / Table 2-1](https://sre.google/workbook/implementing-slos/); [*Example Error Budget Policy*, “Background”](https://sre.google/workbook/error-budget-policy/). **AEcon:** use existing request/Call evidence and one synthetic public browse + one protected paid-path probe in a safe environment; count correctness of search coverage and money state, not HTTP 200 alone. Before enough real traffic, record failure counts and consequences instead of claiming a statistically meaningful 99.9% target.

## Anti-patterns to delete (not safety fences)

- **One global optional-config/readiness gate:** REL05-BP01 says core function should survive applicable dependency failures, and REL04-BP01 warns against synchronous chains. Scope model, Coinbase refresh, custody and funding config to their actual actions rather than first-request/public readiness; keep required authority on the action. [AWS REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_graceful_degradation.html); [REL04-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_identify.html). AEcon evidence: [external A1/D1](fragility-external.md), [UI A1](fragility-ui.md).
- **Emergency-only fallback to a larger upstream or duplicate “unavailable” states:** Amazon's retail cache→database fallback amplified a partial outage, and Google warns latent degraded paths frequently fail. Move authoritative, bounded last-good data into the normal serving path, delete old refusals *only when the new path satisfies the same truth checks*. [AWS Builders' Library, Gabrielson, pp. 5–7](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf); [Google SRE Book, ch. 22](https://sre.google/sre-book/addressing-cascading-failures/#load-shedding-and-graceful-degradation). AEcon: [external J3–J7](fragility-external.md).
- **Partial result falsely presented as exhaustive, or empty price masquerading as zero:** AWS calls serving no data when independent partial data exists and inconsistent partial transactions anti-patterns; the acceptable result depends on what is core. Show accurate coverage/freshness and refuse unverifiable monetary action. [AWS REL05-BP01, “Common anti-patterns”](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_graceful_degradation.html). AEcon: [backend D3](fragility-backend.md), [external J5](fragility-external.md).
- **Unbounded retry/await or stacked “resilience” products:** AWS warns indefinite waits and chains of synchronous dependencies are brittle; Google describes retry feedback loops; constant work avoids sudden failure-driven traffic. Remove unnecessary request-path hops before selecting circuit breakers, queues or a second cache. [AWS REL04-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_identify.html); [Google SRE Book, ch. 22, “Retries”](https://sre.google/sre-book/addressing-cascading-failures/#retries); [AWS REL04-BP03](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_constant_work.html). AEcon: [external J13/J16/D2](fragility-external.md).
- **Delete NO money/identity integrity checks in the name of availability:** AWS explicitly treats inconsistent partial transactions as an anti-pattern; a dependency is hard when failure prevents the *agreed function*, including correctness. Keep verified Clerk authorization, Formance funds/reservation, Stripe signature/idempotency, x402 payment challenge and outcome-unknown reconciliation. [AWS REL05-BP01, “Implementation guidance”](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_graceful_degradation.html); [AWS Availability](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html). AEcon evidence: [external “fences to retain”](fragility-external.md), [backend J7/J8](fragility-backend.md).

## Six-step solo-founder protocol — one worksheet, one executable proof per important row

| Step | Action and exit condition | Minimum artefact |
|---|---|---|
| **1. Inventory** | Select 5–6 complete user actions (public find/compare, sign-in, publish, fund, Quote/Call, receipt); enumerate actual synchronous calls, env/boot checks, background refreshes and UI-wide joins; record where each can abort. Source: [Google Workbook, “Getting Started”](https://sre.google/workbook/implementing-slos/); [AWS REL04-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_identify.html). | One journey × dependency table: `journey | dependency | sync/async | failure trigger | current user-visible effect | code evidence`. Extend existing alpha findings rather than another catalogue. |
| **2. Classify** | For *each edge*, mark **H** (necessary to deliver truthful action), **S** (core action can run without it), or **C** (currently hard, could be softened by removal/normal-path precomputation). Write the exact invariant and maximum acceptable freshness where relevant. Source: [AWS Availability](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html); [REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_graceful_degradation.html). | Add `H/S/C | required invariant | failure blast radius`; never classify “Stripe” globally when checkout versus search differ. |
| **3. Analyse** | For top takedown modes record failure→effect→cause→existing detection/prevention. Triage app-wide/money-critical first; label S/O/D high/medium/low, with observed versus hypothetical occurrence and evidence. Severity cannot be washed out by multiplying guesses. Source: [NIST §2](https://doi.org/10.6028/NIST.AMS.300-7); [AWS REL12-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_failure_injection_resiliency.html). | Add `mode | S/O/D + basis | proposed removal | retained safety fence | owner` to the same table. |
| **4. Redesign** | Delete soft dependency from the core path, or move its validated facts into normal persisted serving; remove superseded special modes/refusals; keep H gates for authority/money and request budgets on real network calls. Source: [AWS Builders' Library, Gabrielson, “How Amazon avoids fallback”](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf); [REL04-BP03](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_constant_work.html). | Same row states `before graph → after graph`, specifically which former blocker disappeared. No extra architecture document. |
| **5. Verify by injection** | Baseline one real user-facing action; inject *one fault at a time* at the dependency boundary in isolated local/staging, rerun that action **and an unrelated one**, observe response, bounded elapsed time, authoritative state and provider-call count, restore, then try combined faults only where plausible. Hypothesis: “If [fault], [core action] still [truthful outcome] while [protected action] [safe refusal/reconciliation].” Source: [Chaos Principles, “Chaos in Practice”](https://principlesofchaos.org/); [AWS REL12-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_failure_injection_resiliency.html). | Append `fault | expected | observed | proof command/trace | restored | pass/fail` to the row; **not** “test passed” if only a mock/HTTP 200 was observed. |
| **6. Guard** | Keep the smallest deterministic failure-injection regression that catches the eliminated user-visible takedown; rerun after edits to dependency wiring. Schedule a short game day around one critical path when it changes; re-open FMEA row on new incident or failed exercise. Source: [Google SRE Book, ch. 17, “Regression tests”](https://sre.google/sre-book/testing-reliability/); [AWS REL12-BP04/BP05](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_game_days_resiliency.html). | Test next to existing boundary, and a dated result in the same worksheet; no dedicated chaos platform, new telemetry service or faux 24/7 on-call runbook. |

**Minimal injection set to prove the graph, not just the catch block:** run in isolated local/staging against real app entry points, with scoped substituted dependency responses (do not kill shared services, reveal secrets, or submit paid effects). Missing optional `OPENROUTER_API_KEY` / Jev `500` and timeout → public indexed search still returns real, labelled results; invalid *required* Convex config → genuine catalogue boundary fails but static/public non-Convex route stays accessible; Clerk unavailable → protected write refuses, public browse persists; Coinbase discovery `500` → last completed directory still browsable and refresh records failure; FX refresh `500`/timeout → bounded-age validated persisted rate produces exact Quote, expired/no rate refuses Quote but not browse; Stripe `500` → funding remains uncredited, browse persists; Formance failure → paid Quote/Call does not assume funds, directory remains readable; called Provider `500`/timeout → only its Call fails or enters outcome-unknown, no invented success, no blind second charge; optional analytics/telemetry `500` → core pages work; malformed optional env at boot → public path still boots, while protected operation diagnoses only its own missing config. These expected outcomes follow [AWS REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_graceful_degradation.html), [REL12-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_failure_injection_resiliency.html), and the AEcon [external](fragility-external.md)/[backend](fragility-backend.md) source-derived maps; **none is presented as exercised proof here**. For ambiguous payment outcomes, query the original Call reference and reconcile before any repeat, rather than treating timeout as non-execution ([AWS REL04-BP01, indeterminate synchronous outcomes](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_identify.html)).

## Where sources pull in different directions

- **Graceful degradation vs avoiding fallback.** [AWS REL05-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_mitigate_interaction_failure_graceful_degradation.html) allows useful partial/stale results, yet itself says failure paths should be *simpler* and fallback generally avoided; [Gabrielson, pp. 4–7](https://d1.awsstatic.com/builderslibrary/pdfs/avoiding-fallback-in-distributed-systems.pdf) explains the failure-driven second mechanism is the danger. **Choice:** make indexed browse and validity-checked persisted FX the ordinary paths; refresh/ranking are enrichment. Do not call expired price, guessed authority or a second payment provider “graceful degradation.”
- **Production chaos vs protected users.** [Chaos Principles, “Run Experiments in Production” and “Minimize Blast Radius”](https://principlesofchaos.org/) favors production realism; [AWS REL12-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_failure_injection_resiliency.html) recommends first simulating faults outside production and setting stop/restore conditions. **Choice:** pre-alpha solo founder runs scoped local/staging injection first; a live synthetic or tiny canary is optional only after the path is safe and customer impact bounded. Never disrupt real funding/settlement merely for chaos fidelity.
- **Full SLO policy / numeric FMEA vs scarce evidence.** [Google Workbook, ch. 2](https://sre.google/workbook/implementing-slos/) recommends iterative user-centred SLIs and its [example policy](https://sre.google/workbook/error-budget-policy/) freezes releases after a four-week budget breach; [NIST §2](https://doi.org/10.6028/NIST.AMS.300-7) describes 1–10 S/O/D and RPN, while [AWS REL12-BP04](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_testing_resiliency_failure_injection_resiliency.html) starts high/medium/low. **Choice:** record actual user-visible failures/quality, focus fixes on high-severity edges, and defer a percentage target/freeze and precise RPN until enough real events and an explicit product reliability commitment exist. This avoids false confidence, not measurement.
- **Loose coupling vs more infrastructure.** [AWS REL04-BP02](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_loosely_coupled_system.html) offers queues/workflows/microservices to isolate failures, but [REL04-BP01](https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_prevent_interaction_failure_identify.html) identifies new dependencies and duplicate-delivery challenges. **Choice:** first delete incidental sync edges and reuse Convex's existing persistence/scheduling; add a new intermediary only if a tested user journey cannot be made correct with the existing architecture.
