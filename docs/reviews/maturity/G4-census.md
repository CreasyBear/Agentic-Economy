## PC-12 — Receipt and generic Support lose the Call reference
- **Register claim on current main: holds at the route boundary; live symptom recorded, not freshly replayed.** `CallReceiptWorkspace.tsx:30-36` and `CallRecoveryPanel.tsx:122-129` hand `<Link to="/support" search={{callRef}}>` a *raw string*. `/support` `validateSearch` turns that string into `{callRef:{kind:'valid',value:ref}}` and missing search into `{callRef:{kind:'absent'}}` (`src/routes/support.tsx:10-22`). That projected object is the route's search state and is serialized into the URL instead of the raw reference: the register observed `{kind:"valid",value:…}` in the query. When the URL is parsed, the validator requires a string matching `parseCallRef`; an object or its serialization fails and becomes malformed. This is **not** a defect in the link's original argument or `parseCallRef` (`src/modules/capability-execution/call-contracts.ts:65-71`); it is a mismatch between URL wire representation and projected route state. No URL should be treated as an authoritative Call lookup before owner authorization.
- **Behaviour per affected surface:** Web receipt → Get help, including refused and review-needed receipts, can land on the malformed-reference warning; `SupportStatusSection.tsx:20-38` then offers generic **Open Calls**, not **Open this Call**. `useSupportHelpPage.ts:5-7` omits the CallRef from email for malformed/absent states. Workspace menu Support starts from `APP_NAVIGATION`'s `/support` entry (`src/lib/navigation/app-navigation.ts:97-104`, `src/components/ae/layout/app-shell/WorkspaceMenu.tsx:57-76`); `/admin` denial **Ask an Admin for access** uses `<Link to="/support">` (`src/components/ae/layout/AeRouteError.tsx:179-182`, `route-error.contracts.ts:5-7`). Both pass *no* CallRef, but the validator projects `{kind:'absent'}` and the register observed the same object serialized, hence a spurious invalid-reference warning. Direct plain `/support` without a serialized object projects absent and presents general help. Chat/HTTP/MCP/CLI have CallRef/Call-status continuations rather than this browser navigation boundary; no comparable URL mutation was established. MCP `projectMcpActionNext` preserves validated CallRef in a status continuation (`src/modules/actions/mcp-journey.ts:19-30`). Neither Support page nor email is a payment remedy action; it is an escalation/handoff.
- **Source owner and adapters:** `src/routes/support.tsx:10-22,40-43` owns URL decoding and view projection; `src/components/ae/support/help/help.contracts.ts:28-40`, `AeSupportHelpPage.tsx:20-39`, `components/SupportStatusSection.tsx:13-43` own display; receipt links and workspace/admin producers above. Tests: `tests/unit/routes/support-route.test.tsx:110-151` separately tests a raw URL *entering* validation and renders a manually supplied projected search; its Link is mocked (`:18-54`). `tests/unit/routes/call-status-route.test.tsx:47-60,175-180` builds a test `/support` route without the production `validateSearch`, so its raw-link assertion does not cover this edge. No route-with-production-validator round trip established by those tests.
- **Root class:** contract gap (URL search wire type versus route projection), with presentation consequence.
- **Status-quo challenge:** A working Support route that advertises a broken Call handoff and says an absent generic reference is invalid is not mature. Preserve safe reference handling and authorization; challenge whether a generic support link should generate any query string at all.
- **Candidate disposition:** fix the wire/projection mismatch and generic empty-link behaviour for safer, more intuitive escalation; do not turn URL possession into Call authorization.

## PC-13 — Credit purchase has no Call/receipt link
- **Register claim on current main: holds; the ledger row does not hold a raw CallRef.** `CreditLedgerPanel.tsx:20-32` passes `accountHistory` straight to `AccountHistory`. `AeAccountHistoryTable.tsx:159-175` labels a purchase through `accountHistoryLabel` (`src/components/ae/console/owner-credit-format.ts:72-79`) and always renders “Source link: Unavailable from Account history.” The `AccountHistoryEntry` wire schema has transaction ID/ref, signed AUD account and document effects, `sourceRef: null`, and a digest, **not** `callRef` (`src/modules/money/internal/account-history.ts:4-25`). Formance mapping reads `metadata.call_digest` to check reserved addresses and returns it as a one-way `sourceDigest` on `BUYER_SALE_SETTLED`, while `sourceRef` remains null (`src/modules/money/internal/formance-reads.ts:486-497,527-537`). A digest is not a navigable CallRef; a transaction reference is not proven a CallRef. Formance booking writes the Call digest (`src/modules/money/internal/formance-transaction-templates.ts:664-681`). A naive link from the digest would be invented attribution.
- **Behaviour per affected surface:** Web Credit → Ledger offers exact transaction details and signed effects but no Call/receipt jump; Activity separately builds `/calls/${encodeURIComponent(callRef)}` (`src/components/ae/activity/useAeActivity.ts:163-182`). Agent/CLI/MCP Call status can use CallRef, but this authenticated *Account history* response omits it (`account-history.ts:4-25`), so transporting that same result through another client does not restore a link; no HTTP/MCP/CLI Account-history link is established. Other money obligations and Call records store CallRef (`src/modules/money/internal/convex-schema.ts:535-599`), but this Formance transaction-history projection does not.
- **Source owner and adapters:** Formance read and `AccountHistoryEntry` contract above; Credit presentation `CreditLedgerPanel.tsx:20-32`, `AeAccountHistoryTable.tsx:164-175`; owner authentication boundary covered by `tests/unit/convex/money-account-history.test.ts:22-53`. `tests/unit/money/account-history.test.ts:34-55` explicitly expects `sourceLinkCoverage:'unavailable'` and all `sourceRef` values null. Coverage is a documented limitation, not merely a forgotten JSX anchor.
- **Root class:** money record (source attribution contract), not a pure presentation omission.
- **Status-quo challenge:** A booked purchase that cannot be followed to its Call is unacceptable for an account ledger meant to explain spend, but a false link is worse. Determine whether a trustworthy authenticated CallRef-to-transaction mapping can be supplied without relaxing Formance attribution or leaking another owner's record.
- **Candidate disposition:** redesign the source-attributed read model before presenting links; improves safety and reconciliation ergonomics. No synthetic CallRef from a digest.

## PC-14 — Sub-cent Activity obscures exact known spend
- **Register claim on current main: holds.** `useAeActivity.ts:163-180` passes known `audAmountUnits` (AUD exponent 6) to `formatDisplayAmount`; monthly `spend.spendUnits` takes the same path (`:271-279`). Shared `src/modules/money/internal/display-price.ts:4-17,37-40` deliberately caps **both indicative prices and settled/known amounts** at two decimal places and renders any nonzero amount below A$0.01 as `<A$0.01`. Thus different exact Call charges all share the same label; even a monthly exact total below one cent shows a bound. This is a presentation choice, not evidence of rounding the underlying money record. `CallMoneyFacts.tsx:53-65` presents receipt usage with `formatCurrencyAmount`, which preserves exponent-level precision (`src/modules/money/internal/exact-amount.ts:171-183`), e.g. AUD 0.001404. Credit ledger signed amounts also use the capped formatter (`owner-credit-format.ts:82-85`). Additional related loss: Activity CSV constructs `costAud`, GST and net via `Number(units)/1_000_000` and `.toFixed(2)` (`useAeActivity.ts:36-41,137-152`), so sub-cent amounts can export as `0.00`, although the JSON export path needs separate review before claiming its precision.
- **Behaviour per affected surface:** Web recent Calls/monthly Activity hide exact sub-cent values while receipt preserves them; Credit ledger has the same compact cap. Chat's Quote and HTTP/MCP/CLI `tool.quote` return exact `price` `{currency,units,exponent}` (`quote.ts:113-129`, `quote.actions.ts:27-48`); CLI quote prints raw units/exponent (`tools/ae/commands/call.ts:396-415`). No source evidence these machine contract amounts are rounded by Activity formatting. No live payment performed in this census.
- **Source owner and adapters:** `src/components/ae/activity/useAeActivity.ts:38-41,137-152,163-180,271-279`; money display versus receipt formats above. Tests: `tests/unit/money/display-price.test.ts:5-7,23-29` pins tiny-value display even for a *known* amount; `tests/unit/components/ae-activity-filters.test.tsx:36-102,125-137` covers ordinary amounts/released no-charge, not reconciliation of sub-cent rows and export. `tests/unit/ui/demand-console.test.tsx:409-411` asserts the ledger's sub-cent marker.
- **Root class:** presentation (with CSV export fidelity as a neighbouring contract gap).
- **Status-quo challenge:** A compact bound may be fine for an *indicative* market price, but a booked transaction, monthly total and exported financial amount must not masquerade as a rounded zero or imprecise bound when exact facts exist. The receipt proves exact precision already exists.
- **Candidate disposition:** redesign exact-known money presentation and CSV precision while retaining a distinct estimate treatment if justified; makes spend more intuitive and reconcilable. Do not change booked units to fix a display problem.

## PC-43 — One-Tool Quote versus expected multi-Tool spend
- **Register claim on current main: holds for one-Tool schema; independent composition is an assigned harness boundary, not automatically an AE defect.** `src/modules/capability-execution/quote.ts:20-39,113-139` takes exactly one `toolRef` plus concrete `input`, returns one expiring committed Quote with one exact price and one `tool.call` continuation (`quoteRef`, idempotency key). The Call input takes just `quoteRef` and key (`call-contracts.ts:91-101,121-130`). Durable issue stores one Tool/version, normalized input, price and authority (`convex/lib/capabilityExecution/quotes/issueQuote.ts:246-267,313-335`); Call reading binds principal/credential and quote state/expiry, yields the single bound Tool/price (`convex/lib/capabilityExecution/quotes/readForCall.ts:31-75`). There is no bundle components/total/recovery object on these public schemas. The register's Mercator USD 0.006 two-node advisory Quote is external free-path evidence, **not** proof that AE should issue one Quote for unrelated purchases.
- **Behaviour per affected surface:** HTTP `/api/v1/tools/quote` and `/api/v1/tools/call` register POST handlers (`src/routes/api.v1.tools.quote.ts:1-10`, `api.v1.tools.call.ts:1-10`); MCP buy set includes `tool.quote`/`tool.call` (`src/modules/actions/mcp-toolsets.ts:3-7,27-42`); action declares HTTP/MCP/CLI/chat surfaces and no Call at quoting time (`quote.actions.ts:27-49`). CLI `ae quote` displays one exact price/expiry and JSON Quote (`tools/ae/commands/call.ts:396-415`); CLI `ae call` independently quotes, retains a single Call recovery and submits it (`:417-459`), not a multi-Tool transaction. Chat exposes the same `tool.quote`/`tool.call` actions (`src/modules/chat/openui-bundle.ts:8-19`). A harness **can request separate Quotes and sum exact AUD units before invoking either Call**, provided both are committed/current and it accounts for expiry/changed policies; current AE API does not return an aggregate decision or atomic cross-Call recovery. No source or live evidence here proves a harness actually completes this sequencing or resumes between two paid Calls.
- **Source owner and adapters:** public `quote.ts`, `quote.actions.ts`, Call contract and Convex Quote/Call owners above. Tests: `tests/unit/convex/capability-quotes.test.ts:107-145,166-210` cover issuance/state/races; `tests/unit/capability-execution/current-tool-quote.test.ts:64-120` covers current Tool drift; `tests/unit/capability-execution/quote-inspect-continuations.test.ts:48-81` covers refusal guidance. None is an observed multi-Tool paid harness run or a bundle guarantee.
- **Root class:** contract gap *only if* AE offers a quoted bundle as one commercial choice; for independent Tools, an unproven task-level harness/recovery boundary, not missing AE aggregation.
- **Status-quo challenge:** A mature Agent can inspect full expected task spend before its first paid step even when it composes independent Calls; separate, expiring Quotes are sensible, but the task must also survive a stop between Calls. If AE advertises a one-price multi-Tool bundle, pretending per-Tool Quotes bind its total, components or recovery is unsafe.
- **Candidate disposition:** accept separate Quote/Call as designed for independent contributions, subject to a controlled harness proof; redesign a *real* bundled commercial product only if Joel elects to offer one. Value: authority/money safety and intuitive pre-purchase spend visibility. Paid cross-Call proof is blocked on a controlled fixture, not on Quote-schema reading.

## Shared boundaries
- **Within G4:** PC-12's receipt Support hop and PC-13's Credit → Call hop both need an authenticated, stable CallRef, but have distinct failures: URL serialization versus missing money attribution. PC-13 and PC-14 share Credit ledger presentation, while PC-14's actual precision loss is formatter/CSV, not a Formance rounding claim. PC-43's exact quoted AUD units and PC-14's display/export must not diverge; the Quote still must not be mistaken for a settled Charge.
- **G1 Find / G2 choice:** A multi-Tool task's expected spend depends on finding the *right callable* components, current price and input schema (PC-02/04/09/42). A correct sum of irrelevant Quotes is not task success. Indicative catalogue price differs from caller-bound Quote and charged receipt.
- **G3 Agent governance:** Per-Call/grant/budget and principal-binding policy changes (PC-15) can invalidate one or both separate Quotes; total displayed to an Agent must not imply aggregate authority. Generic Admin Help's broken `/support` link straddles G3/G8 access messaging.
- **G5 publish/earn:** Provider obligations refer to CallRef; reconcilable buyer ledger links and Provider earnings need to agree on the actual charged Call, not on estimated price (PC-26).
- **G6 retain/repeat:** Neither saved Tool selection nor resumed task should reuse expired Quotes; Call/status/idempotency must survive multi-step task interruption.
- **G7 developer / G8 operate:** CLI `ae call` has per-Call retained recovery, not full task continuation; support/refusal and operator exception journeys need safe CallRef handoffs. Credit history belongs to authenticated owner, not a public support URL.
