# G6 reference — Retain unmet demand and repeat

Scope: PC-39, PC-40 and PC-41. AE's current behaviour below is from the [papercut register](../2026-09-26-papercut-register.md#highest-priority-register), not a fresh source audit. The [Mercator sample](../../../research/MERCATOR-AECON-BENCHMARK-2026-09-27.md) also found an unmet mediator need presented as unrelated candidates; it did not test retained-demand fulfilment.

## Behaviour: Save an unmet search and notify when suitable supply appears (PC-39)

| Product | How it behaves | Official source URL |
|---|---|---|
| eBay | **Save this search** sits on the results page. Signed-in users revisit saved searches; email alerts report *new listings matching the search*. A saved search is not a promise that an item exists or will appear. | [eBay Saved searches](https://www.ebay.com/help/buying/finding-items-managing-purchases/save-search?id=4051) |
| LinkedIn Jobs | Job alerts notify about *new postings matching preferences*; the member chooses daily or weekly email, app notification, or both. Maximum 20 active alerts. | [LinkedIn Job alerts](https://www.linkedin.com/help/linkedin/answer/a511279/job-alerts-on-linkedin?lang=en) |
| Amazon | Amazon acknowledges Product Availability Alerts, including Available to Order Notifications, in its account/privacy documentation. This is an alert for product availability, **not** evidence of a general saved-search or unmet-category request; the public policy does not establish coverage for every out-of-stock item. | [Amazon Privacy Notice, examples of information collected and accessible](https://digprjsurvey.amazon.com/csad/help/node/GX7NJQ4ZB8MHFRNJ) |
| GitHub Code Search | A named query can be saved from the search interface and revisited from **Saved queries**. Its saved-search documentation does not offer an alert for future matches; saving and notifying are separate promises. | [GitHub Using Code Search, creating and managing saved searches](https://docs.github.com/en/search-github/github-code-search/using-github-code-search#creating-and-managing-saved-searches) |

**Familiar pattern:** A search or availability context can be saved without retyping, but an alert is a separate, explicit notification contract. Define the trigger, channel and scope accurately; do not label a search bookmark a future-match alert. eBay and LinkedIn alert on matching *new* inventory, whereas GitHub only documents reopening a saved query. AE currently has a separate authenticated 30-day phrase-recording action; its public impossible-need path and even canonical `noMatch` do not expose that action, and irrelevant `degraded` candidates can suppress no-match entirely ([PC-39](../2026-09-26-papercut-register.md#highest-priority-register)).

**AE reason to differ:** A new listing is not automatically an eligible, admitted, callable Tool. Any claim that AE found supply must account for Tool readiness/authority and distinguish a *potential match to inspect* from a guaranteed Quote or completed x402 Call. AUD price and settlement do not justify hiding a truthful save action at no-match.

## Behaviour: Check status and withdraw a saved request without losing control (PC-39)

| Product | How it behaves | Official source URL |
|---|---|---|
| eBay | Saved searches live in a signed-in **Saved searches** list. The user can revisit listings, remove the saved search using its heart, and turn emails off/on separately with the envelope; modifying filters creates a *new* saved search. | [eBay Saved searches](https://www.ebay.com/help/buying/finding-items-managing-purchases/save-search?id=4051) |
| GitHub Code Search | **Manage saved searches** lists named queries and offers edit and delete controls. It does not represent a saved query as a pending fulfilment ticket or notification subscription. | [GitHub Using Code Search](https://docs.github.com/en/search-github/github-code-search/using-github-code-search#creating-and-managing-saved-searches) |
| LinkedIn Jobs | A member can configure alert frequency and channel; the product distinguishes receiving updates from an application. The help page documents alert settings, not a status guarantee that a suitable job will arrive. | [LinkedIn Job alerts](https://www.linkedin.com/help/linkedin/answer/a511279/job-alerts-on-linkedin?lang=en) |
| Amazon | Account information includes Product Availability Alert email-notification settings. This source does **not** establish an individual request-status or withdraw workflow; do not infer one from a global preference. | [Amazon Privacy Notice, accessible account information](https://digprjsurvey.amazon.com/csad/help/node/GX7NJQ4ZB8MHFRNJ) |

**Familiar pattern:** A saved object is discoverable again, removable, and independently controllable from its notifications when alerts exist. An alert on/off switch is not withdrawal; a market-supply request's `saved`, `expired`, `withdrawn`, or `matched` status would require an AE-specific contract, not borrowed terminology. AE's register documents phrase retention for 30 days but not an observed authenticated status/withdraw or later-match journey ([PC-39 and coverage gap](../2026-09-26-papercut-register.md#coverage-still-needed-for-full-proof)).

**AE reason to differ:** Tool discovery is not product stock replenishment. If a Provider may see demand, clarify phrase visibility and withdrawal semantics before exposing it; if matching relies on admission/authority, a Provider's publication alone cannot imply that the buyer may Call. No reference establishes that AE must promise proactive matching rather than a revisitable request.

## Behaviour: Reuse a shortlist across an account, browser and agent harness (PC-40)

| Product | How it behaves | Official source URL |
|---|---|---|
| npm | `npm star` marks a package as a boolean favourite, `npm unstar` reverses it, and `npm stars [<user>]` lists a user's starred packages. This is a registry/user collection, not a browser-local list; no alert or price-lock claim. | [npm star](https://docs.npmjs.com/cli/v11/commands/npm-star/), [npm stars](https://docs.npmjs.com/cli/v11/commands/npm-stars/) |
| GitHub | Stars are found on **Your stars**, searchable and filterable there; starring and unstarring are explicit. Public lists can group starred repositories, but the lists feature is labelled *public preview* and is not needed for basic favourites. | [GitHub Saving repositories with stars](https://docs.github.com/en/get-started/exploring-projects-on-github/saving-repositories-with-stars) |
| Chrome | Bookmarks saved in a signed-in Google Account are available on other devices signed into that account; when signed out, existing bookmarks can remain device-only until deliberately saved to the account. The storage boundary is made explicit. | [Chrome Get your bookmarks on all your devices](https://support.google.com/chrome/answer/165139?hl=en) |
| eBay | Signed-in saved searches are visible in the user's feed or Saved area, independent of the immediate results page. This is a saved *query*, not an item favourite. | [eBay Saved searches](https://www.ebay.com/help/buying/finding-items-managing-purchases/save-search?id=4051) |

**Familiar pattern:** Distinguish saved *queries/needs* from saved *specific items*. Make the account/device persistence boundary clear, offer remove/revisit, and avoid suggesting a local browser shortlist follows a signed-in user into another browser or CLI. AE currently accurately discloses browser-local, potentially session-only saved Tools; the register says a different browser or agent harness cannot reuse that shortlist ([PC-40](../2026-09-26-papercut-register.md#highest-priority-register)). None of these references equates a favourite with a ranking override or an automatic repeat purchase.

**AE reason to differ:** Reusing a Tool identity does not freeze its current price, readiness, permissions or Quote; a repeat Call still needs live Tool facts and fresh Quote/authority. That does not justify browser-only persistence if cross-harness repetition is a supported customer promise.

## Behaviour: Make no-results actionable in CLI text without changing machine truth (PC-41)

| Product | How it behaves | Official source URL |
|---|---|---|
| GitHub CLI | `gh search issues` accepts query/filter flags and `--json` fields. The formatting reference distinguishes line-based default output from structured `--json`, with optional `--jq`/templates. A read-only public no-hit probe of `gh search issues 'qzyxwvu_nomatch_aecon_70918' --repo cli/cli --limit 1` produced **blank stdout** in text mode and `[]` with `--json number,title` (observed locally, not a documentation guarantee). | [gh search issues](https://cli.github.com/manual/gh_search_issues), [gh formatting](https://cli.github.com/manual/gh_help_formatting) |
| Stripe CLI + API | Resource commands include `list` and print the API response as JSON in the official CLI example. The Products list API specifies an empty `data` array when no further products are available; it does not prescribe a human-language next-action sentence or prove a no-result CLI text rendering. | [Stripe CLI resource commands](https://docs.stripe.com/cli/resources), [Stripe list products](https://docs.stripe.com/api/products/list) |
| npm CLI | `npm search` documents ordinary output, `--json` machine output and tab-separated `--parseable` output, while exposing `--searchopts` and `--searchexclude` for refining results. Its docs do not promise particular no-hit guidance in ordinary output. | [npm search](https://docs.npmjs.com/cli/v11/commands/npm-search) |

**Familiar pattern:** Keep one search result contract and offer a parseable machine form alongside readable terminal output. These references **do not** establish that mature CLIs always print a helpful next step: GitHub's observed empty text was silent. AE can improve ergonomics beyond that baseline by translating an already-computed `next: broaden` and suggestion into human text (and MCP's text summary) without inventing a different recommendation. AE's HTTP/MCP structured output and CLI JSON already preserve that continuation while CLI plain text omits it ([PC-41](../2026-09-26-papercut-register.md#highest-priority-register)).

**AE reason to differ:** Tool suitability, callable authority and x402 pricing make a false positive more costly than a blank generic search; next-action text must not invite a paid Call of an unrelated/degraded Tool. The reason to preserve exact machine fields across surfaces is Agent ergonomics, not a new settlement-specific transport protocol.

## Anti-patterns mature products avoid

- Confuse a bookmarked query with an active alert, a matching listing with a guaranteed available/callable offer, or a notification with a transaction ([GitHub saved searches](https://docs.github.com/en/search-github/github-code-search/using-github-code-search#creating-and-managing-saved-searches), [eBay saved-search email wording](https://www.ebay.com/help/buying/finding-items-managing-purchases/save-search?id=4051)).
- Conflate deletion of the saved object with muting notifications: eBay exposes separate controls ([eBay](https://www.ebay.com/help/buying/finding-items-managing-purchases/save-search?id=4051)).
- Imply device-only saved state is available in another signed-in context without moving it to an account, as Chrome explicitly distinguishes those storage locations ([Chrome](https://support.google.com/chrome/answer/165139?hl=en)).
- Invent a CLI next step not present in its machine result, or misrepresent an empty list as a transport error. GitHub offers a `--json` contract, while Stripe documents empty `data` on a list boundary ([GitHub CLI](https://cli.github.com/manual/gh_help_formatting), [Stripe Products list](https://docs.stripe.com/api/products/list)).

## Questions the references raise for AE

1. Does saving an unmet Tool need mean **a private bookmark only**, **a 30-day market-demand signal**, or **an opt-in availability alert**? eBay, GitHub and LinkedIn make different promises; AE's phrase-recording action alone cannot settle the buyer promise or whether a Provider sees the phrase ([eBay](https://www.ebay.com/help/buying/finding-items-managing-purchases/save-search?id=4051), [GitHub](https://docs.github.com/en/search-github/github-code-search/using-github-code-search#creating-and-managing-saved-searches), [LinkedIn](https://www.linkedin.com/help/linkedin/answer/a511279/job-alerts-on-linkedin?lang=en)).
2. If alerted, what qualifies: **newly listed**, **admitted and callable for this account**, or **actually fit for the saved need**? Should alerts be in-app, email, agent-readable, or a subset, at what cadence? eBay alerts on listings; LinkedIn offers cadence/channels; neither settles Tool authority ([eBay](https://www.ebay.com/help/buying/finding-items-managing-purchases/save-search?id=4051), [LinkedIn](https://www.linkedin.com/help/linkedin/answer/a511279/job-alerts-on-linkedin?lang=en)).
3. What can a buyer see and withdraw: **request text/expiry**, **alert setting**, **Provider-facing demand**, and **past-match status**? Are expiry and unsubscribe separate? eBay's search/remove/email distinctions do not define an AE request lifecycle ([eBay](https://www.ebay.com/help/buying/finding-items-managing-purchases/save-search?id=4051)).
4. Should saved Tool favourites be **account-bound and agent-readable**, **browser-local only**, or **both with clearly separate labels**? How does sharing across a buyer's agents respect their authority boundary? npm/GitHub expose account collections; Chrome distinguishes local and account storage ([npm](https://docs.npmjs.com/cli/v11/commands/npm-stars/), [GitHub](https://docs.github.com/en/get-started/exploring-projects-on-github/saving-repositories-with-stars), [Chrome](https://support.google.com/chrome/answer/165139?hl=en)).
5. Should CLI/MCP human text print the structured `broaden` advice verbatim or a concise command/example, and when should it offer **save unmet need** instead? GitHub's CLI no-hit text can be blank; that precedent does not settle AE's more consequential Agent no-match UX ([GitHub CLI search](https://cli.github.com/manual/gh_search_issues), [GitHub CLI formatting](https://cli.github.com/manual/gh_help_formatting)).

**Cross-group boundaries:** G1 owns honest no-match vs unrelated `degraded` results, the prerequisite for PC-39/41. G2 owns whether a newly found Tool is genuinely suitable/callable before any match notification. G3 owns which account/agent may see or act on saved demand and favourites. G5 owns Provider demand visibility and eligible publication. G7 shares CLI/MCP/HTTP presentation and fresh-user next steps. G4 remains the Quote/Call authority and price boundary on reuse; saving is never a Quote or purchase ([grouped register](../2026-09-26-papercut-register.md#grouped-register-customer-promise-and-failure-pattern), [protocol dependency order](../../designs/2026-09-27-maturity-subagent-protocol.md#first-milestone-and-dependency-order)).
