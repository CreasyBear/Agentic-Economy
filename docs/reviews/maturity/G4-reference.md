# G4 reference — Price, resolve and explain Calls

Scope: PC-12, PC-13, PC-14 and PC-43. AE's current behaviour below is **the register's evidence**, not a fresh source or paid-Call audit: [papercut register](../2026-09-26-papercut-register.md#highest-priority-register). The existing [Mercator capability map](../../../research/MERCATOR-DOCS-CAPABILITY-MAP-2026-09-27.md) and [free-path benchmark](../../../research/MERCATOR-AECON-BENCHMARK-2026-09-27.md) distinguish published contracts from observed free Quotes. Source revision for this study: `bb6c50ba5`.

## Behaviour: a credit/ledger row resolves to the object that caused it (PC-13)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe | A balance transaction carries its own `txn_` ID, gross amount, fees, net, type and nullable/expandable `source` referring to the related Stripe object; the Charge separately refers back to its balance transaction and exposes its receipt. The source is **not guaranteed for every type of row**. | [Balance Transaction](https://docs.stripe.com/api/balance_transactions/object), [Charge](https://docs.stripe.com/api/charges/object), [receipts](https://docs.stripe.com/receipts) |
| AWS | Cost and Usage Report line items carry account, operation, time interval and optional `ResourceId`; that resource field is blank for API requests, transfers, credits, discounts and taxes. A cost row is not always a link to one resource. | [CUR line items](https://docs.aws.amazon.com/cur/latest/userguide/Lineitem-columns.html) |
| Twilio | A voice Call has a unique SID and eventually a connectivity price; Usage Records aggregate by account/category/period and do not contain a per-Call SID. Twilio directs invoice reconciliation to its billing-integrated Usage API, not a naïve sum of Call prices. | [Call resource](https://www.twilio.com/docs/voice/api/call-resource), [Usage Records](https://www.twilio.com/docs/usage/api/usage-record), [invoice reconciliation](https://www.twilio.com/docs/voice/why-doesnt-my-invoice-match-what-i-pull-from-the-call-logs) |
| Google Cloud | Detailed billing export associates eligible usage rows with resource identity and project, but the resource field is not universally populated. Its Cost table keeps the billing account and invoice number in the report header, not a claim that each row is one resource. | [Detailed billing export schema](https://docs.cloud.google.com/billing/docs/how-to/export-data-bigquery-tables/detailed-usage), [Cost table](https://docs.cloud.google.com/billing/docs/how-to/cost-table) |

Familiar pattern: show the financial row's own identity and type, amount/status, and its *actual* causal object when available; the link targets that object, not a generic search. Non-Call entries need their own truthful source or an explicit reason why no individual object exists. These references **do not establish** that all balance rows can link to one object. AE reason to differ: **AUD money record and Tool–Quote–Call** require a Call-purchase ledger row to resolve to its authenticated Call/receipt and any reversal or remedy, not to Stripe's underlying payment Charge. The register says AE currently declares Call links unavailable even when Activity holds receipts; that is extra work rather than an acceptable no-source case ([PC-13](../2026-09-26-papercut-register.md#highest-priority-register)).

## Behaviour: support starts from a receipt with the right object ID (PC-12)

| Product | How it behaves | Official source URL |
|---|---|---|
| Stripe | Dashboard search finds a payment, refund, dispute or invoice by object ID or receipt number. A Charge has distinct `id`, `receipt_number` and `receipt_url`. Stripe's separate API `Request-Id` is a troubleshooting identifier; none should be confused with a balance transaction or payment object ID. | [Dashboard search](https://docs.stripe.com/dashboard/search), [Charge object](https://docs.stripe.com/api/charges/object), [request IDs](https://docs.stripe.com/api/request_ids) |
| Stripe Connect | From a connected account's details, Stripe shows that account's support cases; an outstanding requirement's **Contact Support** path opens a pre-filled support form. This documents contextual support, not specifically a prefilled payment-ID field. | [Manage individual accounts](https://docs.stripe.com/connect/dashboard/managing-individual-accounts) |
| OpenAI | API responses expose `x-request-id`; OpenAI recommends logging it for support. A caller can supply `X-Client-Request-Id` to investigate a lost response where no server response ID was received. These are *request* IDs, not proof of a charge or receipt. | [API reference: debugging requests](https://developers.openai.com/api/reference/overview#debugging-requests) |
| AWS | A support interaction can prefill a case's subject, description and service; AWS asks for account, Region, resource IDs and other contextual identifiers. | [Create a support case](https://docs.aws.amazon.com/awssupport/latest/user/create-support-case-from-interaction.html) |
| Twilio | API guidance says to provide the `Twilio-Request-Id` to Support; a voice Call's distinct SID identifies the affected Call. A request ID alone should not be passed off as the billed resource ID. | [API best practices](https://www.twilio.com/docs/usage/rest-api-best-practices), [Call resource](https://www.twilio.com/docs/voice/api/call-resource) |

Familiar pattern: preserve a typed object identifier across the direct **Get help** journey, include context in the case, and make that ID copyable/searchable; generic Help must work without inventing an object. Separate CallRef from HTTP request ID and support-case ID. AE reason to differ: **Call authority/remedy** means an authenticated CallRef identifies the user's specific delivery/charge question; do not expose someone else's Call from a shared or guessed URL. The register reports receipt Help serializing a validation wrapper rather than a raw CallRef and generic Help serializing an `absent` wrapper ([PC-12](../2026-09-26-papercut-register.md#highest-priority-register)); neither is a familiar support entry point.

## Behaviour: a sub-cent Call remains legible and totals reconcile (PC-14)

| Product | How it behaves | Official source URL |
|---|---|---|
| Google Cloud | The Cost table exposes **Cost in micros**, **Unrounded cost** (up to six decimal places) and two-decimal **Cost**. Invoice totals sum the unrounded line items *then* round to two decimal places; default report filters include the costs and credits needed to match the invoice. This is an explicit aggregation rule, not a universal AE rounding rule. | [Cost table: fields and totals](https://docs.cloud.google.com/billing/docs/how-to/cost-table#unrounded-cost) |
| AWS | Cost Explorer/API cost amounts are decimal strings; underlying CUR records rates and usage. AWS explains that Cost Explorer and billing have different granularity/rounding, current-month charges are estimated and the **invoice** is final when views differ. Cash billing and amortized analysis answer different questions. | [Cost Explorer resource API](https://docs.aws.amazon.com/aws-cost-management/latest/APIReference/API_GetCostAndUsageWithResources.html), [CUR line items](https://docs.aws.amazon.com/cur/latest/userguide/Lineitem-columns.html), [Billing versus Cost Explorer](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/differences-billing-data-cost-explorer-data.html) |
| OpenAI | Admin Costs returns currency plus numeric amount in daily/grouped buckets without a documented fixed decimal scale. Its monthly **Cost data** CSV grouped by line item is the specified Enterprise API-consumption reconciliation view; **Activity data** is for usage detail, and organization and UTC billing period must match. It does **not** document a per-request monetary ledger precision rule. | [Organization costs API](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/costs), [Monthly cost export](https://help.openai.com/en/articles/20001072-how-do-i-export-monthly-usage-details-from-the-api-usage-dashboard) |
| Twilio | Usage Records report usage, count, price, currency and period; a published example has five decimal places in `price`, but this is not a guarantee of fixed five-place scale. `totalprice` can differ from the sum of category prices because not all costs appear in a usage category. | [Usage Records](https://www.twilio.com/docs/usage/api/usage-record), [invoice reconciliation](https://www.twilio.com/docs/voice/why-doesnt-my-invoice-match-what-i-pull-from-the-call-logs) |
| Stripe | Balance transaction gross, fee and net are integers in the smallest currency unit. Stripe's Price `unit_amount_decimal` can represent fractional smallest-unit *unit prices*, but its balance transaction is **not** evidence that one settled AUD charge can be sub-cent. | [Balance Transaction](https://docs.stripe.com/api/balance_transactions/object), [Create a Price](https://docs.stripe.com/api/prices/create) |

Familiar pattern: show meaningful precision wherever a value is an exact usage/Call charge, retain full calculation precision in source records, identify estimate versus posted money, and explain the **specific** total's inclusion, period and rounding rule. Do not show every positive sub-cent charge as the indistinguishable `<A$0.01`, sum independently rounded display strings, or silently imply usage estimates are invoices. AE reason to differ: **AUD prepaid Call accounting** can have a receipt at `AUD 0.001404` even though ordinary bank/Stripe settlement is in cents; the exact Call charge and credit-balance arithmetic must agree with the authoritative AUD ledger, not import Google or Stripe's rounding policy. AE Activity currently masks that receipt amount in the row and monthly spend ([PC-14](../2026-09-26-papercut-register.md#highest-priority-register)).

## Behaviour: estimate a multi-contribution task before spending; bind a bundle only when sold as one choice (PC-43)

| Product | How it behaves | Official source URL |
|---|---|---|
| Mercator | Its documented plan includes 1–10 nodes with endpoint, input and dependencies. Free `quote_plan` / `POST /v1/quote` returns per-node prices, stages, total and expiry. The quote is **advisory**: submission revalidates price against approved total and node caps. A paid submission uses a persisted idempotency key, returns a durable job ID, then supports polling, cached results and `partially_succeeded` per-node failures; completed purchases remain billable if other nodes fail. These are *documented* paid contracts, not an executed paid-job observation. | [Quote a plan](https://mercator.sh/docs#quote-a-plan), [Create a job](https://mercator.sh/docs#create-a-job), [Get a job](https://mercator.sh/docs#get-a-job) |
| Stripe | A Quote can include multiple products as line items, amounts and expiry/status; draft is editable, finalized/open is awaiting acceptance, and accepted generates an invoice or subscription. This is an accepted commercial quote for those products, **not** a guarantee of an arbitrary multi-Provider execution workflow. | [Quotes overview](https://docs.stripe.com/quotes/overview), [Create a quote](https://docs.stripe.com/api/quotes/create) |
| AWS | Pricing Calculator groups several service estimates, lets a user inspect calculations and export/share expected costs **before** using services. It is a planning estimate, not a prepaid authorization or binding quote; actual bills are separate and the invoice is final. | [Pricing Calculator](https://docs.aws.amazon.com/pricing-calculator/latest/userguide/what-is-pricing-calculator.html), [Billing versus Cost Explorer](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/differences-billing-data-cost-explorer-data.html) |

Familiar pattern: a planning estimate aggregates known components and flags its validity and exclusions; a binding commercial choice states what is included, approved ceiling, expiry, and what happens after partial execution. Resume a paid step by its existing identity instead of assuming a timeout means safe repurchase. Stripe separately documents same-key idempotent retries, but its key retention may end after 24 hours and even an initial `500` response is replayed; do **not** infer a general guarantee of eternal or successful retries ([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)).

AE reason to differ: **Tool–Quote–Call / AUD authority / x402**. The register states Joel assigned independent Tool composition to the customer's harness: inspect each current AE Quote, sum the expected AUD spend and enforce the task budget *before* the first Call, then resume/check each Call separately. There is no reason to invent an AE-issued aggregate Quote merely to summarize independent purchases. If AE *offers one quoted bundle*, by contrast AE must bind its total, components and recovery under one commercial choice; today's single-Tool Quote/Call does not do that ([PC-43](../2026-09-26-papercut-register.md#highest-priority-register)). The existing [Mercator free-path benchmark](../../../research/MERCATOR-AECON-BENCHMARK-2026-09-27.md#functional-probes) observed USD 0.003 one-node and USD 0.006 two-independent-node advisory Quotes with no paid job. Do not present Mercator's published retry/refund contract as observed reliability, or treat a static illustrative travel subtotal as a live Quote ([travel example](https://mercator.sh/use-cases/travel-search)).

## Anti-patterns mature products avoid

- Orphan a financial row when its underlying Call exists; conversely claim that aggregate usage, tax or manual adjustment always has one source resource ([Stripe nullable source](https://docs.stripe.com/api/balance_transactions/object), [AWS optional ResourceId](https://docs.aws.amazon.com/cur/latest/userguide/Lineitem-columns.html), [Twilio aggregate records](https://www.twilio.com/docs/usage/api/usage-record)).
- Drop the object identity at the support handoff, mix object IDs with transport request IDs, or make generic support require a fake object ID ([Stripe search](https://docs.stripe.com/dashboard/search), [OpenAI troubleshooting IDs](https://developers.openai.com/api/reference/overview#debugging-requests)).
- Make all sub-cent rows identical, add individually rounded display values expecting equality, or label a provisional spend chart as the final invoice ([Google unrounded totals](https://docs.cloud.google.com/billing/docs/how-to/cost-table#unrounded-cost), [AWS estimated versus final](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/differences-billing-data-cost-explorer-data.html)).
- Call an unapproved multi-source estimate a binding quote, or retry an uncertain purchase with a fresh identity without first resolving its original result ([Mercator jobs](https://mercator.sh/docs#create-a-job), [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)).

## Questions the references raise for AE

1. **Precision and total:** Should every exact Call row and monthly posted total display as many AUD decimals as the ledger records, or show a compact amount with accessible exact disclosure? How does the displayed month total treat reversals, pending/uncertain charges and rounding? Google rounds summed micros at an invoice boundary; AWS explicitly treats current-period reporting as estimated. Neither chooses AE's AUD policy ([Google](https://docs.cloud.google.com/billing/docs/how-to/cost-table#unrounded-cost), [AWS](https://docs.aws.amazon.com/awsaccountbilling/latest/aboutv2/differences-billing-data-cost-explorer-data.html)).
2. **Source links:** Which AE ledger *types* must link to a Call, funding transaction, reversal/remedy or another retained object, and which entries legitimately lack one? Stripe's nullable source and AWS's missing resource IDs show that “every row links to a Call” is the wrong universal contract; PC-13's Call-purchase rows are the clear counterexample to “no links” ([Stripe](https://docs.stripe.com/api/balance_transactions/object), [AWS](https://docs.aws.amazon.com/cur/latest/userguide/Lineitem-columns.html), [register](../2026-09-26-papercut-register.md#highest-priority-register)).
3. **Support contract:** Should receipt Help open an authenticated Call-specific case with a visible CallRef and suggested remedy, or a general prefilled support form; what is the fallback for a removed/inaccessible Call and for generic Help? Stripe proves object lookup and contextual support but not an AE remedy policy ([Stripe search](https://docs.stripe.com/dashboard/search), [Connect support](https://docs.stripe.com/connect/dashboard/managing-individual-accounts)).
4. **Composition promise:** Is AE actually going to *sell* any bundled contribution as one quoted choice, or only expose a harness-side summed estimate for independent Quotes? If bundles are offered, which component outcomes are payable and how do interruption, partial success and settlement bind? Mercator's advisory plan/job and Stripe's accepted line-item Quote show different commitments; the free-path probe does not establish paid execution outcomes ([Mercator](https://mercator.sh/docs#quote-a-plan), [Stripe](https://docs.stripe.com/quotes/overview), [benchmark](../../../research/MERCATOR-AECON-BENCHMARK-2026-09-27.md#functional-probes)).

Cross-group boundaries: **G2 choice** owns whether a chosen Tool is callable and its buyer AUD price/input truth before Quote; **G3 governance** owns effective Agent authorization/limits before spend; **G4** owns the accepted Quote, Call-specific money trail and remedy; **G6 repeat** may reuse a prior Tool but must not reuse an expired Quote or duplicate a pending Call; **G5 earnings** sees the Provider side of the same paid Call, not the buyer's credit row ([grouped register](../2026-09-26-papercut-register.md#grouped-register-customer-promise-and-failure-pattern)).
