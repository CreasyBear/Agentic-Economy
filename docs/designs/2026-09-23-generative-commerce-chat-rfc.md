# Generative commerce chat RFC: answer first, then decide and act

Date: 23 September 2026  
Version: 2  
Status: proposed; design and owner approval pending  
Decision owner: Joel  
Scope: the signed-in Ask experience, from a question to sourced choices, optional comparison, explicit purchase approval and actual result. This RFC is a target, not a claim that bundles or output comparisons ship today.

## 1. Problem and thesis

A buyer should be able to ask a question, understand the answer, inspect genuinely comparable options, authorise an exact spend and see what happened without learning AE's internal identifiers. The current transcript puts repeated Search/Details/Compare cards ahead of the answer; generic starters send immediately; mobile chrome and tall cards reduce reading room (`agent://ChatLiveRoast/report`, findings 8–10). Existing chat compares listing facts, not executed outputs. A generation has an eight-tool, six-step and one-Call fence (`convex/chatTools.ts:76-85,275-281`; `agent://JevBundleScout/report`). Signed-in pending Calls and subscribed results already exist; replacing them with a model-facing checkout would discard the real authority seam (`convex/chatCall.ts:62-149,154-179`).

**Thesis:** the answer is the front door; commerce is a visible sequence of choices and *separate, accountable* Calls. The model may propose and explain. Only server-verified Quotes and an owner's canonical CallRef decision can cause dispatch. Plain language first, technical facts on demand. This is a consumer product, not a developer console in chat.

## 2. Goals and non-goals

**Goals:** answer-first reading; concise, collapsible work; inline sourced claims; relevant next questions; editable starters; signed-in Stop/Regenerate/Copy/Retry; navigable persistent desktop history and compact mobile reading space; understandable selection, filtering and comparison; two or more comparable actual outputs; a capped, exact-Quote multi-step proposal; per-Call approval and honest outcomes. Every component must pass a **five-second non-technical comprehension check**: a new person can say what this is, what it costs or does not yet cost, what action comes next, and what is known versus claimed without opening Technical.

**Non-goals:** replacing Convex agent streaming or canonical owner approval; automatic spending, a model-created grant or browser-held key; an atomic multi-merchant checkout or guarantee that every step succeeds; fabricated reviews, preview outputs, source citations or refunds; exposing raw reasoning/private chain of thought; converting unadmitted directory listings into callable Tools; adopting an entire chatbot framework, another history store or a second payment/Call path. No outcome comparison from listing descriptions or mock results. Guest session persistence is separate from signed-in history; a guest must not be promised durable history.

## 4. Functional and non-functional requirements

| ID | Requirement |
|---|---|
| F1 | The completed **answer precedes work cards** in reading order. While streaming, show a compact, accurate activity line; after completion, put the answer first, then a collapsed “How I got this” section containing real search, Quote and Call activity. Preserve chronological event order inside the disclosure. Sources attach to the specific claims they support; label provider-reported versus AE-observed facts, stale or unavailable evidence and the actual link. Never cite a Tool result as proof of an unexecuted comparison. Related follow-ups appear after the answer and **fill the composer for editing**, not send on click. Source and related sections disappear when nothing trustworthy exists (`agent://ChatLiveRoast/report`, findings 3–5,8; `src/components/ae/chat/presentation.ts:102-149`). |
| F2 | Signed-in Stop cancels the *turn*, not merely browser rendering: use the owned `cancelTurn` and read its `inFlightEffects`; show “Stopping response; existing Calls may still finish” when appropriate. Never say cancellation reverses a Call or charge (`convex/chatTurns.ts:81-125`). Regenerate starts a new, clearly labelled attempt from the selected prompt/context; preserve the original answer and original CallRefs, never replay an old Quote/Call or auto-approve. Copy copies rendered answer text with attributable source URLs (no private credential or raw tool payload). Retry resumes a refused/failed **read or answer** through a fresh turn; uncertain Call/payment instead links to status/reconciliation. Disable duplicate requests while one is active. |
| F3 | Pending → awaiting owner → approved/dispatching → delivered, denied, expired/refused or outcome uncertain are distinct states. A pending card shows the human Tool, “Sold by” verified Provider or “Listed on” source Host, exact Quote/currency, **every value that will be sent to the Provider** under plain-language field labels, expiry and a remaining cap only if verifiable. Refs/digests may go under Details; consequential input never does. Approval by CallRef goes through the existing owner mutation and fresh MFA; approval UI and AI SDK approval parts merely represent state (`convex/chatCall.ts:85-129`; `convex/lib/callLifecycle/authorityHandlers.ts:847-865`). |
| F4 | Authenticated desktop has a persistent, resizable only if useful history rail with Today / Yesterday / Previous 7 days / Older groups, New chat, owned-thread search, active state and **Load more**. Stable sort and cursor preserve the current selection across new messages and search; show loading, empty and error states. Use current server pagination rather than another index (`convex/chatThreads.ts:113-132`; `src/components/ae/chat/chat-session/useChatSession.ts:101-116,173-179`). At mobile sizes history becomes a Sheet, not a second simultaneous rail; compact header exposes Back/History/New and keeps the composer and pending approvals reachable (`src/components/ae/chat/chat-session/components/ChatHeader.tsx:29-84`). |
| F5 | The empty state says what Ask can actually do. Starters insert editable text and focus the composer. Signed-out and signed-in copy distinguish discovery from approval-only purchasing. No auto-send or misleading saved-history promise (`src/components/ae/chat/ChatTranscript.tsx:111-133`; `agent://ChatCodeAudit/report`). |
| F6 | **OptionsGrid** shows 2–4 sourced, eligible Tool options, one-line outcome, “Sold by” verified Provider or “Listed on” source Host, fixed/indicative/unknown price with per-Call basis, and “Ready to use” only with current observation; otherwise “Not yet verified” or “Price to be confirmed”. Provenance mechanics are in Details, never silently upgraded. **FilterChips** expose constraints and matched counts, are removable and requery the same corpus; Reset restores results. **ComparisonTable** aligns sourced decision facts and labels absent evidence. On mobile, use an aligned two-option dimension view that fits at 320px; serial cards requiring remembered prices are not a comparison. Non-production/degraded candidates cannot be recommended as production alternatives on price alone (`src/modules/registry/internal/listing-projection.ts:6-45`; `agent://ChatLiveRoast/report`, findings 6–7). This is *listing comparison*, never output comparison. |
| F7 | **OutputDiff** accepts 2+ admitted Tools with equivalent validated input. Each has a fresh Quote, separate pending Call and separate owner approval, **including free Calls**. Show **both actual paid outputs and both receipts** whenever two Calls complete, even if their formats differ. Key each result by CallRef, ToolRef, input digest, execution time and receipt/evidence ref where available. Align fields or calculate differences only when meanings and units match; otherwise show originals side by side and say “Not directly comparable”. Failure/denial/uncertainty remains visible, excluded from comparative claims but not hidden. No completed Calls means “No results to compare,” not a preview (`convex/chatCall.ts:79-145`; `src/modules/chat/tool-card.ts:114-129`). |
| F8 | **BundleBuilder** offers a Jev-assessed ordered plan; Jev cannot authorise it. The upfront purchasable batch includes **fixed-input, independent steps only**: each names purpose, admitted Tool, complete Provider-bound input, fresh QuoteRef/expiry, exact amount/currency and separately held pending CallRef. Dependent steps are described but excluded from the batch and upfront exact total: wait for a delivered, evidence-verified predecessor, then construct and display the complete new input, obtain a fresh Quote and seek separate canonical approval. A refused, dispatching or uncertain predecessor blocks its dependents. For the fixed set, the server records owner/account, exact CallRefs, version, one binding currency, sum of **held** amounts and the user's aggregate cap, checking fresh consumed Quotes and hold states; held total must not exceed cap. The existing Formance reservation atomically holds buyer AUD and daily/monthly headroom **per Call** before owner approval, and is the concurrency authority, not a second allocation at approval (`convex/lib/callLifecycle/callReservationActions.ts:222-252`; `src/modules/money/formance-schema.ts:367-400`). Reject mixed/non-comparable currencies; edit or expiry invalidates the batch and requires reconfirmation. “Approve all” submits exactly the recorded set and version, then performs N canonical owner decisions, with item outcomes from canonical status read **before and after each** decision, never the mutation response alone. Before clicking, state the exact maximum, number of Calls and “Some Calls may complete and charge even if others fail”; after, put each outcome beside remaining **aggregate** spend. Never sum per-card remaining-cap snapshots (`convex/chatCall.ts:108-129`). Release definitely unused holds on denial, expiry or blocked dependency; retain uncertain allocations until reconciliation. No atomic checkout claim. |
| F9 | **PurchaseApproval** projects server-read Quote/pending Call facts, never prose pricing. **Receipt/Outcome** distinguishes approval, dispatch, payment, delivery and unknown reconciliation and links actual Call receipts, not funding invoices. **AnalysisPanel** uses only owner-authorised, bounded, redacted projections of executed Call outputs tagged with CallRef. Its generation has **no Quote/Call tools** (no trusted purchase authority or `toolChoice: 'none'`), and raw Provider output never enters model context. Every claim links eligible result evidence and identifies omitted/uncertain steps. A follow-up never issues another Call silently (`convex/chatCall.ts:121-149`; `agent://GenUiPatterns/report`). |
| N1 | Every component passes the five-second non-technical comprehension check. Default labels: “Options”, “Compare details”, “Compare results”, “Plan and total”, “Approve this Call”, “Result”, “How I got this”. Option labels are “Sold by” for verified Provider, “Listed on” for Host, “Ready to use” / “Not yet verified”, and “Price to be confirmed” where appropriate. Provenance and refs/digests go in Details except copyable recovery references. **Every Provider-bound input value stays visible on the approval card**, as do cost/currency and unresolved state. |
| N2 | At 1440px, 390px, 320px and 200% zoom: no document overflow, covered content or obscured composer/approval; logical reading order, keyboard reachability, announced changes, touch targets and safe-area padding. Approval focus moves to its heading on arrival, to status after decision and to a fresh-Quote action on expiry; Stop returns to the stopped turn/status and Regenerate to its new attempt, with no focus loss or duplicate activation. “Approve all” has an accessible name including Call count and exact maximum. Sheet closes back to its trigger. Never auto-scroll a reader away from earlier messages. |
| N3 | Pure presentational leaves receive validated view-models and callbacks, not Convex hooks, money calculation or domain types in `.tsx`. Reuse existing `src/components/ui` primitives and semantic tokens. New compounds own their hooks/contracts/skeletons; no oversized chat mega-component or alternate data authority. |

## 5. Target information architecture and sketches

```text
/t/new, /t/$threadId
Desktop:  [History: New / Search / Today / Yesterday / Older / More]  [Answer + composer]
Mobile:   [Back · History · New]                                [Answer + composer]

QUESTION
Answer in plain language [source beside each factual claim]
[Options: choose / filter / compare details]   (when actual eligible options exist)
[How I got this ▸]                              (real work, collapsed)
[Related question → editable composer]         (when useful)

COMMERCE CONTINUATION (fixed-input steps only)
Two Calls · exact maximum $z ≤ your cap $c · some may charge if others fail
[Approve Call 1] [Approve Call 2]  — or [Approve all 2 Calls, up to $z]
[Call 1: delivered → receipt · remaining aggregate spend]
[Call 2: uncertain → status · held amount retained]
[Both original paid outputs + receipts] [Aligned differences, only if valid]
Dependent Step 3: wait for verified Step 2 result → fresh Quote → separate approval
```

The UI does not surface all seven commerce components at once. Start with an answer; show OptionsGrid only for a real shortlist, ComparisonTable after selection, and original outputs/receipts after two completed Calls whether or not fields align. Technical differences require compatible meanings. Use collapsible technical detail, not a nested marketplace. Owner approval is consequential; a generic “Continue” must never mean “spend”.

## 6. Projection and data/authority policy

`ListingProjection` already distinguishes present/absent facts, source, provenance, readiness and price; use it to feed options and comparisons (`src/modules/registry/internal/listing-projection.ts:6-45`). Current `ToolCardProjection` has a CallRef and output preview but is not a canonical multi-output analysis record (`src/modules/chat/tool-card.ts:114-129`). Current `readOwnerChatCards` verifies owner/thread, credential, grant, Quote and Call linkage and returns pending/results; extend server-owned projections instead of parsing assistant prose (`convex/chatCall.ts:62-149`). The existing OpenUI parser binds a role to a validated tool card, not arbitrary tool execution (`src/modules/chat/openui-bundle.ts:113-185`).

Proposed *read/interaction contracts* (names illustrative, **not shipped types**): `OptionView` = sourced facts and eligible ToolRef or explicit non-callable reason; `ComparisonView` = selected options and aligned sourced dimensions; `ResultEvidence` = CallRef, ToolRef, input digest, terminal state, original owner-visible output and receipt/evidence ref; `BundleIntent` = owner/account, immutable ordered **fixed-input** CallRef set, consumed QuoteRefs, one binding currency, exact held total, user cap, version and item statuses. Store the intent server-side only after all member holds are confirmed; incomplete/unknown reservations never produce an approvable batch. No new money allocation: individual reservation holds own available funds and period headroom. No domain contract in `.tsx`. Raw Provider outputs remain in owner-authorised result reads, **not model context**. Analysis receives only bounded, redacted facts with CallRef provenance and has no purchase tools.

Jev assesses bounded decision questions and discovery candidates, not a bundle executor; it may rank plan fit but cannot establish price or permission (`src/modules/decision-engine/jev-client.ts:12-53,91-117`; `agent://JevBundleScout/report`). Convex owns Quotes, Calls, history and streaming (`convex/chatGenerate.ts:52-95,98-153`). Current limits are **one Call, eight tools, six steps per generation** (`convex/chatTools.ts:76-85,275-281`). Keep `MAX_CHAT_EXECUTE_CALLS = 1` for every other `agent_key` chat, especially autonomous `spending_policy` and `unrestricted_test_only` credentials; a higher finite execute limit applies **only** when `applicationRef === 'ae-owner-chat'` **and** authority mode is `approval_required`, with a separate finite cap on pending owner-chat Calls per turn. Route multi-Call workflow through bounded server continuations across generations, preserving last-step-for-answer, per-step idempotency and stop points; never raise all ceilings globally. The one-Call fence remains until C6 proves held cap, fixed membership and recovery. Owner-chat generation stops at pending approval; continuation reads CallRef status (`convex/chatGenerate.ts:63-95`; `convex/chatCall.ts:154-179`; `convex/chatTools.ts:489-497`).

## 8. Threat model and failure states

| Threat/failure | Mandatory control |
|---|---|
| Model or UI invents consent, total, price or provider identity | Tool inputs are proposals; server projects bound, current Quote/Call and verified identity. Dedicated `approval_required` owner-chat authority reserves pending Calls only. Fresh-FVA `canonicalOwnerApprovalDecisionHandler` decides each CallRef (`convex/lib/callLifecycle/callReservationActions.ts:331-367`; `convex/lib/callLifecycle/authorityHandlers.ts:847-865`). |
| Prompt injection in Tool outputs/sources asks the agent to approve, hide a charge or run another Tool | Treat Provider output as untrusted data. Selection/analysis inputs are bounded, redacted projections with CallRef attribution, never raw output in the model context. Analysis uses no Quote/Call tools (`createChatAgent` without purchase authority or `toolChoice: 'none'`). A downstream dependent input is displayed completely and separately quoted/approved only after predecessor delivery and evidence verification. |
| Aggregate-cap race across tabs/plans or stale Quotes | The existing Formance reservation atomically holds buyer AUD plus daily/monthly headroom **per Call** (`src/modules/money/formance-schema.ts:367-400`); do not add another approval-time allocation. Server records an immutable CallRef set/version only after confirming all holds and sum of fresh consumed Quotes ≤ user cap in one currency. Approve-all rejects a mismatched set/version. Per-card “remaining” figures are Quote-time snapshots, never summed (`convex/chatCall.ts:108-129`). Race proof covers two tabs, partially held sets and timeout/replay. |
| Stop, retry, regenerate or partial bundle failure duplicates paid effects | Stable per-step idempotency, original CallRef recovery and canonical status reads **before and after each** Approve-all item; derive outcomes from status, not mutation responses, which may refuse after a prior success (`convex/lib/callLifecycle/admissionApprovals.ts:367-403`). Release definitely unused holds on deny/expiry/blocked dependency; keep uncertain holds until reconciliation. No automatic retry of uncertain Calls; stopping generation does not void a pending/in-flight Call (`convex/chatTurns.ts:81-125`). |
| Mixed-currency or unknown budget gives false confidence | Reject aggregate action without a binding one-currency total and verifiable cap; show unknown, expiry and recovery instead of “nothing charged”. Indicative conversions never set a spend cap. |
| Source leak or forged citation | Whitelist attributed URLs and owner-visible result refs; sanitize source text; no raw secrets or private Call output in public shares, copied answer or model follow-ups. |

## 10. Risks, decisions and review gate

1. **Bundle recording on existing holds:** Formance already holds buyer AUD and daily/monthly headroom when each pending Call is reserved (`convex/lib/callLifecycle/callReservationActions.ts:222-252`; `src/modules/money/formance-schema.ts:367-400`). Determine where to durably record the exact fixed-input CallRef set/version and each held/consumed/released/uncertain state, with no second money allocation. Do not enable Approve-all until a two-tab race, partial booking and crash/replay prove membership/cap and unused-hold release. Default: existing individual approvals, no batch action.
2. **Comparable outputs:** require the same semantic input and compatible units/meaning. Default: original outputs side by side and an honest “not directly comparable,” not synthetic scoring.
3. **Freshness/amount:** a displayed amount is not a binding Quote after input or time changes. Default: disable approval, get new Quotes and reconfirm exact total.
4. **Streaming sources:** private reasoning is deliberately excluded by current projection (`src/components/ae/chat/presentation.ts:102-105`). Do not present a generated explanation as raw trace. Default: grounded activity steps and actual attributable source links.
5. **Responsive rail:** keep one history component with desktop rail/mobile Sheet presentation; if a persistent rail damages 1440px reading width, size it conservatively rather than shrinking the answer to a card column.

Review against the existing owner-chat security model in `docs/designs/2026-09-23-platform-cohesion-rfc.md:202-218`, bounded module imports, source/provenance semantics, aggregate-cap race, truthful Call outcomes and the five-second test before implementation. Owner sign-off gates commerce work; this RFC does not assert live paid execution.
