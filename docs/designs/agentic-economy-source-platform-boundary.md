## Problem Statement

Agentic Economy is being built toward a market that agents use when they need a capability beyond those already available in their model and harness. The current product already publishes, admits, discovers, invokes, settles, and recovers atomic Operations, but its future market behavior is not yet available as one capability-boundary call that any outside agent can use from its own harness.

The design problem is to define the SOURCE and PLATFORM requirements that let an agent encounter a missing next contribution, find unfamiliar outside supply, invoke it through Agentic Economy, carry the contribution into its next step, and create observable demand that attracts competing suppliers. These are runtime product requirements, not supplier or buyer onboarding requirements.

## Demand Evidence

- Agents already depend on connectors, MCP servers, APIs, Apify Actors, and computer-use tools when inference alone cannot complete a task.
- OpenRouter demonstrates that callers adopt a unified allocation and invocation surface even when supply remains provider-native.
- The working demand hypothesis is that agents will repeatedly cross capability boundaries while pursuing user goals, and suppliers will compete where those requests accumulate.
- This hypothesis is not yet proven by recurring external Agentic Economy usage. The first product slice must test that behavior rather than assume a mature market.

## Status Quo

- Agentic Economy has an admitted Operation catalogue, stable operation references, input and output schemas, pricing, availability, effects, and data-use fields.
- HTTP, MCP, CLI, `llms.txt`, and `SKILL.md` surfaces expose the existing market and invocation lifecycle.
- Invocation supports completed, pending, refused, reconciliation-required, cancellation, status, and recovery outcomes.
- Supply can be described using AE-native envelopes, OpenAPI, MCP, Agent Plugin MCP, and x402, but most external supply is not yet discovered and translated automatically from provider-native sources.
- Search is catalogue-oriented and keyword-like. It does not yet represent an agent's bounded missing next contribution or explain candidate fit and mismatch.
- Recent AE chat work is useful as a reference client, but must not become the required harness, planning environment, or state container.
- The installed MCP SDK currently exposes protocol `2025-11-25`. Product validation uses the current HTTP and MCP surfaces first. Migration to the stateless `2026-07-28` caller protocol is an independent compatibility step rather than a prerequisite for proving capability allocation.

## Target User and Narrowest Wedge

The first caller is a developer-operated agent running in an external harness. During a real task, the agent reaches a step its installed tools cannot perform.

The narrowest useful wedge is one installed AE capability boundary with separate `resolve` and `invoke` operations:

1. The outside agent sends one self-contained capability lookup to AE.
2. AE resolves the request against the currently admitted catalogue.
3. The agent selects and invokes an unfamiliar Operation through AE.
4. The first slice returns one synchronous contribution in the existing canonical result form.
5. AE records only what it directly observes: demand, candidate exposure, selection, invocation, delivery, failure, and any subsequent switch through AE.

Automatic SOURCE intake, async handles, buyer feedback, reputation, and supplier-facing demand aggregation follow only after this vertical behavior works. The first automatic source family is a bounded remote MCP profile; bounded OpenAPI follows separately.

## Constraints

- The agent and its harness remain owned and operated outside AE.
- AE stays in the invocation path for the selected capability.
- Supplier sources remain native; publishing a complete AE-specific contract is not a prerequisite.
- Calls are stateless at the caller-facing transport boundary. Supplier adapters may maintain bounded internal sessions when required by older suppliers, but that state never becomes a caller dependency.
- AE may judge contract conformance and invocation evidence, but cannot guarantee that a contribution is useful to an arbitrary buyer workflow.
- Existing admitted Operations and HTTP, MCP, and CLI behavior should be reused rather than replaced.
- The design must create the observable beginnings of a market feedback loop, not merely a larger directory. Unobservable downstream outcomes remain unknown.
- Supplier and buyer onboarding experiences are outside this design.

## Premises

1. **Capability allocation is the controlled primitive.** AE owns the point where an agent describes a missing next contribution and receives callable options.
2. **Source standards remain plural.** MCP, OpenAPI, x402, Apify, and future native descriptions feed one market projection.
3. **Translation belongs to AE.** Suppliers state native facts and commercial claims; AE derives identity, normalized fields, conservative unknowns, readiness, and admission.
4. **Invocation remains brokered.** The selected call passes through AE so the market can provide one interface, recovery, metering, and demand evidence.
5. **Continuation is a compatibility target, not a usefulness guarantee.** Results arrive in a declared form the caller can place into its next step. The caller decides whether the contribution was useful, and missing feedback is recorded as unknown rather than inferred.
6. **State is explicit.** Invocation references, task handles, resource references, and input-required handles cross calls as data. AE does not require a hidden session.
7. **Market memory is centralized while agent context is not.** AE remembers capability demand and observed outcomes, not the caller's private conversation or plan.
8. **Reputation separates observation from opinion.** AE-observed conformance, reliability, latency, retries, refunds, and switches are distinct from optional buyer-reported acceptance. Buyer opinion does not initially affect automated allocation.

## Responsibility Boundary

| Party | Accountable for | Not accountable for |
| --- | --- | --- |
| Agentic Economy | Faithful source projection, honoring hard constraints, invoking the selected endpoint and revision under the displayed terms, invocation integrity, recorded evidence, and recovery | Guaranteeing candidate usefulness, supplier output quality, or progress in the buyer's wider project |
| Supplier | Accuracy of capability claims, endpoint behavior, availability, and the contribution returned for valid inputs | How the buyer agent integrates or reasons over the contribution |
| Buyer agent and harness | Describing the missing contribution, selecting supply, providing valid context and authority, and deciding whether and how to continue | Supplier implementation quality or AE routing correctness |

AE reputation is evidence about prior interactions, not a warranty. A caller may report `accepted`, `rejected`, or `unused`, but that report is stored with `buyer-reported` provenance and remains separate from objective evidence. No report produces `unknown`, never an inferred rejection. “Routing correctness” means honoring hard constraints, the selected Operation revision, endpoint, and terms. Candidate fit remains an estimate.

## Cross-Model Perspective

Two clean Ox instances inspected the current repository and challenged the initial framing.

- Ox found that execution and recovery are substantially more mature than discovery and source normalization.
- Its strongest correction was that SOURCE is translation rather than supplier authorship: provider-native descriptions should become AE-normalized market records.
- It recommended controlling capability resolution as the one agent-visible primitive, without importing the caller's plan, thread, or harness state.
- It identified demand memory as a platform responsibility: unresolved capability classes, candidates shown, selections, invocations, failures, switches, completions, and repeat demand.
- It challenged the idea that stable references alone create recurrence. The selected design therefore requires allocation and outcome evidence to accumulate into routing and reputation.

## Approaches Considered

- **Brokered vertical slice:** AE resolves and invokes selected supply through one gateway. Chosen because it creates the complete market behavior and observable feedback loop.
- **Source exchange first:** AE resolves but the agent calls suppliers directly. Rejected as the primary shape because AE would lose dependable invocation, outcome, and switching evidence.
- **Embedded market client:** resolution and routing happen partly inside each harness. Deferred because client fragmentation and optional telemetry weaken the shared market before its central behavior is proven.

## Recommended Approach

Build a brokered, stateless capability market over the existing Operation runtime.

### OPERATIONAL TERMS

- **Contribution:** the bounded output of one Operation, not the buyer's final outcome.
- **Capability request:** the caller's description of its missing next contribution plus hard constraints and optional preferences.
- **Capability class:** an AE-derived, privacy-bounded grouping of similar capability requests used only after aggregation thresholds are met.
- **Fit:** an estimated match between a candidate's declared contract and the capability request.
- **Mismatch:** a declared or observed fact that weakens fit but does not necessarily exclude the candidate.
- **Hard constraint:** a caller requirement that excludes a candidate when contradicted or unknown.
- **Readiness:** AE's latest bounded observation that the configured supplier route can accept an invocation. It is not a guarantee of future availability.
- **Delivered:** AE received and returned a supplier response that conforms to the declared transport and result envelope.
- **Accepted, rejected, unused:** optional buyer-reported judgments about the delivered contribution. They are contextual, not conformance states.
- **Switch:** the caller invokes a different candidate under the same resolution reference after exposure to or invocation of another candidate.
- **Repeat:** the same authenticated caller resolves the same derived capability class in a later independent interaction.

### SOURCE

Each source adapter must produce a versioned observation containing:

- Native source identity, location, revision, observation time, and freshness.
- Provider identity and native capability identifier.
- Human description plus available input and output schemas.
- Native access and invocation method.
- Commercial claims, limits, and authorization requirements when published.
- Declared effects and data use when published.
- Explicit unknowns where the source is silent.
- A callable adapter configuration and readiness observation.

AE then owns the market identity, revision history, normalization, conservative classification, admission, and removal or degradation state. The first automatic adapter reads remote MCP discovery and tool listings. Bounded OpenAPI follows as a separate source milestone. Existing x402 and AE-native sources remain supported.

#### Bounded source profiles

Automatic translation is deliberately incomplete rather than universal.

- **Remote MCP profile:** MCP `2026-07-28` over Streamable HTTP and HTTPS. There is no initialization handshake or protocol session. AE may call optional `server/discover`, then bounded `tools/list`; invocation uses `tools/call` with the required protocol, method, and tool-name headers. JSON Schema stays within configured byte, depth, and validation-time limits. Sampling, roots, arbitrary resource crawling, and execution during ingestion are excluded. A separate compatibility adapter may support MCP `2025-11-25` using `initialize`, negotiated capabilities, `tools/list`, and any returned `Mcp-Session-Id` behind AE's stateless caller boundary.
- **OpenAPI profile:** OpenAPI 3.1; HTTPS; HTTP JSON request and response bodies; local or explicitly allowlisted references; supported parameter serialization; fixed documented authentication; no callbacks, webhooks, arbitrary external `$ref`, streaming, multipart, or undocumented effectful methods in automatic admission.
- Unsupported constructs are rejected or quarantined for an explicit adapter extension. They are never silently projected as callable Operations.

#### Source security and lifecycle

- Source retrieval blocks loopback, link-local, private-network, and cloud-metadata destinations unless the operator explicitly allowlists them.
- The same egress policy applies to admission probes and every runtime supplier request. AE resolves and revalidates destination IPs at connection time, rejects DNS rebinding into blocked ranges, and validates every redirect target before following it.
- Documents, descriptions, schemas, redirects, references, and recursion are bounded. Descriptions are treated as untrusted data and never promoted into platform instructions.
- Unknown effects or data-use behavior fail closed for automatic admission. A candidate with an unknown hard-constrained field is excluded from that resolution.
- Every resolution stores a snapshot map from each exposed candidate to its Operation revision, atomic terms, and individual expiry. Switching is allowed only while the selected alternative's snapshot remains valid. Invocation after expiry returns `stale_resolution` and requires re-resolution.
- If a source changes before invocation, AE may invoke the pinned revision only while it remains admitted, available, and inside the terms expiry. Otherwise AE refuses the stale reference.
- In-flight work retains its pinned contract and terms. Refresh failure degrades readiness until the source freshness window expires, after which new allocation stops.

### PLATFORM

The first agent-visible surface is a stateless capability lookup, provisionally named `resolve`.

Its bounded input describes:

- The missing next contribution in plain language.
- Inputs the caller can provide, including values or schemas where useful.
- The expected output or artifact shape when known.
- Constraints such as maximum price, permitted effects, data use, authorization, and invocation timeout. Supplier latency claims and observed latency percentiles are ranking preferences, never guaranteed hard constraints unless backed by an enforceable service term.

It does not accept or require the caller's full conversation, project plan, work tree, or harness state.

The response contains ranked candidates with:

- Stable Operation reference and revision.
- Fit and mismatch reasons tied to the request.
- Supplier, price, availability, effects, data-use, and authorization facts or explicit unknowns.
- Exact invocation path.
- A resolution reference used for attribution, switching, and later reputation evidence.

Hard constraints are evaluated before ranking. Contradicted or unknown hard-constrained fields exclude a candidate. Ranking algorithm `allocation-v1` then applies ordered comparison: output-schema compatibility (`exact`, `compatible`, `unspecified`); bounded lexical relevance between the capability description and Operation description; readiness (`available`, `degraded`, `unknown`); an explicitly requested price preference; then stable Operation reference as the final tie-break key. Every candidate exposes the ranking version, reason codes, and material unknowns. If none qualify, AE returns `no_match` with excluded-reason counts, not a weak fallback disguised as a match.

The chosen Operation is invoked through AE. The normalized response supports:

- Immediate structured or unstructured content.
- Images, audio, files, resource links, and external artifacts.
- Pending work with explicit task or invocation handles.
- Missing input or authority with a self-contained continuation request.
- Refusal, failure, reconciliation, cancellation, recovery, and alternative candidates.

The same logical contract is exposed through stateless MCP and HTTP. CLI remains a diagnostic and operator-quality client of the same contract.

#### Normative caller contract

- Every caller is authenticated to an AE principal and tenant. Resolution records, invocation handles, credentials, quotas, and telemetry are tenant-isolated.
- `resolve` accepts a caller request reference, bounded capability description, input and output schemas, hard constraints, preferences, and candidate limit. Values are excluded by default. Within a provisional twenty-four-hour window, the reference is idempotent per tenant and canonical request fingerprint: an exact replay returns the same resolution snapshot and does not record another exposure or demand event; reuse with a different fingerprint returns `idempotency_conflict`; replay after expiry creates a new resolution and event chain.
- `invoke` accepts the resolution reference, selected Operation reference and revision, input, authority reference, timeout budget, and caller-supplied idempotency key.
- Invocation idempotency is scoped to tenant, principal, and key and stores a canonical fingerprint of the resolution snapshot, Operation revision, input, authority, timeout, and effective terms. An exact replay returns the original invocation reference and cannot duplicate payment or supplier effects. Key reuse with a different fingerprint returns `idempotency_conflict`.
- Retries are automatic only when the adapter can prove the supplier did not accept the call. Ambiguous effects enter reconciliation rather than blind retry.
- Request bytes, schema depth, execution time, candidate count, and per-tenant rate are bounded by server configuration and disclosed through machine-readable limits.
- For the first slice, invocation uses only existing admitted Operations and current AE authority models. New supplier credential delegation is not introduced by this design slice.
- Handles are opaque, principal-bound, and expiry-aware. Terminal invocation states are immutable. Non-terminal work exposes status and permitted cancellation through the existing recovery lifecycle.

#### Versioned wire contract

The first slice uses this canonical contract over HTTP and MCP. Names are product contracts; implementation types may differ.

```ts
type ResolveRequestV1 = {
  apiVersion: "ae.capabilities/v1";
  callerRequestRef: string;
  capability: { description: string; inputSchema?: JsonSchema; outputSchema?: JsonSchema };
  hardConstraints?: {
    maximumPrice?: { amount: string; currency: string };
    permittedEffects?: string[];
    permittedDataUse?: string[];
    authorityKinds?: string[];
    invocationTimeoutMs?: number;
  };
  preferences?: { lowerPrice?: boolean; lowerObservedLatency?: boolean };
  limit?: number;
};

type CandidateV1 = {
  operationRef: string;
  revision: string;
  termsSnapshotRef: string;
  expiresAt: string;
  supplier: { ref: string; name: string };
  summary: string;
  price?: { amount: string; currency: string };
  readiness: "available" | "degraded" | "unknown";
  fit: "exact" | "compatible" | "unspecified";
  reasonCodes: string[];
  unknownFields: string[];
};

type ResolveResponseV1 =
  | { kind: "resolved"; apiVersion: "ae.capabilities/v1"; resolutionRef: string;
      rankingVersion: "allocation-v1"; candidates: CandidateV1[] }
  | { kind: "no_match"; apiVersion: "ae.capabilities/v1"; resolutionRef: string;
      excludedReasonCounts: Record<string, number> }
  | { kind: "idempotency_conflict"; apiVersion: "ae.capabilities/v1";
      callerRequestRef: string };

type InvokeRequestV1 = {
  apiVersion: "ae.capabilities/v1";
  resolutionRef: string;
  operationRef: string;
  revision: string;
  input: unknown;
  authorityRef?: string;
  timeoutMs?: number;
  idempotencyKey: string;
};
```

Initial exclusion and explanation reason codes are versioned and closed: `schema_incompatible`, `price_exceeds_maximum`, `effect_not_permitted`, `effect_unknown`, `data_use_not_permitted`, `data_use_unknown`, `authority_unavailable`, `unavailable`, `terms_expired`, `lexical_match`, `schema_exact`, `schema_compatible`, `price_preferred`, and `readiness_observed`.

Successful HTTP resolution:

```json
{
  "kind": "resolved",
  "apiVersion": "ae.capabilities/v1",
  "resolutionRef": "resolution:01",
  "rankingVersion": "allocation-v1",
  "candidates": [{
    "operationRef": "operation:restaurant-booking",
    "revision": "rev:17",
    "termsSnapshotRef": "terms:92",
    "expiresAt": "2026-08-24T08:00:00Z",
    "supplier": { "ref": "supplier:example", "name": "Example Booking" },
    "summary": "Reserve an available restaurant table",
    "price": { "amount": "0.20", "currency": "USD" },
    "readiness": "available",
    "fit": "exact",
    "reasonCodes": ["schema_exact", "lexical_match", "readiness_observed"],
    "unknownFields": []
  }]
}
```

Valid no-match response:

```json
{
  "kind": "no_match",
  "apiVersion": "ae.capabilities/v1",
  "resolutionRef": "resolution:02",
  "excludedReasonCounts": { "price_exceeds_maximum": 2, "effect_unknown": 1 }
}
```

HTTP exposes `POST /api/v1/capabilities/resolve` and the existing brokered invocation endpoint with the versioned invoke request. Authentication or malformed-envelope failures use HTTP status and the platform error envelope; `no_match`, `stale_resolution`, supplier refusal, and pending work are valid product responses.

MCP exposes `resolve` and `invoke` tools whose input schemas mirror these types. The canonical response is returned in `structuredContent`; human-readable summaries may also appear as text content. Malformed tool arguments return `isError`; `no_match`, `stale_resolution`, supplier refusal, and pending work remain valid structured results. Thus the successful and no-match JSON examples above are identical inside MCP `structuredContent`, avoiding protocol-specific market semantics.

#### Canonical result envelope

The internal versioned result envelope is the source of truth. It preserves the existing completed, pending, refused, reconciliation-required, and failure distinctions. Provenance is attached to envelope metadata and market events, not injected into opaque supplier-result fields. A new metadata field is optional and backward-compatible within the current envelope version; a breaking shape change requires a new version.

- HTTP returns the envelope as JSON, with artifact URLs or resource references rather than embedding unbounded files.
- MCP returns the same envelope in `structuredContent`, maps presentable content to MCP content blocks, and maps artifacts to resource links. A transport-level failure remains distinct from a valid tool result describing an Operation refusal or pending state.
- Conversions that cannot preserve a native supplier representation retain an artifact or resource reference plus media type. AE does not silently coerce it into misleading JSON.
- The first slice requires synchronous structured content only. Artifacts, input-required continuations, and async task handles are later envelope variants built on the same invocation reference.

### MARKET MEMORY AND REPUTATION

AE records a maximal observable event chain keyed by the resolution and invocation references. Every event carries `ae-observed`, `buyer-reported`, or `derived` provenance:

`capability sought -> candidates shown -> selected -> invoked -> response delivered/failed -> optional accepted/rejected/unused -> optional switched -> optional repeated`

The guaranteed chain may end at `response delivered` or `failed`. Downstream use remains `unknown` unless the buyer reports it. Private prompt and plan content is not required. AE may later derive an aggregated capability class for routing or supplier demand visibility only after privacy and minimum-volume thresholds are satisfied.

Reputation has separate dimensions so one party is not blamed for another's failure:

- Source accuracy and freshness.
- Invocation reliability and latency.
- Contract and schema conformance.
- Buyer acceptance and rejection, weighted against buyer history and sample size.
- Refunds, disputes, retries, switches, and repeat selection.

The first slice records AE-observed events internally and does not use buyer feedback in automated allocation. Later reputation requires verified-invocation eligibility, minimum sample sizes, confidence ranges, Sybil and self-dealing controls, task-difficulty cohorts, and an explicit `insufficient_evidence` state. No composite score should conceal the separate dimensions.

### PRIVACY BOUNDARY

- `resolve` defaults to a bounded description and schemas, not raw input values, full prompts, conversations, files, secrets, or credentials.
- If values materially improve matching, the caller must explicitly mark and submit only those fields. Secret-shaped values are rejected or redacted before indexing and telemetry.
- Invocation input is disclosed only to the selected supplier route under its declared data-use terms. Candidate suppliers do not receive the request.
- Resolution and invocation data are encrypted in transit and at rest and tenant-isolated. Pilot retention is configuration owned by the AE operator and changed only through reviewed deployment policy: raw resolution descriptions for seven days; resolution snapshots and provenance-labelled market events for ninety days; invocation inputs and returned payloads for thirty days. A principal may delete those records immediately unless an active reconciliation or dispute requires a hold. Financial receipts retain only the fields required by the existing finance policy and never retain raw capability descriptions or supplier payloads.
- Supplier-facing capability aggregation is disabled during the pilot. Enabling it requires explicit product approval and at least twenty distinct authenticated principals plus fifty qualifying events in a capability class during a rolling thirty-day window. Direct identifiers are stripped. Buyer feedback is not reused for supplier-facing analytics without explicit product consent.

## First-Slice Flow

1. An outside agent calls `resolve` with its missing next contribution and constraints.
2. AE filters and ranks existing admitted Operations, snapshots every exposed candidate revision and terms, and records one candidate-exposure event.
3. The agent invokes one candidate through AE using the resolution and Operation references.
4. AE calls the existing supplier adapter and returns one synchronous structured contribution or an existing refusal or failure result.
5. The caller continues in its own harness. Downstream use remains unknown unless the caller opts into a provenance-labelled pilot report.
6. The same resolution may select another still-valid candidate after failure. Replayed resolution requests and invocations do not duplicate market events, payment, or supplier effects.

## Later End-State Flow

1. A source observer reads one bounded native MCP description and stores a versioned source observation.
2. AE derives, classifies, probes, and admits candidate Operations with conservative unknowns.
3. The first-slice allocation and invocation flow runs over both existing and source-derived supply.
4. Later envelope variants return artifacts, explicit task handles, or input-required continuation requests.
5. AE-observed evidence remains separate from buyer-reported judgment. Neither is interpreted as proof of the buyer's final outcome.
6. After volume, privacy, and abuse thresholds are met, aggregated capability demand may become visible to suppliers and reputation may influence allocation.

## Open Questions

1. What is the smallest `resolve` input that produces useful allocation without becoming a prompt dump?
2. Which existing admitted Operations form a credible first pilot without requiring new credential delegation?
3. What minimum volumes, confidence bounds, and abuse controls must exist before contextual buyer feedback can influence allocation?
4. Which product and legal review must approve changing the provisional retention periods or enabling supplier-facing aggregation?
5. After HTTP and the current MCP surface prove the behavior, what compatibility window should AE maintain while adopting caller-facing MCP `2026-07-28`?

## Success Criteria

### First-slice product criteria

- An agent in an external harness uses AE without creating an AE chat, thread, or plan.
- One self-contained capability lookup returns explainable, callable candidates from the existing admitted catalogue.
- Hard constraints fail closed, material unknowns remain visible, and no qualifying supply returns `no_match`.
- The agent invokes one unfamiliar admitted Operation through AE and receives one synchronous structured contribution.
- A failed delivery can be switched to another candidate using the original resolution reference.
- AE records only the provenance-labelled events it observes without storing the caller's private plan or inferring downstream use.
- HTTP and the currently supported MCP protocol expose the same product behavior, while CLI can exercise it independently.
- Existing Operation invocation, money, idempotency, status, cancellation, recovery, and reconciliation semantics remain intact.

### Pilot demand criteria

These are falsifiable pilot gates rather than market forecasts:

- At least three independently operated external harnesses attempt at least twenty real capability resolutions.
- At least five invocations select an Operation the calling harness did not already have installed.
- At least two callers return with a second capability gap within thirty days.
- Candidate coverage, invocation, delivery, switch, and optional-feedback rates can be calculated without treating missing feedback as rejection.
- Pilot review identifies absence of supply, poor matching, and supplier delivery failures from AE-observed evidence. Caller-integration failure is assigned only from an opt-in, provenance-labelled pilot debrief; without one, the cause is `downstream_unknown`.

### Later-source criteria

- One bounded remote MCP source can be observed, translated, admitted, refreshed, degraded, and removed without hand-authoring a complete AE contract.
- A later bounded OpenAPI source passes the same lifecycle independently.
- Async handles, artifacts, input-required continuations, reputation, and supplier demand visibility each receive separate acceptance criteria before entering allocation.

## Dependencies

- The existing HTTP and MCP surfaces for first-slice validation. A TypeScript MCP SDK supporting protocol `2026-07-28`, or a bounded compatibility implementation, is required only for the later protocol migration.
- Existing Operation catalogue, source publication, invocation gateway, recovery, and money components.
- JSON Schema normalization and validation for source-derived input and output contracts.
- A capability matching strategy that can begin with hybrid lexical and structured constraint matching before stronger learned ranking exists.
- Privacy-preserving aggregation and abuse controls before capability demand or buyer feedback becomes supplier-visible or affects allocation.

## Distribution Plan

Agentic Economy remains a hosted web service using the existing deployment pipeline. The capability market is distributed through:

- A public stateless MCP endpoint as the primary installed agent surface.
- A matching HTTP API for direct harness and SDK integration.
- CLI commands as an executable reference client and diagnostic surface.
- Generated `SKILL.md`, `llms.txt`, and machine-readable manifests that teach arbitrary agents when and how to call the capability boundary.

## Discrete Build Sequence

1. **Resolve current supply:** add bounded `resolve` over admitted Operations, with hard filters, explanations, `no_match`, and no new source ingestion.
2. **Complete one synchronous brokered loop:** invoke one selected admitted Operation through the existing gateway and record AE-observed provenance-labelled telemetry.
3. **Run the external-harness pilot:** test recurrence and identify whether supply, matching, supplier delivery, or caller integration is the binding failure.
4. **Automate one native SOURCE family:** observe and translate the bounded remote MCP profile. Add bounded OpenAPI only after the MCP lifecycle is proven.
5. **Expand the canonical envelope:** add artifacts and resources, pending tasks, missing input or authority, and explicit handle lifecycles.
6. **Adopt the newer caller protocol:** move the public MCP surface toward `2026-07-28` independently of product validation, retaining a documented compatibility window.
7. **Develop reputation privately:** calculate separated objective and contextual dimensions with confidence and abuse controls, without affecting allocation.
8. **Expose market learning:** allow reputation to influence routing and show aggregated demand to suppliers only after volume, privacy, and manipulation thresholds are met.

Each step must leave a usable product surface. No step depends on AE becoming the agent harness.

## Reviewer Concerns

The three-round adversarial review converged on the source/platform and responsibility boundaries. These implementation-contract questions remain open and must be resolved before their corresponding build step:

1. `CandidateV1` must add structured effects, data-use terms, authorization requirements, and exact invocation surfaces tied to the pinned terms snapshot.
2. Allocation must filter for bounded input satisfiability, and invocation must validate supplied input against the pinned Operation input schema.
3. The wire contract must define the exact `InvokeResponseV1` union, including success, stale resolution, idempotency conflict, refusal, reconciliation, and supplier failure examples.
4. Resolve replay eligibility must end at the effective expiry of its candidate snapshot, or define a refresh path that does not double-count demand.
5. The remote MCP source step needs an explicit `2026-07-28` client implementation dependency, or must initially use the supported `2025-11-25` compatibility path.
6. Pilot reporting must keep unreported caller-integration failures as `downstream_unknown` everywhere, including the build sequence.
7. `allocation-v1` needs exact, bounded input/output schema compatibility and lexical matching procedures before exposure evidence can be compared consistently.
8. Hard-constraint semantics must define array allowlists, omitted versus empty values, currency mismatch, and the source of authority availability.
9. MCP source adapters must pin the authoritative protocol schema, exact header names and methods, and conformance fixtures for sessionless and compatibility profiles.
