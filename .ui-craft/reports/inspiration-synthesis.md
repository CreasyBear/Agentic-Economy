## What AE Should Borrow

### 1. Scan order must prove the product in five seconds

The first viewport must resolve in this order:

1. Product identity: "Agentic Economy".
2. Category: source-owned answer records for local-service trust.
3. Signature object: the answer record with question, source, known, unknown, unavailable, and next step.
4. Primary action: claim the answer record.

This adapts SmoothUI's landing hero squint test. Generic SaaS asks the hero to move from headline to CTA to product screenshot. AE asks the hero to move from identity to claim action to the answer record, because the answer record is the product. A fake dashboard, abstract AI visual, or marketplace preview fails even if it looks premium.

### 2. Proof must be custody proof, not popularity proof

AE should avoid borrowed social-proof defaults when it cannot support them with source-owned facts. Logos, testimonial cards, and vanity metrics can make an early trust product feel less trustworthy.

AE proof should instead show:

- Claim path: how a source owner takes responsibility for the record.
- Publish path: what becomes public and agent-readable.
- Correction path: how stale or wrong facts are challenged.
- Boundary path: what is known, unknown, unavailable, and handed off to a human.

Shopify Editions proves maturity with release cadence. AE's equivalent is not "thousands of businesses"; it is a visible chain of custody and correction.

### 3. Trust architecture is the interface

Okta's transferable lesson is that authority and access should be visible in the product language. For AE, trust architecture means every public or owner-facing surface answers:

- Who owns this fact?
- What tier of trust is it in?
- What is known from the source?
- What is unknown?
- What actions are unavailable?
- What can a human do next?

Do not hide this behind tooltips or an about section. These fields are the interface.

### 4. Frontier positioning needs boundary discipline

Mistral shows the power of claiming a frontier category directly. AE should also feel category-defining, but its ambition must be phrased through current truth:

- Good: "Source-owned records assistants can read."
- Good: "Known, unknown, unavailable, then human handoff."
- Bad: "Book, pay, and dispatch through autonomous agents."
- Bad: "MCP/OpenAPI/callable commerce rails are live."

AE should sound like it is building the future of agentic commerce while showing exactly which rails are live today.

### 5. The real visual is a governed object

SmoothUI's landing recipe prefers real product visuals over invented illustration. AE's real visual is not a SaaS screenshot. It is a governed answer record:

- Customer question or service intent.
- Business identity.
- Source/custody label.
- Known facts.
- Unknown facts.
- Unavailable actions.
- Safe next step or human handoff.
- Claim/correction path.

Oryzo's transferable lesson is object specificity. Floema's is durable civic structure. AE should merge those into a record that feels concrete, public, and inspectable.

### 6. Section rhythm should answer trust questions in sequence

AE should adapt the SmoothUI recipe section grammar as:

| Recipe role | Generic SaaS default | AE adaptation |
| --- | --- | --- |
| Hero | Headline, CTA, product shot | Agentic Economy identity, claim action, source-owned answer record |
| Proof strip | Logos or metric | Claim, publish, correct |
| Feature rows | Product screenshots | Answer anatomy: known, unknown, unavailable, next step |
| Credibility/depth | How it works | Source ledger, custody, correction, human handoff |
| Final CTA | Start trial or book demo | Claim your answer record |
| Footer | Sitemap/legal | Registry, correction/removal, privacy, public routes |

Every section should answer one user question. If a section cannot name the trust question it resolves, cut it.

### 7. Motion must communicate state, not spectacle

High-end references often use motion to create confidence, pace, or product drama. AE should use restrained motion only for:

- Focus and hover affordances.
- Disclosure of record sections.
- Navigation-level continuity where it preserves orientation.
- Loading skeletons that mirror final answer-record geometry.

Avoid scroll-jacking, magnetic theatrics, bouncy easing, decorative particle systems, and animated status dots. Reduced-motion users must receive a fully usable static interface.

### 8. Brand specificity must appear in the first viewport

Lando Norris is a useful reminder that branded public surfaces need unmistakable subject identity. AE's first viewport must not read like "AI landing page." Required first-viewport signals:

- "Agentic Economy" as literal brand/product name.
- Source-owned answer record language.
- Command ink, signal cobalt, hairline ledgers, tabular metadata.
- Local-service example with known/unknown/unavailable states.
- Claim/correction path.

No vague AI SEO headline can replace this.

### 9. Human handoff is a premium trust detail

MindMarket's transferable rule is that human insight has design value. For AE, the highest-trust ending of an answer record is often not automation. It is a safe human handoff:

- "Send a human inquiry with photos."
- "Owner confirmation required."
- "Request correction or removal."
- "Availability unknown until the owner replies."

This makes AE feel more serious than a product that pretends every action is automated.

### 10. Finish quality is measurable

The inspiration set only matters if future agents can run gates. AE's frontier bar is not "make it premium"; it is:

- SmoothUI landing acceptance bar adapted to answer records.
- Nielsen 10 scored 1-5.
- Six design laws pass/fail.
- UI Craft finish bar with zero Critical and zero Major findings.
- AE overclaim scan for future-phase commerce language.
- Visual QA screenshots across exact viewport sizes.

## AE Frontier Frontend Design System Checklist

Run this before any public, owner, registry, or command-surface UI work.

### A. Source-Owned Product Gate

- [ ] The surface names what is known, unknown, unavailable, and next.
- [ ] Source/custody is visible near the facts it governs.
- [ ] Trust tier is not inflated. Nothing says verified unless trust tier is `registry_verified`.
- [ ] The public object is an answer record, service page, source ledger, registry row, or status readback. No fake dashboards.
- [ ] Human handoff is explicit where live automation is not available.

### B. SmoothUI Landing Recipe Gate

Use `.agents/skills/ui-craft/references/recipe-landing.md` as a core gate.

- [ ] One conversion action exists. For current AE public landing, it is "Claim your answer record".
- [ ] Hero squint order is H1 -> primary claim action -> answer record.
- [ ] The page has proof strip, varied feature/anatomy modules, credibility/depth, final CTA, and footer.
- [ ] At least one specific proof point is visible, but it is custody/source proof rather than fake popularity.
- [ ] No uniform icon-card grid exists.
- [ ] CTA hierarchy has distinct nav, hero, and lower-section levels.
- [ ] One signature detail exists. For AE, it is the known/unknown/unavailable/next-step answer-record grammar with source stamp.
- [ ] Mobile has no horizontal overflow at 375px and preserves the claim/correction path.
- [ ] Reduced motion is honored and no scroll-jacking exists.

AE adaptation note: the recipe's "real product shot" requirement becomes "real source-owned answer record". Product-forward visuals are allowed only when they show actual source-owned record UI or registry/status readbacks. Generic SaaS screenshots, fake metric boards, abstract AI imagery, and dashboard theatre fail the gate.

### C. SmoothUI Heuristic Gates

Score Nielsen's 10 from 1 to 5. Any score below 4 needs a finding; any score 1 or 2 blocks release.

| Heuristic | AE-specific pass condition |
| --- | --- |
| Visibility of system status | Claim, correction, loading, pending, failed, degraded, and published states are visible and textual. |
| Match real world | Copy uses owner/public language: claim, correct, known, unknown, unavailable, next step. |
| User control and freedom | Correction, removal, back, cancel, retry, and human handoff paths are discoverable. |
| Consistency and standards | Claim/correct/explore verbs and status labels remain stable across surfaces. |
| Error prevention | Unavailable bookings, payments, wallets, callable actions, MCP, OpenAPI, and autonomous actions are clearly absent. |
| Recognition over recall | The answer-record anatomy is visible; users do not infer trust state from color or memory. |
| Flexibility and efficiency | Operators can scan dense records; owners can act from mobile without extra explanation. |
| Aesthetic and minimalist design | One accent, one signature object, no filler sections, no decorative AI styling. |
| Error recovery | Failures name consequence and recovery, including support/correlation IDs where appropriate. |
| Help and documentation | Complex terms are explained inline beside the relevant record field. |

### D. Design Law Gates

- [ ] Fitts: primary actions are at least 44px high on touch screens and are reachable near the decision context.
- [ ] Hick: public nav stays at or below 4 choices; no multi-choice CTA pileups.
- [ ] Doherty: user actions respond perceptually within 400ms; skeletons appear within 200ms for data-backed sections.
- [ ] Cleveland-McGill: comparisons use position, length, rows, or direct text; no pie charts, fake gauges, or color-only meaning.
- [ ] Miller: record anatomy stays chunked into source, known, unknown, unavailable, next step, and correction.
- [ ] Tesler: AE absorbs phase-gate complexity; users see clear boundaries, not internal architecture.

### E. Finish-Bar Gates

Run the UI Craft finish bar before shipping public UI. Done means zero Critical and zero Major findings.

- [ ] Hierarchy: one primary thing per viewport; public landing resolves to answer record and claim.
- [ ] Type system: no more than three visible weights; tabular numbers for data; readable prose measure.
- [ ] Surface stack: canvas, raised, command, and overlay surfaces are intentional.
- [ ] Spacing rhythm: inner spacing, group spacing, and section spacing use the AE scale.
- [ ] Iconography: one icon family, no emoji-as-icons, stroke weight matches type.
- [ ] State coverage: idle, loading, empty, error, success, partial, conflict, and offline are considered where applicable.
- [ ] Motion tuning: targeted properties only, no `transition-all`, reduced motion honored.
- [ ] Microcopy voice: no placeholder strings, generic CTAs, or product-internal language.
- [ ] Pixel honesty: borders, shadows, radii, truncation, and overflow hold at 200% zoom.
- [ ] Data formatting: dates, counts, routes, IDs, and status metadata use the right precision and format.

### F. AE Overclaim Gate

Reject public/owner copy that implies unavailable phase-gated capability:

- payments, wallets, checkout, paid activation
- bookings, scheduling, guaranteed response
- marketplace, request market, demand network
- hosted agents, autonomous actions, automated fulfillment
- MCP, OpenAPI, callable endpoint, agent-callable tools
- verified unless `registry_verified`

Safe replacement pattern: "Unavailable: [capability] is not live here. Next step: [human/source-owned action]."

## Top Transferable Principles

1. Make the answer record the hero, not a decoration.
2. Use custody and correction as proof.
3. Show boundaries as product strength.
4. Keep one conversion action: claim the answer record.
5. Replace feature cards with answer anatomy, source ledgers, service rows, and boundary panels.
6. Make human handoff visible where automation is not live.
7. Use motion only for state, orientation, and affordance.
8. Preserve command calm: neutral field, command ink, signal cobalt, hairline grids, tabular metadata.
9. Keep frontier language ambitious but phase-true.
10. Require measurable gates before shipping, not subjective premium polish.
